# Brief: getting-started-screenshots

起点: 2026-10-10 の棚卸で `getting-started-story-guide` から分割した。入門ガイドの書き直しは 22〜24 タスクになり、20 を超えた。本文は今すぐ書けるが、絵は新しいシェルを待つ。そこで、本文を元の spec に残し、絵と実機での確かめをこの spec に出した。

## Problem

入門ガイドには、ゴーストがしゃべっている様子の絵が 1 枚も無い。読者は、辞書を書いた結果が画面でどう見えるのかを、自分で起動するまで知ることができない。「何ができるのか」を先に見せられないので、物語の形に書き直しても、文字だけの手順書に見える。

もう 1 つ、8 段目「触ったら反応してほしい」は、書いたとおりに動くことを実機で確かめた人がいない。今のシェルには当たり判定が無く、触った部位の名前が空になるためである。

## Current State

- 入門ガイド（`book/src/getting-started/` の `index.md`・`prerequisites.md`・`first-ghost.md`）に、画像の行は 1 つも無い。
- マニュアルに置いてある画像は、台詞の部品に使う顔の絵（`book/src/img/claudia/` の 16 枚）だけである。
- 段階表（`crates/pasta_sample_ghost/STAGES.md`）は 13 段ある。辞書を持つのは 1〜12 段目で、段階の辞書は配布版の辞書そのもの（`crates/pasta_sample_ghost/ghosts/hello-pasta/ghost/master/dic/` の `01-boot.pasta`〜`12-lua.pasta`）である。
- 8 段目の辞書（`dic/08-touch.pasta`）は、触られた部位の名前（付加情報の 4 番目）を台詞に入れる。段階表は、頭の部位名を `Head` としている（同じ表の注記では「仮の名前」）。`hello-pasta-shell-art` は、この名前を `Head` のまま確定し、当たり判定を新しいシェルに付ける。
- SSP を外から操作する道具がある（SSP の MCP サーバー。イベントを送る・さくらスクリプトを流す・表示中の絵やバルーンを書き出す・ログを読む、などの操作を持つ）。2026-10-09 に `hello-pasta-tutorial-stages` が、これで実機の確かめをした（`.kiro/specs/completed/hello-pasta-tutorial-stages/tasks.md` の実装メモ 6.1）。絵の書き出しがガイド用の絵としてそのまま使えるかは、確かめていない。
- マニュアルの検査は、画像の参照先が実在することと、外部の画像を読み込まないことを確かめる（`book/tools/verify-static.mjs`・`book/tools/link-check.mjs`）。入門の章は、スキル用の文書を生成する対象（`book/tools/gen-skill-refs.mjs` の生成元の一覧）に入っていない。そのため、章に画像の行を書いても、生成は止まらない。
- 人手の確認が 1 件残っている。`sakura-script-newline` の Task 5.1（実機の SSP で、段落の区切りの改行の見た目を 3 通り確かめる。`.kiro/specs/completed/sakura-script-newline/tasks.md` の 60 行目から）である。

## Desired Outcome

- 入門ガイドの各章で、その章の表現が画面でどう見えるかを絵で確かめられる。絵は新しいシェル（`hello-pasta-shell-art`）で撮ったもので、章の作例と同じ台詞が写っている。
- 絵を撮り直す手順が残っている。シェルや辞書が変わったら、同じ手順で撮り直せる。
- 8 段目が、新しいシェルの上で、本文に書いたとおりに動くことを実機で確かめてある。
- 撮影の道具が無い環境でも、マニュアルの自動検査は通る。

## Approach

起票時の見立て。要件と設計で確定する。

- 絵はリポジトリに入れた画像ファイルとして置く。自動検査は、画像を作らずに、置いてある画像の参照だけを確かめる。
- 撮り方は設計で決める。候補は、実機の SSP を手で撮る方法と、SSP を外から操作する道具で台詞を出して撮る方法の 2 つ。どちらにしても、撮るときの台詞の出し方（どのイベントを、どの付加情報で送るか）を手順として残す。同じ名前のシーンから 1 つ選ぶ作例は、出る台詞が毎回変わるので、狙った台詞を出す方法も手順に含める。
- 絵には、何が写っているかを言葉で書いた代わりの文を付ける。絵が見えない読者にも、台詞の中身が伝わるようにする。
- 8 段目の確かめは、撮影と同じ実機の作業の中で行う。

## Scope

- **In**:
  - 撮影の手順（撮り方・台詞の出し方・画像の大きさと形式・置き場所）と、その記録
  - 画像ファイル
  - 入門ガイドの各章への画像の行（代わりの文を含む）
  - 新しいシェルでの 8 段目の実機の確かめ
  - 画像にかかわる検査の追従（要る場合）
- **Out**:
  - 入門ガイドの本文（`getting-started-story-guide` が持つ。本 spec が章に足すのは画像の行だけ）
  - シェルの絵と当たり判定（`hello-pasta-shell-art` が持つ）
  - 段階表と hello-pasta の辞書（完了した `hello-pasta-tutorial-stages` が決めた。本 spec は変えない）
  - 動画（デバッグの章にある動画の扱いは `manual-print-media-refs` が持つ）
  - 入門ガイド以外の章の絵

## Boundary Candidates

- 撮影の手順と記録
- 画像ファイルと、章への画像の行
- 8 段目の実機の確かめ
- 残っている人手の確認（`sakura-script-newline` の Task 5.1）を同じ作業で済ませるか

## Out of Boundary

- 章の文章・章立て・作例。絵に合わせて本文を直したくなったら、本 spec では直さず、理由を付けて開発者に確かめる。
- 絵を自動検査の中で撮り直す仕組み。

## Upstream / Downstream

- **Upstream**:
  - `hello-pasta-shell-art`（撮る絵そのものと、当たり判定）
  - `getting-started-story-guide`（画像の行を足す先の章。章の数と名前はここで決まる）
  - 完了した `hello-pasta-tutorial-stages`（段階表と段階の辞書。実機の確かめの前例）
- **Downstream**: なし。

## Existing Spec Touchpoints

- **Extends**: なし（新規。`getting-started-story-guide` の Scope にあった「スクリーンショットの撮影と掲載」を引き取った）
- **Adjacent**:
  - `getting-started-story-guide`: 同じ章のファイルを触る。本文が main に入った後に、画像の行だけを足す。
  - `manual-print-media-refs`: マニュアルの検査（`book/tools/verify-static.mjs`）と自動検査の定義（`.github/workflows/manual.yml`）を今のウェーブで持つ。本 spec は次のウェーブ以降なので重ならない。
  - 完了した `sakura-script-newline`: Task 5.1 の人手の確認を、同じ実機の作業で済ませる候補。

## Constraints

- 撮影できない環境でも、マニュアルの自動検査は通ること。
- 現行の版で実際に出る画面だけを載せる。作り物の絵や、加工で台詞を書き換えた絵は載せない。
- マニュアルは外部の画像を読み込まない（オフラインでも読める）。画像はリポジトリに入れる。
- 絵に写る台詞は、その章の作例と食い違わないこと。
- 完成度を優先する。絵を一部の章にだけ載せて残りを後回しにする出し方はしない。どの章に載せるかを要件で決め、決めた分は全部そろえる。

## 2026-10-10 棚卸の測定（main add05022）

- **規模**: 4〜6 タスク（撮影の手順 1、撮影と画像 1〜2、章への画像の行 1、8 段目の実機の確かめ 1、通しの確認 1）。
- **先に要るもの**: `hello-pasta-shell-art`（新しいシェルと当たり判定）と `getting-started-story-guide`（章の本文）。どちらも未完了。
- **種別**: 文書（入門ガイドに絵を足す。動作は変えない）。
- **要件定義のモデル**: Opus（方針は決まっている。残るのは、撮り方の条件と、どの章に何を載せるかの整理）。
- **要件定義の議題**:
  - どの章に絵を載せるか（13 段の全部か、見た目が変わる段だけか。準備の章にフォルダーの絵などを載せるか）。

  - 画像の形式・大きさ・1 枚あたりと合計の重さの上限。マニュアルの公開ページとリポジトリの両方に効く。
  - 7 段目「挨拶したい」の切り替えの絵に、相手役の emo2 を写すか。
  - 8 段目の実機の確かめで、本文や辞書と食い違いが見つかったときの扱い（どの spec で直すか）。
  - `sakura-script-newline` の Task 5.1（実機の SSP で、段落の区切りの改行を 3 通り目で確かめる）を、同じ実機の作業のついでに済ませるか。済ませるなら、確かめた結果の記録の置き場所も決める。
  - シェルや辞書が後で変わったときに、絵を撮り直す決まりを置くか。

## 申し送り（getting-started-story-guide より・2026-10-10）

本文の spec が完了した。この brief の Current State の「`index.md`・`prerequisites.md`・`first-ghost.md`」は古い。参照先は `.kiro/specs/completed/getting-started-story-guide/` の `design.md` と、`tasks.md` の `## Implementation Notes`。

- **章の形が変わった**: 入門ガイドは 16 章（`index.md`・`prerequisites.md`・`setup.md`・`01-boot.md`〜`13-nar.md`）。`first-ghost.md` は消え、`index.html` への転送ページだけが残る。画像の行はまだ 1 つも無い。
- **画像の行は、今の本文検査に落ちる**: `C-prose`（`book/tools/tutorial-check.mjs` の `findProseParagraphs`）は、画像だけの行・HTML の行を除外しない。章に画像の行を足すと「台詞でも箇条書きでもない段落」として報告される。画像の行をどう書くか（検査の側で除外するか、書き方を決めるか）を要件で決め、`book/AUTHORING.md` 第 8 節の雛形にも足す。
- **検査のフェンスの除去が 3 本のバッククォート固定**: `book/tools/verify-content.mjs` の `stripCodeFences`・`extractCodeFences` は、4 本のフェンス（`12-lua.md` が使う）の中の ``` と組になる。今は結果が合っているが、辞書のコメントの中の ``` の数が変わると崩れうる。検査を触るなら一緒に直す。
- **準備の章の終わりは、何も写らない**: 辞書が 1 枚も無い間は、立ち絵も吹き出しも出ない（立ち絵は最初の台詞と一緒に出る）。`setup.md` に載せられる絵は、フォルダーの絵か `pasta.log` くらいである。
- **6 段目の時報は、実際の正時にしか出ない**: SSP の「現在時刻の仮想的変更」は pasta に届かない（pasta は OS の時計で判定する）。撮るなら正時を待つ。「狙った台詞を出せること」の条件に効く。
- **外から起こした `OnTalk` では、チェイントークの続きが出ない**: 11 段目の「さっきの寄り道、楽しかったね。」は、自然なおしゃべりの次の回にだけ出る。
- **9 段目の 1 つ目の選択肢が切れて見える**: 「おやつの話をする」が問いかけと同じ行に続いて描かれ、吹き出しの右端で「をする」が切れる。そのまま撮ると絵に写る。直すなら辞書・トランスパイラ・バルーンのどれかで、この spec の外（別に起票した）。
- **開発者の確認が 4 点残っている**（公開後。`.kiro/steering/roadmap.md` の「人手の確認が残っている項目」）: 準備の章の SSP 側の操作（`ghost/` の下へ置いて切り替え、立ち絵が無い状態でタスクバーの SSP のアイコンからメニューを開いて終了する）、目次の持ち越し、7 段目の emo2 そのものとのメニューからの切り替え、13 段目のフォルダーのドロップでの `.nar` の作成。実機の作業のついでに済ませるかを要件で決める。13 段目では、できた `.nar` に読者の `profile/`（10 段目のセーブとログ）が入るかも見る（章には書いていない）。
- **8 段目**: 今のシェルには当たり判定が無いので、実機では部位名が空のときの台詞（「えへへ……なでなで？」）だけが出る。部位名つきの台詞は、`Reference4` に `Head` を渡して確かめた。
