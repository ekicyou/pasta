# Research & Gap Analysis: manual-link-anchor-check

2026-10-10・main `ea40c363`（ロードマップの棚卸 2 回目を取り込んだ後）で調べた。`/kiro-validate-gap` の成果物で、要件ディスカッションと設計フェーズの材料にする。決定は書かず、事実と選択肢を並べる。

## Summary

- **本の中のリンクの見出しは、今は 1 本も検査されていない**。他の章へのリンクは `#` より後ろを捨ててファイルの実在だけを見る。同じ章の中の見出しへのリンク（`#見出し`）は、空のパスとして読み飛ばす。対象は 585 本ある。
- **今のマニュアルに、切れた見出しリンクは無い**（585 本すべてが実在の見出しを指す）。直すリンクは 0 本で、本 spec の成果は「これから切れたら気づける」ことになる。
- **見出しの `id` は、今の関数（`headingSlugs`）と mdBook の出力が全 764 個で一致した**。手元の mdBook 0.5.4 のビルドと、CI（0.5.3）がビルドした公開サイトの両方で確かめた。brief の議題 1（関数を合わせるか、ビルドした出力を読むか）は、どちらも要らない。
- **クレートの README の公開 URL は、すでに見出しまで検査されている**（`pasta-runtime-internals-doc`・PR #50 で入った）。brief の「ここも見出しまでは見ていない」は実装と食い違う。Desired Outcome の 2 つ目は、`crates/*/README.md` については達成済みである。
- **足す部品はほぼ揃っている**。アンカーの集合を作る関数（`anchorSet`）、フラグメントの復号（`decodeAnchor`）、スキルの検査の同じ形の照合（`skill-anchor`）がある。規模は brief の見立て（2〜4 タスク）より小さい側に寄る。

## 3. 実装アプローチの選択肢

### Option A: `detectBrokenLinks` に照合を足す（既存の拡張）

- 相対 `.md` リンクは、ファイルの実在を確かめた後に、フラグメントを復号して `anchorSet` と照合する。`#…` だけのリンクは、自分の章の `anchorSet` と照合する。違反は新しい区分で報告し、`BOOK_KINDS` に足す。
- 章ごとの `anchorSet` はキャッシュする（585 本が 60 章を指す）。`manualUrlProblem` も同じキャッシュを通せば、要件 4.2（同じ規則）が形の上でも保証される。
- 触るファイル: `link-check.mjs`（20〜30 行ほど）、`link-check-test.mjs`（(B-11) の見本の直し・(A) の区分の写し・新しい節）。
- 良い点: 新しいファイルも依存も無い。スキルの検査（`skill-anchor`）と同じ形で読みやすい。ビルドなしで走る。
- 悪い点: `id` の作り方は mdBook の写しのままで、食い違いうる形の見出しが書かれたら、誤検出か見逃しになる（今は 0）。

### Option B: ビルドした出力の `id` を読む

- `book/book/**/*.html` の `id` を集めて照合する。mdBook の出力そのものなので、食い違いは原理的に起きない。
- 悪い点: ビルドが要る。DoD のゲートはビルドなしで走らせるので、ゲートの手順（`workflow.md`）か、リンク検証の中でのビルドが要る（mdBook が手元に無い環境で落ちる）。古いビルドが残っていると誤判定する。`link-check.mjs` の「読むだけ・git に依らない・決定的」の方針から外れる。ロードマップの約束（触るのは `link-check.mjs` と自己テストだけ）にも収まりにくい。
- 計測で食い違いが 0 だったので、これを選ぶ理由は今は無い。

### Option C: A に、食い違いへの備えを足す（ハイブリッド）

A を土台にして、次のどれかを足す。

- **C1 食い違いうる形の見出しを落とす**: 1.3 の表の形（全角空白・下線の見出し・引用やリストの中の見出し・`{#id}`）を見つけたら、リンク検証が違反にする。ビルドなしで走る。執筆者に「その形の見出しは書けない」という新しい決まりを課すことになり、`AUTHORING.md` に書けないこのウェーブでは、報告の文面だけが案内になる。
- **C2 自己テストが、ビルドした出力が在るときだけ突き合わせる**: `link-check-test.mjs` が、`book/book` が在れば全章の `headingSlugs` と HTML の見出しの `id` を比べ、無ければ飛ばす。CI は自己テストをビルドの後に走らせるので、`manual.yml` を触らずに CI で毎回確かめられる。手元では、古い `book/book` が残っていると自己テストが落ちる（DoD のゲートは `link-check.mjs` だけを走らせるので、ゲートは止まらない）。
- **C3 何も足さない**: 完了時に 1 度だけ突き合わせて記録する（要件 3.7 の確かめ）。

## 4. 工数とリスク

- **工数: S（1 日ほど）**。照合の部品は揃っていて、足すのは `detectBrokenLinks` の分岐 2 つと区分 1 つ、自己テストの節 1 つである。直す切れリンクは今は 0 本。C1 か C2 を足しても S に収まる。
- **リスク: Low**。既存の型（`skill-anchor`）の横展開で、`id` の一致は 764 個で確かめてある。残るリスクは次の 2 つ。
  - 同じウェーブの spec が先に見出しを変えると、本 spec の PR で初めて違反が出る（見つかったら要件 7.4 のとおり直す）。
  - 本 spec が入った後は、DoD のゲートが見出しの切れでも止まる。意図した変化だが、ゲートが落ちる理由が 1 つ増える。

## 5. Research Needed（設計フェーズへ送る調査項目）

- **RN1**: mdBook 0.5.3 と 0.5.4 の `id` の作り方（空白類・重複の付番・強調を含む見出し）を、ソースか変更履歴で確かめる。今回は出力の突き合わせだけで、作り方そのものは読んでいない（1.3 の「違いの中身」は、mdBook の版を上げるときの注意として残す）。
- **RN2**: C2 を採る場合、CI の `book/book` は着色・台詞部品の変換・検索索引の再生成を経た後である。見出しの `id` がそのままか（今回の突き合わせは変換前の出力と公開サイトで行い、どちらも一致した）、`book/book/classic/`（自己テストの後に作られる）と `print.html` を数えない書き方を確かめる。C2 は要件ディスカッションで採ると決まった（要件 7.6・7.7）。手元に古い `book/book` が残っているときの扱い（落とす・飛ばす・ソースより古い章だけ飛ばす）もここで決める。
- **RN3**: 新しい区分の名前と報告の文面（`skill-anchor` の「リンク先 … に見出し／明示アンカー "…" が無い」に合わせるか）、行番号を付けるか。
- **RN4**: `anchorSet` のキャッシュを `manualUrlProblem` と共有する形（関数の引数で渡すか、モジュールの中に置くか）。

## 未決事項（要件ディスカッションへ）

`requirements.md` の「前提と未決事項」と同じ番号である。

1. `id` の食い違いへの備え（C1・C2・C3 のどれか）。→ 決定: C2（自己テストが、ビルドした出力が在るときだけ突き合わせる）。
2. 見出しのほかのアンカー（`<a id|name>` だけを合格にするか、ほかの要素の `id` も合格にするか）。→ 決定: `<a id|name>` だけ。
3. 公開 URL の検査の対象を広げるか（`SOUL.md`・スキルの手書きファイル・ルートの `README.md`・`roadmap.md`）。→ 決定: ルートの `README.md`・`SOUL.md`・2 スキルの Markdown へ広げる。`roadmap.md` は入れない。
4. 公開済みの README が指す見出しを変えたとき、次のリリースまで切れることを受け入れるか。→ 決定: 受け入れる。
5. 執筆者への案内の置き場所（このウェーブでは `AUTHORING.md` を触れない）。→ 決定: 違反の報告の文面だけ。申し送りはしない。
6. コードフェンスやインラインコードの中のリンクの記法を、見出しの検査から外すか。→ 決定: 外さない。
