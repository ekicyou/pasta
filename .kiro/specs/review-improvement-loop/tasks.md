## Task 1: 環境プリフライトとベースライン検証

- [ ] 1. 既知環境制約を無害化し、グリーンベースラインを確立する
  - steering（tech.md / workflow.md）・プロジェクトメモリ・design.md「環境制約表」を読み、検証コマンドに影響する既知制約（本リポジトリでは `NoDefaultCurrentDirectoryInExePath`・`PASTA_DEBUG`・`PASTA_DEBUG_PORT` の解除）を列挙する
  - 無害化をコマンド文字列として織り込んだ正準コマンド表（design.md「検証コマンドメニュー」の本実行インスタンス）を確定し、tasks.md の Implementation Notes へ記録する（以後の全サブエージェントへコマンド文字列として伝搬し、解釈余地を残さない。無害化はコマンド毎に適用する）
  - 正準全体検証（本リポジトリでは env 無害化付き `cargo test --workspace` を軸とする全体テスト）を実行し、グリーン状態を確認する
  - RED の場合: 環境起因（env 変数・ポート競合・ツール不在）かコード起因かを切り分け、環境起因なら無害化して再試行、コード起因なら失敗内容を開発者へ報告して実行を中断する（改善作業に着手しない）
  - 完了条件: ベースライン GREEN のエビデンス（テスト件数・所要時間）と正準コマンド表が Implementation Notes に記録されている
  - _Requirements: 4.1, 4.2, 4.7_
  - _Boundary: 環境プリフライト（読み取り＋検証のみ。コード変更なし。書き込みは tasks.md Implementation Notes のみ）_

## Task 2: 領域発見・マトリクス生成・セルタスク生成

- [ ] 2. レビュー領域を自己発見し、マトリクスとセルサブタスクを生成する
  - design.md「領域発見プロトコル」の資産カテゴリ検出規則（マニフェストファイルの存在からのエコシステム検出 — 事前定義の固定領域リストは使用禁止）により、対象リポジトリの全ソース資産カテゴリを実行時に発見する（移植先でも同一規則で再発見できること）
  - 各資産カテゴリの品質検証インフラ（テスト・lint・監査ツール）を検出し、Task 1 の正準コマンド表と突き合わせる
  - 領域分割規則を適用する: トップレベル構成単位（クレート・パッケージ・資産ディレクトリ）を最小粒度とし、src 実測行数が約 3,000 行を超える単位はサブモジュール境界で細分化する（1 ディスパッチの点検対象 ≦ 約 2,000 行）
  - 領域 × 次元グループ（G1〜G5 — design.md「次元グループ定義」）でセルを生成する。小領域（<1,500 行）はグループ統合で 1〜3 セルに圧縮し、横断 D7（サプライチェーン監査・台帳同期・drift-check）は全体セル 1 件に集約する
  - matrix.md を生成する（design.md「matrix.md スキーマ」準拠。全セル PENDING・実行開始日時・ベースラインコミット hash を記録）
  - 本ファイル下方の GENERATED-CELLS マーカー区間へ 3.x サブタスクを追記する。書式は design.md「Data Models › tasks.md GENERATED-CELLS 追記書式」のコードブロックに**逐語準拠**する（固定部の編集は禁止）
  - 再実行時は GENERATED-CELLS 区間をクリアしてから再生成する（冪等）
  - 完了条件: 機械検証 — `- [ ] 3.{番号}` 形式のサブタスク行数（メジャータスク行 `- [ ] 3. …` 自体は除く）が matrix.md のセル行数と一致し、追記された全行がチェックボックス書式（`_Requirements:`・`_Boundary:` フッター含む）に適合している
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 8.2, 8.3, 8.4_
  - _Boundary: 領域発見プロトコル（書き込みは matrix.md と tasks.md GENERATED-CELLS 区間のみ。固定部・改善対象コードの変更なし）_

## Task 3: セル実行ループ（サブタスク 3.x は Task 2 が動的生成）

- [ ] 3. 全セルを点検・改善・検証・記録し、終端状態へ到達させる（コンテナタスク）
  - 本メジャータスクは直接の実行単位ではない。実行単位は GENERATED-CELLS 区間に Task 2 が追記するサブタスク 3.x である
  - 前提: GENERATED-CELLS 区間に 3.x サブタスクが 1 件以上存在すること（空であれば Task 2 が未完了 — 本タスクに着手しない）
  - 各セルは design.md「セル実行プロトコル」に従う: 自己修復プレリュード（porcelain 確認・前セル Blocked 残置の巻き戻し＋SKIPPED 遡及記録）→ 点検 → 改善（G1→G2→G3→G4→G5 の昇リスク順・資産種別に適用不能な次元は N/A＋理由を記録）→ 2 段検証（領域スコープ → コミット前全体）→ 改善ありセルのみ独立レビュー（kiro-review）→ コミット（`Riloop-Cell: {area}x{group}` トレーラ必須・個別 `git add`）
  - 挙動保存: design.md「セルエージェントへの必須プロンプト制約」に従う（正常系の外部観測挙動を厳密保存・新機能/外部仕様変更禁止・許容ハードニングは境界回帰テストを必ず追加し matrix.md に記録・等価性は既存テスト＋スナップショットの GREEN で検証）
  - 検証 RED は kiro-debug（最大 2 ラウンド）で根本原因修復を試み、非収束時は design.md「巻き戻し手順」（porcelain で当該セルのファイル集合を特定 → `git restore <file>` 個別適用・新規ファイル個別削除・禁止 Git 操作不使用・他セッションの未コミット作業は巻き込まない）で復元し SKIPPED＋理由を記録する
  - NO_CHANGE は次元別の新鮮な点検証拠を matrix.md Notes に記録して初めて成立する（証拠なき宣言は未完了扱い）。空コミットは作成せず、台帳更新（matrix.md・チェックボックス）はセルのコミットへ同梱する
  - 完了条件: matrix.md の全セルが終端状態（IMPROVED / NO_CHANGE / SKIPPED のいずれか）であり、GENERATED-CELLS 区間の 3.x が全て `[x]`。途中での完成宣言（MVP・部分実装等)は行わない
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 2.6, 2.7, 2.8, 2.9, 2.10, 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 3.7, 4.3, 4.4, 4.5, 4.6, 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 6.1, 6.2, 6.3_
  - _Boundary: セル実行プロトコル（各セルの変更可能範囲は当該サブタスクの `_Boundary:` paths に限定。クレート単位検査の指摘は design.md「指摘の帰属規則」に従う）_

## Task 4: 改善レポート集約

- [ ] 4. matrix.md とコミット履歴から改善内容レポートを生成する
  - 前提クリーンチェック: `git status --porcelain` を確認し、最終セルが Blocked で変更残置がある場合は自己修復プレリュードと同じ手順（巻き戻し＋SKIPPED 遡及記録＋台帳 chore コミット）を実行する
  - 前提条件: matrix.md に PENDING が存在しないこと（存在する場合は Task 3 のセル処理へ戻る）
  - matrix.md と `git log --grep "Riloop-Cell:"`（ループ開始コミット以降）を入力として、`reports/{YYYY-MM-DD}-improvement-report.md` を生成する（同日再実行時は上書きせず `-2` 等のサフィックスで併存）
  - 必須 5 セクションを含める: ①セル別実施結果（領域・次元・改善内容・コミットハッシュ）②許容した挙動変化（攻撃面ハードニング）と境界を明示した回帰テストへの参照 ③スキップ一覧と理由 ④確認済み（改善不要）一覧 — 改善実施セルと区別し、既知負債領域の NO_CHANGE は「要注意」として明示 ⑤導入したツールと環境変更の記録
  - 完了条件: 必須 5 セクションをすべて満たすレポートファイルが reports/ に存在し、開発者へ報告されている
  - _Requirements: 5.5, 7.1, 7.2, 7.3, 7.4, 7.5_
  - _Boundary: レポート集約（書き込みは reports/ と、前提クリーンチェックに伴う巻き戻し・台帳記録のみ）_

  - _Requirements: 5.6, 6.4, 8.1_
