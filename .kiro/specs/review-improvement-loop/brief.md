# Brief: review-improvement-loop

## Problem
リポジトリ全域のコード品質（テスト網羅性・簡潔性・安全性）を、**外部から観測可能な挙動を変えずに**継続的に底上げしたい。しかし現状は次の課題がある。

- 品質改善が「その都度の手作業」に依存し、再現性・網羅性・移植性がない。
- レビューの観点（テスト・簡素化・脆弱性 等）が暗黙知で、領域（クレート）ごとに抜け漏れが生じる。
- 改善作業中の「破壊（リグレッション）」検知と巻き戻しが属人的で、途中放棄が起こりうる。
- 1回の実装指示で「全領域 × 全観点」を完走させる仕組みがない。

## Current State
- Cargo ワークスペース。7クレート構成（概算規模）:
  - `pasta_dsl` (~2,500行 / Pest PEGパーサー)
  - `pasta_core` (~600行 / レジストリ)
  - `pasta_lua` (~8,000行 / トランスパイラ＋LuaJITランタイム＋デバッグ基盤、**最大領域**)
  - `pasta_shiori` (~1,500行 / SHIORI・FFI・unsafe境界)
  - `pasta_lsp` (~400行 / LSP・WASM対応)
  - `pasta_check` (~500行 / リリースCLI)
  - `pasta_sample_ghost` (~300行 / サンプルゴースト生成)
- ロードマップ Phase 3 で `audit-pasta-*` を**クレート個別spec**として脆弱性監査・簡素化を実施済み（完了・アーカイブ）。ただし:
  - 個別spec方式のため**統合された再実行可能ループがない**。
  - **テスト網羅性**という観点が体系的次元として組み込まれていない。
  - **別プロジェクトへの移植性がない**（pasta固有の領域に固定）。
- 既存の品質インフラ: `cargo test --workspace`、`cargo clippy`、`cargo-audit`、`cargo-deny`（`deny.toml`）、`insta`（スナップショット）、`TEST_COVERAGE.md`（テストマッピング台帳）。
- ビルド注意点: `cargo build/test` 前に環境変数 `NoDefaultCurrentDirectoryInExePath` を外さないと mlua-sys/LuaJIT ビルドが exit 101 で失敗する（既知の地雷）。

## Desired Outcome
1回の実装指示（`/kiro-impl review-improvement-loop`）で、以下が中断なく完走すること:

1. **領域を自己発見**（ギャップ分析）し、`レビュー領域 × レビュー内容` のマトリクスを動的生成する。
2. 各セルを**サブエージェントに委譲**して実行し、メインエージェントのコンテキストを枯渇させない。
3. 各改善サイクルで**自己レビューにより破壊（リグレッション）が無いこと**を検証する。
4. サイクル完了ごとに**コミット**する。
5. デバッグ不能な不具合に陥った領域は**直前コミットへ巻き戻して次タスクへ進む**（全タスク完走を保証し、途中放棄を禁止）。
6. 全完走後に**改善内容レポート**を生成する。
7. この仕様を**別プロジェクトへコピーして再実行するだけ**で、そのプロジェクトの領域を自動再発見し同等の効果が得られる。

## Approach
**自己発見ループ型（再実行可能プロセス仕様）** を採用。

- **design.md = 普遍手順**。pasta固有の領域名・クレート名を設計にハードコードせず、「領域発見 → マトリクス生成 → セル実行ループ → 自己レビュー → コミット → 巻き戻し判断 → レポート」を普遍的な作業として記述する。
- **tasks.md 冒頭に「領域ギャップ分析タスク」** を置く。サブエージェントが対象リポジトリを分析し、`レビュー領域（最低でもクレート単位、必要なら細分化）× レビュー内容` のマトリクス（ワークリスト）を動的に生成する。
  - 細分化基準: サブエージェント1回で安全に処理できる粒度に収める（例: `pasta_lua` ~8,000行はサブモジュール=`code_gen`/`runtime`/`loader`/`sakura_script`/`debug` 等へ分割）。大きすぎる領域はタスク障害を招くため必ず分割する。
- **release-workflow 同様の再実行型spec**として運用する（`completed/` へ移動せず `.kiro/specs/` 直下に留まり、`/kiro-impl` のたびにループを再走できる）。
- **移植**: 別プロジェクトへ spec ディレクトリをコピー → `/kiro-impl` 再実行 → ギャップ分析タスクがそのプロジェクトの領域を再発見。

### レビュー内容（次元）— 確定 7 次元
1. **テスト網羅性**: 不足テストの追加。不要テストの除外（除外は慎重判断・根拠明記）。
2. **コード簡素化**: `/karpathy-guidelines` スキル準拠の検証と改善。
3. **脆弱性対策**: 脆弱性レビューと対策コード投入。
4. **clippy/lint 徹底**: `cargo clippy` を warnings=deny 相当で全領域通過、慣用句逸脱を是正。
5. **デッドコード/未使用除去**: 未使用の pub export・関数・依存を検出し除去（コード量削減）。
6. **パニック経路削減**: `unwrap`/`expect`/index panic を `Result`/明示エラーへ。FFI/SHIORI 境界を特に重視。
7. **ドキュメント/依存整合**: `TEST_COVERAGE.md`/README/`doc/spec` 同期、`cargo-audit`/`cargo-deny` サプライチェーン監査の組み込み。

### 挙動保存ポリシー（確定）
- **正常系（妥当な入力）の外部観測挙動は厳密に保存する**。
- **脆弱性対策は、不正入力・攻撃面のハードニングに限り挙動変化を許容**する。許容した挙動変化は**回帰テストで境界を明示**し、レポートに記録する。
- 純粋な挙動等価改善（簡素化・clippy・デッドコード除去・パニック経路化のうち正常系で観測不能なもの）は、既存テスト＋スナップショットで等価性を担保する。

### 破壊検知と巻き戻し（確定フロー）
- 各サイクル前後で**ベースライン検証**（`cargo test --workspace` 等）を実行し、改善前後で破壊が無いことを確認する。
- セル単位でサイクルを回し、**サイクル完了＝グリーン確認＝コミット**を1単位とする。
- あるセルでデバッグが収束しない場合（`kiro-debug` プロトコルでも完遂不能）、**当該セルの変更を直前コミットへ巻き戻し、スキップ理由を記録して次セルへ進む**。
- **全タスク完走を保証**（途中中断・部分出荷宣言は禁止。`workflow.md` の MVP禁止・回帰責任・危険Git操作禁止に整合）。

### サブエージェント委譲（確定）
- ギャップ分析・各セル改善・自己レビュー・レポート集約をそれぞれサブエージェントへ委譲する。
- メインエージェントはオーケストレーション（ワークリスト管理・コミット・巻き戻し判断・進捗追跡）に徹し、コンテキストを温存する。
- 既存スキル `kiro-review`（敵対的レビュー）・`kiro-debug`（根本原因デバッグ）・`kiro-verify-completion`（完了前の新証拠ゲート）・`karpathy-guidelines` を各段で活用する。

## Scope
- **In**:
  - 全レビュー領域 × 全7次元のマトリクス改善を1仕様・1実装指示で完走するループ。
  - 領域の自己発見（ギャップ分析）、サブエージェント委譲、サイクル毎コミット、破壊検知、巻き戻し、最終レポート。
  - 既存の品質インフラ（cargo test/clippy/audit/deny/insta）の活用と、必要なら追加。
- **Out**:
  - 新機能の追加・外部仕様の変更（本仕様は挙動保存が前提）。
  - 既存の完了済み `audit-pasta-*` spec の改変・再オープン（本仕様は独立した新境界）。
  - ベンチマーク性能の最適化を主目的とする作業（簡素化の副次効果は可、性能チューニング自体は対象外）。
  - CI 設定そのものの再設計（既存 `.github/workflows/` の整合確認は可、再設計は別仕様）。

## Boundary Candidates
- **ギャップ分析・マトリクス生成**（領域発見の責務シーム / 移植性の核心）。
- **セル実行ループ**（領域×次元の1セルを改善するサブエージェント単位）。
- **破壊検知・巻き戻しオーケストレーション**（グリーン判定・コミット・rollback 判断）。
- **改善レポート集約**（全セル結果の収集と報告書生成）。
- **挙動保存検証**（ベースライン確立・スナップショット・回帰テスト）。

## Out of Boundary
- Kiro ワークフロー自体（spec/skill 群）の改修。
- pasta DSL 文法・Lua API の仕様変更（本仕様は挙動保存）。
- リリース・配布フロー（`release-workflow` の領分）。
- マニュアル `book/` の内容拡充（`pasta-user-manual` 系の領分。ただしドキュメント整合次元での同期確認は In）。

## Upstream / Downstream
- **Upstream（依存・前提）**:
  - 既存品質インフラ: `cargo test/clippy`、`cargo-audit`、`cargo-deny`、`insta`、`TEST_COVERAGE.md`。
  - 既存スキル: `karpathy-guidelines`、`kiro-review`、`kiro-debug`、`kiro-verify-completion`。
  - `workflow.md` の DoD・回帰責任・危険Git操作禁止・MVP禁止ルール。
  - ビルド地雷回避（`NoDefaultCurrentDirectoryInExePath` 環境変数）。
- **Downstream（消費者・後続）**:
  - 別プロジェクトへの移植利用（本仕様の主要価値）。
  - 改善レポートが今後のリファクタ・テスト戦略の入力になる。

## Existing Spec Touchpoints
- **Extends**: なし（新規独立仕様）。
- **Adjacent**:
  - 完了済み `audit-pasta-*`（Phase 3）— 脆弱性監査・簡素化の先行事例。アプローチの参考にするが改変はしない。
  - `release-workflow` — 再実行型spec（`completed/` へ移動しない）の運用パターンを踏襲する。

## Constraints
- **挙動保存**: 正常系厳密、攻撃面ハードニングのみ挙動変化許容（境界はテストで明示）。
- **1仕様・1実装指示で完走**: 途中中断・部分出荷禁止。全タスク完走を保証。
- **移植可能性**: 設計に pasta 固有領域をハードコードしない。コピー＋再実行で別プロジェクトに適用可能。
- **サブエージェント委譲**: メインエージェントのコンテキスト枯渇を防ぐ。タスク粒度はサブエージェント実行可能な範囲に分割。
- **再実行型運用**: `completed/` へ移動せず、`/kiro-impl` のたびに再走可能。
- **ビルド**: `cargo` 実行前に `NoDefaultCurrentDirectoryInExePath` を解除（mlua/LuaJIT ビルド失敗回避）。
- **言語**: 仕様ドキュメントは日本語（spec.json.language=ja）。
- **Git**: 危険な破壊的操作禁止（`workflow.md` 準拠）。巻き戻しは「直前コミットへの当該セル変更の復元」に限定し、他セッションの作業を巻き込まない。
