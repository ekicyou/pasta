# Gap Analysis: review-improvement-loop

**分析日**: 2026-06-10
**対象**: 要件 R1〜R8（8要件/42受け入れ基準）と既存コードベース・プロセス資産のギャップ

---

## 1. 分析サマリー

- 本仕様は**プロセス型メタ仕様**であり、ギャップ分析の対象は「機能コード」ではなく (a) 品質インフラと現在のコード状態、(b) 再利用可能なプロセス資産（kiro スキル群・再実行型 spec パターン）である
- **プロセス資産は要件の大半を既にカバーする**: `kiro-impl` の自律モード（タスク毎サブエージェント＋独立レビュー＋検証ゲート＋選択的コミット＋デバッグ2ラウンド上限）は R4/R5/R6 の機構をほぼ提供済み。設計は「ゼロから発明」ではなく「既存実行器への適合」が主作業
- **最大の構造的ギャップは「動的ワークリスト × 静的 tasks.md」の整合**: 領域は実行時に自己発見される（R1.4）が、`kiro-impl` は tasks.md のチェックボックスを権威的ワークリストとして駆動する。この橋渡し方式が設計の核心的意思決定
- **コード状態の実測はbriefの想定を大きく超える**: pasta_lua は src 約24,000行（brief想定 ~8,000行の3倍）、ワークスペース全体でパニック経路1,001箇所、clippy ゲート完全不在。セル粒度設計と実行コスト見積もりに直結する
- **未知数（Research Needed）**: 全体テストの実時間、clippy 警告の初回ボリューム、未使用依存検出ツールの選定。いずれも設計フェーズで確定可能

## 3. プロセス資産の調査（再利用可能機構）

### 3.1 kiro-impl（実行器）— R4/R5/R6 の機構を概ね提供済み

| 機構 | 内容 | 対応要件 |
|---|---|---|
| タスク毎の新鮮なサブエージェント | サブタスク 1 件 = 実装サブエージェント 1 体。毎イテレーションで tasks.md を再読 | R6.1, R6.2 |
| 独立レビュー | タスク毎に別の新鮮なレビュアー（kiro-review）が `VERDICT: APPROVED/REJECTED` | R6.3 |
| 完了検証 | APPROVED 後に kiro-verify-completion（新鮮な証拠ゲート） | R6.4 |
| 選択的コミット | `git add <個別ファイル> tasks.md`（`git add -A` 禁止） | R4.4, R5.3 |
| デバッグ上限 | レビュー REJECTED 3回目でデバッガー投入、**デバッグ 2 ラウンド上限**で `_Blocked:` 注記しスキップ | R5.1, R5.2 |
| 検証コマンドの一括発見 | コントローラが TEST/BUILD/SMOKE コマンドを 1 回発見し全サブエージェントへ伝搬 | R4.6 |

**ギャップ**: kiro-impl の「Blocked → スキップ」は**変更を巻き戻さない**（ワークツリーに残置）。R5.1 は「当該セルの変更のみを直前コミット時点へ復元」を要求 → **巻き戻し手順の明示設計が必要**（§5 ギャップ表 G-3）

### 3.2 release-workflow（再実行型 spec の先例）— R8 のパターン提供

- spec は `.kiro/specs/` 直下に常駐、`kiro-spec-complete` がアーカイブ手順（移動・パス更新）をスキップ
- 再実行前に tasks.md のチェックボックスを `[x]` → `[ ]` へ**手動リセット**
- spec.json の `phase` は `completed` にならず `ready_for_implementation` を維持
- タスク表記規約: `(P)` 並列マーカー（実際は逐次処理）・`_Depends:_`・`_Boundary:_`

### 3.3 補助スキル

| スキル | 提供内容 | 対応要件 |
|---|---|---|
| kiro-review | 敵対的レビュー（回帰安全・境界遵守・TBD/TODO 残置・秘密情報の機械チェック＋重大度別所見） | R6.3 |
| kiro-debug | 根本原因デバッグ。`NEXT_ACTION: RETRY_TASK / BLOCK_TASK / STOP_FOR_HUMAN` で非収束判定を構造化 | R4.5, R5.1 |
| kiro-verify-completion | `STATUS: VERIFIED / NOT_VERIFIED` の新鮮証拠ゲート。チェックボックス全 `[x]` での自動合格を拒否 | R6.4, R5.6 |
| karpathy-guidelines | 簡素化基準（最小コード・投機的機能禁止・外科的変更・検証可能な成功基準） | R2.4 |

### 3.4 tasks.md 規約（.kiro/settings/）

- サブタスクが実行単位（`- [ ] 1.1 説明`）、メジャータスク連番、`_Requirements: X.X_` フッター必須
- **最終タスクは「ドキュメント整合性確認」が必須**（workflow.md）→ 次元 7 と統合可能
- サブタスク数に上限なし → 動的に件数が伸びる構造を許容

## 5. 主要ギャップ詳細（設計フェーズへの申し送り）

### G-1: 動的ワークリスト × 静的 tasks.md の橋渡し【最重要の設計判断】

領域は実行時に発見される（R1.4）が、kiro-impl は tasks.md を権威的ワークリストとして駆動する。3 方式が考えられる:

- **B1: tasks.md 自己拡張方式** — Task 1（領域発見）が発見結果から**具体的なセルタスク群を tasks.md へ追記生成**する。kiro-impl は毎イテレーション tasks.md を再読するため、追記されたタスクを自然に処理する。「レビュー領域の数だけタスクを分類」という要求と移植性が両立
  - ✅ kiro-impl の実行モデルと完全整合・チェックボックス進捗が領域粒度で可視
  - ❌ 実行中の tasks.md 変異は前例なし（リスク: 追記書式の崩れ → 設計でテンプレートを厳格定義して緩和）
- **B2: 外部ワークリスト方式** — Task 1 がマトリクスを別ファイル（matrix.md 等）へ生成し、後続の固定タスクがそれを消費してループ
  - ✅ tasks.md は静的のまま
  - ❌ 「ループ全体で 1 サブタスク」になると 1 サブエージェントに全セルが集中し委譲粒度が崩壊（R6 違反）。kiro-impl の 1 サブタスク=1 サブエージェント原則と不整合
- **B3: tasks 再生成方式** — 移植時に /kiro-spec-tasks を再実行して具体タスクを再列挙
  - ❌ discovery で却下済み（pasta 具体特化と同型）

**示唆**: B1 が kiro-impl の実行モデル・ユーザー要求（領域数分のタスク分類）・移植性のすべてと整合する。

### G-2: セル粒度と実行コスト

- 領域数の見込み（**全資産スコープ確定後・2026-06-10**）: 小規模 6 クレート（pasta_check/core/dsl/lsp/sample_ghost ＋）＋ pasta_lua 細分化（code_gen / debug / loader / runtime / sakura_script+search+encoding / transpiler+top ≒ 6 領域）＋ **Lua 資産**（pasta_scripts / lua_specs ≒ 1〜2 領域）＋ **VSCode 拡張 TS**（1 領域）＋ **book/tools JS**（1 領域）＝ **約 15〜18 領域**
- 15〜18 領域 × 7 次元 = **約 105〜126 セル**（ただし資産種別ごとに適用不能次元は「該当なし」で即終了。例: Lua 領域に `cargo clippy` 次元は N/A、TS 領域に `cargo-audit` は eslint/npm audit へ読替）。セル毎に「改善サブエージェント＋レビュアー＋検証」を回すと検証コストが支配的になる恐れ
- 緩和オプション（設計で選択）:
  - セル検証はクレートスコープ（`cargo test -p`）を一次とし、コミット前に全体（`--workspace`）を確認する 2 段検証
  - 次元の束ね（例: 次元 4+5 lint/デッドコードを 1 セルに統合）で総セル数を圧縮
  - lint（次元4）はクレート単位が自然粒度（clippy はクレート単位実行）— pasta_lua 細分化領域では「担当モジュールの警告のみ対処」と境界定義

### G-3: 巻き戻し手順（R5.1〜R5.4 の安全な実現）

workflow.md は `git reset --hard` / `git checkout --` / `git clean -fd` を禁止。許容される機構:
1. セル開始前に `git status --porcelain` でベースライン記録（コミット直後なのでクリーンのはず）
2. セル失敗時、`git status --porcelain` で**当該セルが触れたファイル集合**を特定
3. 変更ファイル: `git restore <file>` を個別適用（慎重使用が許容されている）
4. 新規追加ファイル: 個別削除（`git clean` 不使用）
5. 直前コミットがセル単位で刻まれているため、復元先は常に「直前のグリーンコミット」と一致

### G-4: 改善レポートの蓄積形式（R7）

セル毎の結果（領域・次元・改善内容・コミットハッシュ・スキップ理由・許容挙動変化）を**逐次蓄積する場所**が必要。候補: spec 配下の `report/`（実行日付別）または単一 `improvement-report.md` へ追記。tasks.md の `## Implementation Notes` は kiro-impl の学習記録と衝突しない範囲で併用可。

### G-5: 移植時の品質インフラ自動発見（R8.4）

「Cargo.toml → cargo test/clippy、package.json → npm test、pyproject.toml → pytest…」のような**検出優先順位表**を design.md に普遍手順として定義する必要がある。本リポジトリ固有値（NoDefaultCurrentDirectoryInExePath 等）は「プロジェクト既知制約の発見手順」（steering/memory 参照）として一般化する。

## 6. 実装アプローチ評価

### Option A: kiro-impl 標準フローへの完全適合（拡張なし）
静的 tasks.md に pasta の具体領域を列挙。
- ✅ 最小リスク・即実行可能
- ❌ R1.4（固定リスト禁止）・R8.3（移植性）に**違反**。discovery 決定と矛盾
- **判定: 不採用**（要件違反）

### Option B: 自己発見ループ型 = Task 1 発見 + tasks.md 自己拡張（B1）+ kiro-impl 機構再利用
design.md に普遍手順（発見アルゴリズム・セルプロンプト・巻き戻し手順・レポート様式）を定義し、tasks.md は「Task 1: 領域発見とセルタスク生成」＋「生成されるセルタスクのテンプレート」＋「最終: レポート集約・ドキュメント整合」で構成。
- ✅ 全要件と整合。kiro-impl の実証済み機構（委譲・レビュー・コミット・デバッグ上限）を最大再利用
- ✅ 「領域の数だけタスクを分類」を実行時に実現
- ❌ tasks.md 実行中変異という新規パターン（テンプレート厳格化で緩和）
- **判定: 推奨**

### Option C: ハイブリッド = 次元フェーズ静的 + 領域動的（外部ワークリスト併用）
7 次元を静的メジャータスクとし、各次元内で外部ワークリストの領域を順次処理。
- ✅ tasks.md 静的維持
- ❌ 次元タスク 1 件 = 全領域処理となり 1 サブエージェントへの集中（R6 違反）か、コントローラ直接ループ（kiro-impl 逸脱）の二択になる
- **判定: 次点**（B が tasks.md 変異リスクで頓挫した場合の代替）

## 7. 工数・リスク評価

| 対象 | 工数 | リスク | 根拠 |
|---|---|---|---|
| 仕様作成（design + tasks） | **M**（3〜7日相当） | **Low** | プロセス文書化が主。既存スキル群の機構流用で発明要素は G-1/G-3 に限定 |
| ループ実行（/kiro-impl 1 回の完走） | **XL**（77〜91 セル × 改善+レビュー+検証） | **Medium** | 機構は実証済みだが、検証実時間・clippy 初回量・パニック経路 1,001 箇所の規模が未知。巻き戻し機構で完走自体は保証される |

リスクが High でない理由: 完走保証機構（巻き戻し＋スキップ）が失敗の影響を「当該セルのスキップ記録」に局所化するため、最悪ケースでも部分的成果＋完全なレポートが残る。

## 8. 設計フェーズへの推奨事項

1. **Option B（自己発見ループ＋tasks.md 自己拡張）を採用**し、セルタスクの追記テンプレートを design.md で厳格に定義する（書式崩れ防止）
2. **2 段検証**（クレートスコープ → コミット前ワークスペース全体）でセル毎の検証コストを制御する
3. **次元の束ね**を検討（4 lint + 5 デッドコード統合等）し総セル数を 60 前後へ圧縮する
4. **巻き戻し手順**を G-3 の安全機構（porcelain 差分 → 個別 restore）として普遍手順化する
5. **品質インフラ発見表**（R8.4）をプロジェクト種別ごとの検出優先順位として design.md に定義する
6. **レポート蓄積**は spec 配下への逐次追記とし、セルコミットと同時に記録する（後からの再構築不要）

## 9. 要件ディスカッション由来の設計判断（2026-06-10・設計フェーズへ先送り）

要件ディスカッション（`kiro-requirements-discussion`）で抽出され、how に属するため設計フェーズで解決する項目。

### B-a: 領域内の次元実行順序（テストファースト・ブートストラップ）
- **論点**: R3.4 は挙動等価性の検証に「既存テスト」を前提とするが、pasta_check はテスト 0 件・pasta_core もテスト 1 ファイルのみ。テスト網羅が薄い領域では、次元2/4/5/6（簡素化・lint・デッドコード・パニック経路）の挙動保存を既存テストで担保できない
- **推奨**: 1 領域内では**次元1（テスト網羅性）を先行実行**し、後続の挙動保存依存次元に安全網を張る順序を design.md で規定する（領域内のセル実行順序＝1→3→6→2→4→5→7 等）。テストが十分な領域では順序自由

### B-b: 再実行セマンティクス（resume と reset の区別）
- **論点**: R8.2「タスク実行状態を初期化し...再走」と、kiro-impl が tasks.md の未チェックタスクを継続する挙動（1 回の /kiro-impl で全セル未完了の場合の途中再開）が混在しうる
- **推奨**: design.md で 2 概念を明確に分離する。(1) **同一ループの再開** = /kiro-impl を再呼び出しし、未チェックのセルタスクを継続（context/時間切れ対策・release-workflow と同じ）。(2) **新規ループの開始** = チェックボックス一括リセット＋マトリクス再生成（R8.2 が指すのはこちら）。リセットは意図的操作とする

### B-c: テスト網羅「十分性」の判定基準
- **論点**: R2.2「不足しているテストを特定して追加」の「不足」の基準が未定義。固定カバレッジ % ゲートは移植性を損なう（プロジェクトごとに計測基盤が異なる）
- **推奨**: ハード % ゲートを置かず、**判断ベース**（未テストの公開挙動・未到達分岐・回帰が起きやすい複雑経路）で不足を定義する。本リポジトリでは TEST_COVERAGE.md 台帳と実測（#[test] 1,502 件 vs 台帳宣言 1050+ の乖離）を入力に、領域ごとに不足を特定

### B-d: セル粒度と次元束ね（G-2 参照）
- 約 11〜13 領域 × 7 次元 = 77〜91 セルを 60 前後へ圧縮するため、lint（次元4）＋デッドコード（次元5）の統合等を design.md で確定する。クレート単位が自然粒度の次元（lint）と、サブモジュール単位で回せる次元（テスト・パニック経路）の粒度差を整理する

## 10. 設計フェーズ Discovery（2026-06-10・実測＋非Rust資産調査）

### 10.1 ベースライン実測（ライブ計測）

| 計測項目 | 結果 |
|---|---|
| `cargo test --workspace`（現環境そのまま） | **RED**: 1424 passed / **86 failed**（~36秒） |
| 同上（`PASTA_DEBUG` 解除後） | **GREEN**: **1510 passed / 0 failed**（**23秒** warm） |
| `cargo test -p pasta_core`（クレートスコープ・warm） | **4秒**（67 tests・実テスト時間 <0.02s、壁時間はほぼ cargo オーバーヘッド） |
| `cargo clippy --workspace --all-targets` | **117 警告**（pasta_lua 101 / pasta_shiori 12 / sample_ghost 2 / core・dsl 各1 / check・lsp 0）。上位: needless_borrows_for_generic_args 21, collapsible_if 18, needless_borrow 14, doc_lazy_continuation 14 — 大半が機械的修正可能 |
| `cargo audit`（0.22.2 導入済み） | **PASS**: 脆弱性 0 / 344 依存。許容警告 7（unsound: imageproc×2, rand / yanked: core2 / unmaintained 等） |
| `cargo deny` | **未導入**（deny.toml は存在 — 設定だけあり実行手段なし） |
| cargo-machete / cargo-udeps | 未導入。nightly toolchain は導入済み（udeps 実行可能） |

**重大発見 — 環境起因の偽 RED**: 現シェルに `PASTA_DEBUG=1`・`PASTA_DEBUG_PORT=9276` が設定されており、全テストランタイムが DAP リスナーを固定ポートへ bind しようとして `AddrInUse`（os error 10048）で 86 件失敗する。コード起因ではない。**ループの検証ハーネスは `NoDefaultCurrentDirectoryInExePath` に加え `PASTA_DEBUG`/`PASTA_DEBUG_PORT` も解除しなければ、グリーンベースラインゲート（R4.1/R4.2）が永遠に通らない**。→ 設計に「環境プリフライト（既知制約の発見と無害化）」を第一級コンポーネントとして置く根拠。

**コスト含意**: warm 全体検証 23〜36 秒は**セル毎コミット前の全体検証として十分安価**。2段検証（セル内はスコープ検証 ~4秒、コミット前に全体 ~30秒）で 60 セル想定でも検証総コスト ~30〜40 分に収まる。

### 10.2 非 Rust 資産の検証コマンドメニュー（実在確認済み）

| 資産 | lint | build | test | audit |
|---|---|---|---|---|
| VSCode 拡張（editors/vscode・TS 5.5 strict） | `npm run lint`（eslint・設定ファイル所在不明=点検対象） | `npm run compile`（esbuild） | `npm run test`（grammar+unit×4+e2e・自前 node ランナー） | `npm audit`（lockfile あり） |
| book/tools（JS・Node 20） | なし（ギャップ） | mdbook build + 各ツール | 各ツール同梱 `*-test.mjs`（フレームワーク無し最小 assert）＋ drift-check/tutorial-check | `npm audit`（lockfile あり） |
| Lua 資産（crates/pasta_lua） | luacheck（`.luacheckrc` 設定済み・**CI 未ゲート**・scriptlibs/ にベンダー） | — | `cargo test -p pasta_lua --test lua_unittest_runner -- --nocapture`（lua_specs 44 ファイル・lua_test BDD） | —（Rust 側 cargo audit が包含） |

**CI 不在チェック（ローカルループで価値が高い）**: vscode 拡張の test/lint、luacheck、book ツールの `*-test.mjs` はいずれも CI に組み込まれていない → ループ実行が唯一の定期検証機会。

### 10.3 設計判断（Design Decisions）

#### 決定 D-1: tasks.md 自己拡張は「固定メジャータスク + 動的サブタスク」方式
- **選択**: tasks.md のメジャータスク構造は固定（1 プリフライト＋ベースライン / 2 領域発見＋マトリクス生成＋セルタスク生成 / 3 セル実行〔サブタスク 3.x を Task 2 が動的追記〕/ 4 レポート集約 / 5 ドキュメント整合＋完了検証）。Task 2 がマーカー区間（`<!-- GENERATED-CELLS -->`）内へ `- [ ] 3.{i}` サブタスクを追記する
- **根拠**: メジャータスク番号が不変のため kiro-impl の番号整合・進捗追跡が壊れない。G-1 の B1 案を、番号再採番リスクなしに実現する最小形
- **却下**: メジャータスク自体の動的追加（再採番が必要になり kiro-impl の前提と衝突）

#### 決定 D-2: 環境プリフライトを第一級コンポーネント化
- **根拠**: PASTA_DEBUG 偽 RED の実証（10.1）。既知制約は steering/memory/設計書の「環境制約表」から発見し、検証コマンド定義（正準コマンド表）に env 無害化プレフィックスを織り込む。ベースライン RED 時は「環境起因かコード起因か」を切り分け、環境起因なら環境を直し、コード起因なら R4.2 に従い中断

#### 決定 D-3: セル＝領域×次元グループ（5 グループ束ね）＋小領域はさらに統合
- **次元グループ**: G1=テスト網羅(D1) / G2=lint＋デッドコード(D4+D5) / G3=ハードニング(D3+D6) / G4=簡素化(D2) / G5=ドキュメント/依存整合(D7 領域分)。加えて D7 の横断部分（サプライチェーン監査・台帳同期・drift-check）は**全体セル 1 件**に集約
- **領域内実行順序（B-a 解決）**: G1（テスト安全網）→ G2（機械的修正・低リスク）→ G3（挙動変化を伴うハードニング）→ G4（簡素化・安全網必須）→ G5（最終状態の文書化）の昇リスク順
- **セルサイズ規則**: 1 ディスパッチの点検対象 ≦ 約2,000 行を目安に、小領域（<1,500 行）はグループ統合（1〜3 セル）、大領域は 5 セルフル分割。pasta_lua はサブモジュール 6 領域へ分割。**総セル数見込み ≈ 55〜65**
- **記録**: 束ねても次元別の結果記録は維持（R2 の各次元適用と R2.10 の「該当なし」記録を満たす）

#### 決定 D-4: 2 段検証（スコープ検証 → コミット前全体検証）
- セル作業中: 領域スコープの検証（`cargo test -p {crate}` 等・~4 秒）で高速イテレーション
- コミット直前: 全体検証（`cargo test --workspace` ~30 秒＋当該資産種別の lint/test）で破壊検知（R4.3）
- 根拠: 10.1 実測でコミット前全体検証が十分安価と判明

#### 決定 D-5: 巻き戻しは「ファイル単位の追跡と個別復元」（G-3 確定）
- セル開始時はコミット直後（クリーン）→ 失敗時 `git status --porcelain` で当該セルの変更ファイル集合を特定 → 変更ファイルは `git restore <file>` 個別適用、新規ファイルは個別削除。`reset --hard`/`clean -fd` 等の禁止操作は不使用（R5.4）

#### 決定 D-6: ツール供給ポリシー（build vs adopt）
- **設定が存在するのに実行手段がないツールは導入してよい**（dev 環境変更・リポジトリ非変更・レポートへ記録）: cargo-deny（deny.toml 既存）を全体 D7 セルで `cargo install cargo-deny`
- 未使用依存検出（D5）: **cargo-machete を採用**（コンパイル不要・高速・誤検知少）。未導入なら導入し記録。cargo-udeps（nightly 要・ビルド必要）は不採用
- 導入失敗時はその検査を「該当なし（ツール不可）」として記録し続行（完走優先）

#### 決定 D-7: コミット規約とレポート集約の機械化
- セルコミット: `<type>({area}): {summary}` ＋ 本文末尾に `Riloop-Cell: {area}x{group}` トレーラを必須化。type は次元グループに応じ test/refactor/fix/docs/chore
- レポート集約（Task 4）は matrix.md（セル台帳）＋ `git log --grep "Riloop-Cell:"` から機械的に再構成可能 — 集約サブエージェントのコンテキストを最小化

#### 決定 D-8: 実行状態の二重台帳（tasks.md = 実行状態 / matrix.md = 結果台帳）
- tasks.md のチェックボックス = kiro-impl の実行進捗（既存プロトコル）
- `matrix.md`（spec 配下・Task 2 生成）= セル結果台帳（Status: PENDING/IMPROVED/NO_CHANGE/SKIPPED、コミットハッシュ、次元別所見、N/A 記録）。各セル完了時にコントローラが更新（G-4 解決・R7 の入力）
- 再実行（B-b 解決）: 「同一ループの再開」= tasks.md 未チェック継続（kiro-impl 標準）。「新規ループ」= チェックボックス全リセット＋ GENERATED-CELLS 区間クリア＋ matrix.md 退避（reports/ へ）＋再発見から実行（R8.2）

### 10.4 リスクと緩和

- **リスク: clippy 117 警告の一括対処が pasta_lua セルを肥大化** — G2 セルは `cargo clippy --fix` の機械適用＋目視確認を一次手段とし、非機械的警告のみ個別判断（テスト後続のため安全網あり）
- **リスク: tasks.md 自己拡張の書式崩れ** — 追記テンプレートを design.md に逐語定義し、Task 2 の完了条件に「追記後の tasks.md がチェックボックス書式に適合していること（機械検証）」を含める
- **リスク: 環境変数が再発混入（PASTA_DEBUG 等）** — 正準検証コマンド表に env 無害化を埋め込み、サブエージェントへはコマンド文字列として伝搬（解釈余地を残さない）
- **リスク: 非 Rust 資産の検証が薄い（book ツール等）** — 各資産の既存 `*-test.mjs` を検証ゲートに採用。lint 不在領域は「lint 次元 = 該当なし」記録で完走を優先
