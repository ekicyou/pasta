# 暫定設計の検証: novel-checkpoint-rollback

- 対象: `provisional-design.md`（1 章「暫定の要件」を requirements.md の代わりに読んだ）
- 正とした物: `novel-areka-contract/final-model-2026-11-19.md`（以下「骨子」）、この spec の `brief.md` の「決定（2026-11-19。最終形）」
- やり方: `kiro-validate-design` を対話なしで走らせた。件数の上限は外し、重大と大きいものは全部挙げた。設計は直していない。コードの主張は、引かれたファイルを開いて確かめた。
- 2026-11-19。机の上の検証で、実行はしていない。

## 判定

**GO_WITH_CONDITIONS（条件付きで進めてよい）**

戻る道を `CHECKPOINT.jump` の 1 本にまとめ、控えを「コルーチンが止まる所」で取る芯は、骨子に合っていて、今のコードの上で作れる見込みがある。コードについての主張も、ほとんどが正しい。ただし、次の 2 つは、このままだと骨子の例（2.1 の設定の画面・4 章 A の「演劇は続く」）で動かない。

- 控えの「足取り」をコルーチンごとに持ち、待っている物語を `STORE.co_scene` から引く作り（重大 1）
- 早回しの組み立てが、続きの決まり（`_spoke`・`_on_speech`・`_interrupted`）を動かしてしまうこと（重大 2）

どちらも `novel-talk-flow` との取り決めで直せる。骨子に決めてもらう物が 3 つある（大きい 4・5・6）。

## 重大（critical）

### 重大 1. 足取りをコルーチンに付けたので、骨子の「再生位置は、いつも 1 つ」が、シーンの終わりと設定の画面で消える

- 区分: cross-spec（`novel-talk-flow`）。骨子との食い違いでもある
- 根拠:
  - 設計 3.3・4.3・D4 は、再生位置・`pending`・`last_id`・`story` を `STORE.checkpoint.tracks[co]`（弱い参照）に置く。`current_id`・`position`・`story_actor`・`reapply_story_actor` は「`STORE.co_scene` の足取り」を読む（5.1）。
  - 骨子 3 章は「演劇の状態は、呼んだ流れ（コルーチン）に付く」を取り下げ、「状態は、ゴーストに 1 つ」とした。
  - 骨子 4 章 A: シーンが最後の行まで走って `＞` が無くても演劇は続き、今のシーンは変わらない。ところが、最後の行の後でコルーチンが終わると、`set_co_scene` は終わったコルーチンを nil にする（`shiori/event/init.lua:115-122`）。参照が切れて、足取りは GC で消える。`position()` も `current_id()` も nil になり、ローカルの反応を先に探す元（骨子 2.3）も既読の鍵も無くなる。
  - 骨子 2.1 の例の設定の画面（`＊OnMouseClick　＆＄ｒ４＝「設定」　＆再生モード：設定`）は「どうする？」と台詞を出す。今の続きの決まりでは、台詞を出した割り込みは `STORE.co_scene` を自分に替える（`init.lua:274-280`。`drive_kind` は `interrupt`、`spoke` は真）。待っていた物語のコルーチンは捨てられ、その足取りも消える。`story_actor()` は nil を返し、R16 と 6.5 の `＞演劇再開` は作れない。設計 10.1 の頼み 5 は、ロードの場合しか挙げていない。
- 影響: R3・R12（設定の場面からのセーブ以外）・R16 と、`novel-talk-flow` に渡す `position`・`current_id` が、骨子の基本の例で壊れる。
- 提案: 2 段に分ける。
  - コルーチンごとの足取りは「仮の物」として残す（D4 の理由、つまり台詞を出さないシーンが物語の `pending` を汚さない、は正しい）。
  - 物語の足取りを 1 つ、ゴーストの所（`STORE.checkpoint.story`）に置く。仮の足取りを物語の足取りへ上げるのは、そのコルーチンが続きになった時（`EVENT.drive` の 8 番で `set_co_scene` が採った時）か、目印付きの 1 本を確定した時とする。
  - コルーチンが終わっても、物語の足取りは残す（4 章 A）。設定のモードの間に待っている物語のコルーチンを、どこに持つか（`STORE.co_scene` のままか、別の欄か）は `novel-talk-flow` と決め、決まった物を `story_actor` などの引き元に書く。

### 重大 2. 早回しで捨てる組み立てが、続きの決まりの欄を立て、`＊チェイントーク中断` を走らせる

- 区分: cross-spec（`novel-talk-flow`。続きの決まり）
- 根拠:
  - `SHIORI_ACT_IMPL.build` は、組み立てのたびに `self._spoke` を立てる。`_on_speech` が在れば中断のシーンを走らせ、`_interrupted = true` にする（`shiori/act.lua:72-93`）。
  - `EVENT.drive` は、`interrupt` の種類のときだけ `_on_speech = run_interrupt_scene` を掛ける（`init.lua:239-248`）。`_interrupted` が立てば、古い続きもこのコルーチンも捨てる（`init.lua:274-276`）。
  - `OnPlayRollback` は `co_preempt` なので種類は `preempt` になり、この道は通らない。一方、設定の場面の選択肢（`・ロードする` → `＞スロット読込`）は、選ばれたローカルシーンが新しいコルーチンで走る。そのため種類は `interrupt` になる。早回しで捨てる最初の台詞の組み立てで中断のシーンが走り、`_interrupted` が立って、ロードした物語のコルーチンが捨てられる。ゴーストに `＊チェイントーク中断` が在ると、こうなる。
  - 10.1 の頼み 5 の「1 本目に字が無いので台詞の無い割り込みと見られ、古い続きが残る（`init.lua:279`）」は、半分しか合っていない。`spoke` は `scene_act._spoke` で決まる（`init.lua:269-272`）。早回しが台詞のある 1 本を組み立てていれば真、1 本も組み立てていなければ nil で、出力が空でないので真になる。台詞の無い 1 本だけを組み立てていれば偽で、古い続きが残る。結果は、早回しした中身しだいで変わる。
- 影響: 設定の画面からのロード（骨子 2.1・4 章 C の主な道）が、ゴーストと台本の中身によって、黙って壊れる。
- 提案: 早回しの間は、組み立ての副作用のうち、続きの決まりの欄（`_spoke`・`_on_speech`・`_interrupted`）を動かさない（`CHECKPOINT.replaying()` の間は `SHIORI_ACT_IMPL.build` の 76〜93 行を飛ばすか、早回しの組み立ては `ACT.IMPL.build` と `BUILDER.build` を直に呼ぶ）。あわせて、「ロード・巻き戻しのコルーチンは、いつも続きを置き換える」を、続きの決まりに 1 つの規則として足すよう `novel-talk-flow` に頼む（`co_preempt` の印を `スロット読込` の道でも付ける、など）。`_spoke` の偶然に頼らない。

## 大きい（major）

### 大きい 1. R10 の着せ替えの差分の元（`before`）を、早回しで動いた後に取っている

- 区分: within-spec
- 根拠: `land` は `ACTOR_STATE.apply` の戻り値（置く前の `STORE.appearance.actors`）を `before` にする（5.1）。`jump` は変数しか置かないので、早回しの組み立てが `STORE.appearance` を巻き戻しの時点の画面から書き進める（`shiori/act.lua:99-104`）。早回しの途中で外した部品は `before` から消えるが、その出力は捨てるので、画面には付いたまま残る。これに 0 が打たれない。
- 提案: `before` は `jump` の頭（早回しの前。遊ぶ人の画面のまま）で写し、`Replay` に持たせる。

### 大きい 2. 失敗の道の順番: 確かめる前に、控えを捨て、物語の続きを捨てている

- 区分: within-spec（ロードの道は `novel-save-slots` も）
- 根拠: `OnPlayRollback` は、`drop_after(id)` と `co_preempt` の付いたコルーチンを作った後で `jump` に入る。シーンが在るかは、その中で初めて確かめる（5.4・5.1）。8 章は「控えのシーンが無い … 状態は変えない」と書くが、実際は後ろの控えが消え、待っていた物語の続きも `preempt` で捨てられる（`init.lua:129-138`・`274-280`）。ロードも、`clear()` を `jump` より先に呼ぶ（6.4・10.3）。
- 提案: `find` の後、捨てる前に `SCENE.get(cp.pos.scene, cp.pos.local_scene)` を確かめる。無ければ、何も捨てずに失敗の表記を返す。ロードの `clear()` も、確かめた後に回す。

### 大きい 3. 字の無い、待つ 1 本に目印を付けない（R2）のは、骨子と食い違う。控えの数の数え方（R5）も brief と違う

- 区分: cross-spec（`novel-areka-contract`）
- 根拠: 骨子 2.5「演劇のどの 1 本にも、目印が付く」、4 章「演劇の行は全部に目印が付く」。brief は「字の無い、待たない 1 本には付けない」で、骨子 2.2 が目印を付けないのは「後ろにアクション行が無い残り（待たない 1 本）」だけである。R2 は「字が在るとき」に絞り、12 章 1 で別の読みを下書きにした。areka への頼みは「字の無い 1 本は、バックログに行を作らない」なので、目印を付けても困らない。R5 は「控えの数」で数えるが、brief は「数え方は目印の数」である（12 章 2）。
- 提案: 骨子のとおり、待つ 1 本にはどれも目印を付ける（areka は字の無い 1 本では行を作らないだけ）。そうすれば、R5 の数え方も brief と同じになる。

### 大きい 4. 早回しの種 `head` と、再生位置の `args` は、骨子の「控え」の形と、スロットの形を変える。13 章の「差し戻しは無い」は言い過ぎである

- 区分: model
- 根拠: 骨子 1 章・2.5 の控えは「再生位置・変数・アクター状態」で、再生位置は「シーンの名前と行の番号」である。設計は `head`（着いた時の変数）と `args` を控えに足し、スロットにも書く（4.2・10.3 の頼み 4）。13 章自身も「骨子の言葉を足す決定」と認めている。`args` に書けない値（表・関数）が入ると R14 で外れ、早回しが別の道を通る。
- 提案: 骨子に 2 つを決めてもらう。(1) 早回しをどの変数で始めるか（`head` を持つか、控えの変数で始めて分岐のずれを受け入れるか）。(2) 引数つきの最後の行の `＞` で着いたシーンの再生位置に、引数を入れるか。決まるまでは、`novel-save-slots` のスロットの形を固めない。

### 大きい 5. 早回しのずれは「同名シーンの乱数」だけではない。`＆順番` と並べ替えの位置は、戻るたびに進む

- 区分: model
- 根拠: 骨子 2.5 が受け入れたのは「行の数の違う同名シーンを引き直すと、着く行がずれる」だけである。早回しは途中の行の `＞` の候補選びをもう一度行い、Rust の側の並べ替えの位置（`crates/pasta_core/src/registry/scene_table.rs` の `cache`・`select_from_cache`）を進める。
  - `scene-pick-modes` の `＆順番`（`completed/scene-pick-modes/requirements.md` の Requirement 2）は乱数でなく、作者が決めた巡回である。戻るたびに 1 つ先の候補が選ばれ、早回しで着く行がずれるうえ、戻った後の巡回の位置も、早回しした回数だけ進む。
  - 分岐の条件（`＆＄＊x≧…`・`＞＄x`）にスロット変数でないグローバル変数を使うと、その変数は戻らない（骨子 2.5）ので、早回しが別の道を通りうる。
- 提案: 骨子に「早回しでも候補選びの位置は進む（戻さない）」と、その帰結を書いてもらう。そのうえで、`manual-novel-guide` への頼み（10.7）の (2) を、同名シーン・`＆順番`・スロットでないグローバル変数で決まる分岐、の 3 つに広げる。

### 大きい 6. `＞演劇再開` で待っている行のアクター状態を置き直す（R16）のは、「戻るのはロードとバックログだけ」に触れる

- 区分: model
- 根拠: 開発者の原則と骨子 2.5「状態が元へ戻るのは、バックログの行を選んだ時と、ロードした時だけ」、4 章 C「単に戻る … 何も戻さない」。R16 と `reapply_story_actor`（6.5）は、設定の場面で変わった並びと表情を、物語の物へ戻す。出し直しは areka が残る命令を全部既定へ戻すので、画面を全部書く要は在る。それでも、「何を書くか」（物語の画面か、設定の後の画面か）は骨子が決めていない。
- 提案: 骨子に決めてもらう。「出し直しは、待っている行の画面（アクター状態）を書く。STORE の記録もそれに揃える。変数と再生位置は戻さない」と書くか、設定の場面の中でアクター状態を変えないことを決まりにするか、である。どちらでも、`story` は `pending.actor` と同じ物なので、別に持たずに引ける（大きい 10）。

### 大きい 7. 「並び」を `STORE.actor_spots` で表すと、舞台に出ていないアクターも並びに入る

- 区分: cross-spec（`cue-command-runtime` の `cast_script`）
- 根拠: `STORE.actor_spots` は、読み込みの時に `pasta.toml` の `actor.spot` の値で埋まる（`pasta/store.lua:111-121`）。アクター指定行の在るシーンの頭で消されるまで残り、トークの場面をまたいでも残る（`sakura_builder.lua:594-601`）。骨子 1 章の並びは「誰が出ているか」で、areka の `\![play,cast,…]` に渡す物である。D7 の「同じ物を 2 か所で持たない」は、名前→スポット番号の表と、出ている人の表が同じ物であることを前提にしているが、その前提は今のコードで成り立たない。
- 提案: 並びを「今のシーン（または、着いた時）のアクター指定行の内容」から決めるか（柱と同じく、属性と階層から引く形に寄せる）、`cue-command-runtime` と「`actor_spots` のうち、アクター指定行が書いた物だけ」を並びとする取り決めを作る。

### 大きい 8. 再生位置のシーンを、読み込みの順で振られる登録名（`放課後_1`）で持つので、台本を直すとスロットが黙って別のシーンを指す

- 区分: within-spec（`novel-save-slots` と合わせる）
- 根拠: 登録名は、ベース名ごとの数え上げで作る（`pasta/scene.lua:160-170` の `create_scene`・`get_or_increment_counter`）。同名のシーンを足したり、ファイルの読み込みの順が変わったりすると、番号がずれる。`jump` は `SCENE.get(cp.pos.scene, …)`（`scene.lua:87-94`）で引くので、別のシーンが見つかってもエラーにならない。8 章の「シーンが無い」の道にも乗らない。`scene_written` は「手がかり」として書くだけで、照合に使っていない。
- 提案: ロードのときは、`scene_written`・`local_written` と、引いた関数の書いた名前が一致するかを確かめる（合わなければ「シーンが無い」と同じ扱い）。どちらを鍵にするかを `novel-save-slots` と決める。

### 大きい 9. ローカル変数の控えに、イベントから写した日時と Reference が入る。ロードの後に、古い日時が出る

- 区分: within-spec（決まっていない事として挙げる）
- 根拠: イベントの act は、`ｒ０`〜・`r0`〜・`req_id`・日時の変数（`時`・`季節`・`曜日` など）を `act.var` へ写す（`shiori/act.lua:164-249`、`init.lua:104-109`）。12 章 13 は「全部入れる」と下書きした。一週間後にロードすると、`＄季節`・`＄時` が、セーブした時の値で台詞に出る。骨子の「ローカル変数が戻る」の読みとしては一貫しているが、作者には直観的でない見込みがある。
- 提案: 要件定義の議題にする。案は (a) 今のとおり全部戻す（マニュアルに 1 行）、(b) ロードのときだけ、日時の変数を今の値で写し直す、の 2 つ。(b) は場合分けなので、骨子の原則に照らして決める。

### 大きい 10. 口と形が、作るのに足りない

- 区分: within-spec
- 根拠と提案:
  - `CHECKPOINT.finish_short(act)` は 5.1 の地の文・5.4・10.3 で使うが、5.1 の口の一覧に無い。中身（何を置き、何を返すか）を書く。
  - `land` は `tr.reuse_id` を書くが、`Track`（4.3）に欄が無い。
  - `arrive` は「足取りを作り直す」とあるが、早回しの間は `jump` が付けた `replay` を残さねばならない。`jump` 自身が引き起こす最初の着き方と、5.1 の「目当ての前に別のシーンに着いた」とを見分ける決まりが無い（`count == 0` かどうか、など）。擬似コードを足す。
  - `take(act, tr)` は、`tr.pos` の写しを控えに入れること（`seal` が `tr.pos.beat` を後から増やすので、同じ表を共有すると、どの控えの `beat` も動く）を明記する。
  - `tr.story` は、同じ `seal` の中で取る `pending.actor` と同じ物である。別に持たずに、`pending.actor` から引ける（開発者の原則「保存より導く」）。

### 大きい 11. テストが、壊れ方の芯を捕まえない

- 区分: within-spec
- 根拠: 9 章は、モックの `copy` を Lua の深い写しで代える。そのため、単体テストでは、R14 で外れるキーと「メモリの控えとスロットの控えは同じ」（4.2）のずれが見えない。e2e の項目に、次が無い。
  - 設定の場面（台詞を出す）を開いて `＞演劇再開` と `＞スロット読込` で戻る（重大 1）
  - `＊チェイントーク中断` の在るゴーストで、設定の選択肢からロードする（重大 2）
  - 早回しの途中で外した着せ替え部品が 0 で打たれる（大きい 1）
  - シーンが無いときに、控えも続きも変わらない（大きい 2）
  - 最後の行まで読み終えた後（4 章 A）の `position()`
  - ゴーストを読み直した後の ID の重なり（12 章 9）
- 提案: 上の 6 つを e2e に足す。Rust 側に「`copy` の結果を保存して読み直すと、同じ表になる」テストを 1 つ置き、モックの代わりの深い写しが、それと同じ物差しかを確かめる。プロジェクトの決まりに沿って、`copy` の整数のテストは x86・x64 で期待を分けて両方で走らせる。

## 小さい（minor）

1. **ID の頭**（4.4）: `os.time()` は秒の細かさなので、1 秒の内に読み直すと頭が重なる。`std_os` を外した設定では無い（`runtime_config.rs` の `std_os`）。`CLOCK.steady` か、読み込みの回数を混ぜる。（within-spec）
2. **`REG.OnPlayRollback` が作者のシーンを隠す**: REG の値は、シーンを探す既定より先に引かれる（`init.lua:316-320`）。作者が `＊OnPlayRollback` を書くと、走らない。R17 の「1 文字も変えない」に、厳密には触れる。名前を決めるとき（`novel-areka-contract`）に、予約の名前として書く。（cross-spec）
3. **表記の細部**: 7.2 の例の `\![bind,髪型,ポニー,1]` は、`APPEARANCE.restore` が実際に出す `\![bind-noevent,…]`（`appearance.lua:517`）と違う。5.2 の「`restore_surface` は必ず `\s[…]` を返す」は、覚えた表情も既定も無いときと、先頭に表情のタグがあるときは返さない（`appearance.lua:386-405`）。（within-spec）
4. **SSP での出し直し**: `＞演劇再開` で柱を全部書き直すと、SSP では曲が頭から鳴り直しうる（12 章 21。`cue-command-runtime` と `novel-areka-contract`）。（cross-spec）
