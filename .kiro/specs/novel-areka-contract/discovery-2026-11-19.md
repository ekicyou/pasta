## 開発者が形を出し、areka も異論なし（このメモで初めて書く。brief へは、下の「まだ案のもの」が決まったときに一緒に書く）

- **バックログに貯める・貯めないは、トグルで切り替える**: `\![play,backlog,1]`／`\![play,backlog,0]`（開発者の案。値は 1／0。ukadoc の `\![bind,…,数値]`・`\f[bold,1]` と同じ流儀で、`on`／`off` の形は ukadoc に見当たらない）。既定は 1。pasta は、返す台本の頭に毎回 1 か 0 を打つ（戻し忘れを防ぐ。areka の勧め）。areka は、起動・ゴーストの切り替え・SHIORI の読み直しで 1 に戻し、1／0 と true／false の 4 つを受ける。
- **出し直しの印は、その台本 1 本だけに効く**: `\![play,again]`。areka は、バックログに貯めず、字を一度に出し、単発の音と転換を飛ばす。トグルにしない。
- オートと高速再生の命令も、同じ形にそろえる（仮 `\![play,auto,1]`・`\![play,skip,1]`）。入切の状態をどちらが持つかは、まだ議論していない（areka の勧めは「状態は areka、切り替えの口は `play` の命令」）。

## まだ案のもの（開発者の返事待ち）

### 物語の途中でセーブ画面などを開いたときの扱い

困りごと: セーブ画面も pasta のシーンなので、物語の途中で開くと、今のチェイントークの決まり（台詞を出すシーンが割り込むと続きを捨てる）で物語の続きが捨てられる。セーブ画面に目印が付き、字がバックログに貯まる。

案の移り変わり（開発者の指摘で 2 回改めた）:

1. シーンに印 `＆システム画面` を付ける → 取り下げ（開発者「シーンはシーン。現在の枠組みで扱えないか。パーサーはいじりたくない」）。
2. 関数の対 `＞物語停止`・`＞物語再開` → 取り下げ（開発者「OnXXX で扱いを変えれば？」）。
3. 物語のイベントで走ったシーンだけを、物語として扱う → 改める（開発者「考え方が汎用的じゃない気がする。ループというかステートが複数ある。演劇状態のステート、演劇画面・タイトル・設定画面などのステート」）。
4. **今の案: 状態は 2 層ある。扱いは、イベントの名前でなく、前に出ている画面で決まる。**（下の「状態は 2 層」の節。ホワイトボードの下半分に図がある）

5. 開発者の原則（2026-11-19）: **「全ての画面はシーンであり、さくらスクリプトである。areka から見たら、イベント起動が付いたさくらスクリプトを延々と再生しているに過ぎない。シーンによって状態を管理する責務があるのは SHIORI 側」**。4 の案のうち、「pasta が状況から『別の画面が開いた』と判断する」「pasta が画面の名前を持つか」は、画面をシーンの外の物として扱っていたので改める。

#### 状態はシーンで決まる（開発者が承認。「その区切りにして良いが、本質的にはタイトル画面も『色んな分岐があるシーン』に過ぎない。最初のシーンということ」。brief へ書いた）

- 状態は「いまどのシーンに居るか」。画面という物を、pasta にも areka にも作らない。
- 読み（まだ確かめていない）: 開発者の「OnXXX で扱いを変えれば」は、イベントの名前でなく、**シーンの名前**のこと。グローバルシーンの名前が `On` で始まる（別名を畳んだ後）＝イベントの受け口＝システム側。それ以外のグローバルシーン＝演劇。ローカルシーンは親のグローバルシーンに従う。
- この読みで素直に書けるもの（どれも今の `＞` のジャンプ）:
  - システム側のシーンから演劇のシーンへジャンプ＝演劇をそこから始める（はじめから・ロード・当たり判定のクリックで進む物語）。「演劇を始める」口を別に作らない。
  - 演劇のシーンから `On` のシーンへジャンプ＝演劇を終える（タイトルへ戻る）。
  - 演劇が待っている間に、イベントで `On` のシーンが走る＝演劇は裏で止まる。そのシーンが終わると演劇へ戻る（最後の行を出し直す）。
- 前提: 今のゴースト（`＊OnTalk` から `＞雑談ネタ` へ飛ぶ形）の動きを変えないために、ゴーストごとの入切が要る（残りの議題 6）。
- 未決: システム側のシーンの行にも、既定の末尾（続きのイベントの起動）を付けるか。途中の行の `＞`（呼び出し）で境目をまたいだときの扱い。

#### 状態は 2 層（4 の案。上の読みで改める所がある）

- **演劇の状態**（1 つ・長生き）: 止まっている続き・最後に返した行・目印と控え・スロット変数。セーブ・ロード・巻き戻しの相手はこれだけ。画面が替わっても残る。
- **画面の状態**（いま前に出ている画面・1 つだけ）: 演劇画面・タイトル・セーブ画面・設定画面など。それぞれが「出す → 入力を待つ → 出す」のループを持つ。演劇の状態を進めるのは、演劇画面だけ。

| 前に出ている画面 | 演劇画面 | それ以外の画面 |
| ---------------- | -------- | -------------- |
| 行の区切り | アクション行 1 つ＝台本 1 本 | 今までどおり |
| 目印 | シーンの頭に作る | 作らない |
| バックログ | 貯める（`\![play,backlog,1]`） | 貯めない（`\![play,backlog,0]`） |
| 続きの置き場 | 演劇の状態（画面が替わっても残る） | その画面の間だけ（今のチェイントークと同じ決まり） |
| 続き・選択肢のイベント | 演劇が受ける | その画面が受ける |

画面の移り変わり:

| 移り変わり | きっかけ | 決める人 |
| ---------- | -------- | -------- |
| 演劇を始める | 作者が台本で指す（形は未定。選択肢の飛び先を `On` で始めると、ベースウェアがそのイベントを直接送る今の仕組みが使える） | 作者 |
| 別の画面が開く | 演劇が待っている間に、別のイベントのシーンが台本を返す | pasta |
| 演劇へ戻る | その画面のシーンが、待ちを残さずに終わる。pasta が、そのイベントの返事として最後の行を出し直す（`\![play,again]`） | pasta |
| ロード・巻き戻し | 演劇を、控えたシーンの頭から始め直す | pasta |

- pasta が持つのは「演劇が、無い／前に出ている／裏で止まっている」の 3 つだけ。タイトル・セーブ・設定の区別は、作者のシーンと変数に任せる（今の条件の属性 `＊OnMouseClick　＆＄＊画面＝「設定」` で、状態ごとに受け口を分けられる）。
- 前の案から消えるもの: 「出し直す」イベント（仮 `OnPlayResume`）・「選択肢のイベントは、出した側の扱いを引き継ぐ」決まり・物語に入るための raise の往復。
- 残りの議題 6 の「ノベルゲームモードの切り替え」は、この案では「演劇画面が前に出ている間」になる。
- 未決: 「演劇を始める」の書き方。当たり判定のクリックで物語を進める形（`shell-element-click`）は、同じ口（演劇を、このシーンから続ける）で受ける見込み。

areka の見立て（2026-11-19・読むだけ・実機は未確認）:

- 困る点は無い。areka は、台本がどのイベントへの返事かで出し直しの扱いを変えない。areka に頼む物は前と同じで、軽くも重くもならない。
- 置き換えられたトークの残りは配られない（コードで確かめた事実）。だから、割り込まれた行の末尾の `\![raise,OnPlayNext]` は出ない。
- 再生中に届いた GET の返事の台本は、`OnSecondChange` と倍率（`OnShellScaling`・`OnBalloonScaling`）を除いて、全部が今のトークを置き換える。待っている間の `OnSecondChange` は NOTIFY で、pasta の自発のトークは割り込まない（`\x` の待ちが「再生中」の扱いになることは見立て）。
- 画面のシーンが台本を返して終わると、次に届くのは `OnSecondChange`（話していないときは GET）で、そこで出し直すと最大 1 秒の空きができる。空きを作らないには、閉じるボタンの返事でそのまま出し直しを返す。
- 落とし穴: バルーンの左ダブルクリックは台本を止めてバルーンを消す（中断）。末尾の `\![raise,OnPlayNext]` が出ず、物語が止まる。避け方は、演劇の台本の頭で正典の中断の抑止を打つか、pasta が `OnBalloonBreak` の返事で出し直すか（未決）。

前の案（3）の表（参考）:

| 届いたイベント | 走るもの | 扱い |
| -------------- | -------- | ---- |
| `OnBoot`・`OnMouseClick` など | 今までどおりのシーン | 今のゴーストと同じ。台本の頭に `\![play,backlog,0]` |
| 物語を始める（仮 `OnPlayStart`） | 名前で指したシーン | 物語 |
| 続きを求める（仮 `OnPlayNext`） | 止まっている続き | 物語 |
| 出し直す（仮 `OnPlayResume`） | 最後に返した行（`\![play,again]` 付き） | 物語 |
| 巻き戻す（仮 `OnRollback`） | 控えたシーンの頭 | 物語 |

- 物語として扱うとは、行ごとに区切り、シーンの頭に目印を作り、台本の頭に `\![play,backlog,1]` を打つこと。
- 物語に入る・戻るのは、正典の `\![raise,…]`。ト書きの行で書ける（`！raise（OnPlayStart、第一章）`・`！raise（OnPlayResume）`）。新しい文法も関数も作らない。ト書きを台本へ流す仕組みは `cue-command-runtime` の仕事で、まだ無い。
- 選択肢のイベントは、選択肢を出した側の扱いを引き継ぐ。
- 物語の続きは、チェイントークの続きとは別の置き場に持つ（チェイントークの今の決まりを変えない）。捨てるのは、巻き戻し・ロード・`スロット消去` だけ。

### ゴーストごとの入切（推奨を出した。開発者の返事待ち）

- 推奨: `pasta.toml` に `[play]` の表が在るゴーストだけ、「`On` 以外のシーンは演劇」の区切りが効く。行の末尾の既定のスクリプトの置き場所が入切を兼ねる（キーの名前は仮 `line_tail`）。表が無いゴーストは今までどおり。
- 気になる所: つつき・撫でのショートカット（`＊つっつき反応女の子Head` のように `On` で始まらない名前でイベントを受けるシーン）が、演劇に数えられてしまう。設計で扱いを決める。

### 設定画面への入口（開発者の問い・2026-11-19。areka へ見立てを聞いている）

- 開発者の言葉: 「本質的に特殊な扱いが必要なシーンは『設定画面』と、そこから呼ばれるセーブロードくらい。設定画面はどのシーンからでも呼び出される可能性がある。設定画面へのショートカットはどうするか。画面に常に表示されるボタンとか、キーボード・コントローラーショートカット？」
- pasta の側の見立て: どの入口でも「イベントが届いて、`On` のシーンが走る」だけで、新しい仕組みは要らない。受け口は今の条件の属性で分けられる（`＊OnMouseClick　＆＄ｒ４＝「設定」`・`＊OnKeyPress　＆＄ｒ０＝「F1」`）。入口が複数でも、同じ設定のシーンへ飛ばせば済む。
- 入口ごとの今の事実:
  - 常に出ているボタン: areka に、名前つきの当たり判定のクリック（`OnMouseClick` の Reference4）が在る。SSP でも同じ。
  - キーボード: 正典に `OnKeyPress` が在るが、今の areka には無い。
  - コントローラー: 正典に当たるイベントを知らない。areka の予定を聞いている。
- areka の答え（2026-11-19・読むだけ・実機は未確認）:
  - **右クリックは、今もう SHIORI へ回せる**（areka の追加は 0）。areka は右ボタンを離すたびに、正典のリソース `sakura.popupmenu.visible`（スコープ 0）・`kero.popupmenu.visible`（スコープ 1）を SHIORI へ照会し、返事でメニューを出すかを決める。pasta が演劇の間だけ「出さない」と答えれば、右クリックは `OnMouseClick`（Reference5＝1）で届く。止めている間は areka のメニュー（終了・ゴーストの切り替え）へ行けないので、pasta の設定のシーンに終了の道（`\-`）が要る。3 つ目からのスコープと席の窓では、照会する名前がまだ決まっていない。
  - **ボタン**: ボタン用の席を 1 つ持ち、そこにボタンのシェルと名前つきの当たり判定を置く形でよい（席の仕掛けは brief `shell-multi-compose`）。今の areka が窓を出すスコープは 0 と 1 だけ。席の前に試すなら、キャラクターが 1 人のときにスコープ 1 をボタン用に使うか、着せ替え（`\![bind]`）でボタンの絵を重ねて全部のサーフェスに同じ名前の当たり判定を書く。待っている間の当たり判定の上のクリックは `OnMouseClick` で届き、待ちを解かない（`talk-fast-forward` の要件に書く決まりで、今のコードの事実ではない）。
  - **キーボード**: `OnKeyPress` は無く、持ち主の brief も無い。下の層（wintf のキーの受け口）は在るので、足すのは軽い〜中。分け方の勧めは、送りのキー（Enter・Space など少数）は areka が使って待ちを解き、ほかのキーは `OnKeyPress` で送る。マウスの決まりと同じ形。areka の窓が手前のときだけキーが届く（推測）。
  - **コントローラー**: 予定なし。足すなら、別のイベントを作らず、キーと同じ 2 つの道へ寄せる。0.7.0 の取り決めには入れない勧め。
- **決定（開発者「キーも必須にする」）**: 0.7.0 の入口は、右クリック・常に出ているボタン・キーボードの 3 つ。コントローラーは入れない。`novel-areka-contract` の「設定のシーンへの入口」に書いた。areka のセッションへは、この決定をまだ知らせていない（次に相談するときに一緒に伝える）。
- 待っている間の入力の切り分け（案。areka へ見立てを聞いている。決定の同期も一緒に送った）:
  - areka の勧めは「物語を進める入力は areka が使って、pasta に届かない。それ以外はイベントで届く」だった。
  - 開発者の言葉: **「OnKeyPress はどんな状態でも拾って、無視すればいいだけ」**。
  - 開発者の指摘: 「マウスイベントはもともといつも送ってない？ イベントって絞り込んでましたっけ」。**ukadoc で確かめた（2026-11-19）: 絞り込んでいない。**
    - `OnMouseDown`・`OnMouseUp` は「ボタンが押された・放された際に発生」。`OnMouseClick` は「`OnMouseUp` に反応しない場合に発生」。話している最中かどうかの条件は書かれていない。Reference3 がキャラクター、Reference4 が当たり判定の識別子、Reference5 がボタン（左 0・右 1）。
    - `OnKeyPress` は「本体がアクティブな状態でキーが入力された際に発生」。条件はアクティブだけ。Reference0 がキートップの文字、Reference1 が Win32 の仮想キーコード。
    - `\x` は「**バルーン**をクリック待ちにする」。正典では、待ちを解くのはバルーンのクリックで、キャラクターの窓のクリックはマウスのイベントになる。2 つはもともと別の物である。
    - 中断（バルーンのダブルクリック）を止める正典のタグは `\![enter,nouserbreakmode]`／`\![leave,nouserbreakmode]`（SSP）。
  - だから、「イベントを送る・送らない」を取り決めに書く必要は無い（正典のまま）。前の案の「マウスもそろえるか」という問いは要らなかった。残るのは areka の再生の側の話だけ: 絵の上（バルーンの外）の左クリックと、送りのキーでも待ちを解くか。
  - areka の答え（2026-11-19・読むだけ・areka も SSP も実機は未確認）:
    - 「いつも送る」でよい。マウスは今のコードがもうそうである。キーで「送らない」を勧めた理由は、マウスの勧めと形をそろえることだけだった。
    - pasta がイベントの側に 204 を返すなら、待ちが解けるのとイベントが届くのが重なっても、届く順がどちらでも結果は同じ。areka の側は、`\![raise]` を作る spec で重なりの確かめを 1 つ持つ（クリックの 2 段の列が、返事を出どころで見分けていないように読める）。
    - **残る食い違いは 1 つ**: areka の brief `talk-fast-forward` に、開発者が確定した行「シェル内バルーンの箱のクリックは、話している最中なら早送りだけを行い、シェルのクリックのイベントは送らない」が在る。状態で送る・送らないを分ける決まりなので、今回の原則とぶつかる。決め方は 2 つ（開発者の決め）: 箱の上は場所の決まりにする（箱が出ている間、箱の上のクリックは箱の物で、シェルのイベントは送らない）か、箱の上もいつも送る（ふつうのゴーストでは、早送りのクリックでつつきの反応が出る）か。discovery の見立て: 前者は正典（バルーンのクリックはキャラクターの窓のイベントにならない）と同じ形である。
    - 取り決めに足してほしいこと: 待ちを解く入力のイベントには、SHIORI は 204 を返す（台本を返すと待っているトークを置き換え、末尾の `\![raise,…]` が出ない）。送りのキーの押しっぱなしでは待ちを解かない（最初の 1 回だけ。イベントは繰り返しのぶんも送る）。
  - 改めた案（参考）: areka は、入力のイベント（`OnKeyPress`・マウスのイベント）を、状態で分けずにいつも送る。「送らない」という決まりを作らない。分けるのは「待ちを解くかどうか」だけ。左クリック（名前つきの当たり判定の外）と送りのキー（Enter・Space など）は、イベントを送るのに加えて待ちを解く。名前つきの当たり判定の上のクリック・右クリック・ほかのキーは、待ちを解かない。pasta は、要らないイベントに 204 を返して無視する。
- 確かめていないこと: pasta がリソースの照会（`sakura.popupmenu.visible`）に答える口の書き方。メニューを止めたときに右クリックのイベントが届く順と回数。

### 画面の作り方（開発者の問い・2026-11-19。案。areka へ事実を聞いている）

開発者の言葉:

- 「本質的には、head とか、マウス反応すべきところだけ拾ってる感じ。その考え方の拡張で行けない？ ただ、さくらスクリプトで指定できる任意の場所で待機を作らないといけないかもだけど」
- 「play 中は現在のボーダーレスモードとは別に、一般的ウィンドウの中で描画するモードも実現したい」
- 「アクターに、紙芝居の背景の役割も持たせたい。『教室』アクターで、窓の外が雨、たまに雷が鳴るなどの『表情』があるかんじ」

確かめた事実（ukadoc・pasta）:

- 当たり判定は、surfaces.txt のサーフェスごとの定義（`collision*`・`collisionex*`。長方形・楕円・円・多角形・画像の色の領域）。アニメーションの間だけの当たり判定（`animation*.collision*`）も在る。さくらスクリプトで当たり判定を作るタグは、正典に無い（在るのは表示の `\![enter,collisionmode]` だけ）。
- SHIORI のリクエストに `Status` ヘッダが在る（`talking`＝スクリプトを実行中・`choosing`＝選択肢の表示中 など）。pasta はもう `req.status` を読んでいて、自発のトークと撫でを止めるのに使っている（`virtual_dispatcher.lua` の `is_blocked`）。
- pasta には、アクターと部位の名前でシーンを選ぶ口が在る（つつき `＊つっつき反応<アクター名><部位>`・撫で `＊さわり反応…`）。ただし `OnMouseDoubleClick` と `OnMouseMove` の物で、1 回のクリック（`OnMouseClick`）には無い。

案（discovery。まだ決定ではない）:

1. **画面はアクターの重なり**。背景（教室）も、登場人物も、ボタンの置き場も、アクター（スコープ＋サーフェス）。表情＝サーフェス。「たまに雷」は surfaces.txt のアニメーション。背景という物を pasta に作らない（残りの議題 5 の「背景の書き方」は、アクターの表情で書く）。
2. **押せる所は、アクターの表情ごとの当たり判定**。場面ごとに押せる所が変わるのは、表情が替わるから。さくらスクリプトで任意の場所に待ちを作るタグは、足さない見込み。
3. **入力は全部イベントで届き、pasta は拾う所だけ拾う**。`OnMouseClick`（Reference3＝どのアクター・Reference4＝当たり判定の名前・Reference5＝ボタン）と `OnKeyPress`。
4. **物語を進めるのも、pasta の側でやる**（前の決定「areka の側はクリック待ちトーク・待ちの解き方 3 通り」「行の末尾に `\x\![raise,OnPlayNext]`」を改める案。開発者の承認が要る）。
   - 台本の末尾に `\x` を置かない。台本は 1 行ぶんで終わり、演劇は pasta の中で次の入力を待つ。
   - 演劇が待っている間に届いた「どのシーンも拾わなかった左クリック」と「送りのキー」で、pasta が次の行を返す。
   - 字が出ている途中（`Status` が `talking`）と選択肢の表示中（`choosing`）の入力は、pasta が無視する。字の早送りは areka の仕事のまま。
   - オートと高速再生の状態は pasta が持つ。オートは末尾に `\_w[時間]\![raise,続きのイベント]` を付け、高速再生は字を一度に出して `\![raise,…]` を付ける。areka は、待ちを解く決まり（どこのクリック・どのキー）を持たなくて済む。
   - SSP でも、キャラクターの窓のクリックと `OnKeyPress` で同じ台本が進む見込み。バルーンのクリックでは進まない。
5. **窓のモード**: ボーダーレス（今）と、ふつうのウィンドウの中に舞台を描くモード。台本と pasta は、どちらのモードでも同じ。ウィンドウのモードでは窓の中の全部にクリックが届くので、「どこを押しても進む」は 4 の決まりでそのまま成り立つ。切り替えの持ち主は areka に聞いている。
