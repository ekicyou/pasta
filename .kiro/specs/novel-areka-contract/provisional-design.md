# 暫定設計: novel-areka-contract（2026-11-19）

この文書は、Phase 13 の 8 本の spec を設計まで通して、設計の食い違いを先に洗い出すための**暫定の設計**である。`requirements.md` と `spec.json` はまだ無い。正は `final-model-2026-11-19.md`（以下「骨子」）と、この spec の `brief.md` の「決定（2026-11-19。最終形）」の節（以下「brief の決定」）である。命令の名前は、この文書でも仮である（確定は、この spec の要件定義）。

この spec の成果物は**文書**である（コードを書かない）。だから「設計」は、取り決めの文書・areka への依頼書・対応表の、構成と中身の計画と、その確かめ方である。

## 1. 暫定の要件

EARS に寄せた短い形で書く。番号は、後の節から引く。

### R1. 置き場所と版

- R1.1 取り決めの文書は、マニュアルの内部設計の部に 1 章として置く（骨子 2.8）。フェーズ 1〜3 を 1 本で持つ。
- R1.2 文書は版の番号を持つ。互換の無い変更（名前・引数の並び・意味の変更）のとき、版の頭の数を上げる。
- R1.3 文書は、命令ごとに「どのフェーズで要るか」と「areka のどの版から使えるか」を持つ。後者は、areka の返事を受けて埋める。

### R2. 言葉と名前

- R2.1 取り決めは、ベースウェアの言葉（シェル・サーフェス・スコープ・バルーン・当たり判定・さくらスクリプト）で書く。「画面」「システム画面」「演劇」「シーン」「台本」という言葉を、取り決めの決まりに入れない（brief の決定「原則」）。
- R2.2 命令の名前の頭は `play` とする（並走の `\![parallel,…]` を除く。§10 の 3）。命令とイベントの名前に `pasta` を入れない。
- R2.3 正典（ukadoc）に在る物は、正典のタグで出す。`play` の命令は、正典に無い物だけにする（骨子 2.8）。
- R2.4 値のフラグは 1／0 にする。時間はミリ秒の整数にする。
- R2.5 取り決めは、ベースウェアに固定のイベント名を作らない。続きのイベントと目印のイベントの名前は、SHIORI がタグの引数で渡す。

### R3. さくらスクリプト 1 本の形

- R3.1 SHIORI が 1 行ずつ渡すとき、1 本の末尾は、正典の `\x` と `\![raise,イベント名,ID]` である。
- R3.2 選ばれるのを待つ 1 本（選択肢の在る 1 本）は、`\x` を持たない。
- R3.3 ベースウェアは、`\x` で待つ間と、`\![raise]` を打ったさくらスクリプトが終わってから SHIORI の返事が届くまで、Status に `talking` を立てたままにする。`\x` で待つ間、台詞の箱を閉じない。
- R3.4 待ちを挟まずに続けて書いた命令は、同じフレームで見える。ベースウェアは、同じ時刻の命令を全部当ててから、最初の絵を出す。

### R4. 目印とバックログ

- R4.1 ベースウェアは、`\![play,mark,イベント名,ID]` を含む 1 本が作るバックログの行に、目印を付ける。
- R4.2 遊ぶ人が目印の付いた行を選んだとき、ベースウェアは、その行を含めて後ろの行を捨て、そのイベントを GET で送り、Reference0 に ID を載せる。
- R4.3 目印の無い行は、選んでも何も起きない。字の無い 1 本は、行を作らない。
- R4.4 ID は英数字だけとする。中身は SHIORI だけが読む。
- R4.5 `\__v[disable]` の区間は、バックログに貯めない（正典）。

### R5. 出し直し

- R5.1 `\![play,again]` を頭に持つ 1 本を受けたとき、ベースウェアは、鳴っている途中の単発の音と声を止め、並走を全部止め、残る命令の値を全部既定へ戻してから、続く命令を当てる。
- R5.2 SHIORI は、出し直しの 1 本で、残る命令の値を、いつも全部書く。

### R6. 待ちの解き方と時間

- R6.1 正典の `\x` は、台詞の箱のクリックで解ける。待っている間の、絵の上のクリックは、`OnMouseClick` で SHIORI へ届き、返したさくらスクリプトは、待っている 1 本を置き換える（残っていた `\![raise]` は実行されない）。
- R6.2 `\![play,xtimeout,ミリ秒]` を含む 1 本の `\x` は、`\x` に着いてからその時間で解ける。0・負・読めない値は「解かない」。時間で解けたときも、続きの `\![raise]` へ進む。
- R6.3 オート・高速再生の入切と時間は、SHIORI が覚える。ベースウェアは状態を持たない。

### R7. イベント

- R7.1 取り決めのイベントは、すべて GET で送る（NOTIFY には SHIORI がさくらスクリプトを返せない）。SHIORI は 5 秒以内に返す。
- R7.2 ベースウェアは、`\![raise]` と目印の引数で渡された名前のイベントを、許可の一覧に依らずに送る。
- R7.3 ベースウェアは、`OnMouseClick`（Reference3＝スコープ・Reference4＝当たり判定の名前・Reference5＝ボタン）・`OnKeyPress`（Reference0＝キー・Reference1＝仮想キーコード・Reference4＝修飾キー）・`OnSecondChange`（Reference3＝トークを再生できるか）・`OnChoiceSelectEx`・`OnChoiceTimeout`・`OnClose` を、正典の Reference の並びで送る。
- R7.4 ベースウェアは、要求の `Sender` に自分の名前を載せ、版をセマンティックバージョンで知らせる（正典の `basewareversion`）。

### R8. 入力と設定の画面への入口

- R8.1 ベースウェアは、キーの入力を `OnKeyPress` で送る。Alt+Enter も自分で処理せず、`OnKeyPress` で送る。
- R8.2 SHIORI が正典のリソース `sakura.popupmenu.visible`（`kero`・`char*` も）に 0 と答えたとき、ベースウェアは右クリックのメニューを出さず、右クリックを `OnMouseClick`（Reference5＝1）で送る。
- R8.3 ベースウェアは、止まった舞台から遊ぶ人が必ず出られる道を持つ。

### R9. 舞台・並び・箱（フェーズ 3 の前半）

- R9.1 `\![play,stage,形]` で舞台の窓を開き、`\![play,stage]`（引数なし）で閉じる。形は `window`・`fullscreen`・`borderless`。
- R9.2 舞台が開いている間、デスクトップの窓とバルーンを隠す。閉じると、隠す前の位置と絵で戻す。閉じるとき、残る命令を全部「無い」に戻し、バックログの目印を全部外す。窓の × と Alt+F4 は `OnClose` へ流す。
- R9.3 基準の大きさは 1920×1080（96DPI の論理の大きさ）。比を保って拡大縮小し、余りは黒。マウスの座標は基準の大きさの値で送る。黒い余白のクリックは送らない。窓の大きさは覚えない。最大化のボタンは押せなくする。
- R9.4 `\![play,cast,名前,…]` が並び（今の舞台の全部）である。並びに無いアクターは消える。スコープの番号は並びの順。
- R9.5 位置・重ね順・大きさ・透明度の命令を持つ。位置を明示しないアクターは、並びと役から自動で置く。役と席の名前は、シェルの定義（`descript.txt` の areka の独自キー）に書く。
- R9.6 台詞の字は、話者のスコープに打たれ、「トークの場所」の役のアクターの箱へ出る。箱のアクター自身のスコープの字は、その箱に出る。トークの場所が並びに居なければ、話者自身のシェルの箱へ出る。舞台の中にふつうのバルーンは出さない。
- R9.7 `\![play,speaker,名前]` で、その 1 本の話者の名前を替える。既定は並びの名前。名前は、台詞の箱のシェルの中の決まった名前の小さい箱に出る。

### R10. 並走と転換（フェーズ 3 の前半）

- R10.1 `\![parallel,1]`〜`\![parallel,0]` の区間を、別の流れとして始める。主の流れは区間の時刻を進めない。区間に書ける物は見た目・音・待ち。
- R10.2 `\![play,trans,ミリ秒]` の後の変更を、直前の絵から新しい絵へ、その時間で替える。まとめの終わりは「次の字・次の待ち・次の転換・1 本の終わり」。0 は前の転換の組を終わらせる。
- R10.3 揺れ（`shake`）・フラッシュ（`flash`）を持つ。

### R11. フェーズと線引き

- R11.1 文書は、命令ごとに、フェーズ 1（今の SSP）・2（SSP が対応すれば）・3 の前半（areka 最低限）・3 の後半（areka 重い）を書く（骨子 2.9）。
- R11.2 合格の測り方: 正典だけで動く層は SSP の実機で、`play` の命令の層は areka の実機で測る。

### R12. 依頼と対応表

- R12.1 文書から、areka への依頼書を、areka の決まり（1 spec は 20 タスクまで・まとめて量産しない）に合う束に分けて起こす。束ごとに、フェーズの線を書く。
- R12.2 この spec の最後のタスクで、依頼書を areka のセッションへ渡す。pasta のセッションから areka のリポジトリを書き換えない。
- R12.3 areka の側でどの brief になったかの対応表を、pasta の側に残す。
- R12.4 後続の spec が依頼を足す・変える手順（文書を直す → 版を上げる → areka のセッションへ知らせる → 対応表を直す）を、文書に書く。
- R12.5 依頼に、areka の `doc/PASTA_PROFILE.md` §5 の作例の訂正（手書きの `\w[500]` を `\_w[500]` に）を添える。

### R13. 作らないもの

- R13.1 キーを押している間だけの早送り・絵のアニメーションに合わせて音を鳴らす口・押したときの絵・コントローラー・ベースウェアの側のセーブの控え・取り決めの「バックログを開く」以外の操作（brief の決定「作らないもの」）。

## 2. 概要

- **目的**: pasta（と、ほかの SHIORI）がさくらスクリプトに載せる物と、ベースウェアがそれをどう受け取るかを、1 か所の文書にする。後続の 7 本は、命令・イベント・引数の名前を、この文書から引く。areka は、この文書から起こした依頼書で、自分の brief を作る。
- **読み手**: pasta のコントリビュータ（後続の spec の実装者）と、areka のセッション。ベースウェアの作者（SSP を含む）にも読める形にする。
- **変える物**: マニュアルに章が 1 つ増える。内部設計の部の検査の数が 1 つずつ増える。ソース（Rust・Lua・文法）は触らない。

### 目標

- 命令の表・残る命令の表・イベントの表・1 本の形が、名前と引数の並びまで決まっている（R2〜R10）。
- 依頼書が束に分かれ、areka のセッションへ渡り、対応表が在る（R12）。

### 目標でない物

- pasta の側の作り（タグへ直す表・早回し・控え。後続の spec）。
- areka の側の作り方。
- 文法の変更。

## 6. データモデル（取り決めの中身）

### 6.1 命令の表（仮の名前）

「区分」は 残る（窓に残る値）／瞬間／1 本（その 1 本だけに効く）。「SSP」は、SSP で何に直すか（直すのは `cue-command-runtime`）。

| 用途 | 形 | 区分 | 既定（「無い」） | フェーズ | SSP |

### 6.2 残る命令の決まり

- 残る命令は、窓に値を残す。同じ値をもう一度受けたら何もしない（曲を鳴らし直さない・背景を替え直さない）。
- 「無い」の打ち方は、引数なし（サーフェスは `\s[-1]`）。
- 曲と環境の音（`\![sound,loop,…]`）は正典の音で、この表に入れない。出し直しの頭でも止めない（止めるのは単発の音と声だけ）。同じ曲を打たないのと、止めるときに名前を付けるのは、SHIORI の仕事である（§14 の 6）。
- 舞台を閉じたとき、ベースウェアは、この表の値を全部既定へ戻す。

### 6.5 誰が何を持つか

| 物 | SHIORI | ベースウェア |
| -- | ------ | ------------ |
| 再生位置・控え・セーブデータ・既読 | 持つ | 持たない |
| オート・高速再生の入切と時間・窓の形の設定 | 持つ（`stage` と `xtimeout` で毎回伝える） | 持たない |
| 残る命令の今の値 | 覚える（同じ値を打たない・出し直しで全部書く） | 窓に持つ（同じ値は何もしない） |
| バックログの一覧と目印 | 目印を埋めるだけ | 持つ |

## 7. 流れ（文書の「処理とデータの流れ」に載せる）

イベント名は、例として pasta の仮の名前を使う。

- **F1 1 行ずつ進む**: 1 本（`…\x\![raise,OnPlayNext,12]`）→ 遊ぶ人が箱を押す → ベースウェアが `\x` を解く → GET `OnPlayNext`（R0＝12）→ SHIORI が次の 1 本を返す。待ちの間も talking。
- **F2 待ちの間のクリック**: 1 本が待っている → 絵の上のクリック → GET `OnMouseClick` → SHIORI の返した 1 本が待っている 1 本を置き換える（元の `\![raise]` は実行されない。SSP 2.9.34 で確かめた: `research-ssp-capabilities.md` の D 節 5）。
- **F3 時間で次へ**: areka は `\![play,xtimeout,3000]…\x\![raise,…]`。SSP は `\![timerraise,3000,1,OnPlayNext,12]\x\![timerraise,0,1,OnPlayNext]\![raise,OnPlayNext,12]`（先にクリックすればタイマーが消える。D 節 6）。
- **F4 バックログの行を選ぶ**: 行（目印 `OnPlayRollback,12`）を選ぶ → ベースウェアがその行から後ろを捨てる → GET `OnPlayRollback`（R0＝12）→ SHIORI が 1 本目（出し直し・画面の状態だけ・字も `\x` も無く `\![raise]` で終わる）を返す → GET `OnPlayNext` → 2 本目（同じ目印 12 で、ふつうに再生）→ 行が貯め直る。
- **F5 単に戻る（`＞演劇再開`）・外から消された行の出し直し**: SHIORI が出し直しの 1 本（画面の状態全部＋字＋`\x`＋`\![raise]`）を返す。目印は付けない（貯めないため）。
- **F6 外から消されたとき**: 待っている 1 本が別のさくらスクリプトで置き換わる → 次の `OnSecondChange` で、Status に `talking` も `choosing` も無い → SHIORI が F5 の 1 本を返す。
- **F7 舞台**: `\![play,stage,window]` → デスクトップの窓とバルーンを隠す → … → `\![play,stage]` → 残る命令を全部既定へ・目印を全部外す・隠す前の位置と絵へ戻す。

## 8. エラーの扱い（文書の「不変条件と制約」に載せる）

| 場合 | ベースウェアの動き |

## 10. 設計の判断（この spec の中で決めること）

1. **章の名前**: `book/src/internals/baseware-contract.md`、題「ベースウェアとの取り決め」（R2.1 で「演劇」を題に入れない）。
2. **版の番号**: 完了時に 1.0.0。足すだけは真ん中、互換が無いのは頭（R1.2）。
3. **並走だけ `play` の頭を付けない**: 骨子 2.8 が `\![parallel,1]`・`\![parallel,0]` と書き、areka の brief `parallel-visual-script` と名前をそろえる決定が在るため。R2.2 の例外として章に書く。作者が単語に書く印（仮 `\![parallel]`、引数なし）は pasta が読む疑似の印で、ベースウェアへは出ない（`novel-talk-flow`）。同じ名前を引数の数で分けることになる（§14 の 3）。
4. **出し直しの中身を正典へ寄せる**: brief の決定は、`again` に「貯めない・字を一度に出す・`\w`・`\_w` を飛ばす」を持たせている。これらは正典の `\__v[disable]` と `\_q` で言える（R2.3「正典に在る物は正典で」）。案: `again` は「止める・既定へ戻す」だけにし、SHIORI は `again` の後に `\__v[disable]` と `\_q` を出し、`\_w` を出さない。SSP でも同じ形が効く（SSP は `again` を読み飛ばすが、貯めないと一度に出すは効く）（§14 の 4）。
5. **舞台の閉じ方は引数なし**: 「無い」は引数なしの決まり（brief の決定）に合わせ、`\![play,stage]` で閉じる。開くときは、SHIORI が遊ぶ人の設定の形を必ず書く（ベースウェアは形を保存しない）。
6. **古い目印の扱いは「外す」**: ロードの後、ベースウェアのバックログに古い ID の行が残る件（骨子 6 章）。areka の勧めは「バックログを空にする」合図だが、バックログはベースウェアの物で、読むのは遊ぶ人である。案: `\![play,unmark]`（目印を全部外す。行は読めるまま残る）を足し、SHIORI は控えを全部捨てた時（ロード・はじめから）の 1 本目に打つ。舞台を閉じたときの「目印を外す」と同じ動きなので、ベースウェアの仕組みは 1 つで済む（§14 の 17）。
7. **並びの空いた欄**: アクター指定行は番号を明示できる（`crates/pasta_dsl/src/parser/grammar.pest:164` の `actors_item = { id ~ ( s ~ set_marker ~ s ~ digit_id )? }`。生成は `crates/pasta_lua/src/code_gen/scope_gen.rs:286` の `act:set_spot("名前", 番号)`）。「スコープの番号は並びの順」を保つため、`cast` は番号の位置に名前を置き、空いた番号は空の欄にする（`\![play,cast,教室,,さくら]`）（§14 の 5）。
8. **字の無い 1 本の目印**: 骨子 2.5 は「演劇のどの 1 本にも目印が付く」、brief の決定の命令の表は「字の無い 1 本には付けない」。取り決めの側は「字の無い 1 本は行を作らないので、目印は使われない」と書き、付けても付けなくても壊れない形にする（§14 の 1）。
9. **依頼書の置き場所**: `.kiro/specs/novel-areka-contract/areka-requests/`。spec と一緒に `completed/` へ移る。後続の追いの依頼は、その spec のフォルダに置く（D4）。

## 15. 上位の決定へ差し戻しが要りそうな所

- **E1. 右クリックのメニューを止める口に、持ち主と書き方が無い**: 骨子 2.6 と brief の決定は、「pasta が、正典のリソース `sakura.popupmenu.visible` に『出さない』と答えると、右クリックが `OnMouseClick` で届く」とする。ところが、今の pasta にリソースへ答える口は無い（§13）。知らない要求の ID はシーンを探すので、作者が `＊sakura.popupmenu.visible` を書くことはできるが、シーンの出力は必ず `\p[N]` で始まり `\e` で終わる（`sakura_builder.lua:45`・`:686`）ので、`0` という値を返せない。DSL で書けないので、Lua で `REG` に書くのは「DSL の穴を Lua で埋める」に当たる。骨子 5 章の持ち分の表にも、この口の持ち主が無い。決めることは 2 つ: (a) 持ち主の spec（`novel-talk-flow` が候補）。(b) 作者の書き方。柱から導く形（例: 再生モードが演劇か設定のシーンが今のシーンなら、pasta が 0 と答える）は原則（柱から導く）に合うが、「自動の動きを足さない」と、デスクトップで演劇を遊ぶときに右クリックのメニューを残したい場合との兼ね合いがある。別の柱（仮 `＆右クリック：シーン`）にする形もある。
- **E2. 取り決めの章を内部設計の部に置くことが、その部の決まりと 3 か所でぶつかる**: 骨子 2.8 は「マニュアルの内部設計の部に 1 章として置く」と決めた。今の決まりは、(i) 内部設計の部の権威は現行実装で、未実装の構想を書かない（`book/src/internals/index.md:17`、`book/AUTHORING.md:237`・`:302`）。取り決めの大半は未実装で、フェーズ 3 の命令は何年も先まで実装されない。(ii) 利用者向けの章から内部設計の章へ逆リンクを張らない（`index.md:70`、`AUTHORING.md:239`）。`manual-novel-guide` の brief は「areka との取り決め（語彙の一覧）へ、リンクで送り出す」とし、シェルを作る人（利用者）は役と席のキーを知る必要がある。(iii) 内部設計の部の読み手はコントリビュータで、ベースウェアの作者は想定に無い。決め方の候補: (a) 内部設計の部に置き、`AUTHORING.md` §6 に「取り決めの章は、ベースウェアに頼む形を書く。権威は取り決めの版」の例外を足す（`index.md` の 17 行も）。逆リンクの禁止は、取り決めの章だけ外す。(b) リファレンスの部（`book/src/reference/`）に置く（利用者が読め、逆リンクの問題が無い。未実装の扱いは同じく例外が要る）。この設計は (a) を仮定して書いた。
