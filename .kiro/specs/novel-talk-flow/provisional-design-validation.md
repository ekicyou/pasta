## 判定

**GO_WITH_CONDITIONS（条件つきで進めてよい）**

止まり方をチェイントークに載せる骨組み（`STORE.co_scene`・`EVENT.drive`・`coroutine.yield`）は、今のコードの上で成り立つ。トークの出力を変えない作り（枠を `BUILDER.build` の頭と `\e` の前だけに置く）も筋が通っている。一方で、次の 2 つは、このままでは骨子の決まりを守れない。

1. 待っている 1 本（`STORE.play.wait`）を、組み立ての中（コルーチンの中）で書くので、`EVENT.drive` の確定より先に書き換わる。設定へ入った時に控える物語の 1 本が、設定の 1 本になる（重大 1）。
2. ト書きの頭で区切る呼び出し（`PLAY.seal`）を、誰も呼ばない。`cue-command-runtime` の暫定設計は呼ぶ約束をしておらず、口の形も食い違う（重大 2）。

条件: 重大 1・2 と、主要 1〜5 を、この spec の設計の中で直すこと。主要 6〜9 は、骨子の側の決定（開発者の判断）を先に取ること。主要 10 は、`novel-checkpoint-rollback` と口の形を 1 つに揃えること。

## 重大な問題

### 重大 1: 待っている 1 本を、確定の前に書き換える（設定へ入ると、物語の 1 本を失う）

- 区分: within-spec
- 根拠:
  - 設計は、枠を付けるたびに `STORE.play.wait = { id, kind, tokens, … }` を置き直すとする（「PLAY_EVENT」の節の「ID は `STORE.play.seq` を…」、「SHIORI の組み立て」の節の「枠を付けた 1 本は、トークン列を `STORE.play.wait` に控える」）。枠は `SHIORI_ACT_IMPL.build` の中で付く。
  - `SHIORI_ACT_IMPL.build` は、シーンのコルーチンの中で呼ばれる（`pasta/shiori/act.lua:72-107`）。コルーチンを走らせるのは `EVENT.drive` の 3 段目（`shiori/event/init.lua:250` の `resume_until_valid`）で、続きを確定するのは 8 段目（同 273-280 行）である。
  - 設計の `PLAY.commit` は 8 段目の前に呼ばれ、設定へ入る時に `p.story = { co = STORE.co_scene, wait = p.wait, … }` と控える。このとき `p.wait` は、もう設定の最初の 1 本（「どうする？」と選択肢）に置き換わっている。
- 起きること: 骨子 2.1 の例で、物語の行（ID 7）を待っている間に「設定」を押す → 設定の 1 本を組み立てた時点で `STORE.play.wait` が設定の 1 本になる → `PLAY.commit` は、その wait を物語の物として控える → `＞演劇再開` は、物語の行でなく「どうする？」を出し直す。骨子 4 章の C（待っていた物語の行を、もう一度出す）を守れない。
- もう 1 つの帰結: 待っている 1 本だけが、続き（`STORE.co_scene`）と別の決まりで動く。続きは「台詞を出した割り込みでだけ置き換わる」（`init.lua:274-280`）が、wait は「枠を付けたら置き換わる」。今のシーン・走り方・続き・待っている 1 本を揃えて確定させる、という設計の判断 4 と食い違う。
- 直し方の案: 枠は、候補の wait を act の欄（例 `act._wait`）に置くだけにする。`PLAY.commit` が、続きと同じ決まり（`replace` が真の時だけ）で `STORE.play.wait` へ移す。設定へ入る時の控えは、移す前の `STORE.play.wait` を取る。テストの「設定: 入ると物語を控える」に、「`＞演劇再開` で出し直す字が、物語の行の字であること」を入れる。

### 重大 2: ト書きの頭で区切る役を、誰も持たない（`cue-command-runtime` との口が合わない）

- 区分: cross-spec
- 根拠:
  - 設計は、ト書きの前で区切るために「ト書きの入口（`cue-command-runtime`）から `PLAY.seal` を呼んでもらう」とする（「骨子・brief との食い違い」の 2、「他の spec との境界」の cue-command-runtime の節）。今の生成は、`！select` 以外のト書きを Lua に出さない（`crates/pasta_lua/src/code_gen/scope_gen.rs:355-360`）ので、入口は `cue-command-runtime` が新しく作る物である。
  - `cue-command-runtime` の暫定設計は、`PLAY.seal` を呼ぶ約束をしていない。逆に、「ト書きのトークンは台詞に数えない。1 本の区切り（アクション行）の数え方に入らない」と書く（`cue-command-runtime/provisional-design.md:582`）。
  - ほかの口も、形が合わない。

| この設計が求める物 | `cue-command-runtime` の暫定設計が渡す物 |
| ------------------ | ---------------------------------------- |
| `PLAY.arrive(act, here, mode)` を、柱を打つ前に 1 回呼ぶ | `CUE.define_pillar("再生モード", fn)`（書いたシーンでだけ呼ばれる）と、`CUE.on_arrive(fn)`（柱を打った後に呼ばれる）・`act.arrival`（同 427・577-578 行） |
| `PLAY.set_line_timeout(act, ms)` を呼ぶ | `act._cue_xtimeout` に値を残す（同 486 行） |
| ト書きのトークンに `instant = true`。高速再生と出し直しで、この設計がトークンを抜く | 組み立ての設定 `config.cue_instant = false` で、組み立ての中で出さない（同 497・580 行） |
| `STAGE.is_areka(act)` | `pasta/baseware.lua` の `BASEWARE.kind()`（同 228・453 行） |
| `PLAY_MODE_KEYS` を「柱として流さない名前」に入れる | `＆再生モード` を、意味を知る柱として登録する（同 577 行） |

- 起きること: どちらの設計どおりに作っても、`さくら：降ってきたね。／！効果音（雷）／教室：＠稲光／さくら：きゃっ！` の雷が、前の 1 本（「降ってきたね。」）に入る。骨子 2.2「ト書きは、直後のアクション行の 1 本に入る」と、骨子 2.2 の作例（1 本目と 2 本目の分け方）を守れない。
- 直し方の案: 区切りの判定を、どちらか 1 か所に寄せる。案 A: `cue-command-runtime` の `CUE.push`（ト書きを積む口）の頭で、この spec の登録した関数を呼ぶ（`CUE.on_push` のような知らせの口を足す）。案 B: ト書きの生成の 1 行目に `act:line()` と同じ形の印（例 `act:cue_head()`）を出し、この spec がそれを読む。どちらでも、走り方の値の受け取り（`define_pillar` か `arrive` か）・時間で次へ・瞬間の命令の抜き方・ベースウェアの判定の名前を、2 本の設計で 1 つに揃える。

## 主要な問題

### 主要 1: 継続行の前にト書きを挟むと、継続行が次の 1 本へ落ちる

- 区分: within-spec（直し方によっては cross-spec）
- 根拠: brief の「要件定義へ送ること」に「継続行の前にト書きを挟む書き方が、今の検査を通るか」が在る。設計は、この項目を扱っていない。設計の区切りは「ト書きの頭で `PLAY.seal`」「継続行の頭 `act:line(true)` では区切らない」なので、`さくら：Ａ／！効果音（雷）／　Ｂ`（Ｂは継続行）では、ト書きの頭でＡが 1 本になり、Ｂは次の 1 本に入る。暫定の要件 R2.1（アクション行と、その継続行の末尾まで）に反する。
- 直し方の案: この書き方を許すかを、まず決める（今のパーサーが通すかを、`parse_scene.rs` で確かめる）。許すなら、ト書きの頭では「区切る予約」だけを立て、次の頭が継続行なら予約を捨てる。許さないなら、`pasta_check validate` と読み込みの誤りにする（作成ツールは問題があれば止める、の方針）。

### 主要 2: 「待っている物」（`act._pending`）を、区切った後に消す所が無い

- 区分: within-spec
- 根拠: 擬似コードの `PLAY.seal` は、`yield` の後で `act._pending` を消さない。`PLAY.line` は `act._pending = act._pending or "click"` とする。`_sealing` は「build が外す」と書くが、`_pending` については書いていない（「部品とインターフェース」の擬似コード、「act の欄」の表）。
- 起きること: 区切った後も `_pending` が残るので、(1) シーンの終わりのト書きだけの残り（R2.5・R3.3 の「待たない 1 本」）でも、`SCENE.wrap` の最後の組み立てが「待っているアクション行が在る」と見て、クリック待ちの枠を付ける。(2) `＞Ａ／＞Ｂ` と続くと、2 つ目の `＞` の頭で、トークンの無い区切りをもう一度起こす。ID と `STORE.play.wait` が無駄に進む（`SHIORI_ACT_IMPL.build` が nil を返す道に入るかは、`frame` の書き方しだい）。
- 直し方の案: `_pending` を消す所を 1 つに決める（`PLAY.seal` が `yield` の直前に消す）。テストに「区切った直後の `＞`」と「最後の行の後ろのト書き」を足す。

### 主要 3: 選択肢の待ちが、選ばれても残る

- 区分: within-spec
- 根拠: `STORE.play.wait` を消すのは、`REG.OnPlayNext`・`PLAY_EVENT.advance`・`REG.OnChoiceTimeout`・`PLAY.abort` と、次の枠の置き直しだけである。`OnChoiceSelectEx`（`shiori/event/choice_select.lua:26-71`）は触らない。
- 起きること: 選ばれた先のシーンが字を出さずに終わる（変数を書くだけの `・閉じる` など）と、`kind = "choice"` の wait が残る。次の `OnSecondChange` では、Status に choosing が無いので、`PLAY_EVENT.reshow` が、答えた選択肢を出し直す。これが毎秒続く。
- あわせて: `REG.OnChoiceTimeout` は、選択肢の待ちで飛び先が無いと nil を返し、作者の書いた `・OnChoiceTimeout`・`＊OnChoiceTimeout` を探さない。骨子 2.3「時間切れも、イベントでシーンが選ばれたら、再生位置はそのシーンへ移る」と、今の動き（`EVENT.no_entry` でイベント名のシーンを探す。`init.lua:222-226`）から外れる。
- 直し方の案: 選択肢の待ちは、`OnChoiceSelectEx` を受けた時に消す（`REG` の鎖で前に 1 つ挟むか、`PLAY.commit` で「イベントが来た」ことを見て消す）。時間切れで飛び先が無い時は、`PLAY_EVENT.event_scene` に落とす。

### 主要 4: 物語から最後の行の `＞` で設定のシーンへ飛ぶと、`＞演劇再開` が設定へ戻る

- 区分: within-spec
- 根拠: `PLAY.commit` は、設定へ入る時に `p.story.co = STORE.co_scene` とする。最後の行の `＞` で設定のシーンへ飛んだ場合（章の終わりにセーブの画面を出す、など）は、物語と設定が同じコルーチンで走る（`return act:call`。`element_gen.rs:231-239`）。確定の時の `STORE.co_scene` は、今まさに設定を走らせているコルーチンである。
- 起きること: `＞演劇再開` が `STORE.co_scene` を控えたコルーチンへ戻すと、設定のシーンの続きが走る。物語の行は出ない。設計の R10 と流れの図は、イベントで入る形しか扱っていない。骨子も「どの場面からも開ける（入口は、条件の属性で書いたイベントのシーン）」とだけ書き、`＞` で入る形を禁じていない。
- 直し方の案: `＞` で設定へ入った時の物語の扱いを決める。案: 物語の続きは「待っている 1 本を出したコルーチン」ではなく「待っていた 1 本」（`wait`）と今のシーンだけで控え、`＞演劇再開` は出し直しの後、次の `OnPlayNext` を物語の続きの無い状態として扱う（物語のコルーチンは、そこで終わっている）。または、`＞` で設定へ入ったら控えを作らない（`＞演劇再開` は R10.4 と同じに何もしない）。どちらかを要件に書く。

### 主要 5: 演劇から戻った時に、時報とランダムトークの時計を決め直さない

- 区分: within-spec
- 根拠: 設計は、門（`virtual_dispatcher.lua:257-259`）に「トークでなければ止める」を足すだけである。自動トークの停止は、再開の時に `virtual_dispatcher.restart_timers` で時計を決め直す（`shiori/entry.lua:39-46`、`virtual_dispatcher.lua:274-288`）。brief の申し送り（2026-10-22）も「止めている間に過ぎた時報は出さない」と書く。
- 起きること: 長い演劇の後で `＆再生モード：トーク` のシーンへ戻ると、門が開いた最初の `OnSecondChange` で、過ぎた正時の時報（数時間前の物でも）か、ランダムトークがすぐ出る。
- 直し方の案: 走り方がトーク以外からトークへ確定した時（`PLAY.commit`）に `restart_timers` を呼ぶ。テストの「門」に「演劇の間に正時をまたいでから、トークへ戻った最初の `OnSecondChange` で時報が出ない」を足す。

### 主要 6: 演劇の間に `＊チェイントーク中断` と、つつき・撫での近道を止めるのは、骨子に無い自動の振る舞いである

- 区分: model
- 根拠: 設計の R6.3（`EVENT.drive` の中断を演劇と設定の間は掛けない）と R6.4（`mouse.lua` の近道を演劇と設定の間は探さない）。骨子 2.3 は、演劇の間に動かしたくない反応の止め方を「条件 `＆＄演劇＝「」` を書く」の 1 つにしている。brief もこの 2 つを決めていない（「`＞チェイントーク` を呼んだときの扱い」はあるが、中断のシーンと近道は無い）。開発者の原則「場合で処理が変わる設計は、一般化が出来ていない兆候」「自動の振る舞いを足さない」に触れる。
- 根の所: 中断のシーンも近道も、完全一致の `SCENE.co_exec_exact` で引くので、条件を見ない（`init.lua:190`、`mouse.lua:117-124`、`scene.lua:284-290`）。そのため `＆＄演劇＝「」` が効かない。設計の 9 は、ここを見つけているが、条件を効かせる代わりに走り方で止めた。
- 直し方の案: 中断のシーンと近道を、条件を見て引く形にする（`SCENE.search` の完全一致版で `act` を渡す。`scene-exact-match` と揃える）。そうすれば、作者は骨子どおり `＆＄演劇＝「」` で止められ、走り方の場合分けが要らない。どちらにするかは、開発者に決めてもらう。

### 主要 7: 設定の間の「今のシーン」と `＄演劇` の値が、骨子の文と食い違う

- 区分: model
- 根拠: 設計の R8 は、`＄演劇` を「演劇か設定の間は今のシーンのグローバルシーンの名前」とする（食い違いの 7）。骨子 2.3 と brief は「演劇の間は今のシーンのグローバルシーンの名前、演劇でなければ空」と書く。文のとおりなら、設定の間は空になり、`＆＄演劇＝「」` を書いたいつもの反応が、設定の画面の間に走る。また、設定の間の「今のシーン」（ローカルを先に探す先）が設定のシーンか物語のシーンかを、骨子は書き分けていない（骨子 1 章の「今のシーン」と「再生位置」、2.1 の「設定は再生位置を動かさない」）。`shell-element-click` の暫定設計も、同じ所を骨子の補いとして挙げている（`shell-element-click/provisional-design.md:423・427・438`）。
- 直し方の案: 骨子に 1 文足してもらう。「設定の間、今のシーン（ローカルを先に探す先・`＄演劇` の値）は設定のシーンへ移る。物語の再生位置は止めたまま別に持つ」「`＄演劇` は、演劇と設定の間は今のシーンのグローバルシーンの名前」。あわせて、brief の候補の `＄再生モード` を採らないことを決めてもらう。

### 主要 8: 走り方は「書いていなければ前のまま」なので、ロードで階層から決まらない場合がある

- 区分: model
- 根拠: 骨子 2.1 と brief は「ロードとバックログの巻き戻しでは、その行の階層の柱が打たれるので、モードも一緒に決まる」とする。一方で、走り方は「上書きで、書いていなければ前のモードが続く」。物語のシーンの階層に `＆再生モード` が無い（`＊OnBoot` から `＞第一章` で入った物語の、ファイル属性にも書いていない）とき、設定の画面から `＞スロット読込` すると、階層を引いても値が無く、走り方は設定のまま残る。設計は `PLAY.set_continuation({ co, mode, … })` で控えの走り方を運ぶ形にしているが、これは「保存せず階層から決める」という骨子の決まりから外れる（控えに走り方を入れることになる）。
- 直し方の案: どちらかを骨子で決めてもらう。案 A: 演劇の行のモードは、階層に値が無ければ「演劇」とみなす（控えは演劇の 1 本でしか作られないので、戻り先はいつも演劇）。この形なら、何も保存せずに済む。案 B: 控えに走り方を入れる。案 A のほうが、原則「保存より、属性から導く」に沿う。

### 主要 9: `！select` の時間の単位（設計の「差し戻し」の 1 に同意する）

- 区分: model
- 根拠: 骨子 2.4「時間は、どれもミリ秒で書く」と、骨子 2.3・brief の作例 `！select（２００００、時間切れ）`。今のコードは秒である（`sakura_builder.lua:457` の `inner.seconds * 1000`、`scope_gen.rs:395-411`、`book/src/getting-started/09-choice.md:46` の `!select(10)` は 10 秒）。`cue-command-runtime` の暫定設計も、同じ食い違いを、この spec が決める物として挙げている（`cue-command-runtime/provisional-design.md:708`）。
- 直し方の案: 開発者に決めてもらう。作例を秒に直すなら、骨子 2.4 の「どれも」に `！select` の例外を書く。ミリ秒に替えるなら、今のゴーストの辞書が 1000 分の 1 になるので、移し替えの手当て（`pasta_check validate` で小さすぎる値を注意にする等）が要る。

### 主要 10: ID と、戻る仕組みの口が、`novel-checkpoint-rollback` の暫定設計と合わない

- 区分: cross-spec
- 根拠:

| 所 | この設計 | `novel-checkpoint-rollback` の暫定設計 |
| -- | -------- | -------------------------------------- |
| `\![raise,OnPlayNext,ID]` の ID | `STORE.play.seq` の通し番号（この spec が持つ） | `CHECKPOINT.current_id()` が待っている行の ID を返し、この spec がそれを使う（同 283-285 行） |
| 戻る時の 1 本目の末尾 | `PLAY_EVENT.again_script` が組む | この spec の `PLAY.next_tail()` を呼ぶ（同 347・575・626 行） |
| 戻る時の早回し | `act._play_target` が在る間、`PLAY.seal` がトークンを捨てて進める | `CHECKPOINT.jump` が自分で早回しし、`CHECKPOINT.arrive` が文字列を返したら呼んだ側が `yield` する（同 39・499-502 行） |
| 画面の状態 | `ROLLBACK.state_tokens(act)`（トークン） | `CHECKPOINT.state_script(…)`（文字列）と `reapply_story_actor()`（同 539-540 行） |

## よい所

- 止まり方を、今のチェイントーク（`STORE.co_scene`・`EVENT.drive`・続きを捨てる 3 つの場合）にそのまま載せた。骨子 2.3「今のトークと同じ動き」を、新しい止まり方を作らずに満たしている。

- 区切りを「次に始まる物の頭」で判定する考え（アクション行の終わりには生成の印が無いことを踏まえた）は、生成をほとんど触らずに済む、よい選び方である。継続行だけ `act:line(true)` にする仮定も、行の数を変えず、ソースマップを崩さない。

- 骨子・brief に無い所を「仮定」と明記し、`！select` の単位を差し戻しとして正しく挙げている。
