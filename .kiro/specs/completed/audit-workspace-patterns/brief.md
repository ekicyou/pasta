# Brief: audit-workspace-patterns

## Problem
7クレートそれぞれの監査で改善が施された後、クレート横断で見たときのエラーハンドリングパターン、コード規約、共通パターンの一貫性が保証されない。重複するユーティリティコード、異なるエラー処理スタイル、共通化できるパターンが各クレートに散在している可能性がある。

## Current State
- 7クレートでそれぞれ独自のエラー型定義（全て thiserror 使用）
- ファイルI/Oエラーハンドリングの重複（pasta_check, pasta_sample_ghost, pasta_shiori）
- ログ出力パターン（tracing使用）が複数クレートに散在
- Wave 1完了後に各クレートの改善状況を統合的に評価する必要がある

## Desired Outcome
- クレート横断のエラーハンドリングパターン統一
- 共通ユーティリティの抽出・共通化（重複除去）
- コーディング規約の一貫性確保
- 全テスト全パス、外部振る舞い不変

## Approach
Wave 1完了後に、各クレートの改善結果を横断的にレビューし、共通パターンの抽出・統一を行う。共通化が過度にならないよう、2回以上の重複に限定する。

## Scope
- **In**: クレート横断のエラーハンドリング統一、重複コードの共通化、コーディング規約の一貫性チェック
- **Out**: 個別クレート内のロジック変更（Wave 1で完了済み）、新しい共通クレートの作成、アーキテクチャ変更

## Boundary Candidates
- エラー型定義パターンの統一
- ファイルI/Oヘルパーの共通化
- ログ出力パターンの統一

## Out of Boundary
- 個別クレートの内部ロジック改善（Wave 1範囲）
- 新しい共通クレートの新設
- クレート間の依存関係の再構成

## Upstream / Downstream
- **Upstream**: Wave 1全spec（各クレートの監査結果）
- **Downstream**: なし

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: Wave 1全audit spec

## Constraints
- 外部振る舞い不変
- 共通化は2箇所以上の重複がある場合のみ
- 過度な抽象化を避ける（1回しか使わないヘルパーは作らない）
- 既存テスト全パス必須
