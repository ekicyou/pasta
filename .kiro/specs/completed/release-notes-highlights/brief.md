# Brief: release-notes-highlights

起点: 2026-10-11 の discovery。開発者が GitHub のリリースのページ（<https://github.com/ekicyou/pasta/releases>）を読み、「修正点の記載が多すぎて目に入ってこない」と指摘した。

## Problem

リリースの本文が、前の版からのコミットの件名を全件並べた一覧になっている。読む人（ゴーストを作る人・pasta を使ってみようとする人）は、その版で何が良くなったのかを本文から読み取れない。

- 件数が多い。v0.3.8 は 57 行で、3,842 文字ある。
- 件名は開発者向けの言い回しで、頭に spec 名が付いている（`feat(scene-name-alias): …`）。
- 利用者に関係のない内部の作業（spec の起票・ロードマップの棚卸・スキルの文書）も同じ一覧に並ぶ。

## Current State

2026-10-11 の main（`b292737a`）と、公開済みの v0.3.8 のリリースを見て確かめた。

- **作り方**: リリース CI（`.github/workflows/release.yml` の github-release の job、471〜480 行）が、`.github/scripts/release/release-notes.ps1` でノートを作り、`.github/scripts/release/github-release.ps1` へ `-NotesFile` で渡す。ノートはそのまま本文になる。
- **ノートの中身**: `release-notes.ps1`（101 行）は、1 つ前のリリースタグからリリースタグまでのコミット（マージコミットを除く）の件名を、Conventional Commits の種類で 6 つの見出しに分ける。件名は、種類とスコープを付けたまま載せる。末尾に Full Changelog のリンクを付ける。取捨選択はしない。
- **除外の条件**: 除くのはスコープが `spec` のコミットだけである（75 行）。種類が `spec` のコミット（`spec(discovery): …`）は、6 種類に無いので Maintenance に入る（完了した `release-ci` の `tasks.md` の実装メモ 3.4 も、そう書いている）。
- **v0.3.8 の内訳**: Features 7・Bug Fixes 25・Refactoring 1・Documentation 11・Maintenance 13。このうち 20 行ほどが、内部の作業である（`spec(discovery)`・`docs(roadmap)`・`docs(skills)`・`docs(release-workflow)`・`chore(release)` など）。
- **添付**: `github-release.ps1`（133 行）は、添付の名前を 3 つに決め打ちしている（72 行。`pasta.dll.zip`・`hello-pasta.nar`・`pasta-vscode-X.Y.Z.vsix`）。「公開済みで 3 つがそろっていれば飛ばす」「足りないものだけを添付する」の判定も、この 3 つで行う。ノートは添付しない。
- **公開済みの Release**: 題名とノートを触らない（`github-release.ps1` 88〜89 行。`release-ci` の要件 6.4・7.3）。
- **タグの検査**: verify の job（`release.yml` 29〜50 行）が `.github/scripts/release/verify-tag.ps1` で、タグの形・版の一致・main からの到達性を見る。ここで落ちれば、後ろの job は何も公開しない。
- **リリースの手順**: `release` スキル（`.claude/skills/release/`。2026-10-11 に、常駐 spec `release-workflow` の手順を移した）の段 4 が、版の表記の 5 ファイルだけを 1 つのコミットにする。「5 ファイルだけ」は、段 4 の確認・段 5 の PR の確認・再開の判定など、スキルの `SKILL.md`・`procedure.md` の多くの場所に出てくる。
- **自動テスト**: `release-notes.ps1`・`github-release.ps1` を動かすテストは、リポジトリに無い。
- **今の方式を書いている文書**: `.kiro/steering/tech.md` 205 行（「リリースノートはコミット履歴から生成」）、`.claude/skills/pasta-check/SKILL.md` 133 行（同じ）、`crates/pasta_sample_ghost/RELEASE.md` 44 行、完了した `release-ci` の要件 6.6〜6.9。
- **令嬢の口調の定義**: マニュアルの執筆規約（`book/AUTHORING.md` 第 1 節「Claudia 令嬢ボイスの定義」）に、一人称・語尾・人物像がある。
- **Claudia の出どころ**: マニュアルの Claudia とアンソニーは、ponapalt さんのゴースト「悪役令嬢クローディア」（[ponapalt/claudia](https://github.com/ponapalt/claudia)。Unlicense）の人物と顔アイコン・意匠を借りている。口調の定義は pasta の側で書いたもので（上の第 1 節）、ゴーストの台詞の写しではない。出典は、マニュアルの表紙の末尾のクレジットに書いている（`book/src/introduction.md` 92 行。完了した `manual-claudia-theme` の要件 150〜153 行）。リリースのページには、クレジットが無い。
- **areka の同じ spec**: areka のリポジトリにも、同じ日に `areka-P0-release-notes-highlights` が起票された（areka は spec 名に `areka-P0-` を前に付ける決まり）。決定 1〜7（本文は見どころの紹介・令嬢の口調・spec 名なし・詳細は Assets・版を上げる PR で書く・無ければ公開の前に止まる・見出しに PR の番号）と、議題の番号 1〜10 をそろえてある。仕組みの違い（areka は GitHub に一覧を作らせている・再実行は頭からやり直す・公開しない試しの実行がある）は合わせていない。

## Desired Outcome

- リリースの本文は、その版で特に注目に値するいくつかの内容を、日本語で紹介する文章である。Claudia（令嬢）の口調で書く。spec 名を載せない。
- 見どころの見出しの末尾に、元になった PR の番号を付ける（`### 「＊会話」と書けば、ランダムトークになりますの(#83)`。2026-10-11 開発者の指示）。GitHub が PR へのリンクに変えるので、見どころから変更の中身へたどれる。
- すべての変更を並べた詳しいリリースノートは、Assets にドキュメントとして添付する。本文から、その添付へたどれる。詳しいリリースノートにも spec 名を載せない。
- 本文の文章は、公開する前に PR で読めて、git に残る。
- 見どころの無いリリースタグでは、リリース CI が何も公開する前に止まる。
- リリースの手順（`release` スキル）が、見どころを書く段と、その確かめ方を持つ。
- 公開済みの v0.3.8 のページも、同じ形（見どころの本文と、詳しいリリースノートの添付）になっている。それより前の版は、今のままである。

## Approach

**見どころをリポジトリのファイルとして書き、リリース CI がそれを本文に使う**（2026-10-11 開発者の決定）。

1. リリースの手順が、版を上げるコミットで、その版の見どころのファイルを書く。版の更新の PR に入るので、タグを打つ前に読める。
2. リリース CI が、タグの検査の段で、その版の見どころのファイルが在ることを確かめる。無ければ、何も公開する前に止まる。
3. リリース CI が、今の全件の一覧を、詳しいリリースノートとして Markdown のファイルにし、Assets に添付する（4 つ目の添付）。
4. リリース CI が、見どころのファイルに、詳しいリリースノートへのリンクを足したものを本文にする。

- **採らなかった案**:
  - 公開の後で本文を書き換える案（CI は定型文で公開し、その後に手順が `gh release edit` で差し替える）: CI の変更は小さい。ただし、公開の通知メールは定型文のまま届き、差し替えに失敗しても気づきにくく、公開の前に読めず、git に残らない。
  - 機械だけで短くする案（本文を新機能と破壊的変更の件名だけにする）: 書く手間は無い。ただし、紹介の文章にならず、令嬢の口調で書けない。
- **開発者に見せた例**（v0.3.8 を題材にした本文。形を決めたものではない）:

  ```markdown
  ## Claudia の見どころ紹介

  おほほ、ごきげんよう。今回の目玉は、わたくしが選んでさしあげますわ。

  ### 「＊会話」と書けば、ランダムトークになりますの(#83)
  これまでは ＊OnTalk と書く決まりでしたけれど、＊会話 と書けるようにしましたわ。
  別名は pasta.toml の [scene.alias] で、お好きに足せましてよ。

  ### ご注意あそばせ — 動きが変わる点が 3 つ
  - Call から戻ると、呼び出し元の文脈に戻ります
  - タグだけの出力では、段落区切りの改行を出しません
  - シーンの登録名が「名前_通し番号」になりました

  ---
  すべての変更（57 件）は、Assets の release-notes-v0.3.8.md にまとめてありますわ。
  ```

## Scope

- **In**:
  - 見どころのファイルの置き場所・名前・形の決まり
  - リリース CI の変更（見どころの有無の検査、詳しいリリースノートの添付、本文の組み立て）。`release-notes.ps1`・`github-release.ps1`・`verify-tag.ps1`（または検査の段）・`release.yml`
  - 詳しいリリースノートから spec 名を外すことと、内部の作業の扱い
  - `release` スキルの `SKILL.md`・`procedure.md` への、見どころを書く段の追加（版の更新のコミットに入るファイルが 1 つ増える）
  - 今の方式を書いている文書の更新（`tech.md`・`RELEASE.md`・`pasta-check` のスキル）
  - ノートを作るスクリプトの、動かして確かめられる検査を 1 つ
  - 公開済みの v0.3.8 の本文の差し替えと、詳しいリリースノートの添付（1 回きり。配布物とタグは変えない）
- **Out**:
  - v0.3.7 より前の公開済みのリリースの書き直し
  - 見どころの材料を、spec の完了のたびに溜めておく仕組み。書く人は、リリースのときに前のタグからのコミットを読んで選ぶ
  - マニュアル（`book/`）に更新履歴のページを足すこと
  - コミットの件名の書き方の決まりを変えること
  - 英語の本文

## Constraints

- **席**: リリースの実行中は、`release.yml` と補助スクリプトを触るこの spec を main へ入れない（ロードマップ「リリース」の決まり）。
- **問題があれば止める**: 見どころが無い・空である・版が合わないときは、警告で続けずに、公開の前に失敗させる。
- **再実行で続けられること**: 今のリリース CI は、失敗した job を再実行すると、足りないものだけを補う。添付が 4 つになっても、同じ性質を保つ。
- **公開済みの Release**: 添付の削除・上書きをしない決まり（`github-release.ps1` 9 行）を保つ。
- **技術的な正確さ**: 口調は飾りである。動きが変わる点（破壊的変更）は、口調のために読み違えられないように書く（`book/AUTHORING.md` 43 行の考え方）。
- **スキルの編集**: `.claude/skills/pasta-check/SKILL.md` の編集は、開発者の許可が要る。
- **言語**: 本文は日本語。
