## 1. 要約

- **根は 2 か所の切り出し**。`tokenizer.rs:199`（自動ウェイトと種類の判定）と `line_breaker.rs:145`（budoux の改行。`tokenize_plain_chars` は自前の切り出し）が、どちらも `remaining.chars().next()` で 1 コードポイントずつ進む。片方だけ直しても、もう片方は割れたまま。`wait_inserter.rs:157` の `text.chars()` は、トークンが 1 クラスタになれば 1 トークン 1 ウェイトに直すだけで済む。
- **既定の `chars_*` の落とし穴を見つけた**。既定の `chars_line_start_prohibited` の末尾 `ｰﾞﾟ`（U+FF70 U+FF9E U+FF9F）は、UAX #29 では 1 つのクラスタになる。設定の文字列を素直にクラスタへ分けると、`ｰ`・`ﾞ`・`ﾟ` が単独では行頭禁則に当たらなくなり、半角の `ｰ` を含む台詞（1 コードポイントの文字だけ）の出力が変わる。要件 5.1 を破る。設定の分け方は設計で決める必要がある（議題 Q1）。
- **幅の API の差**。`UnicodeWidthStr::width_cjk` は組み合わせの絵文字を 2 と数える（確かめた）。ただし、制御文字（タブ・LF・CR・NUL）を 1 と数える。今の `UnicodeWidthChar::width_cjk(c).unwrap_or(0)` は 0 と数える。クラスタごとに文字列の幅を呼ぶだけだと、1 コードポイントの制御文字の幅が変わる。1 コードポイントのクラスタでは文字の幅を使い続けるなどの手当てが要る。
- **単位の読み取りを先に**。Prepend の文字（U+0600 など）の後ろの `\` は、UAX #29 では前の文字のクラスタに入る（`"\u{600}\h"` → `["\u{600}\", "h"]`。確かめた）。クラスタの切り出しは、次の `\`（単位の頭）の手前で止める必要がある（要件 1.3）。
- **推奨の方向**: 既存の 3 ファイルを拡張し、クラスタの切り方は `unicode-segmentation` を足す（brief の候補 A）。規模は M、危険度は中（既定の `chars_*` と幅の差の 2 点に気をつければ低）。

- 組み合わせの絵文字の幅は、クラスタごとに文字列の幅を呼べば 2 になる（要件 4.4 は満たせる）。

## 5. 実装の選択肢

### 5.1 全体の形

**選択肢 A: 今の 3 ファイルを拡張する**
- `tokenizer.rs`: タグでない所で次のクラスタを 1 トークンにする（次の `\` の手前で止める）。`CharSets` をクラスタで引けるようにする。
- `wait_inserter.rs`: 1 トークン 1 ウェイト。単独の `\` の判定をクラスタで。
- `line_breaker.rs`: `PlainChar` にクラスタ（`&str`）を持たせ、`tokenize_plain_chars` もクラスタで切る。幅はクラスタごと。budoux の区切りをクラスタの境界へ写す。
- ✅ 触るファイルが brief の見込みと同じ。`mod.rs` を触らない。差分が小さい。
- ❌ クラスタの切り出し（「次の `\` の手前で止める」規則を含む）が `tokenizer.rs` と `line_breaker.rs` の 2 か所に入る。規則がずれる危険が残る。

**選択肢 B: クラスタの切り出しを新しい小さなモジュールにまとめる**
- 例: `sakura_script/grapheme.rs` に「単位でない区間をクラスタに分ける」「クラスタの幅」「`chars_*` の文字列を項目に分ける」を置き、`tokenizer.rs` と `line_breaker.rs` の両方から使う。
- ✅ 規則が 1 か所。単体テストを 1 か所に集められる。
- ❌ ファイルが 1 つ増える。公開するかどうかを決める必要がある。

**選択肢 C: 切り出しを 1 本にする（`line_breaker` が `Tokenizer` のトークン列を使う）**
- `line_breaker` の自前の切り出しをやめ、`Tokenizer::tokenize` の結果からクラスタと後ろの単位を組む。
- ✅ 根の 2 か所が 1 か所になる。
- ❌ `break_lines_impl` はウェイトを入れた後の文字列を受け取り、`break_lines`（Lua）は生のテキストを受け取る。どちらも `tag_regex.find_iter` で読み直している。流れの組み替えが大きく、`vertical-balloon-lines` で固めた列の数え直しに触れる危険がある。0.4.2 の不具合の直しとしては重い。

見立て: A か B。B の「切り出しの関数を 1 つ」は、A の中で `tokenizer.rs` に関数を置いて `line_breaker.rs` から使う形でも得られる（ファイルを増やさない B）。

### 5.2 クラスタの切り方

- **候補 A: `unicode-segmentation` を足す**（brief の推奨）。UAX #29 の全規則。依存なし・`MIT OR Apache-2.0`・小さい。`Cargo.lock` の席はこの spec が持つ（`lua-cmodule-robustness` とは別の行）。
- **候補 B: 手書き**（ZWJ・異体字セレクタ・肌色の修飾子・結合文字だけを見て伸ばす）。国旗（地域指示子の対）・ハングルの字母・Prepend・半角の濁点などで漏れる。要件 1.5 の国旗をこれだけで満たすには地域指示子の対の規則も要る。`ponytail:` の注記が要る。
- どちらでも、「次の `\` の手前で止める」はこちらで足す（`unicode-segmentation` の外の規則）。

### 5.3 `chars_*` の分け方（議題 Q1 の設計の候補）

- **(i) クラスタに分けた項目＋各コードポイント**: 設定の文字列をクラスタに分けた項目と、文字列のコードポイント 1 つずつの項目の両方を集合に入れる。既定の `ｰﾞﾟ` も、`ｰ`・`ﾞ`・`ﾟ`・`ｰﾞﾟ` で引ける。副作用: `🙆‍♀️` を書くと、台詞の単独の `♀`（や行頭の U+FE0F）も当たる。
- **(ii) クラスタに分けた項目＋「1 コードポイントずつ書かれた」と見なせる所だけ**: 例えば、クラスタの 2 つ目以降が全部「単独でも字幅を持つ文字」なら分ける、など。規則が複雑になる。
- **(iii) 区切りの記法を足す**（空白や `,` で区切る）。設定の書き方が変わる。既定の値の読み方も変わる。公開の設定の約束に触る。
- **(iv) 既定の値だけ特別扱い**（既定の文字列をコードポイントで分けておく）。作者が既定の値を写して足した設定では効かない。
- 見立て: (i) が最小で、要件 3.4・3.5 を満たす。副作用（部品が単独で現れたときの一致）を許すかを議題 Q1 で決める。

### 5.4 公開 Rust API（議題 Q4 の設計の候補）

- `CharSets` のフィールドを `HashSet<String>` に変え、`classify(&str)` にする（破壊的。0.4.x の patch で出すことになる）。
- `classify(char)` を残し（中で 1 文字の文字列にして引く）、クラスタ版 `classify_cluster(&str)` を足す。フィールドの型は変える（フィールドを直接読む利用者がいなければ実害は小さい）。
- フィールドを非公開にする（今後の変更に強いが、これも破壊的）。

### 5.5 budoux の区切りをクラスタへ写す

- 本文（budoux に渡す文字列）は、今と同じくコードポイントの並びのまま渡す。1 コードポイントのクラスタだけの台詞では区切りが今と同じになる（要件 5.1）。
- `parse_boundaries` の `char` の位置を、各クラスタの先頭の `char` の位置の表で引き、クラスタの先頭に当たらない区切りを捨てる。または `parse` の語の `chars().count()` を積み、語の境界がクラスタの途中なら次のクラスタの頭へ寄せる。前者のほうが「捨てる」（要件 4.2）をそのまま書ける。

## 6. 工数と危険度

- **工数: M（3〜7 日）**。触るのは 3 ファイルの切り出しと幅の所（本体は合わせて約 500 行）・依存の追加・テスト・マニュアル 4 ページ・スキル references の再生成。brief の見立て（8〜11 タスク）と合う。
- **危険度: 中**。仕組みは小さいが、(1) 既定の `chars_*` がクラスタでつながる問題、(2) 制御文字の幅の差、(3) 単独の `\` の守りを 2 か所で判定し直すこと、の 3 点で「1 コードポイントの文字だけの台詞の出力を変えない」を破りやすい。どれも特性化テストで捕まえられるので、テストを先に置けば低くできる。

## 要約

- 種別: 既存の仕組みの拡張（軽い発見の手順。`design-discovery-light`）。新しい依存は `unicode-segmentation` の 1 つ。
- 読んだもの: `requirements.md`（要件ディスカッションの決定を含む）・`brief.md`・この文書の 1〜7 節・steering（`tech.md`・`structure.md`）・`tokenizer.rs`・`wait_inserter.rs`・`line_breaker.rs`・`mod.rs`・`budouy 0.2.2` の `parser.rs`・`deny.toml`・`about.toml`・`.github/workflows/build.yml`・`doc/release-notes/README.md`。
- 使ったスキル: `kiro-spec-design`（規則: design-principles・design-discovery-light・design-synthesis・design-review-gate）、`kiro-validate-design`（design-review）。ドメインのスキル（`pasta-lua-coding`・`pasta-ghost-authoring`）は、Lua の API の形を変えないので読んでいない。
- 主な結論:
  - クラスタの切り方を `tokenizer.rs` の `next_cluster` 1 つにまとめ、2 つの切り出しが使う。ファイルは増やさない。
  - `next_cluster` は、2 つ目以降のコードポイントの `\` の手前で必ず切る（単位の頭でも、単位にならない `\` でも）。
  - `CharSets` は `HashSet<String>`。項目は「クラスタに分けた項目」＋「各コードポイント」。判定は「全体を全種類」→「先頭のコードポイントを全種類」→ 一般。
  - 幅は「1 コードポイントと `\r\n` は今の数え方、それ以外は文字列の幅」。
  - budoux は `parse_boundaries` の `char` の位置を、クラスタの先頭の位置と照合する。

## 調査の記録

### `\` で切る規則（申し送りの 1・3）

- 試した（スクラッチパッドの `gc` の `examples/d.rs`。`unicode-segmentation 1.13.3`）。
  - `\u{600}\あ` → `\u{600}`・`\`・`あ`（切らないと `\u{600}\` が 1 つになり、後ろのウェイトで `\\` ができる）。
  - `\u{600}\h` → `\u{600}`・`\`・`h`（トークナイザでは `\` の位置で `\h` が単位として先に読まれる）。
  - `\` ＋ ZWJ ＋ `x` → `\‍`・`x`。`\` ＋ U+0301 ＋ `a` → `\́`・`a`。`\\` → `\`・`\`（トークナイザでは `\\` はエスケープの単位として先に読まれる）。
- 結論: 「単位の頭の `\` だけで切る」は不十分（単位にならない `\` を前のクラスタに入れると要件 2.6 を破る）。「どの `\` でも切る」が最小で正しい。
- `\` ＋ 結合文字のクラスタは、今の出力と同じになる（今は `\`（ウェイトなし）＋ U+0301（ウェイト）＝ `\́\_w[…]`。直した後も `\́\_w[…]`）。単独の `\` の判定は「クラスタが `\` ちょうど」で、ウェイトの側と改行の側（決定 9）で同じにする。

### 幅（申し送りの 4）

- 試した: `\r\n` のクラスタの文字列の幅は 1、今の数え方（`\r`・`\n` の文字の幅の和）は 0。`🇯🇵🇺🇸` は 2・2。`❗️` は 2。`ｰﾞﾟ` は 1（今の和も 1）。
- UAX #29 の GB4・GB5 により、制御文字が他の文字とつながるクラスタは `\r\n` だけ。
- 結論: 1 コードポイントと `\r\n` は今の数え方、それ以外は `UnicodeWidthStr::width_cjk`。`\r\n` を 0 に保つのは前提（設計の OPEN QUESTION 3）。

### budoux の区切りの写し（申し送りの 7 節の推奨）

- `budouy 0.2.2` の `Parser::parse_boundaries(&str) -> Vec<usize>` は、`char` の位置の区切り（その位置の字の前で割る）を返す。`parse` は同じ区切りで語の文字列を作るだけ（`parser.rs` 29〜45 行）。
- 結論: `parse_boundaries` に替え、クラスタの先頭の `char` の位置と照合する。語の文字列を作らずに済み、「捨てる」（要件 4.2）をそのまま書ける。本文は今と同じコードポイントの並びなので、1 コードポイントの台詞では区切りが今と同じ。

### トークナイザと改行の側でクラスタがずれないか

- `talk_to_script` の経路では、改行の側はウェイトの入った文字列を切り直す。ウェイトはクラスタの境界にしか入らず、`next_cluster` は `\` の手前で切るので、ウェイトの手前でクラスタが終わる。境界から切り始めた UAX #29 の結果は、元の文字列での結果と同じ（地域指示子の対も、境界から数え直せば同じ）。
- 結論: 切り出しを 1 本にする（ギャップ分析の選択肢 C）必要は無い。共通の関数で足りる。

### 文字の種類の判定の順（申し送りの 2）

- 要件 3.6 の文言は「`chars_*` のどの項目とも全体では一致しないとき」。よって、全体の判定を全種類で先に見て、全部外れてから先頭のコードポイントを見る（種類ごとに全体 → 先頭、ではない）。
- 決定 1 と決定 2 を重ねると、`chars_period = "🙆‍♀️"` のとき `🙆‍♂️` も先頭の `🙆` で句点に当たる。要件 3.3 は 2 つ目以降の部品だけを禁じるので、要件の文言には合う。2 段目を「書いたクラスタの項目」だけに絞る案は、既定の `ｰﾞﾟ` で台詞の `ｰﾞ`（1 クラスタ）が一般になる（今は `ｰ`・`ﾞ` とも行頭禁則）ので採らない。設計の OPEN QUESTION 1。
- 気づいたこと: 要件 5.3 は今の出力を `ｶ\_w[…]ﾞ\_w[…]` と書くが、既定では `ﾞ` が行頭禁則（自分の値を持たない）なので、今は `ｶ\_w[…]ﾞ`。動きの約束は変わらない。設計の OPEN QUESTION 6。

### 公開 API（申し送りの 5）

- `CharSets`・`classify` の呼び出し元は、ワークスペースの中では `tokenizer.rs` と `edge_case_test.rs` の 2 行だけ（2026-10-23 に確かめた）。`pasta_check`・`pasta_lsp`・`pasta_shiori` は使っていない。

## 統合（design-synthesis）

- **一般化**: 2 つの切り出しの「1 コードポイントずつ進む」所は、どちらも「単位でない所の次の 1 文字」という同じ問い。`next_cluster` 1 つにまとめた。`classify` の 2 段も、1 コードポイントのときは 1 段と同じ結果になる 1 つの規則にした。
- **作るか使うか**: クラスタの切り方は `unicode-segmentation` を使う（UAX #29 の全規則。手書きは国旗・ハングル・Prepend で漏れる）。幅は `unicode-width` の文字列の幅を使う。語の区切りは `budouy` の `parse_boundaries` を使う。自前で書くのは「`\` で切る」1 行と「`\r\n` は 0」1 行だけ。
- **単純化**: 新しい型・新しいモジュール・設定のキーは足さない。クラスタは入力の `&str` のまま持つ。`mod.rs` と Lua は触らない。`classify(char)` の互換の関数も残さない。

## 設計の決定

### 決定: クラスタの切り出しは `tokenizer.rs` の `next_cluster` 1 つ

- 代案: (1) 新しいファイル `grapheme.rs`、(2) 切り出しを 1 本にする（ギャップ分析の選択肢 C）。
- 選んだもの: `tokenizer.rs` の `pub(crate) fn next_cluster`。`line_breaker.rs` から使う。
- 理由: 規則は数行で、ファイルを増やすほどではない。選択肢 C は流れの組み替えが大きく、`vertical-balloon-lines` の数え直しに触れる。
- 引き換え: `line_breaker.rs` → `tokenizer.rs` の依存が 1 つ増える（同じモジュールの中で、向きは一方だけ）。

### 決定: `chars_*` の項目は「クラスタ」＋「各コードポイント」、判定は 2 段

- 要件ディスカッションの議題 1・2 の決定どおり。判定の順は要件 3.6 の文言から「全体を全種類 → 先頭のコードポイントを全種類」。

### 決定: 幅の規則

- 1 コードポイントと `\r\n` は今の数え方、それ以外は文字列の幅。

### 決定: 公開 API は置き換え

- `CharSets` のフィールドは `HashSet<String>`、`classify(&str)`。`classify(char)` は残さない。

# PR の「動きが変わる点」の材料（実装後・2026-10-23）

リリースノートは PR の本文のこの節から書く（要件 5.3）。

## 台詞の見え方

- 直したこと: 絵文字（`🙆‍♀️`・`👍🏽`・`🇯🇵` など）や結合文字（`が`＝`か`＋U+3099（結合用の濁点）の合成前の形、`é`＝`e`＋`́` など）の途中に、自動ウェイト（`\_w[...]`）と自動改行（budoux）が入らなくなった。1 つの書記素クラスタは 1 文字として扱い、ウェイトはクラスタの後ろに 1 つだけ入る。
- 変わること: 半角カナの濁点・半濁点つき（`ｶﾞ`・`ﾊﾟ` など）は、今まで `ｶ` と `ﾞ` の 2 文字だったものが 1 文字になる。ウェイトは `ｶﾞ` の後ろに 1 つ入り、`ｶ` と `ﾞ` の間で改行しない。種類は全体（`ｶﾞ`）→ 先頭（`ｶ`）の順で判定するので、一般の文字として扱う。
- 変わること: 台詞に CRLF（`\r\n`）の文字がそのまま入っていると、今まで `\r` と `\n` の後ろにそれぞれ入っていたウェイトが、`\r\n` の後ろに 1 つになる（2 コードポイントのクラスタなので、要件 5.1 の約束の外）。
- 変わらないこと: 1 コードポイントだけの台詞（ひらがな・漢字・ASCII・既定の `chars_*` の文字・タグ・単独の `\`）の出力は、ウェイトも改行も今と同じ（特性化テストで確かめた）。
- 幅: 1 コードポイントと `\r\n` は今の数え方。それ以外のクラスタは文字列の東アジアの幅で数える（`🙆‍♀️` などは 2）。
- `chars_*` の書き方: 複数のコードポイントの文字（絵文字など）を書くと、そのクラスタ全体と、各コードポイントの両方で一致する。先頭のコードポイントでも当たるので、`🙆‍♀️` を書くと `🙆‍♂️` も当たる（設計ディスカッションの議題 1 で受け入れた）。

## 公開 Rust API（`pasta_lua::sakura_script`）

- `CharSets` の各フィールド（`period`・`comma`・`strong`・`leader`・`line_start_prohibited`・`line_end_prohibited`）の型を `HashSet<char>` から `HashSet<String>` へ置き換えた。
- `CharSets::classify` の引数を `char` から `&str`（書記素クラスタ 1 つ）へ置き換えた。`classify(char)` は残していない。
- トークンの粒度: タグでない所のトークンが 1 コードポイントごとから 1 書記素クラスタごとになった（`Token::text` が複数のコードポイントを持つことがある）。
- `insert_waits`: 一般・リーダーのトークンに、トークン（クラスタ）1 つにつきウェイトを 1 つ入れる（今までは 1 文字ごと）。
- Lua からの呼び方（`@pasta_sakura_script` の `talk_to_script`・`break_lines`）は変えていない（`mod.rs` と Lua のソースに差分なし）。

## 確かめ方

- x86・x64 で同じ動きになることは、PR の `build.yml` の 2 つのターゲットの `cargo test --all` で確かめる（ローカルでは x64 だけ）。
