# Requirements Document

## Project Description (Input)
マニュアル（`book/src/`）の章どうしのリンクは、見出し（`#…`）まで指していることが多い。リンク検証（`book/tools/link-check.mjs`）は、本の中のリンクについてはリンク先のファイルの実在までしか見ない。そのため、執筆者が見出しの文言を変えると、そこを指すリンクは黙って切れ、CI も DoD のゲートも気づかない。読者は章の先頭に着地し、目当ての節を自分で探すことになる。本 spec は、本の中のリンクが実在しない見出しを指していたらリンク検証が落ちるようにし、クレートの README などから公開 URL で指している見出しも同じ規則で確かめる。今のマニュアル（60 章）で誤検出を 0 件に保つ。新しいツールや依存は足さず、`link-check.mjs` が既に持つ見出しの `id` を作る関数（`headingSlugs`）を使う。詳細は `brief.md` を参照。

## Introduction

マニュアル（`book/src/`・60 章）には、見出しまで指すリンクが 585 本ある（同じ章の中の見出しへ 162 本、他の章の見出しへ 423 本。入門ガイドだけで 44 本。2026-10-10・main `ea40c363` で計測）。リンク検証は、他の章へのリンクについてはリンク先のファイルが在るかどうかだけを見て、`#` より後ろを捨てている。同じ章の中の見出しへのリンク（`#見出し`）は、まったく見ていない。見出しの文言を変えると、そこを指すリンクは黙って切れる。

本 spec は、リンク検証が見出しの実在まで見るようにする。見出しに付く `id` は公開されるページのものと同じ文字列で比べ、実在する見出しを指すリンクは 1 本も落とさない。今のマニュアルには切れた見出しリンクが無い（計測で 0 件）ので、本 spec の主な成果は「これから切れたら気づける」ことである。

クレートの README から公開 URL で指している見出しは、今のリンク検証がすでに確かめている（`pasta-runtime-internals-doc` で入った。brief の「ここも見出しまでは見ていない」は実装と食い違う）。本 spec はこの検査を保ち、本の中のリンクと同じ規則で判定することを約束する。あわせて、検査の対象を、読者に届くほかの文書（ルートの `README.md`・`SOUL.md`・2 スキルの Markdown）へ広げる。これらは公開 URL を持つのに、今は章の実在も見出しも検査されていない。

リンク検証の利用者は「マニュアルの執筆者（AI エージェントを含む）」と「spec を完了させる開発者（DoD のゲートでリンク検証を走らせる）」である。恩恵を受けるのは、リンクをたどって目当ての節に着地できる「マニュアルの読者」である。

## Boundary Context

- **In scope**:
  - 本の中のリンクのうち、他の章の見出しを指すもの（`章.md#見出し`）と、同じ章の中の見出しを指すもの（`#見出し`）の、見出しの実在の検査
  - クレートの README（`crates/*/README.md`）から公開 URL で指している見出しの検査を保ち、本の中のリンクと同じ規則で判定すること
  - 公開 URL の検査の対象を、ルートの `README.md`・`SOUL.md`・2 スキル（`pasta-ghost-authoring`・`pasta-lua-coding`）の Markdown へ広げること（章の実在と見出しの実在）
  - リンク検証の自己テスト（`book/tools/link-check-test.mjs`）の追従
  - 実装の時点で見つかった、実在しない見出しを指すリンクの修正（そのリンクの行だけ）
- **Out of scope**:
  - 外部サイトの見出し、GitHub の URL のフラグメント（`#L10` など）
  - 印刷用ページ（`print.html`）の中のリンク
  - 公開されるページの見出しの `id` の作り方を変えること
  - 章の本文の書き直し（切れたリンクの行のほかは変えない）
  - マニュアルの CI の定義（`.github/workflows/manual.yml`）、出力の検査（`book/tools/verify-static.mjs`）、執筆規約（`book/AUTHORING.md`）の変更（ロードマップの「同じウェーブに置くときの約束」。前の 2 つと `AUTHORING.md` の「CI と同じ順」の一覧は、同じウェーブの `manual-print-media-refs` が持つ）
  - DoD のゲート（`.kiro/steering/workflow.md` の Manual Sync Gate・Internals Sync Gate）の手順の変更
  - スキルの自己完結の検査（`skill-anchor` ほか）の規則の変更
  - 公開 URL の検査の対象を、前提 A3 に挙げた文書のほかへ広げること（`.kiro/steering/roadmap.md` などの内部の作業メモは対象にしない）
  - リンク検証がリンクとして拾う記法を増やすこと（参照形式のリンク・HTML タグのリンクなど。今のマニュアルには 1 本も無い）
- **Adjacent expectations**:
  - DoD の Manual Sync Gate と Internals Sync Gate、マニュアルの CI が、今と同じコマンド（`node book/tools/link-check.mjs`）でリンク検証を走らせる。誤検出があると無関係な spec の完了が止まるので、誤検出 0 件は本 spec の必達条件である
  - 同じウェーブの spec が章の見出しを変えることがある（`choice-line-layout` の 9 段目の章、`hello-pasta-shell-art` の 8 段目の章）。後から main に入る側が、リンク検証に通る状態に合わせる
  - スキル `references/` の生成ファイルが持つ公開 URL の見出しは、章の相対リンクから生成される。章の側のリンクを本 spec の検査が見るので、生成ファイルの側を別に守る必要は無い（鮮度は `gen-skill-refs.mjs --check` が見る）。スキルの公開 URL の検査で、生成ファイルを手書きファイルと分けて外すかどうかは設計で決める（どちらでも、完了時点の違反は 0 件である）
  - マニュアルに章を足す spec・見出しを変える spec（`pasta-check-dic-validate`・`scene-anchor-link` など）は、本 spec の検査で切れに気づける

## Requirements

### Requirement 1: 他の章の見出しを指すリンクの検査

**Objective:** As a マニュアルの執筆者, I want 他の章の見出しを指すリンクが切れたらリンク検証が落ちること, so that 見出しの文言を変えたときに、そこを指すリンクの直し忘れに気づける

#### Acceptance Criteria
1. If 章のリンクが他の章の見出しを指していて（`章.md#見出し`）、リンク先の章にその見出しが無い, then the リンク検証 shall そのリンクを違反として報告する。
2. When 章のリンクが他の章の見出しを指していて、リンク先の章にその見出しが在る, the リンク検証 shall そのリンクを違反として報告しない。
3. If リンク先の章のファイルそのものが無い, then the リンク検証 shall これまでどおりファイルが無いことを報告し、見出しの違反を重ねて報告しない。
4. When リンクのフラグメントが空である（`章.md#`）, the リンク検証 shall 見出しの検査をせず、章の実在だけを見る。
5. The リンク検証 shall 台詞部品（引用ブロック）の中のリンクも、地の文のリンクと同じ規則で見出しの実在を検査する。

### Requirement 2: 同じ章の中の見出しを指すリンクの検査

**Objective:** As a マニュアルの執筆者, I want 同じ章の中の見出しへ飛ぶリンク（`#見出し`）も検査されること, so that 章の中の目次や「前の節を参照」のリンクが黙って切れない

#### Acceptance Criteria
1. If 章のリンクが同じ章の中の見出しを指していて（`#見出し`）、その章にその見出しが無い, then the リンク検証 shall そのリンクを違反として報告する。
2. When 章のリンクが同じ章の中の見出しを指していて、その章にその見出しが在る, the リンク検証 shall そのリンクを違反として報告しない。

### Requirement 3: 見出しの照合の規則

**Objective:** As a マニュアルの読者, I want リンク検証が「在る」と判定した見出しへ、公開されたページで実際に着地できること, so that 検査に通ったリンクをたどって目当ての節に着く

#### Acceptance Criteria
1. The リンク検証 shall リンクのフラグメントを、公開されるページでその見出しに付く `id` と同じ文字列かどうかで照合する（大文字と小文字を区別する）。
2. When リンクのフラグメントがパーセントエンコードされている, the リンク検証 shall 復号した文字列で照合する。
3. When 1 つの章に同じ文言の見出しが複数ある, the リンク検証 shall 2 つ目以降を、公開されるページと同じ付番（`-1`・`-2`…）の `id` で区別して照合する。
4. The リンク検証 shall 記号・全角文字・インラインコードを含む見出しについても、公開されるページの `id` と同じ文字列を導く。
5. The リンク検証 shall コードフェンスの中の `#` で始まる行を、見出しとして扱わない。
6. Where 章の本文に明示のアンカー（HTML の `<a id="…">`）が書かれている, the リンク検証 shall そのアンカーを指すリンクを、見出しを指すリンクと同じく実在するものとして扱う。（前提 A2）
7. The リンク検証 shall 本 spec の完了時点のマニュアルの全章のすべての見出しについて、マニュアルをビルドした出力の見出しの `id` と同じ `id` を導く。

### Requirement 4: 公開 URL で見出しを指すリンク

**Objective:** As a README やスキルの読者, I want マニュアルの外の文書にあるマニュアルへのリンクが、指している章と節に着地すること, so that README やスキルからマニュアルの目当ての節へ迷わず行ける

#### Acceptance Criteria
1. If クレートの README にある公開マニュアルの URL が、対応する章に無い見出しを指している, then the リンク検証 shall その URL を違反として報告する（今の動作を保つ）。
2. The リンク検証 shall 公開 URL の見出しと本の中のリンクの見出しを、同じ照合の規則（Requirement 3）で判定する。
3. The リンク検証 shall 公開 URL の見出しを、作業ツリーにある今の章と照合する（公開済みの版の章とは照合しない）。（前提 A4）
4. The リンク検証 shall 公開マニュアルの URL の検査を、クレートの README に加えて、ルートの `README.md`・`SOUL.md`・2 スキル（`pasta-ghost-authoring`・`pasta-lua-coding`）の Markdown にも行う。（前提 A3）
5. If 検査の対象の文書にある公開マニュアルの URL が、対応する章のファイルが無いページを指している, then the リンク検証 shall その URL を違反として報告する。
6. If 検査の対象の文書にある公開マニュアルの URL が、対応する章に無い見出しを指している, then the リンク検証 shall その URL を、クレートの README のときと同じ区分と文面で違反として報告する。
7. When 本 spec の完了時点のリポジトリに対して走らせた, the リンク検証 shall 広げた対象の文書について、公開 URL の違反を 0 件と報告する。

### Requirement 5: 違反の報告と終了

**Objective:** As a マニュアルの執筆者, I want 違反の報告を読むだけで、どのリンクのどの見出しが無いのかが分かること, so that 報告から直す場所へまっすぐ行ける

#### Acceptance Criteria
1. When 見出しの違反を報告する, the リンク検証 shall リンク元のファイル、書かれているとおりのリンク先、リンク先の章、見つからなかった見出しを示す。
2. The リンク検証 shall 見出しが無い違反を、リンク先のファイルが無い違反と見分けられる区分で報告する。
3. If 見出しの違反が 1 件以上ある, then the リンク検証 shall これまでのリンク切れと同じく、失敗として終了する。
4. When 違反が 1 件も無い, the リンク検証 shall 成功として終了する。
5. The リンク検証 shall 同じ入力に対して、同じ違反を同じ順で報告する。

### Requirement 6: 誤検出が無いことと、走らせ方を変えないこと

**Objective:** As a spec を完了させる開発者, I want リンク検証が今と同じ手順で走り、正しいリンクを落とさないこと, so that 無関係な spec の完了が、この検査の誤検出や手順の変更で止まらない

#### Acceptance Criteria
1. When 本 spec の完了時点のリポジトリのマニュアルの全章に対して走らせた, the リンク検証 shall 見出しの違反を 0 件と報告し、成功として終了する。
2. The リンク検証 shall マニュアルをビルドしていない作業ツリーでも、ビルドした後の作業ツリーと同じ結果を出す。（前提 A1）
3. The リンク検証 shall 今と同じコマンドで走り、追加のインストールもネットワーク接続も求めない。
4. The リンク検証 shall これまでの検査（リンク先のファイルの実在・リポジトリ内を指す GitHub の URL・内部設計章のパス・README の公開 URL・スキルの自己完結）の判定を変えない。
5. The リンク検証 shall 見出しの検査の対象を、今の検査がリンクとして拾っているものと同じ範囲にする。（前提 A5）

### Requirement 7: 自己テストと、見つかった切れリンクの修正

**Objective:** As a マニュアルの保守者, I want 見出しの検査そのものが自己テストで守られ、今ある切れが直っていること, so that 検査が黙って効かなくなることがなく、検査を入れた日から CI が緑である

#### Acceptance Criteria
1. The リンク検証の自己テスト shall 実在しない見出しを指すリンク（他の章・同じ章・公開 URL のそれぞれ）を入れた見本で、違反が検出されることを確かめる。公開 URL は、広げた対象の文書（ルートの `README.md`・`SOUL.md`・スキルの Markdown）に入れた見本でも確かめる。
2. The リンク検証の自己テスト shall 実在する見出しを指すリンク（日本語の見出し・記号を含む見出し・重複の付番・パーセントエンコード）を入れた見本で、違反が報告されないことを確かめる。
3. The リンク検証の自己テスト shall 実リポジトリのマニュアルに対して、見出しの違反が 0 件であることを確かめる。
4. If 実装の時点で、実在しない見出しを指すリンクが見つかった, then the 本 spec shall そのリンクの行だけを直し、章のほかの文を変えない。
5. The リンク検証の自己テスト shall これまでどおり、追加の依存なしで、本物の `book/src/` を書き換えずに走る。
6. Where マニュアルをビルドした出力が作業ツリーに在る, the リンク検証の自己テスト shall 全章のすべての見出しについて、リンク検証が導く `id` とビルドした出力の見出しの `id` が同じであることを確かめ、食い違いがあれば章と見出しを示して失敗する。
7. When CI の外で走っていて、マニュアルをビルドした出力が作業ツリーに無い, the リンク検証の自己テスト shall 6 の確かめを飛ばし、ほかの確かめの結果を変えない。
8. While CI の中で走っている, the リンク検証の自己テスト shall マニュアルをビルドした出力が在り、全章を 1 つも飛ばさずに突き合わせたことまで求め、満たさなければ失敗する。

## 前提と未決事項（要件ディスカッションで確かめる）

本書は、開発者に質問せずに書いた下書きである。brief で決まらなかった点は、次の前提を置いて要件を書いた。前提を変えるときは、括弧で前提を引いている受け入れ基準を直す。計測の詳細は `research.md` にある。

### 前提

- **A1（見出しの `id` は章のソースから導く）**: リンク検証は、マニュアルをビルドした出力を読まない。計測では、今の関数が導く `id` と公開ページの `id` は、全 60 章・764 個の見出しで 1 つも食い違わなかった（手元の mdBook 0.5.4 のビルドと、CI の 0.5.3 がビルドした公開サイトの両方）。DoD のゲートはビルドなしでリンク検証を走らせるので、ビルドした出力を読む形にするとゲートの手順（`workflow.md`）まで変わる。
- **A2（見出しのほかのアンカーは、明示の `<a id>` だけ）**: 今のマニュアルには、見出しのほかのアンカーが 1 つも無い（章のソースにも、ビルドした出力の本文にも無い）。台詞部品（`> 【表情】…`）は `id` を持たないので、リンクの行き先にならない。スキルと README の検査がすでに `<a id|name>` を合格にしているので、同じ扱いにした。
- **A3（公開 URL の検査の対象は、読者に届く文書）**: `crates/*/README.md`・ルートの `README.md`・`SOUL.md`・2 スキルの Markdown。brief の「クレートの README など」の「など」を、要件ディスカッション（議題 2）でここまで広げた。内部の作業メモ（`.kiro/steering/roadmap.md`）は入れない。
- **A4（公開 URL は、作業ツリーの今の章と照合する）**: 今の動作のままである。
- **A5（リンクを拾う範囲は、今の検査と同じ）**: 今の本の中のリンクの検査は、コードフェンスの中やインラインコードの中に書いたリンクの記法も拾う。見出しの検査も同じ範囲にした（今のマニュアルでは、そこに見出しを指すリンクは 0 本）。

### 未決事項

1. **`id` の食い違いへの備え（brief の議題 1）**: 今は食い違いが 0 件なので、A1 のとおり「関数を合わせる」も「ビルドした出力を読む」も要らない。残るのは、これから食い違う見出しが書かれたときの備えである。食い違いうる形は、全角空白を含む見出し、強調（`_x_`）を含む見出し、`===` の下線で書く見出し、引用やリストの中の見出し、`{#id}` の属性、ASCII の外の大文字。今のマニュアルにはどれも無い。備えの案: (a) 何もしない（Requirement 3.7 を完了時に 1 度確かめるだけ）、(b) 食い違いうる形の見出しを見つけたらリンク検証が落とす、(c) ビルドした出力がある所（CI）で突き合わせを続ける（`manual.yml`・`verify-static.mjs` を触らない約束があるので、このウェーブでは置き場所が限られる）。→ **決定（2026-10-10・議題 1）**: (c)。自己テストが、ビルドした出力が在るときだけ全見出しを突き合わせる（Requirement 7.6・7.7）。CI は自己テストをビルドの後に走らせるので、`manual.yml` を触らずに毎回確かめられる。食い違いうる形の見出しを禁じる決まりは足さない。手元に古いビルドが残っているときの扱いは設計で決める。
2. **見出しのほかのアンカー（brief の議題 2）**: A2 でよいか。`<a>` のほかの要素の `id`（`<span id>`・`<div id>` など）も合格にするか。→ **決定（2026-10-10）**: A2 のまま。今のマニュアルに 1 つも無い書き方を、先回りして合格にしない。要るようになった時点で足す。
3. **公開 URL の検査の範囲（brief の議題 3）**: クレートの README は、すでに見出しまで検査されている（brief の記述と食い違う）。対象を広げるか。見出しつきの公開 URL を持ち、今は検査されていないファイルは、`SOUL.md`（2 本）、スキルの手書きファイル（`pasta-ghost-authoring` の `SKILL.md` に 1 本、`references/authoring-patterns.md` に 4 本）、`.kiro/steering/roadmap.md`（1 本）。スキルの生成ファイル（122 本）は、章の相対リンクから作られるので数えていない。ルートの `README.md` は公開 URL を 9 本持つが、見出しつきは 0 本で、章の実在も検査されていない。今はどれも切れていない。→ **決定（2026-10-10・議題 2）**: 読者に届く文書まで広げる（ルートの `README.md`・`SOUL.md`・2 スキルの Markdown。Requirement 4.4〜4.7）。`roadmap.md` は内部の作業メモなので入れない。
4. **公開済みの README と見出しの変更（brief の議題 3）**: crates.io に公開済みの README は、公開した版の時点の見出しを指す。見出しを変えると、リポジトリの README は検査で直せるが、公開済みの README のリンクは次のリリースまで章の先頭に着地する。これを受け入れるか。README から指されている見出しを変えるときに、古い `id` を明示のアンカーで残す決まりを足すか（足す場合は執筆規約の話になり、未決事項 5 と同じ制約がかかる）。→ **決定（2026-10-10）**: A4 のまま受け入れる。公開済みの README は書き換えられず、切れても章の先頭には着地する。古い `id` を残す決まりは足さない。
5. **執筆者への案内の置き場所**: 「見出しを変えたら、そこを指すリンクも直す」「見出しに強調や全角空白を入れない」は、今は `AUTHORING.md` がスキルの生成対象章についてだけ書いている。本 spec でこの注意は全章に広がるが、このウェーブでは `AUTHORING.md` を触らない約束である。案内は違反の報告の文面だけで足りるか。`AUTHORING.md` への追記を、`manual-print-media-refs` が入った後の作業として申し送るか。→ **決定（2026-10-10・議題 1）**: 違反の報告の文面だけで足りる。執筆者に新しい決まりを課さないので、`AUTHORING.md` への申し送りはしない。
6. **コードとして書いたリンクの記法（A5）**: コードフェンスやインラインコードの中のリンクの記法を、見出しの検査から外すか。外すなら、ファイルの実在の検査と範囲がずれる。→ **決定（2026-10-10）**: A5 のまま外さない。ファイルの実在の検査と範囲をそろえ、これまでの判定（Requirement 6.4）を変えない。
