# Requirements Document

## Introduction

pasta ゴーストの作者（利用者）向けに、Pasta DSL 文法・Lua ランタイム API/コーディング・入門チュートリアルを統合した利用者マニュアルを、**サーバー不要の静的サイト**として提供する。知識が複数の場所（`doc/spec/`、`GRAMMAR.md`、AI 向けスキル）に分散している現状を解消し、利用者が検索可能な単一サイトで学習・参照できることを目的とする。本マニュアルは利用者向けの派生ドキュメントであり、`doc/spec/` の権威的仕様を置き換えるものではない。本文は案内役キャラクター「Claudia 令嬢」のボイスで執筆する。

> 技術選定（mdBook 採用）・代替案の却下理由・上流下流などの背景は [brief.md](./brief.md)（discovery 成果物）を参照。本要件は利用者・運用者から観測可能な振る舞いのみを定義し、実装技術の選択は design フェーズに委ねる。

## Project Description (Input)

pasta ゴーストの作者向けの利用者マニュアル（Pasta DSL 文法・Lua API/コーディング・入門チュートリアル）を、サーバー不要の静的 HTML+JS サイトとして構築する。既存 `doc/spec/` Markdown 資産を流用し、検索可能で日本語表示が正しく、GitHub Pages 等にそのまま公開できること。本文は「Claudia 令嬢」ボイスで、軽妙トークはキャラ口調・説明本体は普通の文体で執筆する。

## Boundary Context

- **In scope**: 静的サイトの生成と GitHub Pages での公開導線／クライアントサイド全文検索／日本語表示・ナビゲーション・閲覧体験／Pasta DSL 文法マニュアル／Lua API・コーディングマニュアル／入門・チュートリアル／執筆ボイス・トーン設計／既存資産の再利用。
- **Out of scope**: Lua 言語仕様本体の取り込み（外部参照リンクのみ）／`doc/spec/` の権威的ソースの置き換え／多言語化（i18n、初版は日本語のみ）／自動 API ドキュメント生成／**pasta Lua ランタイムの内部設計・アーキテクチャ解説**（2パストランスパイル・yield/resume・シーン検索・ローダ自己展開・SHIORI 非同期基盤等。読者層がコントリビュータ寄りで境界が異なるため、別途将来仕様として記録。R5 は API の「使い方」に集中する）。
- **前提環境**: 対象 OS は **Windows**（現状限定）。推奨ベースウェアは **SSP**。他の伺か互換ベースウェアでも概ね動作する想定（手順は SSP 主軸＋補足注記）。pasta の辞書ソース（`.pasta`）・コンテンツは **UTF-8** エンコーディングである（SHIORI 境界での ANSI 変換は `@enc` 等ランタイムの責務であり、作者は UTF-8 で記述する）。
- **Adjacent expectations**: `doc/spec/` は文法の権威的ソースであり続ける（本マニュアルは準拠する消費側）。素の Lua 言語仕様は外部リファレンス（ランタイム＝LuaJIT 2.1 に対応する日本語 Lua 5.1/5.2 リファレンスおよび LuaJIT 公式ドキュメント）が所有し、本マニュアルはリンク参照に留める。版の離れた Lua 5.5 系資料（`ekicyou/lua55-manual-ja` 等）はランタイム方言と一致しないため言語リファレンスとしては採用しない。コンテンツの母体として既存 `GRAMMAR.md` および AI 向けスキル（`pasta-lua-coding` / `pasta-ghost-authoring`）の知識を再利用する。

## Requirements

### Requirement 1: 静的サイトの生成と GitHub Pages 公開（サーバー不要）

**Objective:** 公開担当者として、サーバーランタイムなしで配布できる静的なマニュアルサイトを生成し、GitHub Pages で公開したい。利用者がブラウザから直接アクセスできるように。

#### Acceptance Criteria

1. When マニュアルをビルドしたとき, the マニュアルビルド shall サーバーランタイムを要しない静的成果物（HTML・CSS・JS、およびフォント・画像等の静的アセット）を出力する
2. The マニュアルサイト shall サーバーサイドのランタイム・アプリケーションサーバー・データベースなしで全ページを表示する
3. The マニュアル公開 shall 公開先プラットフォームとして GitHub Pages を用いる
4. When 生成物を GitHub Pages に配置したとき, the マニュアルサイト shall 追加のサーバー設定なしで正しく表示される
5. If 利用者が生成物をローカルファイル（オフライン・zip 配布等）として開いたとき, the マニュアルサイト shall ページ閲覧とナビゲーションを提供する（相対パス構成によりサーバーなしで閲覧できること。全文検索機能は R2-5 のとおり HTTP 配信時のみで、ローカルでは対象外）

### Requirement 2: 全文検索（クライアントサイド）

**Objective:** 利用者として、マニュアル全体を日本語キーワードで検索したい。語中の部分一致でも必要な情報へ素早く到達できるように。

#### Acceptance Criteria

1. When 利用者が検索ボックスにキーワードを入力したとき, the マニュアルサイト shall 一致するページを結果一覧として提示する
2. The マニュアルサイト shall 検索機能をサーバーサイド処理なし（クライアントサイドで完結）で動作させる
3. When 利用者が検索結果の項目を選択したとき, the マニュアルサイト shall 該当ページへ遷移する
4. When 利用者が任意の連続2文字以上の日本語語句で検索したとき, the マニュアルサイト shall その語句を本文に含むページを検索結果に提示する（語中部分一致の合格基準）
5. While マニュアルが GitHub Pages 等の HTTP 配信で公開されているとき, the マニュアルサイト shall R2-4 の検索機能を提供する（ローカルファイル直開きでの検索動作は保証対象外。R1-5 はローカルでの閲覧・ナビゲーションのみを保証する）

### Requirement 3: 日本語表示・ナビゲーション・閲覧体験

**Objective:** 利用者として、日本語コンテンツを読みやすく辿りたい。目次から目的の章へ迷わず到達できるように。

#### Acceptance Criteria

1. The マニュアルサイト shall 日本語（UTF-8）テキストを文字化けなく表示する
2. The マニュアルサイト shall 全章を一覧できる目次（ナビゲーション）を提供する
3. When 利用者がコード例を含むページを開いたとき, the マニュアルサイト shall コードブロックを判読可能な書式で表示する
4. Where ページ間に相互参照があるとき, the マニュアルサイト shall リンクによる遷移を提供する

### Requirement 4: Pasta DSL 文法マニュアル

**Objective:** ゴースト作者として、Pasta DSL の文法を利用者視点で学びたい。自力で辞書を書けるように。

#### Acceptance Criteria

1. The マニュアル本文 shall Pasta DSL の**全実装済み文法要素**（マーカー、ブロック構造、アクション行、リテラル、変数・スコープ、単語定義、アクター辞書、さくらスクリプト、Call/Jump 等、`doc/spec/` の実装済み章に対応）を**網羅的に**解説する
2. The マニュアル本文 shall 各文法要素について利用者が試せる具体例を示す
3. While 文法を解説するとき, the マニュアル本文 shall `doc/spec/` の権威的仕様に準拠し矛盾しないように記述する
4. The マニュアル本文 shall 実装判断向け仕様書とは別に、利用者向けの平易な学習導線を提供する
5. The マニュアル本文 shall 文法リファレンスを、入門チュートリアル（Requirement 6）とは独立した参照型セクションとして提供する
6. Where 文法要素が未実装・将来仕様であるとき, the マニュアル本文 shall それを網羅対象から除外するか Requirement 9.3 に従い「将来変更あり」として明示区別する

### Requirement 5: Lua API / コーディングマニュアル

**Objective:** ゴースト作者として、Lua ランタイムでカスタムロジックを書けるようになりたい。公開 API とコーディング規約を理解できるように。

#### Acceptance Criteria

1. The マニュアル本文 shall pasta ランタイムが Lua へ公開する主要モジュール・API（検索、永続化、設定、ロギング、さくらスクリプト変換、エンコーディング等）を解説する
2. The マニュアル本文 shall `scripts/` のカスタムスクリプト記述パターン（シーン関数、イベントハンドラ登録、単語一括投入等）を示す
3. The マニュアル本文 shall DSL と Lua の使い分け基準を提示する
4. The マニュアル本文 shall 各 API について利用者が試せる具体例を含める
5. The マニュアル本文 shall 対象 Lua 方言を **LuaJIT 2.1**（Lua 5.1 系＋有効化された拡張）として明示し、Lua 5.5 等の他バージョンと混同させない記述とする
6. While 読者がプログラミング初心者であるとき, the マニュアル本文 shall Lua の基本概念（変数・関数・テーブル等）への最小限の入口（短い導入または参照リンク）を提供する

### Requirement 6: 入門 / チュートリアル

**Objective:** プログラミング初心者を含む初学者として、ゼロから最初のゴーストを作りたい。専門用語に詰まらず、途中で迷わず完成まで到達できるように。

#### Acceptance Criteria

1. The マニュアル本文 shall ゼロから最初の pasta 辞書を作成する手順をステップ順に提供する
2. When 利用者がチュートリアルの手順を順に実行したとき, the マニュアル本文 shall 動作する最小限のゴースト例に到達できる完結した手順を提供する
3. The マニュアル本文 shall チュートリアル開始に必要な前提環境・準備を明示する
4. The マニュアル本文 shall プログラミング初心者でも追従できるよう、専門用語に説明を添えるか平易に言い換える
5. The マニュアル本文 shall 対象実行環境（Windows、推奨ベースウェア SSP、他の伺か互換ベースウェアでも概ね動作）を明示する
6. The マニュアル本文 shall `.pasta` 辞書ファイルを UTF-8 で作成することを明示する（旧来の Shift_JIS 辞書からの移行時の注意を含む）

### Requirement 7: 執筆方針（ボイス・トーン）

**Objective:** 読者として、親しみやすく、かつ正確なマニュアルを読みたい。楽しく学びつつ誤解なく実装できるように。

#### Acceptance Criteria

1. The マニュアル本文 shall 導入・語りかけ・章の繋ぎ・締めの部分を案内役キャラクター「Claudia 令嬢」のボイスで記述する
2. The マニュアル本文 shall 仕様・構文・手順・API の説明本体を平易で正確な普通の文体で記述する
3. While キャラ口調を用いるとき, the マニュアル本文 shall 技術的正確さを損なわない
4. The マニュアル本文 shall コードブロック・表・構文定義・コマンド例の内部にはキャラ口調を持ち込まない
5. The マニュアル本文 shall 語り口の一貫性を保つための基準ボイスガイド（サンプル）を確立し、以降の章をそれに準拠させる

### Requirement 8: 既存資産の再利用と外部参照

**Objective:** 保守担当者として、既存ドキュメント資産を再利用し二重管理を避けたい。更新コストを抑えられるように。

#### Acceptance Criteria

1. While コンテンツを作成するとき, the マニュアル本文 shall 既存の `doc/spec/` および `GRAMMAR.md` の内容を可能な限り流用する
2. Where 素の Lua 言語自体のリファレンスが必要なとき, the マニュアル本文 shall ランタイム（LuaJIT 2.1, Lua 5.1 系）に対応する外部リファレンス——日本語 Lua リファレンス（Lua 5.1/5.2 相当、例: milkpot 版）および LuaJIT 公式ドキュメント（luajit.org、英語）——への参照リンクを提供し、言語仕様本体は取り込まない
3. The マニュアル本文 shall 版の離れた Lua 5.5 系資料を素の Lua 言語リファレンスとして案内しない（ランタイム方言と不一致のため）
4. The マニュアルサイト shall `doc/spec/` を権威的ソースとして置き換えず、利用者向け派生物として位置づける

### Requirement 9: 対象バージョンの明記と陳腐化対策

**Objective:** 利用者として、マニュアルがどのバージョンの pasta を対象としているか把握したい。記述と実際の挙動の食い違いに惑わされないように。

#### Acceptance Criteria

1. The マニュアルサイト shall 対象とする pasta のバージョン（系列）を読者が確認できる形で明示する
2. The マニュアル本文 shall 安定した文法・API を主たる記述対象とする
3. Where 記述対象が未確定・実装予定・将来変更の可能性がある機能であるとき, the マニュアル本文 shall 「将来変更あり」等の注記でそれを明示し、安定機能と視覚的・記述的に区別する
4. The マニュアル本文 shall ランタイムの対象 Lua 方言（LuaJIT 2.1）をバージョン情報の一部として明示する

### Requirement 10: ドリフト検出と完了承認ゲート統合

**Objective:** 保守担当者として、`doc/spec/` の変更時にマニュアルとの乖離を自動検出し、未解決のまま spec を完了承認できないようにしたい。マニュアルと権威仕様の整合を継続的に保てるように。

> 注: 本要件は「実装完了を承認」フロー（`kiro-spec-complete` / `workflow.md` の DoD）への変更を**意図的に本仕様スコープへ含める**もの（設計ディスカッション#3 でのスコープ拡大決定）。横断プロセスへの影響を避けるため、ゲートは条件付き（R10-5）で発火する。

#### Acceptance Criteria

1. The マニュアルビルド shall 各マニュアル章と由来する `doc/spec/` 章・節の対応関係（マッピング）を機械可読な形で保持する
2. When `doc/spec/` の参照元が変更されたとき, the ドリフトチェック shall 対応するマニュアル章が未更新であることを検出し、警告または失敗を返す
3. While spec 完了承認（DoD ゲート）を実行するとき, the 完了ワークフロー shall マニュアルと `doc/spec/` の整合チェックを DoD の一部として実行し、未解決のドリフトがあれば完了を中断する
4. The ドリフトチェック shall リンク切れ（マニュアル→`doc/spec/`、および外部参照リンク）を検出する
5. Where 変更が `doc/spec/` にもマニュアル（`book/`）にも触れないとき, the 完了ワークフロー shall 当該チェックをスキップし、無関係な spec の完了承認を重くしない
