## Research Log（設計フェーズ）

### 改行をまたぐ引用のエラー行（Research Needed 1）
- **Context**: 要件 1.2 の「エラーの位置（行番号）」が、文脈ごとにどの行を指すかを確定する。
- **Sources Consulted**: A1（`string_contents = @{ (!(PEEK | "\r" | "\n") ~ ANY)+ }`）を一時適用し、`pasta_dsl::parser::parse_str` で実測した（測定後に元へ戻した）。
- **Findings**（特記の無い入力は 1 行目が `＊s`。`⏎` は改行）:

| 入力 | 結果 |
| ---- | ---- |
| `　＄x＝「a⏎b」`（式） | エラー 2:5（開始した行） |
| `　＄x＝"a⏎b"` | エラー 2:5（開始した行） |
| `　＞t（「a⏎b」）`（Call の引数） | エラー 2:5（開始した行） |
| `　＠＠cmd（「a⏎b」）`（キューコマンドの引数） | エラー 2:3（開始した行） |
| `　＠？t「a⏎b」`（選択肢行の表示テキスト） | エラー 2:5（開始した行） |
| グローバル `＠w：「a⏎b」`（1 行目） | エラー 2:1（次の行。1 行目は引用なしの値 `「a` として通る） |

### 空の候補の実行時挙動（Research Needed 2）
- **Context**: 要件 3.4・3.5 がランタイムの変更なしで満たせるか。
- **Sources Consulted**: `pasta_scripts/pasta/word.lua`（`entry` は `#values > 0` なら値を素通しで登録する。`""` 1 個でも 1 件）、`act.lua` の `search_dictionary`（`result ~= nil` で判定）と `act:word`（ハンドラが `nil` のときだけ警告して `nil` を返す）、`actor.lua`（同じ判定）、`pasta_core` の `word_table::search_word`（`Result<String, …>`）、`pasta_lua` の `search/context.rs`（`Option<String>`）。
- **Findings**: 空文字列は Lua で真値かつ `nil` ではないため「見つかった」扱いになる。単語テーブル側に空文字列を除く処理は無い。
- **Implications**: ランタイムのソースは変えず、テストだけを足す。テストが失敗した場合、直す場所はこの仕様の境界の外（`act.lua` は同じ Wave の別仕様が持つ）なので、実装を止めて境界を見直す。

### B1 のエスケープと `\` の同時出現（Research Needed 3）
- **Context**: さくらスクリプトを含む値（`\` を含む）と改行が同時に来たとき、正しく読み戻せるか。
- **Findings**: 文字単位の 1 回の走査で `\` → `\`、`"` → `\"`、CR → `\r`、LF → `\n` に置き換える。置き換えた結果を再び置き換えないため、`\` の後ろに改行が続いても `\` と `\n` が別々に出て、Lua は元の 2 文字に読み戻す。使うのは Lua の標準エスケープだけである。
- **Implications**: 推論で解決済み。ランタイムテストの読み戻し（`return <リテラル>` を評価して元の値と比べる）で固定する。

### マニュアルの追加例と検査ツール（Research Needed 4）
- **Context**: 足す例がハイライトのテスト・`link-check`・`verify-content` を壊さないか。
- **Findings**: ハイライト文法は全規則が 1 行の `match` で、引用文字列はキューコマンドの引数でしか色分けしない。足す例は既存の構文（変数代入・単語定義・属性行）だけで、新しいスコープは要らない。ハイライト文法の変更は不要である。
- **Implications**: 実際の検査はマニュアルを編集してからでないと走らせられないため、実装時の検証手順として設計に入れた（`book/tools/highlight/*-test.mjs`・`link-check.mjs`・`verify-content.mjs`・`gen-skill-refs.mjs --check`）。

## Design Decisions（設計フェーズ）

### Decision: A1 + B1 + C1 を既存の集約点だけで実現する
- **Context**: U24・U25 の修正と多層防御。
- **Alternatives Considered**: ギャップ分析の A2〜A4・B2・B3・C2（上の「実装アプローチの選択肢」）。
- **Selected Approach**: 文法 `string_contents` から CR・LF を除く（A1）。`literalize_with_span` の先頭に「改行を含む値は `"…"` 形式でエスケープ」の分岐を足す（B1）。`parse_attr`・`parse_key_words` の `Rule::string_blank` を空文字列にする（C1）。
- **Rationale**: 3 つとも呼び出し元を触らずに全経路へ効く。同じ Wave の別仕様が持つ `element_gen.rs`・`act.lua` を触らない。
- **Trade-offs**: 同じ行の `""…""` の曖昧さは残る（要件 2.3 で注記に確定済み）。
- **Follow-up**: Call の動的ターゲットのエラー行を実装時に測る。

### Synthesis の結果
- **Generalization**: 「空の引用は空文字列」は、式・キューコマンド引数で既に成り立っている規則である。単語値・属性値を同じ規則へ揃えるだけで、新しい共通関数は作らない（分岐 2 つを書き換えるほうが小さい）。
- **Build vs. Adopt**: エスケープは Lua の標準エスケープを使う。外部クレートは足さない（4 文字の置き換えだけである）。
- **Simplification**: 新しいソースファイル・部品・設定は足さない。テストは 2 ファイル（パーサ用とランタイム用）にまとめ、出力形のテストは既存の単体テストに足す。ハイライト文法は変えない。U06 は文法を変えず、テストとマニュアルで固定するだけにする。

## Risks & Mitigations（設計フェーズ）
- 次の行が単独で文法に合うと、改行をまたぐ引用がエラーにならない — 値に改行は入らない（1.1・1.3 は成り立つ）。扱いは設計ディスカッションで決める。
- 空の候補の実行時挙動が見込みと違う — ランタイムテストで先に確かめる。外れたら境界を見直す。
- マニュアルの例がハイライトの検査を壊す — 既存の構文だけで例を書き、検査を実装の完了条件に入れる。

## 設計ディスカッションの記録（2026-10-04）

### 議題 1: 閉じ忘れた引用がエラーにならない場合がある → 単語値・属性値では書いた行のエラーにする（E1）
- 決定: `word_nofenced`・`attr_string` の先頭に否定先読みを足し、引用なしの値を `「`・`"` で始められないようにする。要件 1.6・1.7 を足し、範囲外にしていた「1 行の閉じ忘れは引用なしの値として読む」を範囲内に入れ直した。
- 理由: `「` で始まって現行で正しく通る引用なしの値は、閉じ忘れだけである（`＠w：「やあ」と言った` は現行でもパースエラー）。エラーが必ず書いた行に出るため、マニュアルに一言で書ける。
- 残す限界: アクション行の中（`さくら：＠f（「a`）は、台詞が `「` を普通に含むため区別できない。現行のまま。
- 実測（3 規則を一時適用して `parse_str` で確認、確認後に戻した）:

| 入力（`⏎` は改行） | 結果 |
| ---- | ---- |
| `＠w：「a⏎b」`、`＠w：「a⏎＠v：b」`、`＠w：「abc`、`＠w："abc` | 1 行目（開始した行）でエラー |
| `＠w：あ、「い` | 1 行目でエラー（桁は `「` の位置） |
| ローカル単語・アクター単語・属性値の閉じ忘れ | 開始した行でエラー |
| `＠w：あ「い、う"え` | 候補 `あ「い`・`う"え`（先頭以外は値の一部） |
| `＆k：a「b` | `AttrString("a「b")` |
| `＞「a⏎b」`（Call の動的ターゲット） | 開始した行でエラー |
| `さくら：＠f（「a⏎b」）` | 次の行でエラー（現行のまま） |

- `cargo test -p pasta_dsl` は 3 規則を適用した状態で全件通った。`pasta_lua` 側（サンプルゴースト・フィクスチャ）は実装時に `cargo test --workspace` で確かめる。

- 空の候補の実行時挙動は、実装の最初にテストで確かめる。外れた場合はこの仕様の中で直す。
