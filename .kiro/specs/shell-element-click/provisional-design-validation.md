# 暫定の設計の検証: shell-element-click

2026-11-19。`provisional-design.md`（以下「設計」）を、書いた人とは別の目で読んだ記録である。`.claude/skills/kiro-validate-design/SKILL.md` と `.kiro/settings/rules/design-review.md` の手順で行い、この実行の決まりに合わせて、次の所だけ変えた: 指摘の数を 3 つに絞らない（重大と大きい物は全部並べる）、設計は直さない、開発者には聞かない。

正としたのは骨子 `novel-areka-contract/final-model-2026-11-19.md`（以下「骨子」）と、この spec の `brief.md`。コードは読むだけで、ビルドもテストも走らせていない。

## 判定

**GO_WITH_CONDITIONS（条件つきで進めてよい）**

設計のコードについての主張は、読んで確かめた限り、どれも正しい（下の「確かめた主張」）。新しい状態を持たず、自動の動きも救済の規則も足していないので、開発者の原則にも沿っている。

ただし、次の 3 種類の穴がある。

1. テストの置き場所と組み方が、狙った失敗を捕まえられない（指摘 1・2）。
2. 「演劇の間はローカルを先に探す」を `EVENT.no_entry` の中だけに置く前提で、既定のハンドラを持つイベント、つつき・撫での近道、右クリック・設定ボタンの入口との関係が、どの spec の持ち分にもなっていない（指摘 3〜6）。
3. 骨子そのものに、設定のモードの「今のシーン」と、ローカルの反応が全体の入口を隠してしまうことについて、決まりが無い（指摘 5・7）。

条件: 指摘 1・2 を設計の中で直すこと。指摘 3〜8 は、`novel-talk-flow`・`novel-checkpoint-rollback` の設計との突き合わせ（まとめのディスカッション）で持ち主を決めること。指摘 5・7 は、骨子に 1 文ずつ足すかどうかを開発者が決めること。

## 指摘

### 指摘 1（大きい・spec の中）: T3 を `lua_specs` に置くと、条件の比べ方を確かめられない

- **根拠**: `lua_specs` を走らせる `crates/pasta_lua/tests/lua_unittest_runner.rs:52-56` は、`@pasta_search` を空の登録で作る（「empty registries」）。辞書は読み込まれず、条件の属性も無い。今の `lua_specs` のテストは `SCENE.search` を差し替えて結果を作っている（`choice_select_test.lua:66` など）。条件の評価は Rust の `scene_cond.rs` にあるので、差し替えたテストでは、R1 の中心（`ドア`・`ドア2`・空・`slot1`／`slot10` が完全一致で分かれること）を確かめられない。
- **影響**: 設計 14 章の T3 が、書いたとおりには作れない。作れたとしても、差し替えた検索を確かめるだけになり、前方一致の取り違えが起きても通ってしまう。
- **提案**: T3 は Rust の結合テストに置く。`crates/pasta_lua/tests/shiori/mouse_event_test.rs` に、辞書を読み込んで Reference を付けてイベントを送る道具が既に在る（`load_ghost`・`fire_with`、13・274 行）。`scene_condition_e2e_test.rs` も同じ形の例である。`lua_specs` に残すのは T1（`search_scoped` の段の順）だけにする。

### 指摘 2（大きい・spec の中）: `choice_select_test.lua` は「変えない」ままでは見張りにならない

- **根拠**: `choice_select_test.lua:19-24` の `setup` は、テストのたびに `pasta.scene`・`pasta.store`・`pasta.shiori.event.choice_select` などを `package.loaded` から外して読み直し、新しい `SCENE.search` を差し替える（66 行など）。`STORE.last_global_scene` も新しい `STORE` に書く（117・167・192・215・244 行）。設計 8.2 の `route.lua` は、ファイルの頭で `SCENE`・`STORE`・`FAILURE` を `require` する。`route.lua` は `setup` で外されないので、最初のテストで読んだ古い `SCENE`・`STORE` を持ち続け、2 本目からは差し替えも `last_global_scene` も届かない。
- **影響**: 設計 5 章の「`choice_select_test.lua` は変えない（挙動が不変であることの見張りに使う）」と、7 章の R2 のたどりが成り立たない。テストが落ちるか、別の物を確かめて通る。
- **提案**: どちらかにする。(a) `route.lua` の中で `SCENE`・`STORE` を関数の中で `require` する（`scene.lua:189` の `@pasta_search` や `init.lua:224` と同じ遅延の形）。(b) `choice_select_test.lua` の `setup` に `package.loaded["pasta.shiori.event.route"] = nil` を 1 行足し、5 章の表を「1 行足す」に直す。どちらでも、設計の「変えない」の記述は直す。

### 指摘 3（大きい・spec をまたぐ）: ローカルを先に探すのが `no_entry` の中だけだと、既定のハンドラを持つイベントに効かない

- **根拠**: 骨子 2.3 は「演劇の間、イベントのシーンは、今のシーンのグローバルシーンのローカルシーンを先に探す」と、イベントを限らずに書く。設計 4.2・8.3・11 章は、その探し方を `EVENT.no_entry` の中に置く前提である。ところが、`REG` に既定のハンドラが在るイベントは `no_entry` を通らない（`init.lua:319`）。`OnBoot`（`boot.lua:17-19`）、`OnMouseDoubleClick`・`OnMouseMove`（`mouse.lua:128`・`144`・`153`・`170` の `exec_event_scene` は `co_exec(act, event, nil, nil)` でグローバルだけ）、明示の `＊OnChoiceSelectEx`（`choice_select.lua:28`）、`OnSecondChange` などである。
- **影響**: 作者が `・OnMouseDoubleClick` や `・OnMouseMove` を場面のローカルに書いても、演劇の間に当たらない。「その場面だけの反応は、ローカルで書く」（骨子 2.3・`play-script-guide.md:162`）が、イベントによって効いたり効かなかったりする。骨子の原則「場合で処理が変わる設計は、一般化が出来ていない兆候」に反する。
- **提案**: 探し方を `no_entry` でなく、イベントのシーンを探す共通の口に置くことを、`novel-talk-flow` と決める。たとえば、`co_exec` を呼ぶ側すべてが、指摘 6 の形（`current_scene` を今のシーンにした act）で探す。この spec の 11 章の「受ける物」に、対象のイベントの範囲（全部か、`OnMouseClick` だけか）を書き足す。

### 指摘 4（大きい・spec をまたぐ）: つつき・撫での近道は条件を見ないので、`＆＄演劇＝「」` で止められない

- **根拠**: つつきの近道は `SCENE.co_exec_exact` で探し（`mouse.lua:120`）、その中の `SCENE.get_exact` は `SEARCH:search_scene_exact(name, nil)` を変数なしで呼ぶ（`scene.lua:255-259`）。条件は評価されない（brief の 2026-11-03 の申し送りの「`get_exact`・`co_exec_exact` は今も条件を見ない」と同じ）。骨子 2.3 の「演劇の間に動かしたくない、いつもの反応には、条件 `＆＄演劇＝「」` を書く。ファイル属性の行に書けば、そのファイルのグローバルシーン全部に効く」は、`＊つっつき反応さくらHead` には効かない。あわせて、ダブルクリックは、その前に `OnMouseClick` を 2 回送るので、演劇の間は 2 行「進める」が走ってから、つつきの反応が割り込む。
- **影響**: 設計の R6（挙動を変えない）と T4 は、この食い違いを固めてしまう。どの spec も、演劇の間のつつき・撫でを持ち分にしていない。
- **提案**: 演劇の間のつつき・撫での扱い（近道に条件を効かせる、演劇の間は近道を探さない、など）の持ち主を、`novel-talk-flow` と決める。この spec に残すなら、R6 を「トークの間の挙動を変えない」と狭め、演劇の間の振る舞いを要件に足す。決めずに R6 のまま進めるなら、17 章に「骨子の `＆＄演劇＝「」` は近道に効かない」と明記する。

### 指摘 5（大きい・骨子）: ローカルの反応が、右クリックや設定のボタンの全体の入口を隠す

- **根拠**: 骨子 2.6 は、設定の画面への入口を「右クリック・常に出ているボタン・キーボード」とし、`novel-areka-contract` の brief（262 行）はその受け口を `＊OnMouseClick　＆＄ｒ４＝「設定」`・`＊OnMouseClick　＆＄ｒ５＝１` のグローバルシーンで書く。一方、骨子 2.3 ではローカルが先に探され、`play-script-guide.md:179` は「外れた所を押して先へ進んでしまうのを避けたいときは、条件なしの `・OnMouseClick` を足す」と勧める。条件なしのローカルは、右クリックも設定のボタンのクリックも先に拾うので、その場面では設定の画面が開かなくなる。設計の例（6.2・6.3、骨子 2.3 の例も）は `＄ｒ５` を見ないので、ドアを右クリックしても、ドアの反応が走る。
- **影響**: 骨子の 2 つの決まりと、手引きの勧めを、同時に満たせない。作者は、全部のローカルの反応に `＆＄ｒ５＝０` などを足す必要に、後から気づく。
- **提案**: 骨子か手引きに、どちらかを 1 文で決めてもらう。候補: (a) 手引きの勧めを「条件なし」でなく `・OnMouseClick　＆＄ｒ５＝０`（左クリックだけ）にし、設定のボタンは並びの中で場面の反応と名前が重ならないようにする、と書く。(b) 全体の入口は、ローカルより先に探す、と決める（ただし、場合で処理が変わる形になる）。この spec の R5 とマニュアルの節は、決まった形の例で書く。

### 指摘 6（大きい・spec をまたぐ）: `SCENE.search_scoped` に替えると、今のイベントの探し方の L3・L4 が落ちる。今の仕組みで足りる見込みがある

- **根拠**: 今のイベントのシーン探し（`co_exec` → `find_handler`）は、L1〜L5 の 5 段である（`act.lua:396-441`）。L3 は act のメソッド、L4 は `GLOBAL[key]`（`act.lua:419-430`）で、Lua で `GLOBAL.OnMouseClick` を書いたゴーストは、今はこれで動く。設計 8.3・11 章は、演劇の間の探し方を `SCENE.search_scoped(act.req.id, PLAY.scope(), act)` にする前提で、これは `SCENE.search` の 2 段だけなので、L3・L4 を通らない。一方、`find_handler` の L2 は `self.current_scene.__global_name__` の範囲でローカルを先に探す（`act.lua:412-417`）。イベントの act の `current_scene` に今のシーンのグローバルシーンの表（`SCENE.get_global_table(PLAY.scope())`）を置いてから、今の `SCENE.co_exec` を呼べば、ローカル → L3 → L4 → グローバルの順になる。シーンが走れば `init_scene` が `current_scene` を書き直す（`act.lua:225`）ので、走った後にも残らない。骨子 2.3 の「選択肢の飛び先や `＞` が、ローカルを先に探すのと同じ順」（`novel-talk-flow` brief 330 行）にも、こちらの方が字どおりに合う。設計 19.2 は、この案を比べていない。
- **影響**: 演劇の間だけ、Lua の `GLOBAL` のイベント関数が呼ばれなくなる（場合で処理が変わる）。`search_scoped` を足すこと自体が要らない可能性があり、その場合、この spec が Phase 13 に渡す部品は無くなる。
- **提案**: `novel-talk-flow` と、どちらの形にするかを決める。今の仕組みに載せるなら、`SCENE.search_scoped` は `ROUTE.to_scene` の中だけの小さな手助けにするか、選択肢の段をそのまま残す。18 章の 2（この spec を `novel-talk-flow` へ統合して閉じるか）の判断材料に、この指摘を足す。

### 指摘 7（大きい・骨子）: 設定のモードの間の「今のシーン」と探す範囲が決まっていない（設計 17 章の 1 と同じ結論）

- **根拠**: 骨子 1 章は、今のシーンを「イベント……で、最後に着いたシーン」、再生位置を「今のシーンと、そこから数えた行の番号」とする。骨子 2.1 は、設定のモードを「物語の再生位置を動かさない」とする。設定のシーンへイベントで着くと、定義どおりなら今のシーンが替わり、再生位置も動くので、2 つが同時に成り立たない。骨子 2.3 は「演劇の間」としか書かず、`＄演劇` の値も、設定の間について書いていない。設計 6.3 のタイトル画面の書き方（`＊OnBoot　＆再生モード：設定` のローカル `・OnMouseClick`）は、設定の間もローカルを先に探すことを前提にしている。
- **影響**: `novel-talk-flow`・この spec・`hello-novel-sample` が、設定の画面のボタンを別々に読む。読み違えると、タイトルやセーブの画面のボタンを全部グローバルで書くことになり、デスクトップの間にも当たる。
- **提案**: 設計 18 章の 1 の提案どおり、骨子に 1 文を足す（設定の間は「ローカルを探す範囲＝設定のシーン」と「物語の再生位置」が別、`＄演劇` の値は設定の間にどうなるか）。言葉の補いで、決まりは変えない。開発者の判断が要る。

### 指摘 8（大きい・spec をまたぐ）: `novel-checkpoint-rollback` との境界で、早回しの間の `＄ｒ４` についての前提が骨子と食い違う

- **根拠**: 設計 11 章は「早回しの間にクリックのシーンを走らせ直すときも、`＄ｒ４` はローカル変数として控えから戻る」と置く。骨子 2.5 は「早回しの後に、控えの変数とアクター状態を置く」で、早回しの間は控えの変数がまだ無い。また、ロードの多くは、セーブ画面のボタンのクリック（`＄ｒ４＝「slot1」`）から始まる。早回しに、そのイベントの act の変数を使うと、走らせ直すクリックのシーンの中で `＄ｒ４` が `slot1` に見える。加えて、今のシーンがイベントで選んだローカル（`教室_1` の `OnMouseClick_1`）のときは、走らせ直しを名前の検索でなく登録名（`SCENE.co_exec_registered`、`scene.lua:297-303`）で行わないと、条件が今の変数で評価し直され、別の候補を引く。
- **影響**: 条件つきの呼び出しや `＠？` を含むクリックの反応で、ロード後に着く行がずれる。骨子が「受け入れる」と書いたのは乱数のずれだけである。
- **提案**: `novel-checkpoint-rollback` と、(a) 早回しはイベントで選んだシーンを登録名の組で走らせ直す、(b) 早回しの間の act の変数を何にするか（控えを先に置くか、ロードのイベントの写しを消すか）を決める。この spec の 11 章の前提は、それまで「未決」と書き直す。

### 指摘 9（小さい・spec をまたぐ）: `ROUTE.to_scene` は条件漏れを必ず止まるエラーにするので、R3 の「呼ぶ側が決める」と合わない

- **根拠**: 設計 8.2 の `ROUTE.to_scene` は、条件漏れで必ず `FAILURE.raise` する。R3 は「条件漏れを止まるエラーにするかどうかは、呼ぶ側が決める」と書く。`scene-anchor-link` の brief（209 行）は、アンカーの条件漏れを止まるエラーにするか 204 にするかを、まだ議題として持っている。
- **提案**: `scene-anchor-link` が 204 を選んでも使えるよう、`ROUTE.to_scene` に止めるかどうかの引数を持たせるか、R3 を「`search_scoped` の段では、呼ぶ側が決める」と言い直す。今、引数を足す必要は無い（使う人が居ない）。R3 の文面を直すだけでよい。

### 指摘 10（小さい・spec の中）: 「確かめていない」とした数と文字列の比べ方は、コードで分かる

- **根拠**: 設計 17 章の 11 と 19.3 は、`＆＄ｒ５＝１` と Reference の文字列 `"1"` の比べ方を「確かめていない」とする。`scene_cond.rs:49-51` は、半角の十進の数の形の文字列を数として読み（`parse_decimal`、76-84 行）、両方が数なら数で比べる（111-120 行）。`scene_condition_e2e_test.rs:57` などでも `＝１` の条件が使われている。だから `＄ｒ５＝１` は右クリックで真になる見込みである。ただし、数の形の当たり判定の名前（`01` と `1`）は、同じ物として比べられる。
- **提案**: 17 章の 11 を、コードの位置を引いた事実に書き換える。T3（Rust の結合テスト）に `＄ｒ５＝１` を 1 件入れるのは、そのまま残す。数の形の名前の扱いは、マニュアルに書くほどの事ではない（書かない）。

### 指摘 11（小さい・spec をまたぐ）: 近道を足さない判断は、`novel-save-slots` の例と合わせる必要がある

- **根拠**: brief の 2026-11-19 の申し送りは、近道を足すかを「この spec の要件定義で決める」とした。設計は 17 章の 3 で「足さない」を前提に置き、`novel-save-slots` の brief の例（32・125 行の `・slot1`）を読み替えるとした。前提として明示しているのは正しい。ただ、`novel-save-slots` と `hello-novel-sample` の暫定の設計が `・slot1` の形で書かれていれば、食い違いが残る。
- **提案**: まとめのディスカッションで、3 本の例を `・OnMouseClick　＆＄ｒ４＝「slot1」` に揃えるかを確かめる。

### 指摘 12（小さい・spec の中）: 手引きの「条件なしのローカル＋`＆優先`」の形をテストしていない

- **根拠**: `play-script-guide.md:179` と `novel-talk-flow` の brief（407 行）は、条件なしの `・OnMouseClick` と、`＆優先：１` を付けた狙いの反応を、同じローカルの段に並べる形を勧める。設計の T1・T3 は、この形を扱わない。`＆優先` は `SCENE.search` の中で効く（brief の 2026-11-03 の申し送り）ので、`search_scoped` でも効く見込みだが、確かめる所が無い。

### 指摘 13（小さい・spec の中）: 6.2 のさくらスクリプトの例に、決まっていない名前が入っている

## 暫定の要件の読み方（brief との照らし合わせ）

- R1〜R9 は、brief と骨子から読める範囲に収まっている。作った要件は無い。
- 落とした物（シェルの中のバルーンへ書く口・「どの画面の場面か」の 2 案・areka への依頼のうち 2 つ）は、骨子 2.7 と「今のシーン」で置き換わったことを理由に書いており、筋が通る。
