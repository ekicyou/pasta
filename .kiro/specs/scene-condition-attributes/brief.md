## Problem

pasta は if を持たない。値によって出すシーンを変えるには、今は Lua が要る。

- **窓際のぱすたさんの「開示の階段」**: ユーザーとの距離に合わせて、事情を少しずつ明かす。段は 0〜3 である。段を上げる条件は、経験値（`＄＊経験値`）と会えた日数の両方がしきい値以上になることである（数値は仮で、段 1 は 3 日・500、段 2 は 7 日・1500、段 3 は 14 日・4000）。段に届くまで、その段の話をランダムトークの候補に入れたくない。今は Lua の `talk_pick`（ghost_dev の `dic/talk.pasta`）と `ball_next`（`dic/ball.pasta`）で出し分けている。構想は ghost_dev の `project/pasta-in-windows/窓際のぱすたさん/doc/設定_開示の階段.md` にある。
- **イベントの振り分け**（2026-10-21 のヒアリング。両ゴーストでいちばん数の多い要望）: イベントの Reference や保存変数で振り分け、どれにも合わなければ何も返さない（204）。今は「`＊イベント` → `＞lua関数` → `act:call(…)`」の 3 段で書いている。実例は閉じた `call-attribute-filter` の brief の「申し送り（2026-10-21 の discovery「PastaDSL機能ヒアリング」より）」にある（下の「`call-attribute-filter` から引き継ぐこと」）。
- **0.5.0 のノベルのフラグによる分岐**: 2026-10-10 に「分岐は Call の絞り込みで書く」と決めた。この spec が、その場面の側の向きを受け持つ。

## Desired Outcome

場面の側に条件を書けば、条件を満たさない場面は候補に入らない。Lua も if も使わない。

```pasta
＊会話
　＄＊経験値＝＄＊経験値＋１
　＞雑談_

＊雑談_今の部屋　＆＄＊経験値≧500　＆＄＊会えた日数≧3
　ぱすた：この部屋、窓が開かないんですよね。

＊ボール巡回　＆優先：1　＆＄＊経験値≧1500　＆＄＊開示_段2済み＝０
　ぱすた：（段 2 に上がる一本。一度だけ出る）
　＄＊開示_段2済み＝１
＊ボール巡回　＆順番：１０
　＞ボール_繋がってる

＊OnUpdateComplete　＆＄ｒ０＝「changed」
　ぱすた：更新できました。
＊OnUpdateComplete
　ぱすた：新しいものはありませんでした。

＊告白　＆＄＊好感度＝「高」
　さくら：……わたしも、好き。
＊告白
　さくら：ごめんなさい。
```

- 窓際のぱすたさんの `talk_pick` と `ball_next` の開示の部分が、DSL だけで書ける。
- マニュアルとスキルの `references/` が、書き方を載せる。`pasta_check validate`、LSP と VSCode の着色が追従する。

## Approach

### 決まったこと 1: 書き方（2026-10-29、ghost_dev の「ぱすた開発」セッションで開発者と合意。同じ日にこのセッションで開発者が確かめた）

記号で役割を分ける。

- **宣言** `＆名前：値`: この場面はこうだ、を書く。エンジンや演出が読む。今の意味のまま（`＆重み：5`・`＆順番：3`・`＆曲：夕焼け`）。
- **条件** `＆＄変数 比較演算子 値`: こういうときだけ候補に入る、を書く（`＆＄＊経験値≧4000`・`＆＄＊好感度＝「高」`・`＆＄ｒ０＝「changed」`）。
- **フラグ** `＆＄変数` だけ: 値が立っているときだけ候補に入る（`＆＄＊初回待ち`）。
- 決まりは「`＄` で始まる属性は条件」の 1 本だけを足す。`＄` の有無で、エンジンの名前（重み・順番・曲…）と作者の変数が取り合いにならない。
- 変数はほかの場所と同じ書き方にする。`＄名前` はローカル変数、`＄＊名前` はグローバル（保存）変数。属性の中だけ `＄` をグローバルの略記にすることはしない（日時・Reference・呼ぶ側で入れた変数など、ローカル変数で絞りたい場面が多い）。
- `：` を全部 `＝` に変える案は採らない（`＆重み＝5` が宣言か条件か読めなくなる）。比較の `＝` は条件の側でだけ使う。
- 条件は場面の側に書く。呼ぶ側は今までどおり `＞雑談_` だけ。ノベルの分岐も `＊告白＆＄＊好感度＝「高」` ＋ `＞告白` で書く。

### 決まったこと 2: 意味（2026-10-29 開発者の決定。推奨案を全部採った）

- **フラグの「立っている」**: 値があり、0 でも空文字列でもないこと。保存変数に入った Lua の真偽値は、true を 1、false を 0 として扱う。真偽値を `≧` などで数と比べても、1 か 0 として比べるだけで、失敗表記も注意も出さない。
- **右辺**: 書いた値（数・「文字列」）だけ。変数は書けない。変数どうしを比べる形（`＆＄ｒ０＝＄ｒ１`。OnShellChanging）は、使う人の事例がもう 1 つ出るまで作らない（ゴースト側も今の Lua で困らない）。
- **演算子**: `≧ ≦ ＞ ＜ ＝ ≠` と、半角の `>= <= > < = !=` の 6 種類。属性の中だけ、`＞`（Call の印）と `＝`（代入の印）を比較として読む。
- **比べ方**: 両辺が数なら数として比べる。それ以外は文字列として比べる（`＝`・`≠`）。数として読めない値を大小で比べたときは、満たさないものとしてログに注意を出す。
- **値の無い変数**: 数の比較では 0、文字列の比較では空文字列とみなす。失敗表記も警告も出さない（初回の起動では、変数が無いのが普通である）。
- **打ち消し**: 新しい記号は作らない。「まだ立っていない」は `＆＄＊開示_段2済み＝０` と書く（値の無い変数と false は 0 とみなすため）。
- **評価**: 候補を選ぶたびに、そのときの値で評価する。条件を複数並べたら、全部を満たすときだけ候補に入る（かつ）。「または」は同じ名前のシーンを 2 つ書けば足りる。チェイントークの続きは選び直さないので、途中で条件が変わっても続きは切れない。
- **候補がゼロのとき**: 名前に合うシーンはあるが条件で全部落ちたら、何も出さずに Call の次の行へ進む（素通り）。イベントや OnTalk なら中身が空なので 204 になる。名前に合うシーンが元から無いときは、今までどおり `【シーンが見つからない：＞…】` を出す（書き間違いは見つかるままにする）。
- **シャッフルとの関係**: 候補の袋は、条件と関係なく名前ごとに作る。引くときに条件を満たさない札は、消費済みにせず袋に残して飛ばす。条件を満たした札は、その時点から今の巡に混ざる（段が上がった直後の話が、一巡の終わりまで待たされない）。候補の控えのキーに、変数の値を入れない。
- **`＆優先：数`**（宣言の属性。この spec に入れる）: 条件を満たした候補のうち、優先のいちばん高いものだけから選ぶ。書かなければ 0。残った候補の中で、`scene-pick-modes` の `＆重み`・`＆順番` を使う。これと打ち消しと本文の代入で、一度だけの話が Lua なしで書ける。ノベルの「どれにも当たらなかったときの場面」も、条件の無い優先 0 の場面として書ける。
- **効く範囲**: 名前で候補を選ぶ所すべてに効かせる。
  - Call の前方一致（グローバルシーンもローカルシーンも。`・締め　＆＄＊経験値≧4000`）
  - `＞＞` の完全一致（`scene-exact-match`）
  - イベントからシーンを起こすとき（`＊OnBoot`・`＊OnTalk`・時報など）
  - 選択肢の飛び先を探すとき
- **効かせない所**:
  - 外から 1 本を名指しする再生（`OnPastaScene`、撫で・つつきの近道。`SCENE.co_exec_exact`・`co_exec_registered`）
  - 選択肢の行そのものを隠すこと（表示の絞り込み）
  - 単語
- **イベントの自動転記**（この spec に取り込む）: イベントのシーンは本文の 1 行目より前に選ばれるので、本文の `＞transfer_req_to_var` では間に合わない。イベントのシーンを選ぶ前に、Reference と日時をローカル変数へ転記する。ロードマップの Direct Implementation Candidates の「イベントのシーンでの Reference の自動の転記」を吸収して閉じる。Call の時点で選ぶシーン（`＊OnBoot` の本文で転記してから `＞起動の挨拶`）は今でも効くが、イベントのシーンそのものの条件（`＊OnBoot＆＄hour≧5`）が黙って外れ続ける落とし穴を残さないために入れる。
- **書き間違いの検査**: `pasta_check validate` が注意を出す。対象は、条件に書いた `＄＊` の変数のうち、辞書のどこでも代入していないもの（`＄＊経験知≧4000`）。Lua の中の代入は見えないので、誤りにはしない。ローカル変数と、エンジンが入れる変数は見ない。
- **ログ**: どの候補がどの条件で外れたかを、trace のログに出す（しきい値の調整で、`OnPastaSetSaveVariable` で値を書き換えて試すときに追うため）。
- **spec の置き方**: この spec を新しく立て、`call-attribute-filter`（呼ぶ側の `＞シーン＆k＝v`）は統合して閉じた（開発者の決定）。`scene-pick-modes`（選び方）とは別の spec のまま。
  - **閉じた理由**: 呼ぶ側の条件と場面の側の条件は、どちらも「名前で候補を集め、条件で絞り、1 つ選ぶ」で、条件を書く場所が違うだけである。場面の側の条件だけで、呼ぶ側の書き方の代わりになる。
    - 呼び出されたシーンは呼び出し元と同じローカル変数を読み、条件は選ぶときの値で評価する。だから、呼ぶ前にローカル変数を入れれば、呼ぶ場所ごとに同じ束を違う条件で絞れる。
    - 条件にグローバル変数を書けば、どこから呼んでも常に効く。仕組みは 1 つで、書く変数の種類で効き方が変わる。
    - 書き方が 2 つあると作者が迷い、両方に条件があるときの合わせ方の決まりも要る。
    ```pasta
    ＊告白　＆＄気分＝「高」
    　さくら：……わたしも、好き。
    ＊告白　＆＄気分＝「低」
    　さくら：ごめんなさい。

    ＊放課後
    　＄気分＝「高」
    　＞告白
    ＊雨の日
    　＄気分＝「低」
    　＞告白
    ```
  - 呼ぶ側に条件を書く書き方は、ローカル変数では書けない事例が出るまで作らない。条件を評価するときに呼び出し元のローカル変数が見えることは、要件で確かめて受け入れ条件にする。

### 要件フェーズで決めること

- **受け入れ条件に入れること**（2026-10-29、ゴースト側の依頼）: OnTalk の別名「会話」は完全一致だけで、`＊会話〜` は前方一致の候補にならない。窓際のぱすたさんは `＊会話` 1 本で経験値を足し、`＞雑談_` の前方一致で選ぶ。条件の属性が、この「`＊会話` → `＞雑談_` の前方一致」の経路で効くことを、受け入れ条件にする。
- **受け入れ条件に入れること**: 条件を評価するときに、呼び出し元のローカル変数が見える（呼ぶ前に `＄気分＝「高」` を入れて `＞告白` を呼ぶと、`＊告白　＆＄気分＝「高」` が選ばれる）。
- 条件をどこで評価するか。変数は Lua の側に、候補の控えは Rust の側にある。候補の並びを Lua へ返して Lua で絞るか、値を Rust へ渡すか。
- 属性の中の `＞`・`＝` と、ほかの記号（Call の `＞`、式の連結の `＆`、比較の無い文法）との見分けを、文法でどう書くか。全角と半角の受け付け。
- 数の値の読み方（全角の数字 `５` を数として読むか）と、ファイルの先頭に書いた条件・`＆優先` をシーンが受け継ぐか。どちらも `scene-attribute-store` の規則に従う。
- `＆優先` の英語の別名（`scene-pick-modes` の `重み`/`weight`・`順番`/`index` に合わせる）と、不正な値（数でない）の扱い（`＆重み` に合わせて読み込みエラーにする案）。
- `＆優先` で残った候補に、`＆順番` の有るものと無いものが混ざったときの検査（`scene-pick-modes` の「混ざったとき」の規則を、優先で残った中に当てる）。
- 自動転記の範囲（どのイベントで、どの変数を）と、入門の 7 段目（`getting-started/07-greeting.md`・段階辞書 `dic/07-greeting.pasta`・`STAGES.md`）の書き直し。
- 条件で全部落ちたときに、ログに何を出すか（素通りの記録を trace に出すか）。
- `pasta_check validate` の注意の種類の名前と、省く理由（`skip_reasons`）があるときに走らせるか（`call-attribute-filter` の申し送りでは「空のときだけ走らせる」を推奨していた）。
- `pasta_core` の公開の関数 `resolve_scene_id`・`find_scene`（本番では使われていない）を消すか、絞り込み条件の新しい形に合わせて残すか（semver に効く）。

## Existing Spec Touchpoints

- **Extends**: なし（`call-attribute-filter` を統合して閉じた）
- **Adjacent**:
  - `scene-pick-modes`: 候補の袋と控えを共有する。同じウェーブに置かない。先に入る側が袋の形を決め、後の側が合わせる。
  - `scene-exact-match`: 完全一致の候補選びにも効かせる。`act:call` の 3 つ目の引数 `attrs` を絞り込みのために空けておく約束は、呼ぶ側の条件を作らないので要らなくなった。

  - `novel-variable-scope`: `＄＊` の保存の範囲が分かれたら、条件の変数もその書き方に従う。

## Constraints

- 条件を書かないシーンの選び方は、今のシャッフル＆順次消費のまま変えない。
- 宣言の属性（`＄` で始まらないもの）の意味を変えない。
- マニュアルが文法の唯一の権威。挙動を変えたら同じ変更でマニュアルを更新し、`node book/tools/gen-skill-refs.mjs` で生成スキルを再生成する。
- `act.lua` は 837 行で 1,000 行に近い。足すなら別のファイルに分ける。
- 規模は 14〜18 タスクの見込み。内訳は、文法と構文木 2、評価と絞り込み 3〜4、袋と控え 2、優先 1、自動転記 1〜2、検査とログ 1〜2、着色 1、マニュアルと生成 2、テスト 1〜2。

閉じた `call-attribute-filter` の brief は、git の `1c88e1e5` の `.kiro/specs/call-attribute-filter/brief.md` で読める。要件の材料として、次を引き継ぐ。行番号は 2026-10-23 の再測定の値である。
