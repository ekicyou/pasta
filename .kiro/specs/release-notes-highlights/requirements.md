# Requirements Document

## Project Description (Input)

詳しい経緯・測定・決定は、同じフォルダの `brief.md`（2026-10-11 の discovery）にある。ここには要点だけを写す。

GitHub のリリースの本文が、前の版からのコミットの件名を全件並べた一覧になっている（v0.3.8 は 57 行・3,842 文字）。件名は開発者向けの言い回しで頭に spec 名が付き、利用者に関係のない内部の作業も同じ一覧に並ぶ。読む人（ゴーストを作る人・pasta を使ってみようとする人）は、その版で何が良くなったのかを本文から読み取れない。

リリースの本文を、その版の見どころを日本語で紹介する文章に変える。

- 見どころをリポジトリのファイル（`doc/release-notes/vX.Y.Z.md`。版ごとに 1 ファイル）として書き、リリース CI がそれを本文に使う。
- 見どころは Claudia（令嬢）の口調で書く。spec 名を載せない。見出しの末尾に、元になった PR の番号を付ける。
- すべての変更を並べた詳しいリリースノートは、Markdown のファイル（`release-notes-vX.Y.Z.md`）として Assets に添付する。本文から、その添付へたどれる。詳しいリリースノートにも spec 名を載せない。
- 見どころのファイルは、リリースの手順（`release` スキル。`/release`）が版を上げるコミットで書く。版の更新の PR に入るので、公開する前に読めて、git に残る。
- 見どころの無い（または空の・版の合わない）リリースタグでは、リリース CI が何も公開する前に止まる。
- 公開済みの v0.3.8 のページも、同じ形（見どころの本文と、詳しいリリースノートの添付）に直す。それより前の版は触らない。
- 今の方式を書いている文書（`tech.md`・`RELEASE.md`・`pasta-check` のスキル）を更新する。
- ノートを作るスクリプトに、動かして確かめられる検査を 1 つ足す。

## Introduction

本ドキュメントは、pasta の GitHub のリリースのページ（<https://github.com/ekicyou/pasta/releases>）の本文を、コミットの件名の一覧から、その版の見どころを紹介する文章へ変えるための要件を定義する。

読む人は、ゴーストを作る人と、pasta を使ってみようとする人である。本文には、その版で特に注目に値する内容を、Claudia（令嬢）の口調で数件だけ書く。すべての変更を並べた一覧は、詳しいリリースノートとして Assets に添付し、本文からたどれるようにする。

見どころは、人（リリースの手順を実行するエージェント）が書く文章である。機械は、文章があること・空でないことだけを見る。文章は版を上げるコミットに入るので、公開の前に PR で読めて、git に残る。

用語:

- **見どころのファイル**: 版ごとに 1 つ置く、リリースの本文のもとになる Markdown のファイル（`doc/release-notes/vX.Y.Z.md`）。
- **見どころ**: 見どころのファイルの中の、見出しを 1 つ持つ紹介の単位。
- **動きが変わる点**: その版へ上げると、これまでの辞書・スクリプト・設定の動きが変わる変更（破壊的変更）。
- **詳しいリリースノート**: 前のリリースタグからの変更を並べた一覧。Assets に `release-notes-vX.Y.Z.md` として添付する。
- **内部の作業**: 利用者に届く配布物とマニュアルの内容を変えない、開発の進め方のための変更（spec の起票と文書・ロードマップと steering・スキルと開発の手順の文書・版の更新のコミット）。
- **リリース CI**: リリースタグの push を契機に動く GitHub Actions のワークフロー（完了した `release-ci` の成果物）。
- **リリースの手順**: `release` スキル（`.claude/skills/release/` の `SKILL.md`・`procedure.md`・`scripts/`）。`/release` のたびに、エージェントが実行する。常駐 spec だった `release-workflow` の手順を、2026-10-11 にスキルへ移したものである（PR #105）。
- **配布物**: `pasta.dll.zip`・`hello-pasta.nar`・`pasta-vscode-X.Y.Z.vsix` の 3 つ。

## Boundary Context

- **In scope**:
  - 見どころのファイルの置き場所・名前・書き方の決まり。
  - リリース CI の、見どころの検査（公開の前に止まる）、詳しいリリースノートの生成と添付、本文の組み立て。
  - 詳しいリリースノートの件名の整形（接頭辞を外す）と、内部の作業を載せないこと。
  - リリースの手順（`release` スキル）への、見どころを書く手順とその確かめ方の追加。版の更新のコミットに入るファイルが 1 つ増えることに伴う、手順の文書の整合。
  - 今の方式（コミット履歴から本文を作る）を書いている文書の更新。
  - 詳しいリリースノートを作る仕組みの、動かして確かめられる検査。
  - 公開済みの v0.3.8 のページの直し（1 回きり）。
- **Out of scope**:
  - v0.3.7 より前の公開済みのリリースの書き直し。
  - 見どころの材料を、spec の完了のたびに溜めておく仕組み（書く人は、リリースのときに前のリリースタグからの変更を読んで選ぶ）。
  - マニュアル（`book/`）に更新履歴のページを足すこと。
  - コミットの件名の書き方の決まりを変えること。件名の本文の書き換え（接頭辞を外すだけで、言い回しは直さない）。
  - 英語の本文。
  - crates.io・Marketplace への公開の段、配布物のビルド、版の決め方、タグの打ち方。
  - マニュアルの執筆規約（`book/AUTHORING.md`）の書き換え（口調の定義を参照するだけである）。
  - 公開した後の本文の直し方（公開済みの Release の本文は、リリース CI が触らない。直すときは、開発者の指示で別に行う）。
  - リリース CI が、見どころの文章の中身（口調・件数・リンク・spec 名の有無）を検査すること。
- **Adjacent expectations**:
  - 完了した `release-ci`: 要件 6.6〜6.9（ノートの作り方）・6.2（添付が 3 つであること）・6.4（公開済みで添付がそろっていれば飛ばすこと）のうち、ノートの中身と添付の数を、本仕様が上書きする。完了した spec の文書は書き換えない。公開先ごとの結果の報告（`published`・`skipped`・`failed`・`not-run` と Release の URL）は、今のまま保つ。
  - `release` スキル（`.claude/skills/release/`）: 本仕様が、その `SKILL.md`・`procedure.md`・`scripts/` を書き足す。リリースの実行そのものは、このスキルが行う。
  - 完了した spec `release-workflow`（`.kiro/specs/completed/release-workflow/`）: 要件と設計の経緯の記録である。本仕様は書き換えない。
  - `book/AUTHORING.md` 第 1 節: Claudia の口調の定義と、「技術的な正確さを最優先する」鉄則の出どころ。
  - 出典: Claudia は、ponapalt さんのゴースト「悪役令嬢クローディア」（<https://github.com/ponapalt/claudia>。Unlicense）の人物を借りている。
  - areka のリポジトリの `areka-P0-release-notes-highlights`: 置き場所・口調・検査の範囲の決定をそろえてある。仕組みの違いは合わせない。
  - `pasta-check-dic-validate`: `release.yml` の `pasta_check` の公開の段を触る場合がある。本仕様が触るのはタグの検査の段と GitHub Release の段なので、後から入る側が合わせる。
  - 席: リリースの実行中は、`release.yml` と補助スクリプトを触る本仕様の変更を main に入れない。
  - スキルの編集: `.claude/skills/` の下（`release` スキルの 3 種のファイルと、`pasta-check/SKILL.md`）の編集は、開発者の許可が要る。

## Requirements

### Requirement 1: 見どころのファイルと書き方の決まり

**Objective:** As a リリースのページを読む人, I want その版で何が良くなったのかを、短い紹介の文章で読みたい, so that コミットの一覧を追わなくても、上げる価値と気を付ける点が分かる

#### Acceptance Criteria

1. The repository shall 見どころのファイルを、版ごとに 1 つ、`doc/release-notes/vX.Y.Z.md`（`X.Y.Z` はその版）に置く。
2. The repository shall 見どころの書き方の決まり（本要件の 3〜10）を 1 つの文書として持ち、リリースの手順からその文書を参照できるようにする。
3. The 見どころのファイル shall 日本語の Markdown で書き、GitHub のリリースの本文としてそのまま表示できる形にする。
4. The 見どころのファイル shall 見どころを 3〜5 件載せる。直しだけの版では 1〜2 件でよい。
5. The 見どころのファイル shall 見どころごとに見出しを 1 つ持ち、見出しの末尾に、元になった PR の番号を `(#83)` の形で付ける。複数の PR にまたがる見どころは `(#63, #77)` の形で並べる。PR を通らなかった変更には、番号を付けない。
6. Where その版に動きが変わる点があるとき, the 見どころのファイル shall 動きが変わる点をすべて載せる。
7. The 見どころのファイル shall 動きが変わる点を、普通の文体の箇条書きで書き、PR を通った項目の末尾に PR の番号を付ける。
8. The 見どころのファイル shall 紹介の文章を、Claudia の口調（`book/AUTHORING.md` 第 1 節の定義）で、Claudia 1 人の語りとして書く。アンソニーを出さない。
9. The 見どころのファイル shall 語り手が「Claudia」と名乗り、最初に名乗る 1 か所だけを、出典（<https://github.com/ponapalt/claudia>）へのリンクにする。出典の断り書きを別に書かない。
10. The 見どころのファイル shall spec 名と、コミットの種類・スコープの接頭辞（`feat(…):` など）を載せない。

### Requirement 2: 見どころの無いリリースタグを公開の前に止める

**Objective:** As a 開発者, I want 見どころを書き忘れたリリースタグが、何も公開されないうちに止まってほしい, so that 本文の無いリリースや、一部だけ公開されたリリースが出ない

#### Acceptance Criteria

1. When リリースタグが push されたとき, the リリース CI shall タグの検査の段で、タグが指すコミットに、タグの版の見どころのファイルが在り、空でないことを確かめる。
2. If タグの版の見どころのファイルが無いとき（別の版のファイルしか無い場合を含む）, the リリース CI shall 警告で続けずに失敗し、どの公開先にも公開しない。
3. If タグの版の見どころのファイルが空であるとき（空白と改行だけの場合を含む）, the リリース CI shall 警告で続けずに失敗し、どの公開先にも公開しない。
4. When 見どころの検査で失敗したとき, the リリース CI shall 確かめたファイルのパス・失敗の理由・どの公開先にも公開していないことを、実行の結果に示す。
5. The リリース CI shall 見どころの検査を、在ること・空でないこと・版が合うこと（ファイルの名前の版がタグの版と同じであること）までにとどめ、文章の中身を検査しない。
6. The リリース CI shall タグの検査の、今ある検査（タグの形・版の一致・main からの到達）の合否と報告を変えない。

### Requirement 3: 詳しいリリースノート

**Objective:** As a リリースのページを読む人, I want その版のすべての変更を、読みやすい件名の一覧でも確かめたい, so that 見どころに載らなかった直しが自分に関係するかを調べられる

#### Acceptance Criteria

1. When リリース CI が GitHub Release を作るとき, the リリース CI shall 1 つ前のリリースタグからリリースタグまでのコミット（マージコミットを除く）から、詳しいリリースノートを Markdown で作る。
2. The 詳しいリリースノート shall 変更を種類ごとの見出し（新機能・不具合の修正など）に分けて並べ、変更の無い見出しを出さない。
3. The 詳しいリリースノート shall 件名から、コミットの種類とスコープの接頭辞（`feat(scene-name-alias): ` など）をすべて外して載せる。スコープが spec 名でもクレート名でも、同じに外す。
4. The 詳しいリリースノート shall 件名の末尾の PR の番号（`(#83)`）を残す。
5. When 件名に破壊的変更の印（接頭辞の `!`）が付いているとき, the 詳しいリリースノート shall 接頭辞を外した後も、その変更が破壊的変更であることが分かる形で載せる。
6. The 詳しいリリースノート shall 内部の作業を載せない。
7. The repository shall 何を内部の作業とみなすかの決まりを、文書に書いて持つ。
8. If コミットの件名が、決まった形（種類と、省略できるスコープ）でないとき, the 詳しいリリースノート shall その変更を黙って落とさず、件名をそのまま、その他の変更の見出しに載せる。
9. Where 1 つ前のリリースタグが在るとき, the 詳しいリリースノート shall 末尾に、全件を比べられる Full Changelog のリンクを載せる。
10. If 載せる変更が 1 件も無いとき, the リリース CI shall 失敗にせず、載せる変更が無いことを書いた詳しいリリースノートを作る。
11. If 詳しいリリースノートを作れないとき（タグが見つからない・履歴を読めないなど）, the リリース CI shall GitHub Release を作らず、失敗として報告する。
12. When 開発者またはエージェントが、リリースタグを打つ前に手元で一覧を求めたとき, the 詳しいリリースノートを作る仕組み shall 1 つ前のリリースタグから指定したコミットまでの変更を、タグが無くても同じ形で出す。

### Requirement 4: GitHub Release への載せ方

**Objective:** As a リリースのページを読む人, I want 本文で見どころを読み、そこから詳しいリリースノートへ進みたい, so that 知りたい深さに合わせて読める

#### Acceptance Criteria

1. When リリース CI が GitHub Release を作るとき, the リリース CI shall タグが指すコミットの見どころのファイルの内容を、書き換えずに本文の先頭に置く。
2. The リリース CI shall 本文の末尾に、詳しいリリースノートの添付へたどれるリンクと、そこに載せた変更の件数を足す。
3. The リリース CI shall 詳しいリリースノートを、`release-notes-vX.Y.Z.md` の名前で、3 つの配布物とあわせて添付する（添付は 4 つになる）。
4. The リリース CI shall 4 つの添付がそろってから、GitHub Release を公開する。
5. The リリース CI shall GitHub Release の題名（`pasta vX.Y.Z`）を変えない。
6. When リリース CI が再実行され、GitHub Release が公開済みで 4 つの添付がそろっているとき, the リリース CI shall GitHub Release の作成を飛ばし、題名・本文・添付を触らない。
7. When リリース CI が再実行され、GitHub Release に添付が足りないとき, the リリース CI shall 足りない添付だけを補う。
8. The リリース CI shall 公開済みの GitHub Release の添付を、削除も上書きもしない。
9. The リリース CI shall GitHub Release の結果の報告（`published`・`skipped`・`failed` と理由・URL）を、今と同じ形で出す。

### Requirement 5: リリースの手順が見どころを書く

**Objective:** As a 開発者, I want リリースのたびに、エージェントが見どころを書いて版の更新と一緒に main へ入れてほしい, so that 書き忘れが無く、文章が公開の前に PR で読めて git に残る

#### Acceptance Criteria

1. When リリースする版が確定したとき, the リリースの手順 shall 1 つ前のリリースタグから main の先頭までの変更を、詳しいリリースノートと同じ形の一覧で手元に出し、見どころの材料にする。
2. When 材料の一覧を出したとき, the リリースの手順 shall 書き方の決まり（Requirement 1）に従って、その版の見どころのファイルを書く。
3. When 見どころのファイルを書いたとき, the リリースの手順 shall 次のことを確かめる。(1) ファイルがその版の名前で在り、空でない。(2) 「Claudia」の名前を出典へのリンクにした箇所が、ちょうど 1 つ在り、それより前に、リンクにしていない「Claudia」が無い。(3) 見出しと箇条書きに付けた PR の番号が、すべて材料の一覧に在る。(4) 材料の一覧に破壊的変更があるとき、その PR の番号がすべてファイルに在る。(5) spec 名が入っていない。
4. If 確認のいずれかが通らないとき, the リリースの手順 shall 見どころのファイルを直して確かめ直し、すべて通るまで版の更新のコミットを作らない。
5. If 見どころのファイルを直しても確認が通らないとき, the リリースの手順 shall 版の更新と見どころのファイルを取り消し、通らない確認を示して作業を止める。
6. When 確認がすべて通ったとき, the リリースの手順 shall 版の表記の更新と見どころのファイルだけを含む、1 つのコミットを作る。
7. When 版の更新のコミットを作ったとき, the リリースの手順 shall 見どころのファイルの全文を開発者に示し、承認を求めずに先へ進む。
8. The リリースの手順 shall リリースタグを、タグの版の見どころのファイルが在って空でないコミットにだけ付ける（リリース CI が検査する条件を、push の前に満たす）。
9. If main の版にリリースタグが無く、その版の見どころのファイルが main に無いとき, the リリースの手順 shall リリースタグを作らずに止まり、見どころのファイルを PR で main へ入れることを求める。
10. When 作業ブランチの main に無い内容が、版の表記の更新と見どころのファイルを含む版の更新のコミットだけであるとき, the リリースの手順 shall それを途中からの再開として扱い、見どころの確認（本要件の 3）をやり直したうえで、main への統合から続ける。
11. The リリースの手順 shall 版の更新の PR に入る変更が、版の表記の更新と見どころのファイルだけであることを確かめてから、作業ブランチを push する。

### Requirement 6: リリースの手順の文書の整合

**Objective:** As a リリースの手順を実行するエージェント, I want 手順の文書のどこを読んでも、版の更新に入るファイルの数と確かめ方が同じであってほしい, so that 古い記述に従って、見どころを落としたり、見どころのあるコミットを異常として止めたりしない

本要件は、本仕様の実装の中で 1 度だけ行う。直す相手は、`release` スキル（`.claude/skills/release/`）である（2026-10-11 に、リリースの手順が常駐 spec `release-workflow` からこのスキルへ移ったので、相手を書き直した）。

#### Acceptance Criteria

1. The 文書 shall `release` スキルの `SKILL.md` の、版の更新に入るファイルを「5 ファイル」と書いている箇所（実行の約束・版の更新の段・統合の段・「このスキルを直すとき」）、タグを付ける前の検査の行数を書いている箇所、リリースの実行が版の表記のほかに文書を変えない旨の箇所を、見どころのファイルを含む形に合わせる。
2. The 文書 shall `release` スキルの `procedure.md` の、版の更新に入るファイルを「5 ファイル」と書いている箇所（再開の判定・版の更新の段の確認と取り消しとコミット・統合の段の確認）と、タグを付ける前の検査の行数・定型コマンドの本数を書いている箇所をすべて、見どころのファイルを含む形に合わせる。
