# Requirements Document

## Project Description (Input)
pasta DSL の編集支援は、今は VS Code 拡張 `ekicyou.pasta-vscode`（v0.5.2）だけが持っている。ゴーストの作者の中には「VS Code を入れたくない」人がいて、その人たちは色も診断も無いテキストエディタで `.pasta` を書いている。書き間違いは SSP で読み込むまで分からない。

VS Code を使わずに `.pasta` を書ける、インストーラの要らない Windows のアプリ `pasta-recipe` を作る。exe 1 つを置き、ゴーストのフォルダを exe にドラッグドロップすると、そのゴーストの `ghost/master` を開く。左のツリーに `ghost/master` のフォルダとファイルと、`.pasta` の下にグローバルシーン ＞ ローカルシーン が並び、押すとその見出しへ飛ぶ。`.pasta` には VS Code 拡張と同じ色と同じ診断が出て、コードブロックの中の Lua にも色が付く。`.lua` も開いて編集・保存できる。ゴースト全体の検査の結果も、VS Code 拡張と同じものが一覧に出る。最近開いたゴーストは残り、次の起動で選び直せる。

包み方（Tauri 2 ＋ Vite ＋ Monaco Editor）・解析を Rust の側で `pasta_lsp`・`pasta_check` を直接呼んで行うこと・置き場所 `editors/recipe/`（`src-tauri` は別の Cargo ワークスペース）・配布は Windows x64 の `pasta-recipe.zip` だけ、は discovery で決まっている。詳しくは `brief.md`。

## Introduction

VS Code を入れていないゴーストの作者が、`.pasta` を、VS Code 拡張（以下「拡張」）と同じ色と同じ診断の下で書けるようにする、単独で動く編集のアプリ（以下「アプリ」。名前は `pasta-recipe`・exe は `pasta-recipe.exe`）を作る。

- アプリは、exe 1 つを置くだけで動く。インストールも、VC++ の再頒布可能パッケージも要らない。Windows に入っている Microsoft Edge WebView2 ランタイムを使う。
- アプリは、ゴーストの `ghost/master` を 1 つ開き、その中のファイルとシーンをツリーに出し、`.pasta`・`.lua` をタブで開いて編集・保存する。
- アプリの色分け・書きながらの診断・ゴースト全体の検査は、拡張と同じ解析器・同じ検査の核から出る。同じ文書・同じゴーストなら、拡張と同じ結果になる。
- アプリは、ゴーストを動かさない（シーンの実行・SHIORI のリロード・変数の表示は `pasta-recipe-dev-actions` が後から足す）。

例（`C:\ghosts\hello` がゴーストのフォルダ）:

```
hello\                      ← これを exe にドラッグドロップする
  ghost\master\             ← アプリはここを開く
    dic\
      挨拶.pasta            ← ツリー: 挨拶.pasta ＞ 挨拶 ＞ 朝
    scripts\
      main.lua
    pasta.toml
```

`挨拶.pasta` が次のとき、ツリーの「朝」を押すと、アプリは `挨拶.pasta` をタブで開き、2 行目の `・朝` へカーソルを移す。

```
＊挨拶
  ・朝
    さくら：おはよう
```

## Boundary Context

- **In scope**
  - exe 1 つの配布と起動（起動の引数・窓へのドロップ・フォルダを選ぶダイアログ・最近開いたものの一覧からゴーストを開く）
  - `ghost/master` のファイルとシーンのツリー、タブでの編集・保存（未保存の印・閉じるときの確かめ）
  - `.pasta` の色分け（コードブロックの中の Lua を含む）と書きながらの診断、`.lua` の色分けと編集
  - ゴースト全体の検査の一覧
  - 外でファイルが変わったときの扱い
  - リリース CI での配布物 `pasta-recipe.zip` の作成と中身の検査、リリースの添付の一覧の更新、第三者の表示
  - マニュアルの「VS Code を使わずに書く」章
  - アプリのテスト（ネイティブの側の処理と、解析の結果をエディタの形に写す処理）
  - ツリーからのファイル・フォルダの作成と名前の変更
  - 2 つ目の起動を今の窓へ渡す（単一インスタンス）
  - ゴースト全体の検査のファイル集めを `pasta_check` のライブラリへ移し、`pasta_check validate` とアプリで共有する（`pasta_check validate` の振る舞いは変えない）
- **Out of scope**
  - シーンの実行・SHIORI のリロード・変数の表示と書き換え（`pasta-recipe-dev-actions`）
  - 補完・ホバー・定義へ移動・参照の検索・シンボルの名前の変更・ゴースト全体の文字の検索
  - `.lua` の構文の診断とステップ実行
  - mac・Linux・arm64・x86 の配布、インストーラ、コード署名、自動更新
  - git・ターミナル・拡張機能・複数の窓
  - `.nar` の作成（`pasta_check release` に任せる）
  - アプリが Windows の設定（レジストリ）に書き込むこと（ファイルの関連付けや「送る」への登録をアプリが行うこと。作者が Windows の機能で行えば、要件 2.1・2.6 の決まりでそのまま開く）
  - ツリーからのファイル・フォルダの削除（取り返しが付かないので、エクスプローラーのごみ箱に任せる）
- **Adjacent expectations**
  - 解析器（`pasta_lsp`）は、色分けのトークン・診断・シーンの並び（`vscode-scene-outline-play` が足した `scenes`）を、拡張に返すのと同じ中身・同じ座標（0 から数えた行・UTF-16 の列）で返す。アプリはそれを写すだけで、解析の中身もシーンの取り出しも直さない。形を変えたいときは解析器の側の spec で行う。
  - 検査の核（`pasta_check` のライブラリ）は、ゴーストのファイルの一覧と中身から、`pasta_check validate` と拡張のゴースト全体の検査と同じ結果を返す。ファイル集め（最上位の `profile` とシンボリックリンクを飛ばす・UTF-8 の判定）は、この spec でライブラリの opt-in の機能へ移し、`pasta_check validate` とアプリが同じ処理を呼ぶ。移す前に今の振る舞いを試験で固定し、WASM 向けの機能なしのビルドを壊さない。
  - 拡張の振る舞い・ビルド（WASM）・CI は変わらない。拡張のファイルは、色分けの種類の凡例を 1 か所にするとき以外は触らない。
  - ルートの Cargo ワークスペースの検査（`cargo test --workspace`・依存の検査）の対象は増えない。
  - `pasta-recipe-dev-actions` が、このアプリのツリー（▶）・エディタ・ネイティブの側に、ゴーストを動かす機能を足す。この spec はその足し場所を塞がない。

## Requirements

### Requirement 1: 配布物と起動

**Objective:** As a VS Code を入れたくないゴーストの作者, I want exe 1 つを置くだけで編集のアプリが動くこと, so that インストールや追加の部品なしに `.pasta` を書き始められる

#### Acceptance Criteria

1. The アプリ shall 1 つの exe ファイルとして配られ、インストールの手順なしに、置いた場所から起動する。
2. The アプリ shall Windows 10（1803 以降）・Windows 11 の x64 で、VC++ の再頒布可能パッケージを入れていない環境でも起動する。
3. The アプリ shall 画面の部品・着色の文法・作業用のスクリプトをすべて exe に含み、ネットワークに接続せずに、この spec のすべての機能が動く。
4. If 起動した環境に Microsoft Edge WebView2 ランタイムが無い, the アプリ shall 黙って終わらず、WebView2 ランタイムが要ることと入手先を伝えるメッセージを出してから終わる。
5. When 引数なしで起動した, the アプリ shall 最近開いたゴーストの一覧・フォルダを選ぶ操作・ドロップで開けることの案内を持つ開始の画面を出す。
6. The アプリ shall アプリの版を画面（窓の題名か「バージョン情報」）で見られるようにし、その版を、同じリリースの pasta の版（ワークスペースの版）と同じにする。
7. The アプリ shall exe のある場所・exe のそばにファイルを作らない。

### Requirement 2: ゴーストを開く

**Objective:** As a ゴーストの作者, I want ゴーストのフォルダを渡すだけで、そのゴーストの `ghost/master` が開くこと, so that どの階層のフォルダを渡したかを気にしなくてよい

#### Acceptance Criteria

1. When ゴーストのフォルダを exe にドラッグドロップした（パスを 1 つの引数として起動した）, the アプリ shall そのパスから `ghost/master` を探して開く（複数のパスを渡されたときは最初の 1 つを使う）。
2. When ゴーストを開いている窓・開始の画面にフォルダをドロップした, the アプリ shall そのフォルダから `ghost/master` を探して開く。
3. When 作者がフォルダを選ぶダイアログでフォルダを選んだ, the アプリ shall そのフォルダから `ghost/master` を探して開く。
4. The アプリ shall 渡されたフォルダが、ゴーストのフォルダ（`X` の下に `ghost/master` がある）・`ghost` のフォルダ（下に `master` がある）・`ghost/master` そのもの、のどれであっても、同じ `ghost/master` を開く。
5. The アプリ shall フォルダの名前 `ghost`・`master` を、大文字・小文字を区別せずに見つける。
6. Where 渡されたパスが `ghost/master` の中のフォルダかファイルである, the アプリ shall 上へたどって最も近い `ghost/master` を開き、ファイルなら、そのファイルもタブで開く（Windows の「プログラムから開く」で `.pasta` を関連付けたときや「送る」から渡したときも、この決まりで開く）。
7. If 渡されたパスから `ghost/master` が見つからない（無いパス・フォルダでないもの・ゴーストでないフォルダ）, the アプリ shall そのパスと見つからない理由を出し、開いているゴーストを変えない。
8. When 別のゴーストを開く操作をした and 開いているゴーストに未保存のファイルがある, the アプリ shall 開き直す前に、保存する・保存しない・取り消す を確かめる。
9. While ゴーストを開いている, the アプリ shall 窓の題名に、開いているゴーストのフォルダの名前を出す。
10. The アプリ shall 1 つの窓で、一度に 1 つのゴーストだけを開く。
11. When アプリが動いているときに、もう一度起動された（exe へのドロップ・関連付けたファイルのダブルクリック・「送る」を含む）, the アプリ shall 新しい窓を開かず、渡されたパスを今の窓へ渡して要件 2.1・2.4〜2.8 の決まりで開き、今の窓を前に出す（渡されたパスが無ければ今の窓を前に出すだけにする）。

### Requirement 3: 最近開いたゴースト

**Objective:** As a ゴーストの作者, I want 前に開いたゴーストを一覧から選び直せること, so that 毎回フォルダを探さなくてよい

#### Acceptance Criteria

1. When ゴーストを開いた, the アプリ shall その `ghost/master` を、最近開いたものの一覧の先頭に記録する（同じものが既にあれば先頭へ移し、重ねて記録しない）。
2. The アプリ shall 最近開いたものの一覧を、新しい順に最大 10 件まで残し、それを超えた古いものを消す。
3. The アプリ shall 最近開いたものの記録を、アプリを終えても残し、次の起動の開始の画面と、ゴーストを開いている間のメニューから選べるようにする。
4. The アプリ shall 一覧の各項目に、ゴーストのフォルダの名前と、フルパスを出す。
5. If 一覧から選んだゴーストのフォルダが無くなっている, the アプリ shall 無くなっていることを出し、その項目を一覧から消す。
6. The アプリ shall 最近開いたものの記録を、利用者ごとのアプリのデータの置き場（`%APPDATA%` の下）にだけ書き、ゴーストのフォルダと exe のそばには書かない。
7. The アプリ shall 最近開いたものの記録を、人が読める TOML で書く。
8. If 最近開いたものの記録が読めない・壊れている, the アプリ shall 起動を止めず、空の一覧として扱って動き続ける。

### Requirement 4: ファイルとシーンのツリー

**Objective:** As a ゴーストの作者, I want ゴーストのファイルと、辞書の中のシーンを 1 つのツリーで見られること, so that 書きたいシーンへ一度で行ける

#### Acceptance Criteria

1. While ゴーストを開いている, the アプリ shall ツリーに、`ghost/master` の中のフォルダとファイルを、階層のとおりに出す。
2. The アプリ shall ツリーの同じ階層の中を、フォルダを先に、それぞれを名前の順（大文字・小文字を区別しない）に並べる。
3. The アプリ shall `ghost/master` の直下の `profile` フォルダ（ランタイムが書く保存の置き場）をツリーに出さず、シンボリックリンクをたどらない（ゴースト全体の検査と同じ範囲）。
4. The アプリ shall ツリーの各 `.pasta` ファイルの下に、そのファイルのシーンを グローバルシーン ＞ ローカルシーン の 2 階層で、ファイルの中の順に出し、項目の名前をシーンの名前（続きのグローバルシーンは受け継いだ名前）にする。
5. When 同じ名前のシーンがファイルの中に複数ある, the アプリ shall それぞれを別の項目として出す。
6. When 作者がツリーのシーンを押した, the アプリ shall そのファイルをタブで開き（開いていればそのタブへ切り替え）、そのシーンの見出しの行へカーソルを移して見える位置に出す。
7. When 作者がツリーのファイルを押した, the アプリ shall そのファイルをタブで開く（開いていればそのタブへ切り替える）。
8. When ゴーストを開いた, the アプリ shall ゴーストのすべての `.pasta` ファイルを解析して、シーンの項目を作る。
9. When `.pasta` ファイルを保存した, the アプリ shall そのファイルのシーンの項目を、保存した中身から作り直す。
10. While `.pasta` ファイルをタブで開いて書き換えている, the アプリ shall そのファイルのシーンの項目を、書き換えている中身の解析に合わせ、押したときに今の見出しの行へ行けるようにする（未保存の書き換えにも追う。拡張のアウトラインと同じ）。
11. While `.pasta` ファイルに構文の誤りがある, the アプリ shall 解析器が返した、解ける部分のシーンだけを出す。
12. The アプリ shall ツリーに、シーンのほかのもの（アクター辞書・単語定義・コードブロック・属性）を出さない。
13. The アプリ shall シーンの並びを自分で取り出さず、解析器の返すシーンの並びをそのまま写す。
14. When 作者がツリーのフォルダ（`ghost/master` そのものを含む）で新しいファイルか新しいフォルダを作る操作をして名前を入れた, the アプリ shall そのフォルダの中に空のファイルかフォルダを作り、ツリーに出し、ファイルならタブで開く。
15. When 作者がツリーのファイルかフォルダの名前を変える操作をして新しい名前を入れた, the アプリ shall その名前に変え、そのファイル（フォルダならその中のファイル）を開いているタブを、未保存の書き換えを保ったまま新しい名前に付け替える。
16. If 作成・名前の変更で入れた名前が、同じフォルダの既にあるもの（大文字・小文字を区別しない）と重なる・Windows のファイル名に使えない・空である, the アプリ shall 作成・名前の変更を行わず、理由を出す。
17. The アプリ shall ツリーから、ファイルとフォルダを削除する操作を持たない。

### Requirement 5: ファイルを開く・タブ・保存

**Objective:** As a ゴーストの作者, I want 複数のファイルをタブで開いて書き、書いた中身を失わずに保存できること, so that 安心して辞書を書き進められる

#### Acceptance Criteria

1. The アプリ shall `.pasta`・`.lua` のファイルを、タブで開いて編集できるようにする。
2. Where `.pasta`・`.lua` 以外の UTF-8 のテキストファイル（`pasta.toml`・`descript.txt` など）を開いた, the アプリ shall 色分けなしのテキストとして開いて編集・保存できるようにする。
3. If 開こうとしたファイルが UTF-8 として読めない（画像などのバイナリ・Shift_JIS のテキストなど）, the アプリ shall そのファイルを開かず、読めない理由を出す。
4. The アプリ shall 複数のファイルを同時にタブで開き、同じファイルを 2 つのタブで開かない。
5. While タブのファイルに未保存の書き換えがある, the アプリ shall そのタブに未保存の印を出す。
6. When 作者が保存の操作（`Ctrl+S` かメニュー）をした, the アプリ shall 今のタブの中身を、そのファイルへ UTF-8 で書き、未保存の印を消す。
7. The アプリ shall 保存のとき、開いたときのファイルの改行の種類（CRLF・LF）と、先頭の BOM の有無を変えない。
8. If 保存に失敗した（読み取り専用・ほかのプログラムが掴んでいる・置き場が無くなった）, the アプリ shall 失敗の理由を出し、エディタの中身と未保存の印をそのまま残す。
9. When 未保存の書き換えのあるタブを閉じようとした, the アプリ shall 閉じる前に、保存する・保存しない・取り消す を確かめる。
10. When 未保存の書き換えのあるタブが残っているときに窓を閉じようとした, the アプリ shall 閉じる前に、保存する・保存しない・取り消す を確かめ、取り消したときは窓を閉じない。
11. The アプリ shall ファイルの中身を、作者が保存の操作をしたときだけ書き換え、自動では保存しない。

### Requirement 6: `.pasta` の色分け

**Objective:** As a ゴーストの作者, I want `.pasta` に VS Code 拡張と同じ色分けが出ること, so that シーン・単語・台詞・さくらスクリプト・コードブロックを見分けて書ける

#### Acceptance Criteria

1. When `.pasta` ファイルを開いた, the アプリ shall 拡張の着色の文法（`pasta.tmLanguage.json`）と同じ規則で、行ごとの下地の色分けを出す。
2. When `.pasta` ファイルを開いた・書き換えた, the アプリ shall その上に、解析器のセマンティックトークンによる色分けを重ねる。
3. The アプリ shall セマンティックトークンの種類と修飾の並び（凡例）を、拡張と同じものにし、拡張と食い違わないことをテストで確かめる。
4. The アプリ shall `.pasta` のコードブロック（3 個以上のバッククォートの柵）の中身に、Lua の色分けを出す。
5. If 解析器の解析に失敗した, the アプリ shall 下地の色分けを残したまま編集を続けられるようにする。
6. The アプリ shall 拡張と同じ部分を同じ種類として塗り分け、色の値そのものの一致は求めない。
7. The アプリ shall 画面の明暗を Windows の明暗の設定に合わせ、どちらでも色分けが読めるようにする。

### Requirement 7: `.pasta` の書きながらの診断

**Objective:** As a ゴーストの作者, I want 書いている途中で書き間違いが分かること, so that SSP で読み込む前に直せる

#### Acceptance Criteria

1. When `.pasta` ファイルを開いた・書き換えた, the アプリ shall 解析器の診断を、その範囲に波線で出す。
2. When 作者が書き換えを止めた, the アプリ shall 止めてからおおむね 1 秒以内に、波線と診断の一覧を書き換えた後の中身に合わせる。
3. While `.pasta` ファイルをタブで開いている, the アプリ shall そのファイルの診断を、ファイル・行・列・メッセージの付いた一覧に出す。
4. When 作者が診断の一覧の項目を押した, the アプリ shall そのファイルのタブへ切り替え、その位置へカーソルを移す。
5. The アプリ shall 診断の行と列を 1 から数えて見せ、その位置を拡張が同じ文書に出す位置と同じにする（全角文字・サロゲートペアを含む行でも）。
6. When `.pasta` ファイルのタブを閉じた, the アプリ shall そのファイルの書きながらの診断を一覧から消す。
7. While 解析器が解析している, the アプリ shall 入力を止めずに受け付ける。

### Requirement 8: `.lua` の編集

**Objective:** As a ゴーストの作者, I want `scripts/` の `.lua` も同じアプリで書けること, so that DSL と Lua のためにエディタを分けなくてよい

#### Acceptance Criteria

1. When `.lua` ファイルを開いた, the アプリ shall Lua の色分けを出して編集できるようにする。
2. The アプリ shall `.lua` ファイルの保存に、`.pasta` と同じ保存の決まり（要件 5）を当てる。
3. The アプリ shall `.lua` ファイルに構文の診断を出さない（この spec の外）。

### Requirement 9: ゴースト全体の検査

**Objective:** As a ゴーストの作者, I want ゴースト全体の書き間違いが、拡張と同じ一覧で分かること, so that 開いていないファイルの誤りや、ファイルをまたぐ誤りにも気づける

#### Acceptance Criteria

1. When ゴーストを開いた, the アプリ shall そのゴースト全体を検査し、結果を一覧に出す。
2. When `.pasta` ファイルか `ghost/master` の直下の `pasta.toml` を保存した, the アプリ shall ゴースト全体を検査し直す。
3. When 外で `.pasta`・`.lua`・`pasta.toml` のファイルが増えた・消えた・変わった, the アプリ shall ゴースト全体を検査し直す。
4. The アプリ shall 検査に、ディスクに保存されている中身を使い、未保存の書き換えを使わない。
5. The アプリ shall 同じゴーストの同じ保存の中身に対して、`pasta_check validate` と拡張のゴースト全体の検査と同じ検査の結果（同じファイルを選び、同じ誤り・警告を出す）を出す。
6. The アプリ shall 一覧の各項目に、誤りか警告か・ファイル・行・列・メッセージを出し、誤りと警告の件数を出す。
7. When 作者が検査の一覧の項目を押した, the アプリ shall そのファイルをタブで開き、その位置へカーソルを移す。行の無い項目ではファイルの先頭へ移す。
8. While ファイルをタブで開いている, the アプリ shall そのファイルの構文の誤りを、書きながらの診断（要件 7）にだけ出し、ゴースト全体の検査の一覧に重ねて出さない（拡張と同じ）。
9. When 検査を続けて求められた（保存が続いた）, the アプリ shall 短い間の求めを 1 回の検査にまとめ、検査の途中で来た求めには、終わった後にもう 1 回だけ検査する。
10. If ゴーストのフォルダを読めず検査できない, the アプリ shall 一覧に検査できない理由を出し、古い結果を残さない。
11. The アプリ shall 開いた `ghost/master` の中で検査に使うファイルの選び方を、`pasta.toml` の設定に従わせ、アプリの独自の決まりを足さない。
12. The アプリ shall 検査に使うファイルを、`pasta_check validate` と同じ処理（`pasta_check` のライブラリのファイル集め）で集め、自分で集め直さない。

### Requirement 10: 外でファイルが変わったとき

**Objective:** As a ゴーストの作者, I want 外のプログラムでファイルが変わったことが分かり、書いた中身を失わないこと, so that エクスプローラーやほかのエディタと並べて使える

#### Acceptance Criteria

1. When 外で `ghost/master` の中のファイルかフォルダが増えた・消えた・名前が変わった, the アプリ shall ツリーを作り直す。
2. When 外でタブに開いているファイルの中身が変わった and そのタブに未保存の書き換えが無い, the アプリ shall そのタブの中身を読み直す。
3. When 外でタブに開いているファイルの中身が変わった and そのタブに未保存の書き換えがある, the アプリ shall 外で変わったことを知らせ、作者が「読み直す」か「今の中身を残す」かを選べるようにし、選ぶまでエディタの中身を書き換えない。
4. When 外でタブに開いているファイルが消えた, the アプリ shall 消えたことを知らせ、タブの中身を未保存として残す（保存すればファイルを作り直せる）。
5. When 外で `.pasta` ファイルが変わった, the アプリ shall そのファイルのシーンの項目を作り直す。
6. The アプリ shall 自分の保存による書き込みを、外での変更として知らせない。

### Requirement 11: 読み書きの範囲

**Objective:** As a ゴーストの作者, I want アプリが、開いたゴーストの中で作者が保存したファイルだけを書き換えること, so that ゴーストやほかのファイルを壊される心配がない

#### Acceptance Criteria

1. The アプリ shall ファイルの中身の読み書きを、開いている `ghost/master` の中のファイルと、利用者ごとのアプリのデータの置き場（最近開いたものの記録（要件 3）と、WebView2 の作業用のデータ）だけに限る。`ghost/master` を探すためのフォルダの有無の確かめ（要件 2.4〜2.7）は、この限りでない。
2. If 開いている `ghost/master` の外のパスの読み書きを求められた, the アプリ shall それを行わない。
3. The アプリ shall ゴーストのフォルダの中に、作者が保存・作成したファイルとフォルダ（要件 4.14・4.15）のほかのもの（作業用のファイル・設定・ログ）を作らない。
4. The アプリ shall この spec の機能では、ゴーストの `profile` フォルダを読まず、書かない（保存変数の表示は `pasta-recipe-dev-actions` が足す）。

### Requirement 12: リリースの配布物

**Objective:** As a pasta のリリースを行う開発者, I want リリースのたびにアプリの配布物が、ほかの配布物と同じ流れで作られ確かめられること, so that 手作業なしに作者へ届けられる

#### Acceptance Criteria

1. When リリースタグを push した, the リリース CI shall ソースからアプリを作り、`pasta-recipe.zip` を配布物に加える。
2. The リリース CI shall `pasta-recipe.zip` の中身が、アプリの exe と `THIRD_PARTY_LICENSES.txt` の 2 つだけであることを確かめ、違えば止まる。
3. The リリース CI shall `pasta-recipe.zip` の exe の版がタグの版と同じであることを確かめ、違えば止まる。
4. The リリース CI shall `pasta-recipe.zip` の大きさが、決めた上限（値は設計で決める）を超えないことを確かめ、超えれば止まる。
5. The アプリの `THIRD_PARTY_LICENSES.txt` shall exe に含まれるネイティブの部品と画面の部品（エディタ・着色の部品・文法）の、両方の第三者のライセンスの表示を含む。6. When GitHub Release を作った, the リリース CI shall 今までの 6 つの添付に `pasta-recipe.zip` を加えた 7 つを添付する。
7. The リリースの手順の補助（リリースの状態の確かめ・添付の一覧・そのテスト）shall 添付が 7 つになったことに合わせる。
8. When 失敗した job を再実行した, the リリース CI shall 今の配布物と同じく、続きから回復する。
9. The リリース CI shall 今の配布物（`pasta.dll.zip`・`hello-pasta.nar`・VSIX・`pasta_check.zip`・`pasta-skills.zip`）の作り方と中身を変えない。
10. The アプリのネイティブの部品の第三者の表示 shall アプリ専用の設定で作り、受け入れるライセンスの並びを、アプリの依存に実際に出てきたもの（ファイル単位のコピーレフトの MPL-2.0 などが出れば、それも）に合わせる。ルートの設定と、ほかの配布物（`pasta.dll.zip` など）の受け入れる並びは変えない。

### Requirement 13: 日々の CI とテスト

**Objective:** As a pasta の開発者, I want アプリが日々の CI でビルドされテストされ、拡張とルートのワークスペースの検査がそのまま通ること, so that アプリの変更でほかが壊れたことにすぐ気づける

#### Acceptance Criteria

1. When main への push・PR・手動の実行があった, the CI shall アプリをビルドし、アプリのテストを走らせる。
2. The CI shall 解析器の WASM のビルドと、ルートのワークスペースの `cargo test --workspace`・clippy・依存の検査を、今までどおりに走らせ、それらの対象にアプリの依存を入れない。
3. The アプリのテスト shall `ghost/master` の探し方（要件 2.4〜2.7）・最近開いたものの読み書き（要件 3）・読み書きの範囲（要件 11）を確かめる。
4. The アプリのテスト shall アプリのネイティブの側が返す解析の結果が、拡張の WASM が同じ文書に返すものと同じ形・同じ中身（トークン・診断・シーンの並び、UTF-16・0 始まりの位置）であることを確かめる。
5. The アプリのテスト shall トークン・診断・シーンの並びをエディタとツリーの形へ写す処理（位置の 1 始まりへの変換を含む）を確かめる。
6. The アプリのテスト shall アプリのゴースト全体の検査が、同じゴーストに対して `pasta_check validate` と同じ結果を出すことを確かめる。
7. The CI shall アプリの依存（アプリの別の `Cargo.lock`）にも、ルートと同じ依存の検査（ライセンス・既知の脆弱性）を当てる。
8. The `pasta_check` のテスト shall ファイル集めをライブラリへ移す前と後で、`pasta_check validate` の結果が変わらないことを確かめる。

### Requirement 14: マニュアル

**Objective:** As a VS Code を入れたくないゴーストの作者, I want アプリの入手から開き方までがマニュアルに書いてあること, so that 迷わず使い始められる

#### Acceptance Criteria

1. The マニュアル shall 「VS Code を使わずに書く」章を持ち、入手（GitHub Release の `pasta-recipe.zip`）・置き方・起動・ゴーストの開き方（ドラッグドロップ・窓へのドロップ・フォルダを選ぶ・最近開いたもの）を説明する。
2. The マニュアル shall 署名していない exe なので、初めての起動で Windows の SmartScreen の警告が出ることと、その通し方を説明する。
3. The マニュアル shall WebView2 ランタイムが要ること（Windows 11 には入っていること）と、無いときの入手の仕方を説明する。
4. The マニュアル shall アプリでできること（色分け・診断・ツリー・ゴースト全体の検査）と、まだできないこと（シーンの実行などは拡張を使うこと）を説明する。
5. The マニュアル shall その章を目次（`SUMMARY.md`）に載せ、リンクの検証を通る。
6. The マニュアル shall Windows の「プログラムから開く」で `.pasta` をアプリに関連付ける方法と、「送る」（`shell:sendto`）にアプリのショートカットを置く方法を説明し、どちらでもそのゴーストが開くこと（アプリが動いていれば今の窓で開くこと）を示す。
