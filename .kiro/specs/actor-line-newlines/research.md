# ギャップ分析: actor-line-newlines

## 要約

- **対象**: `[ghost] line_newlines`（既定 `0`）を足し、継続行（`ContinueAction`）の最初の見える字の前に `\n[N]` を 1 つ入れる。対象は継続行だけ（2026-11-05 の見直し後の brief）。
- **発見の規模**: 既存の拡張（Extension）。設定の読み込み・出力側の状態機械・生成する Lua の 3 か所に、既にある型（`spot_newlines` の遅延方式・`put_break`・`apply_shiori_defaults`）をなぞって足す。Rust の `talk_to_script`・budoux の折り方は変えない。
- **主な難所**: 「既定 `0` で 1 バイトも変えない」（要件 6.1）と「設定しても、規則 6・7 で入れなかった境目は今と同じ」（要件 4.5）。今の `merge_consecutive_talks` は同じアクターの連続した `talk` を 1 つに結合してから `talk_to_script`（ウェイト・budoux）に渡すので、継続行の印が結合を切ると、改行を入れない所でもウェイトや budoux の折り位置が変わりうる。印は「結合を切らない」形で運ぶ必要がある。
- **推奨の方向**: 案 B（印を結合後の台詞の中の「継ぎ目」として持ち、改行を入れると決めた継ぎ目でだけ台詞を分けて `put_break` を通す）。規則 6 の判定は Rust の `column_move` と同じ分類（`\n`・`\n[…]`→次の列、`\c`→最初の列、`\_l[…]`→飛ぶ）を Lua 側に写す形になり、`ColumnMove` の写しの決まり（片方だけ直さない）に入る。
- **工数と危険度**: M（3〜7 日）／中。既存の型に沿うが、継ぎ目の扱いとバイト同一の検証に手間がかかる。
- **設計での結論（2026-11-06）**: 案 B の「継ぎ目」を採り、継ぎ目で台詞を分けずに、入れる継ぎ目でだけ最初の見える字の直前へタグを差し込む案 D にした（下の「設計フェーズの調査」）。

## 統合の難所

1. **結合を切らない**: 今の出力は、同じアクターの連続した `talk` を 1 つに結合してから変換する。継続行の印が独立したトークンだと結合が切れ、既定 `0` でも出力が変わる（要件 6.1 違反）。また印だけが積まれた出力で `ACT_IMPL.build` の空の判定が偽になり、`nil` だった応答が `\e` だけになる。印は、結合・空の判定・話者の遡り（`actor_proxy` の直前の話者）・グループの頭のタグ列（外見の復旧）・`BUILDER.speaks` のどれからも見えない形にする。
2. **印の置き場所とグループ**: 継続行の前に Call 先で別の話し手が字を出していると、`group_by_actor` は話者でないトークンを今のグループ（別の話し手のグループ）に入れる。印を独立したトークンにすると、印が別の話し手のグループに入り、その後の切り替えで捨てる必要がある。印を次の話者のトークン（`talk`・`sakura_script`）の欄として持てば、このずれは起きない。
3. **規則 6・7 は行をまたいで見る**: 継続行の頭のタグは、結合した台詞の中・別の `sakura_script` トークン（DSL の行に書いた `\n`・`\_l[…]`・`\c` は `sakura_script` になる）・`newline` トークンにまたがる。前の行の末尾の改行も同様。判定は「最後の見える字から次の見える字まで」の区間を、トークンの境目と結合した台詞の中の継ぎ目の両方で見る必要がある。
4. **区切りの置き場所**: `spot_newlines` は字を出すトークンの直前（テキストの頭のタグより前）に出る。継続行の改行も同じ置き場所にすると、`　　：＠注目　みんなに…` は `\n[180]\s[注目]みんなに…` になる。手書きの `＠注目　＠改行　…` の出力は `\s[注目]\n[180]…` なので、見た目は同じだがバイトは違う（要件 6.3 は字と字の間と幅だけを求める）。ぱすた開発セッションは「`\n` と表情の bind の前後はどちらでもよい」としたので、作りの都合（`spot_newlines` と同じ置き場所が素直）で設計が決めてよい。
5. **生成する Lua の形と行番号**: 印を別の Lua 行（例 `act:continuation()`）で出すと、以後の Lua の行番号がずれ、`line_map` の文字列・ソースマップ・デバッガの行の対応・比較用の生成物が変わる（`record_span_since` で継続行の span を記録すれば対応は保てる）。同じ行に載せる（例: 継続行の最初のアクションの `actor_proxy` に印の引数を足す、最初の呼び出しの前に `act:continuation();` を同じ行で置く）と行番号は変わらない。ただし最初のアクションが関数呼び出し（`expr_fn`）だと、関数の中で積まれた台詞に印が付く順序の問題がある。
6. **既定のリテラルと SSOT の検査**: `act.lua` の `CONFIG.get("ghost", "line_newlines", 0)` の書き方（`0` か `0.0` か）と、`GhostConfig` の `f64` の表記（`{:?}` で `0.0`）を、`config_defaults_test` の照合に合わせる。
7. **隣の spec**: `cue-command-runtime` は場面に入ったときと Call から戻ったときにアクター指定行を台本へ流し、同じ生成の場所（`scope_gen.rs`・`element_gen.rs`）を触る。`scene-anchor-link` は `act.lua` を触る。同じウェーブに置かない（brief）。

## 実装の案

### 案 A: 印を独立したトークンにする（既存の部品を拡張）

- 生成: 継続行の頭で `act:continuation()`（名前は仮）を出す。`ACT_IMPL.continuation` が `{ type = "continuation" }` を積む。
- act.lua: `merge_consecutive_talks` が印を飛ばして結合を続ける、`is_all_empty_raw_script` が印を無視する、`group_by_actor` が印を次の話者のグループへ回す、などの手当てを足す。
- builder: 印で保留を立て、字を出すトークンの直前で出す。
- ✅ 生成と蓄積が素直。Lua から `act:continuation()` を呼べば同じ挙動になる（ただし要件では Lua の台詞は対象外）。
- ❌ 結合を飛ばすと、結合した台詞の中のどこが継ぎ目かが失われ、継ぎ目で改行を入れられない。結合を切ると要件 6.1・4.5 に触れる。手当ての数が多く、どれか 1 つの漏れで既定の出力が変わる。

### 案 B: 印を結合後の台詞の「継ぎ目」として持つ（推奨の方向）

- 生成: 継続行の最初のアクションに印を付ける（同じ Lua 行に載せる形か、別の行か、は設計で決める）。印は次に積む話者のトークンに `continuation = true` のような欄として付く。
- act.lua: `merge_consecutive_talks` は今までどおり結合し、結合した `talk` に「継ぎ目の位置（バイト位置の並び）」を残す。結合しない境目（`sakura_script` など）では、トークンの欄のまま残す。空の判定・話者の遡り・グループは何も変わらない。
- builder: 継ぎ目を通るとき、保留の条件（同じ話し手・吹き出しに字がある・規則 6・7）を見て、入れると決めた継ぎ目でだけ台詞をそこで分け、前の片 → `put_break` → 後ろの片の順に変換する。入れない継ぎ目では今までどおり 1 つの台詞として変換する。既定 `0` では継ぎ目を一切見ない。
- ✅ 要件 6.1・4.5 のバイト同一を構造で守れる（入れないときは変換の入力が今と同じ）。グループ・空の判定・外見の復旧に手を入れない。
- ❌ 継ぎ目の位置を結合のたびに足し合わせる手間と、分けた後ろの片の頭の扱い（`put` / `put_raw`）・字の判定（`text_parts` を片ごとに）の決め直しがある。builder の複雑度（今 28）がさらに上がるので、継ぎ目の処理を局所関数に出す必要がある。

### 案 C: 混成（生成は案 A の形、運び方は案 B）

- 生成は独立した呼び出し `act:continuation()` にし、`ACT_IMPL.continuation` はトークンを積まずに act の欄（「次の話者のトークンに印を付ける」）を立てるだけにする。以後は案 B と同じ。
- ✅ 生成する Lua が読みやすく（`act:continuation()` の 1 行）、最初のアクションが関数呼び出しのときの順序の問題も、印を立てた後に最初に積まれた話者のトークンに付く、と決めれば扱える。
- ❌ 別の行にすると行番号がずれる（統合の難所 5）。同じ行に `act:continuation(); …` と並べれば避けられるが、生成の 1 行 1 アクションの形が崩れる。

## 工数と危険度

- **工数: M（3〜7 日）** — 設定・生成・builder の 3 か所は既存の型をなぞるが、継ぎ目の扱いと、規則 1〜11 のテスト、既定 `0` と相手役の行のバイト同一の検証、マニュアル 3 章＋生成物の更新がある。
- **危険度: 中** — 未知の技術は無いが、既定の出力を 1 バイトも変えないことを、結合・ウェイト・budoux・外見の復旧・空の判定のすべてで守る必要がある。

- **決めること**: 印の名前と生成する Lua の形（同じ行か別の行か・行番号とソースマップ）、継ぎ目の表し方、区切りの置き場所（頭のタグの前か後か。ぱすた開発セッションの期待値と照合）、規則 6 の分類の Lua の写し（`column_move` と同じ集合。`\n[half]` も次の列、`\c[…]` は数えない）、規則 7 の追跡の持ち方、保留を捨てる所の一覧、`config_defaults_test` の表記。
- **Research Needed**:
  1. 継ぎ目で台詞を分けて変換したとき、ウェイトの挿入（句読点の後・行の終わりの扱い）と budoux（前後の文字から切れ目を決める）の出力が、結合したまま変換したときとどう違うか。改行を入れる継ぎ目だけで分けるなら、違いは「改行を入れた所の前後」に限られるかを確かめる。

  4. ~~ぱすた開発セッションの「出てほしいさくらスクリプト」の原文を受け取る~~ → 受け取り済み（上の「書き方の案」に写した）。設計では、これを builder のテストの期待値に写す（`\![bind,…]` は実際の表情の単語の出力に置き換える）。

- **簡単にできる候補（設計で比べる）**: 既定 `0`（`N` が 0 以下）のときは act.lua が結合（`merge_consecutive_talks`）の前に印を読み捨てる、とすれば、要件 6.1 のバイト同一は印の運び方によらず守れる。残る難所は「設定したゴーストで、規則 6・7 で入れなかった境目を今と同じにする」（要件 4.5）だけになる。行の頭の `＠改行` は単語なので、規則 6 は生成時には判定できず、実行時に見るしかない（単語の中身は実行時に決まる）。

## 設計フェーズの調査（2026-11-06）

### 要約
- **発見の型**: 既存の拡張（軽い発見の手順）。外部の依存・新しいライブラリは無い。
- **使ったスキルと指針**: `kiro-spec-design`（`design-principles`・`design-discovery-light`・`design-synthesis`・`design-review-gate`）、ponytail（最小の完全な変更・既存の型の再利用）。ゴーストの書き方の知見は ghost_dev の「書き方の案」（上）だけを使った。
- **主な発見**:
  1. 継ぎ目で台詞を分けて変換すると、入れない継ぎ目でもバイトが変わる（下の「分けると変わるか」）。分けずに、入れる継ぎ目でだけテキストにタグを差し込む作りにした。
  2. 差し込む位置を「継続行の最初の見える字の直前」にすると、手書きの `＠注目　＠改行　…` とウェイト・budoux・装いまでバイトが同じになる。
  3. 既存の区切り（`spot_newlines`・選択肢の前後）・`newline`・`clear` はすべて `next_column`・`first_column` を通る。行の状態をそこで捨てれば、優先順位の規則が 1 つで済み、`BUILDER.build` に状態変数を足さずに済む。

### 分けると変わるか（Research Needed 1 の答え）
- **きっかけ**: brief の「簡単にできる候補」（既定 0 では印を捨て、設定したら継ぎ目で分ける）で足りるかを確かめる。
- **読んだ所**: `crates/pasta_lua/src/sakura_script/wait_inserter.rs` の `insert_waits`・`flush_pending`、`line_breaker.rs` の `tokenize_plain_chars`・`break_lines_impl`、`mod.rs` の `talk_to_script_impl`。
- **分かったこと**:
  - ウェイト: 句読点（`Period`・`Comma`・`Strong`・`LineStartProhibited`）は `pending_text` に溜め、続く句読点と 1 つのウェイト（最大値）にまとめる。タグ（`SakuraScript`）と普通の字は溜めたものを出し切る。継ぎ目で 2 回の変換に分けると、変換の終わりで溜めたものが出し切られるので、継ぎ目の両側が句読点のとき（例: `…なら。` ＋ `」と…`）、結合なら `。」\_w[950]`、分けると `。\_w[950]」` になる。継ぎ目にタグがあるときは、どちらもタグで出し切るので同じ。
  - budoux: `break_lines_impl` はタグを除いた本文のクラスタを全部つないでから `parse_boundaries` にかける。語の境界は前後の字の並びで決まるので、継ぎ目で分けると、継ぎ目にタグがあっても、継ぎ目の近くの語の境界と折る位置が変わりうる（`test_tag_inside_word_splits_into_fragments` が示すとおり、タグをまたいだ字も 1 語になる）。
  - 列の状態は表で受け渡すので、分けても列の数え方そのものはつながる。
- **含意**: 「設定したら継ぎ目で分ける」は、規則 6・7 で入れなかった継ぎ目のバイト同一（要件 4.5）を budoux のあるアクターで守れない。テキストは分けず、入れる継ぎ目でだけタグを差し込む。差し込んだ `\n[N]` は、ウェイトではタグとして句読点の保留を出し切り（手書きの `＠改行` と同じ）、budoux では本文を変えずに「次」の列の動きになる（手書きと同じ）。

### 局所シーンの頭の継続行（要件 6.4 の前提）
- **読んだ所**: `crates/pasta_dsl/src/parser/grammar.pest`（`local_scene_item` は `continue_action_line` をどこにでも許す）、`crates/pasta_lua/src/code_gen/scope_gen.rs` の `generate_local_scene_items`（局所シーンごとに `last_actor = None` から始め、`ActionLine` だけが更新する。`VarSet`・`CallScene` は更新しない）、`element_gen.rs` の `generate_continue_action`（`last_actor` が `None` なら `TranspileError::invalid_continuation`）、`element_gen_tests.rs` の `continue_action_without_prior_actor_is_invalid_continuation_error`。
- **分かったこと**: 文法（パース）ではエラーにならない。トランスパイル時に、その局所シーンでアクション行より前に書いた継続行が `InvalidContinuation` になる。局所シーンの頭の継続行はエラーで、要件 6.4 の前提は正しい。Call 行・変数代入行の後の継続行は前のアクターを継ぐ（要件 2.5 の例が書ける）。`pasta_check` の `transpile_rules.rs` も同じ規則を写している。
- **含意**: 印はエラーの確認の後に出す。エラーの挙動は変わらない。

### 印の運び方
- **きっかけ**: 印を値によらない形で出し（キャッシュ）、結合を切らずに継ぎ目の位置を残す。
- **分かったこと**:
  - 台詞のトークンを作るのは `ACT_IMPL.talk`・`ACT_IMPL.sakura_script` だけ（アクターのプロキシもここへ委ねる）。ほかの所が積むのは `raw_script` だけ（`failure.lua`・`shiori/act.lua`・`stop.lua`）。
  - `merge_consecutive_talks` は結合した台詞の表を新しく作り、`type`・`actor`・`text` だけを写す。
  - 印の後、台詞より先に `newline`・`clear`・`choice`・`clear_spot` が積まれても、印を次の台詞まで持ち越せば、組み立ての行の状態（区切れ）で同じ結論になる（改行・消去・選択肢の区切りの後は入れない）。
  - `pasta_check` の `builtins.rs` の `ACT_METHODS`（27 個）は act のメソッドを列挙し、一致テスト（`validate_parity_test.rs`）と数の検査（`validate_scenes_test.rs`）がある。マニュアル `book/src/debug/validate.md` にも同じ一覧がある。act にメソッドを足すと、ここを同時に直す必要がある。
- **含意**: 印は独立したトークンにせず、act の欄（`_seam_next`）として持ち、次に積む台詞に `seams = { 1 }` として付ける。結合で位置を足し合わせる。グループ化・空の判定・話者の遡りは何も変わらない。

### キャッシュ（Research Needed 3 の答え）
- `crates/pasta_lua/src/loader/cache.rs` はクレートの版（`CARGO_PKG_VERSION`）とシーンの別名の表でキャッシュを捨てる。`pasta.toml` の値はキャッシュの鍵に入らない。印は値によらないので、値を変えても古くならない。
- 同じ版のまま開発すると、変わっていない `.pasta` は印の無い古い Lua のまま使われ、設定が効かない。0.5.1 への版上げで解消する。テストは一時フォルダで読み込むので影響しない。

### hello-pasta の既定の出力（Research Needed 2 の答え）
- 既定 `0` では act が印を付けず（`seams` がどのトークンにも無い）、組み立ては字を読まない。出力が変わらないことは作りで守られ、既存の出力のテスト（hello-pasta・`sakura_builder_test.lua`）がそのまま回帰の確かめになる。追加の見本の出力のテストは要らない。

## 設計の判断

### 判断: 差し込む位置は最初の見える字の直前
- **きっかけ**: 統合の難所 4（`spot_newlines` と同じく台詞の頭か、表情のタグの後か）。
- **候補**: (1) 継ぎ目（継続行の頭のタグの前）、(2) 継続行の最初の見える字の直前。
- **採用**: (2)。
- **理由**: 手書きの `＠注目　＠改行　…`（`\![bind,…]\n[180]み…`）とバイトが同じになり、要件 6.3 の確かめが「手書きの出力と一致」の 1 つで済む。規則 6（行の頭のタグ）を「保留の間に位置を決めるタグが来たら捨てる」の 1 つで読める。ぱすた開発セッションはどちらでもよいとした。
- **代わりに受け入れたこと**: ghost_dev が書いた「出てほしい」例（`\n[180]\![bind,…]`）とは表情のタグとの順が逆になる。

### 判断: 印は別の Lua の行に出す
- **候補**: (1) `act:continue_line()` を別の行、(2) 最初のアクションの受け手に繋ぐ（`act:continue_line():actor_proxy(…)`）、(3) 同じ行に `;` で並べる。
- **採用**: (1)。生成器の「1 文 1 行」の作りのまま、`generate_continue_action` の 2〜3 行の追加で済む。(2) は `generate_action` の全部の枝の書式を変え、空のエスケープ（何も書かない）のときに印が消える。(3) は字下げの書き出しの作りと合わない。
- **代わりに受け入れたこと**: 継続行より後ろの生成した Lua の行番号がずれ、比較用の生成物の差分が大きくなる。行の対応とソースマップは `out_line` から作るので食い違わない。

### 判断: 印の名前は `continue_line`
- act のメソッドは L3（`self[key]` の関数）で単語・シーンの名前と同じ空間にある。`continuation` より作者のシーン名と重なりにくい動詞句にした。`pasta_check` の一覧に足す。

### 判断: 行の状態を列の状態の表に置く
- **理由**: 行の状態はスポットごとで、列の状態の表と同じ寿命（1 回の出力・`clear_spot` で捨てる）。区切りはすべて `next_column`・`first_column` を通るので、そこで捨てれば優先順位（要件 3.1〜3.5）が 1 つの規則になる。Rust は `line`・`width`・`jump` しか読み書きしないので、Lua だけの欄を置いても変換は変わらない。欄は `nil` で捨てるので、使わないときの表は今と同じ。

### 判断: 型の検査を足さない
- `spot_newlines` は読み込みで検査せず、区切りを作る所の算術で Lua のエラーになる。`line_newlines` も同じく、改行を作る所（差し込む時）で算術を行う（要件 1.5）。act の印の要否は `~= 0` の比較だけにし、算術をしない。

## 合成（design-synthesis）の結果
- **一般化**: 「pasta が出す区切り」と「作者の書いた改行・`\c`」は、どれも列の動き（次・最初・飛ぶ）として読める。継続行の改行の判定を列の動きの上に置き、規則 3・4 を 1 つの状態機械にまとめた。
- **作るか使うか**: 新しい部品は作らない。`APPEARANCE.tag_at`・`unit_shows_text`・`plain_newline_tag`・`next_column`・`first_column`・SSOT の既定値の経路をそのまま使う。Rust の `column_move` は Lua から呼べない（非公開・単位の読み方が正規表現）ので、決まりどおり Lua に写し、一致のテストを置く。
- **簡単にしたこと**: 印のトークン型・保留の状態変数・継ぎ目での台詞の分割・`put_break` の新しい呼び出しを作らない。既定 0 では act も組み立ても何もしない。

## 危険と手当て
- 開発中の古いキャッシュで設定が効かない — 版上げで解消。手で試すときはキャッシュを消す（マニュアルには書かない）。
- `column_move` の写しのずれ — 一致のテスト（`talk_to_script` の列の動きと比べる）を置く。
- 字の無い継続行の保留の持ち越し（下の未決の問い 1）— 規則 4.1 で多くは止まる。開発者の判断で変える場合は、アクション行にも印を出す。
- 作者が台詞の中に書いたスコープの切り替え（`\1` など）は行の状態の区別に入らない — `spot_newlines` と同じ限界。
- `.claude/skills/*/references/` の生成物の書き換えは、ハーネスの分類器が自己書き換えとして拒むことがある — 生成器で作り直し、拒まれたら開発者に許可を求める。

## OPEN QUESTIONS

1. **（設計で残る）字の無い継続行の後に書き直した行が来たとき、改行を入れるか。** 印は継続行の頭にしか無く、実行時には行の終わりが見えない。保留を次の見える字まで持ち越す（brief の遅延方式）と、書き直した行の最初の字の前に改行が入る。要件 2.1 を厳密に読むと（「継続行が見える字を出し」）入れない。
   - **推奨**: 持ち越す（入れる）。brief の「保留として持ち、次の字の直前に入れる」と同じで、作りが小さい。書き直した行の頭に位置を決めるタグ（手書きの `＠改行`・`＠左`）があれば規則 4.1 で入らないので、ghost_dev の局所シーンの頭の 21 行は影響を受けない。入れたくない場合は、アクション行にも印を出す別の作りが要る（生成物が広く変わる）。
   - **例**: `line_newlines = 1.8` で
     ```pasta
     ＊雑談_例
     　ぱすた：なら。
     　　　　：＠笑顔
     　ぱすた：次の話。
     ```
     推奨どおりなら `\p[0]なら。\_w[…]\s[5]\n[180]次の話。\_w[…]\e`、厳密に読むなら `\p[0]なら。\_w[…]\s[5]次の話。\_w[…]\e`。

## OPEN QUESTIONS（要件フェーズ・確定済み）

1. **（確定: N が 0 以下なら入れない）`line_newlines` が負の値、または 100 倍して切り捨てると 0 になる値（`0.009` など）のとき、何を出すか。** brief は「既定 `0` は何も入れない」だけを決めている。`spot_newlines` の換算をそのまま当てると、`-0.5` は `\n[-50]`、`0.009` は `\n[0]` になる。
   - **推奨**: `N`（値を 100 倍して切り捨てた整数）が `0` 以下なら何も入れない（要件 1.3 に仮定として書いた）。`0` が「入れない」の意味なので、`0` より小さい値も同じに読むのが自然で、`\n[-50]`（ベースウェアによって行を戻す・無視するなど挙動が定まらない）を出さずに済む。
   - **例**: `line_newlines = -1` → 継続行の前に何も入れない（`0` と同じ）。`line_newlines = 0.5` → `\n[50]`。
