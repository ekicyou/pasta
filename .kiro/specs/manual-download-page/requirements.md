# Requirements Document

## Project Description (Input)
マニュアルを開いたゴースト作者が、どのファイルを落とせばよいかにすぐ辿り着けない。配布物は 7 つ（`pasta.dll.zip`・`hello-pasta.nar`・VSIX・`pasta_check.zip`・`pasta-skills.zip`・`pasta-recipe.x64.zip`・`pasta-recipe.arm64.zip`）に増えたが、トップページの案内は「関連リンク」の表の 1 つのセルに 7 つのファイル名を詰めた一文で、目的から選べない。トップページも回りくどく、「このマニュアルの歩き方」は扉の目次の言い直しで、AI のスキルを展開する手順までトップページにある。入手の説明は入門ガイド・デバッグの章・README にばらけている。

マニュアルに「ダウンロード」のページを新しく作り、目次の「はじめに」のすぐ下と扉の案内の先頭に置く。ページを開けば「やりたいこと → 取るファイル」が 1 つの表で分かり、そのまま最新版を落とせるようにする。トップページは短くし、「まずダウンロード → 入門ガイド」へすぐ進めるようにする。入手の説明は 1 か所にまとめ、ほかの章と README はそのページを指す（discovery の案 A。2026-11-14 に開発者が推奨案のまま承認。詳細は `brief.md`）。

## Introduction
pasta の利用者マニュアル（GitHub Pages で公開）に、配布物の入手だけを簡潔に説明する「ダウンロード」のページを足し、トップページ（「はじめに」）を削り込む。読者はゴースト作者で、目的（まず動かす・DLL を差し替える・エディタで書く・検査する・AI に書かせる）から取るファイルを選び、最新版をそのまま落とせるようになる。入門ガイド・デバッグの章・README にばらけた入手の説明は、手順の流れを残したまま、入手先の案内だけをこのページへ寄せる。マニュアルは main への push で公開されるので、リリースを待たずに出せる。

## Boundary Context
- **In scope**:
  - マニュアルの「ダウンロード」のページの新設と、目次（サイドバー）・扉の案内からの入口
  - トップページ（「はじめに」）の削り込み（「AI にゴーストを書かせるとき」の節をダウンロードのページへ移すことを含む）
  - 入門ガイドの「前提環境と準備」「ゴーストの最小一式を置く」、デバッグの「VS Code を使わずに書く（pasta-recipe）」「辞書を検査する（pasta_check validate）」「VSCode 接続と拡張導入」の各章と、リポジトリの README の、入手先の案内の付け替え
  - 上の変更で通らなくなるマニュアルの検査と執筆規約の追従、スキルの写しの再生成（写しに影響が出るときだけ）
- **Out of scope**:
  - 配布物そのものの名前・中身・リリース CI
  - 扉の意匠（CSS・顔アイコン）の作り直し
  - 入門ガイドの本文の書き直し（入手先の案内の差し替えだけを行う）
  - 英語版や他言語のページ
  - 過去のリリースノート（`doc/release-notes/`）の記述
  - 配る pasta のスキル（`pasta-check` など）の本文にある入手の説明（仮定。OPEN QUESTION 6）
- **Adjacent expectations**:
  - リリース手順は、トップページの対象バージョンの表の行を機械的に書き換える。この spec はその行の形を変えない。
  - `pasta-dll-multiarch` など、今後配布物を増やしたり形を変えたりする spec は、ダウンロードのページの表と説明を直す。この spec は今の 7 つの配布物だけを載せる。
  - 段階辞書と作例の照合（入門ガイドの検査）の持ち場には触れない。入門ガイドで触るのは入手先の案内だけである。

## Requirements

### Requirement 1: 目次と扉からの入口
**Objective:** As a ゴースト作者, I want マニュアルを開いてすぐに「ダウンロード」の入口を見つけたい, so that 何を落とせばよいかを探し回らずに済む

#### Acceptance Criteria
1. The pasta マニュアル shall 目次（サイドバー）の「はじめに」のすぐ下、最初のパート（入門 / チュートリアル）の見出しより前に、番号の無い項目「ダウンロード」を表示する。
2. The pasta マニュアル shall トップページの扉の案内の先頭の項目として「ダウンロード」（英字の添え書き「Download」付き）を表示し、ほかの 7 つの項目をその後ろに今の順で並べる。
3. When 読者が目次または扉の案内の「ダウンロード」を選んだとき, the pasta マニュアル shall ダウンロードのページを開く。
4. The pasta マニュアル shall ダウンロードのページをサイト内検索の対象に含める。

### Requirement 2: やりたいことから取るファイルを選ぶ表
**Objective:** As a ゴースト作者, I want やりたいことから取るファイルを 1 つの表で選びたい, so that 7 つのファイル名を読み比べずに目的のファイルにたどり着ける

#### Acceptance Criteria
1. The ダウンロードのページ shall 本文の先頭に「やりたいこと」と「ファイル」の 2 列の表を 1 つ置き、次の 6 行をこの順で載せる: まずゴーストを動かしてみる → `hello-pasta.nar`／自分のゴーストの `pasta.dll` を差し替える → `pasta.dll.zip`／VS Code を使わずに書く → `pasta-recipe.x64.zip`・`pasta-recipe.arm64.zip`／VS Code で書く → Marketplace の拡張（VSIX は手動で入れるとき）／辞書を検査する・.nar を作る → `pasta_check.zip`／AI に書かせる → `pasta-skills.zip`。
2. The ダウンロードのページ shall 表に今の配布物 7 つ（`pasta.dll.zip`・`hello-pasta.nar`・VSIX・`pasta_check.zip`・`pasta-skills.zip`・`pasta-recipe.x64.zip`・`pasta-recipe.arm64.zip`）をすべて登場させる。
3. When 読者が表のファイル名（VSIX を除く）を選んだとき, the ダウンロードのページ shall 最新のリリースのそのファイルを直接落とす固定のリンク（`releases/latest/download/<ファイル名>`）で落とさせる。
4. When 読者が表の「VS Code で書く」の行のリンクを選んだとき, the ダウンロードのページ shall VS Code Marketplace の pasta 拡張のページを開く。
5. Where VSIX を手動で入れる案内を載せるとき, the ダウンロードのページ shall 版の番号を含む VSIX のファイル名に固定のリンクが無いため、最新のリリースのページ（GitHub Release）へのリンクで案内する（仮定。OPEN QUESTION 3）。

### Requirement 3: ファイルごとの短い説明
**Objective:** As a ゴースト作者, I want 取るファイルの中身・置き場所・注意を短く知りたい, so that 落とした後に何をすればよいかが分かり、詳しい手順の章へ進める

#### Acceptance Criteria
1. The ダウンロードのページ shall 表の下に、配布物ごとの短い説明を並べ、それぞれに中身・展開や置く場所・使っている pasta と版をそろえる注意を書く。
2. The ダウンロードのページ shall 各説明から、そのファイルを使う詳しい手順の章（入門ガイドの「前提環境と準備」「ゴーストの最小一式を置く」、デバッグの「VS Code を使わずに書く（pasta-recipe）」「辞書を検査する（pasta_check validate）」「VSCode 接続と拡張導入」）へリンクする。
3. The ダウンロードのページ shall `pasta-recipe` の 2 つの zip について、自分の Windows の種類（x64 か arm64）に合うほうを選ぶことを書き、種類の見分け方を説明する章の節へリンクする。
4. The ダウンロードのページ shall 固定のリンクが常に最新版を落とすことと、過去の版はリリースページ（GitHub Releases の一覧）から落とせることを書き、リリースページへリンクする。
5. The ダウンロードのページ shall トップページにあった「AI にゴーストを書かせるとき」の内容（`pasta-skills.zip` に入る 3 つのスキルとその役目の表、ゴーストの開発フォルダの `.claude/skills/` への展開と展開後の木、使っている pasta と同じ版の zip を使うこと、版を上げるときは 3 つのフォルダを消してから展開し直す理由）を、欠けなく `pasta-skills.zip` の説明として載せる。
6. The ダウンロードのページ shall 案内役の掛け合い（Claudia とアンソニーの台詞）を置かず、説明本体を地の文の常体で書く。
7. The ダウンロードのページ shall 各配布物の説明の見出しを、ほかの章や README がアンカーで指せる安定した見出しにする。

### Requirement 4: トップページの削り込み
**Objective:** As a ゴースト作者, I want トップページから回り道なしに「ダウンロード → 入門ガイド」へ進みたい, so that 最初の一歩までに読む量が減る

#### Acceptance Criteria
1. The トップページ shall 扉（掛け合いと案内を含む）、2〜3 行の pasta の説明、「まずダウンロード → 入門ガイド」の案内、対象バージョンの表、「将来変更あり」の注記の節、締めの掛け合いとクレジットを残す。
2. The トップページ shall 「まずダウンロード → 入門ガイド」の案内に、ダウンロードのページと入門ガイドへのリンクをこの順で置く。
3. The トップページ shall 「AI にゴーストを書かせるとき」の節と「このマニュアルの歩き方」の節を置かない。
4. The トップページ shall 「関連リンク」から配布物を並べたセルを除き、GitHub リポジトリ（と README）へのリンクを残す。
5. The トップページ shall 対象 pasta バージョンの表の行を今と同じ形（`| 対象 pasta バージョン | **vX.Y.Z** |`）のまま残し、版を Cargo.toml の版と一致させたままにする。
6. The トップページ shall ランタイムの Lua 方言が LuaJIT 2.1 であることの明示と、「将来変更あり」の注記の説明を残す。
7. The トップページ shall 「利用者向けの文法・公開 Lua API・`pasta.toml` の権威はこのマニュアルで、ほかの文書と食い違うときはマニュアルを正とする」旨の一文を残す（仮定。OPEN QUESTION 7）。
8. If 削った節を指していたリンク（見出しのアンカーを含む）がマニュアルの中や読者に届く文書に残っているとき, the pasta マニュアル shall それを移した先（ダウンロードのページの該当の見出し）へ付け替える。

### Requirement 5: ほかの章からの入手の案内の付け替え
**Objective:** As a ゴースト作者, I want どの章から入っても同じ 1 か所で入手先を確かめたい, so that 章ごとに違う入手の説明を読み比べずに済み、配布物が変わっても案内が食い違わない

#### Acceptance Criteria
1. The 入門ガイドの「前提環境と準備」と「ゴーストの最小一式を置く」の章 shall 手順の流れと掛け合いを残したまま、`hello-pasta.nar`・`pasta.dll.zip` をどこで手に入れるかの案内を、ダウンロードのページの該当の説明へのリンクにする（仮定。OPEN QUESTION 5）。
2. The デバッグの「VS Code を使わずに書く（pasta-recipe）」の章 shall zip の入手先の案内をダウンロードのページの該当の説明へのリンクにし、Windows の種類の見分け方・対応する Windows・zip の中身・置き方・起動の説明はこの章に残す。
3. The デバッグの「辞書を検査する（pasta_check validate）」の章 shall `pasta_check.zip` の入手先の案内をダウンロードのページの該当の説明へのリンクにし、展開・中身・呼び方・`cargo install` での入れ方の説明はこの章に残す。
4. The デバッグの「VSCode 接続と拡張導入」の章 shall Marketplace からの導入手順と VSIX の手動導入の手順を残し、VSIX の入手先の案内にダウンロードのページへのリンクを添える。
5. The 付け替えた各章 shall 付け替えの後も、その章の手順だけを読んで作業を最後まで進められる。

### Requirement 6: README からの入手の案内
**Objective:** As a GitHub でリポジトリを最初に開いた人, I want README から入手のページへ迷わず進みたい, so that マニュアルと README で入手の説明が食い違わない

#### Acceptance Criteria
1. The README shall 配布物の入手について、マニュアルのダウンロードのページ（公開マニュアルの URL）へのリンクを置く。
2. The README shall 配布物 7 つを 1 つずつ並べた一覧を置かず、ダウンロードのページへのリンクと過去の版のリリースページへのリンクの短い案内にする（仮定。OPEN QUESTION 2）。
3. The README shall マニュアルのパートを並べた表に、ダウンロードのページの行を足す（仮定。OPEN QUESTION 2）。

### Requirement 7: マニュアルの検査と執筆規約の追従
**Objective:** As a マニュアルの保守者, I want 変更の後もマニュアルの CI の検査がすべて通り、規約が実態と合っている状態を保ちたい, so that main への push でそのまま公開でき、後の spec も同じ規約で書ける

#### Acceptance Criteria
1. When 変更をマニュアルの CI で検査したとき, the pasta マニュアル shall リンクと見出しのアンカーの検査、内容の検査（対象バージョン・LuaJIT 2.1・「将来変更あり」を含む）、台詞部品の記法の検査、着せ替えの検査、スキルの写しの鮮度の照合、入門ガイドの照合をすべて通る。
2. If ダウンロードのページに案内役の掛け合いが無いことを、掛け合いを章の導入と締めに求める検査が不備として報告するとき, the マニュアルの検査 shall ダウンロードのページをその要求の対象から外し、ほかの章への要求は今のまま保つ（仮定。OPEN QUESTION 1）。
3. The 執筆規約 shall ダウンロードのページが掛け合いを置かない章であることを、掛け合いを置ける場所の決まりに書き足す（仮定。OPEN QUESTION 1）。
4. Where 移した記述や付け替えたリンクがスキルの写し（マニュアルから生成するスキルの `references/`）に写っているとき, the pasta マニュアル shall 写しを生成し直して鮮度の照合を通す。
5. If 削った節や変えた見出しを指すアンカーのリンクが残っているとき, the リンクの検査 shall それを不備として報告し、公開を止める。
