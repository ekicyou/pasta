# 暫定の設計の検証: manual-novel-guide

2026-11-19。`provisional-design.md`（以下「設計」）を、書いた人とは別の目で検証した記録である。手順は `kiro-validate-design` と `.kiro/settings/rules/design-review.md` に従った。ただし、今回の取り決めにより、問題の数に上限を置かず、設計は直さず、開発者には何も尋ねていない。正とするのは `novel-areka-contract/final-model-2026-11-19.md`（以下「骨子」）である。

## 判定: GO_WITH_CONDITIONS

既存のコードについての主張は、確かめた範囲では正しく、照合の道具を組の一覧にする作りも、今の道具の上に無理なく乗る。ただし、部の背骨である「段ごとに辞書のファイルを 1 枚足して、1 本のノベルを育てる」形が、最後の行の `＞` で場面をつなぐ物語と両立しない（問題 1）。この点を `hello-novel-sample` と先に決めないと、章立て・照合・見本の作りがまとめて崩れる。ほかに、CI が見本の辞書の変更で起動しない、手書きのスキルの節に挙動を写す、などの大きな問題がある。どれも骨子へ差し戻す必要はなく、この spec の中か、`hello-novel-sample` との取り決めで直せる。

## 問題（重い順）

### 1. 「前の段を書き換えずに 1 枚足す」形では、1 本の物語がつながらない（critical・cross-spec: hello-novel-sample）

- **根拠**: 設計 3.3 の表の下と 7.1 は、「段 N の辞書は段 1〜N のファイルの集まりで、前の段のファイルを書き換えずに次の段になること」を見本に求め、6.1 は「段 01〜07 で、今の SSP で遊べるノベルが 1 本できる」とする。しかし、骨子では、場面は最後の行の `＞` でつながる（骨子 2.1・2.3）。段 1 の最後の場面が段 2 の場面へ `＞` で飛ぶなら、段 1 だけを組み立てた辞書では飛び先が無く、実行時に `【シーンが見つからない：＞…】` が出る（`book/src/reference/runtime-failures.md` 56 行）。逆に、段 1 の最後の場面に `＞` を書かなければ、段 2 はそこへ `＞` を足せない（前の段のファイルを書き換えることになる）。
- 同じ理由で、ローカルシーン（`・OnMouseClick`）は親のグローバルシーンと同じファイルにしか書けない（`grammar.pest` 272〜280 行の `global_scene_scope`・`local_scene_scope`）。段 06 で「その場面だけの反応」を、段 01〜05 の場面へ足すことはできない。段 02 で既にある場面へ柱 `＆曲` を足すことも、前の段の書き換えになる。
- hello-pasta でこの形が成り立つのは、段ごとに独立したイベント（起動・時報・つつき）を足していくからである（`crates/pasta_sample_ghost/STAGES.md` 55〜57 行）。物語は、前の段の最後と次の段の頭がつながっている点で違う。
- 設計 3.3 の `setup.md` は「`＊OnBoot` からタイトルの場面へ飛ぶ」を教えるが、タイトルの場面は段 07（システム画面）で初めて出る（問題 2 も見よ）。
- **提案**: 要件定義の前に、`hello-novel-sample` と次のどれかを決める。(a) 段ごとに独立した短い場面集にする（段 N の入口を、段 N のファイル自身が持つイベントで開く。物語を 1 本にするのは最後の段だけ）。(b) 前の段のファイルを書き換えてよいことにし、照合は「最終の辞書」と「最終の章」の組で行う（このとき段 01 の章が、後の段で足した行を含む全体を見せることになるので、章の作例の範囲を抜き出しに限る決まりが要る）。(c) 段の章を、見本の辞書の抜き出しでなく、段ごとの別の小さな辞書（テスト用の段の辞書の置き場所）に結び付ける。どれを採るかで、4.2 の照合の組と 5.2 の段の表の形が変わる。

### 2. 準備の章が、まだ無い場面への飛び方を、作例なしで教える（major・within-spec）

- **根拠**: 3.3 の表で `novel/setup.md` は辞書の無い章（`—`）なのに、「`＊OnBoot` からタイトルの場面へ飛ぶ」を新しく覚える表現にしている。4.2 の最後の箇条は「入口と画面の章の作例は ```pasta でなく、段の章へのリンクで示す」とする。辞書の無い章に ```pasta を置くと `no-dic` で落ちる（`book/tools/tutorial-check.mjs` 283・290 行）。タイトルの場面は段 07 の物なので、リンク先の段の章もまだ無い。
- **提案**: `＊OnBoot` の飛び先を、段 01 の最初の場面にする（タイトルは段 07 で足す）か、`setup.md` から書き方の説明を外して「見本の一式を置く」手順だけにする。問題 1 の決め方と合わせる。

### 3. 見本の辞書だけを変えた PR では、マニュアルの CI が走らない（major・within-spec）

- **根拠**: R5 は「見本の辞書が変わったら、同じ変更で部の作例が直ること（直さなければ R4 の検査が落ちること）」を求める。しかし `.github/workflows/manual.yml` の起動条件（`on.push.paths`・`on.pull_request.paths`。36〜61 行）は、辞書については hello-pasta の `dic/**` と `calendar.csv`（45〜46 行・59〜60 行）しか持たない。見本のノベルの辞書だけを変えた PR では `tutorial-check.mjs` が走らず、R5 は機械で守られない。設計 8 章の `manual.yml` の行は「145 行の段の注記に書き足す（コマンドは変えない）」だけで、起動条件に触れていない。
- **提案**: 8 章に「`on.push.paths` と `on.pull_request.paths` に、見本のノベルの `dic/**` を足す」を入れる。9 章の表に「見本の辞書だけを変えた PR で、マニュアルの CI が起動する」ことの確かめを足す。

### 4. 手書きのスキルの節に、骨子の決まりを写す（major・within-spec）

- **根拠**: 4.4 は、`authoring-patterns.md` に「骨子の決まりを 1 行ずつ並べた物」を手書きで足す、とする。同じファイルの頭（`.claude/skills/pasta-ghost-authoring/references/authoring-patterns.md` 5 行）は「文法・実行時の挙動はここでは定義しない。挙動は各節から参照する生成ファイル（マニュアルから生成）を正とする」と決めている。決まりを写せば、手書きの節が挙動の 2 つ目の置き場所になり、先行する spec が挙動を変えても、追従を見る検査が無い（`gen-skill-refs.mjs --check` が見るのは生成ファイルだけで、手書きの 3 ファイルは `gen-skill-refs-test.mjs` 110 行の `HANDWRITTEN` として外される）。また brief の Scope の「スキル references の再生成」が、R13 から落ちている。
- **提案**: 手書きの節は、作例（見本の辞書からの抜き出し）と、生成ファイル（先行する spec が `GENERATION_MAP` に足す文法の章）へのリンクだけにする。R13 に「先行する spec が足した文法の章が、スキルの references に生成されていること（`gen-skill-refs.mjs --check` が通ること）」を戻す。対応表に部を足さない判断（10 章の 13）は、それで良い。

### 5. 照合の組が「見本のノベル 1 本・辞書のフォルダ 1 つ」を前提にしている（major・cross-spec: hello-novel-sample）

- **根拠**: 4.2 の `GUIDES[1]` は `dicRel` を 1 つだけ持つ。一方、`hello-novel-sample` の brief は、置き場所（`crates/pasta_sample_ghost` か新しいクレートか）を未決とし（29 行）、「システム画面の場面一式と、そのシェルが、物語と分けて置いてある」こと（21 行）と、「舞台を使う見本は、areka の準備を待つ」こと（112 行）を書く。「ぱすた開発」の台本も 2 本（舞台を使う 1 本と、SSP だけの 1 本。同 111 行）である。見本が 2 本になるか、システム画面が別のフォルダに分かれれば、1 つの `dicRel` では照合できない。`tutorial-check.mjs` の「辞書から章へ」の向き（261〜276 行）は、辞書のフォルダの全部のファイルに同じ名前の章を求めるので、段に属さないファイル（アクター辞書だけのファイルなど）が 1 枚でもあると `no-chapter` で落ちる。
- **提案**: 7.1 の「求める物」に、「段の章に結び付く辞書は 1 つのフォルダにまとめ、そのフォルダには段のファイルだけを置く」ことをはっきり書き、`hello-novel-sample` の要件定義で確かめる。見本が 2 本になるなら、組を 2 つ（または段の範囲ごとに組）にする形を、5.1 の組の形で受けられるようにしておく。

### 6. 「柱は重なる、選ぶための属性は重ならない」の表が、ファイル属性の段を欠く（major・within-spec）

- **根拠**: R6 と 3.4 は、「柱はグローバル → ローカルで重なるが、選ぶための属性（条件・優先など）は重ならない」を表 1 つで示す、とする。しかし、ファイル属性からグローバルシーンへは、条件も含めて全部が重なる（`crates/pasta_dsl/src/parser/ast/attr_merge.rs` 7〜21・25〜47 行の `merge_attrs` と `global_scene_attrs`。`book/src/grammar/block-structure.md` 324〜326 行）。部が段 06 で教える「ファイル属性の `＆＄演劇＝「」`」（骨子 2.3）は、まさにこの重なりに頼っている。グローバル → ローカルで柱が重なるのも、属性の倉の働きでなく、柱を打つ仕組みが階層を引くからである（`cue-command-runtime` の brief 299 行。倉では、ローカルシーンは何も受け継がない。`block-structure.md` 357 行）。brief 98 行の「ローカルシーンは柱を受け継がない」は、この倉の事実から出た文と読める。表が 2 行だけだと、作者は「ファイル属性の条件も、グローバルシーンへは効かない」と読み違えるか、「ローカルシーンにも `＆＄演劇＝「」` が効く」と読み違える。
- **提案**: 表を 3 段にする。ファイル属性 → グローバルシーン（柱も条件も全部重なる）、グローバル → ローカル（柱だけが、打たれる時に重なる）、選ぶための属性（`＄` の条件・`優先`・`重み`・`順番`）はローカルへ流れない。`cue-command-runtime` の文法の章（7.2）と、同じ言い方にそろえる。

### 7. フェーズ 1 の段に、フェーズ 3 の作例を置く（minor・within-spec）

- **根拠**: 3.3 の段 03（フェーズ 1）は、ト書きの束の例に `＞消えて現れる（さくら、窓際）` を使う。`窓際` は席の名前で、席の名前はフェーズ 3 の前半である（`play-script-guide.md` 106 行）。この束の中身（同 129〜141 行）も、転換（フェーズ 3 の前半）で組まれている。R3 の「章の頭で動くフェーズを示す」と食い違う。
- **提案**: 段 03 の束の例は、フェーズ 1 の命令（効果音・待つ・数値の位置・透明度）だけで組む。席の名前と転換を使う束は、段 09 で見せる。

### 8. 数の引数の書き方が、作例どうしでそろっていない（minor・cross-spec: cue-command-runtime）

- **根拠**: 設計の段 03 は `！待つ（「３００」）`・`！時間で次へ（「１０００」）` と「」で囲む。`play-script-guide.md` は `！待つ（３０００）`（99・116 行）・`！転換（１０００）`（113 行）と囲まない。今の文法では、全角の数字だけの引数は数として読める（`grammar.pest` 142〜143 行の `number_literal`・`digit`、229 行の `cue_arg`）。囲むと文字列になる。骨子 2.4 の「数字で始まる引数は「」で囲む」は、`cue-command-runtime` の brief 42 行の「数として読めない、数字で始まる引数（`01教室`）」の話と読める。
- **提案**: 時間の引数をどちらで書くかを `cue-command-runtime` のリファレンスの章に合わせ、部の作例をそろえる。設計の段 03 の書き方は、そのとき直す。

### 9. 「次の行が無い所で進めると何も起きない」は骨子に無い（minor・cross-spec: novel-talk-flow）

- **根拠**: 3.4 の本文の 3 つ目の箇条は、「この場面には次の行が無いので、何も起きない」と言い切る。骨子 2.3 は、拾われない左クリックは「進める」として次の行を返す、最後の行に `＞` が無ければ止まって次のイベントを待つ、とだけ言い、次の行が無い時の「進める」の答えを決めていない（待っている行を出し直す読みもあり得る）。
- **提案**: 仮定と書き、`novel-talk-flow` の要件定義の答えを待つ（7.3 の「求める物」に足す）。

### 10. 作者に効く骨子の決まりが、章の計画から漏れている（minor・within-spec）

- **根拠**: 骨子 2.1 の「演劇と設定のモードの間は、時報とランダムトークを返さない」は、デスクトップのゴーストに演劇を足す作者に直接効くが、3.3 の表のどの章にも無い。骨子 2.6 のオート・高速再生・既読（遊ぶ人の操作。フェーズ 1）も、段 07 の設定の口（10 章の 7）以外に置き場所が無い。brief の Desired Outcome の合格ラインに挙がっている物である。
- **提案**: 段 01 か入口の章に「演劇の間は時報とランダムトークが出ない」を足す。遊ぶ人の操作（進める・オート・高速再生・既読で止まる・バックログ）は、入口か段 07 に、作者が書かなくても動く物として 1 か所にまとめる。

### 11. 画面の章が、取り決めの語彙を写すおそれ（minor・within-spec）

- **根拠**: R9 は「シェルの仕様と取り決めの語彙は写さないこと」と決めるが、3.3 の `screen.md` の中身は「舞台の定義（`descript.txt` の areka の独自キー）」「基準の大きさ 1920×1080」を含む。これは取り決め（骨子 2.7・2.8。`novel-areka-contract` の持ち分）の語彙である。
- **提案**: `screen.md` は、pasta の場面との噛み合わせ（当たり判定の名前が `＄ｒ４` に入る・アクターの名前と並び・トークの場所の役）だけを書き、キーの名前と値は取り決めの章へのリンクにする。

### 12. 段 08 を辞書の無い段にすると、作例を置けない（minor・cross-spec: hello-novel-sample）

- **根拠**: 10 章の 6 は、見本が段 08 の辞書を足さなければ「手順だけの段」にする、とする。辞書の無い段の章に ```pasta を置くと `no-dic` で落ちる（`tutorial-check.mjs` 290 行）。R7 の「ロードで戻したい曲と舞台は柱に書く」は、作例なしでは伝わりにくい。14 段目の配布（コードの要らない段）とは事情が違う。
- **提案**: 7.1 の「求める物」に、段 08 の辞書（柱で曲を戻す場面と、戻らないグローバル変数を使う場面）を足す。

### 13. 表の無い組で csv の照合を飛ばすと、検査が弱くなる（minor・within-spec）

- **根拠**: 4.2 は `calendarRel: null` なら csv の照合を飛ばす、とする。今の作り（`tutorial-check.mjs` 299〜317 行）では、表が無ければ、章の ```csv ブロックは `no-calendar` で落ちる。飛ばすと、部の章に置いた ```csv が照合されずに通る。
- **提案**: `null` のときも、今と同じく `no-calendar` で落とす（照合の結果の行を足さないだけにする）。`tutorial-check-test.mjs` の新しい自己テストに、この場合を入れる。

### 14. 道具の出す文言が、入門と hello-pasta に決め打ちのまま（minor・within-spec）

- **根拠**: `reportTutorialCheck` の見出しと対処の文（`tutorial-check.mjs` 334・340・357〜360 行）は「入門の章」「hello-pasta」「`GUIDE_REL`」「`CALENDAR_REL`」を書き込んでいる。246・251 行の `fatal` の文も同じである。組を足しても、部の失敗が入門の言葉で出る。
- **提案**: 文言を組の `id`・`guideRel`・`dicRel` から作る。8 章の表の `tutorial-check.mjs` の行に足す。

### 15. 段の章の件数を、検査と同じフォルダから数える（minor・within-spec）

- **根拠**: 4.3 は、`verify-scripts-test.mjs` の N 系の件数を「部のフォルダの段の章から数える」とする。`verify-content.mjs` の N 系も同じフォルダを列挙するので、目次に載せ忘れた章や、フォルダに置き忘れた章の食い違いを、この件数では見つけられない（N-order が見るのは目次との並びだけ）。今の T 系の件数は、目次から数えている（`verify-scripts-test.mjs` 83〜88 行の `summaryChapters`）。
- **提案**: N 系の件数も、目次 `SUMMARY.md` の `novel/` の章から数える。

### 16. フェーズの表示（R3）を、機械で確かめない（minor・within-spec）

- **根拠**: R3 は段の章の頭でフェーズを示すことを求めるが、9 章の表に、それを見る検査が無い。レビューだけに任されている。
- **提案**: N 系に「段の章の頭（`## 叶えたいこと` の前）にフェーズの表記がある」検査を 1 つ足すか、レビューで確かめると明記する。

### 17. 「シーンの頭の自動セーブ」という呼び方（minor・within-spec）

- **根拠**: 3.3 の段 07 の「シーンの頭の自動セーブ」は、`hello-novel-sample` の brief 110 行の言葉をそのまま使っている。中身は、作者がシーンの頭に書く `＞スロット保存`（骨子 2.5「シーンの頭に書いた保存は、そのシーンの頭から続く」）であり、pasta が自動で保存するわけではない。「自動で起きる振る舞いを足さない」という原則の下では、作者が「pasta が勝手に保存する」と読み違えやすい。
- **提案**: 本文では「シーンの頭に書いたセーブ」と呼ぶ。

### 18. アクター指定行の「シーンの頭」が、どのシーンかがはっきりしない（minor・model）

- **根拠**: 骨子 2.4 は「アクター指定行は、シーンの頭にだけ書ける」と言う。今の文法では、グローバルシーンの頭にしか書けない（`grammar.pest` 274 行の `global_scene_init`。280 行の `local_scene_item` には無い）。設計 12 章は「骨子と合う」とするが、柱がグローバル → ローカルで重なる今の骨子では、「ローカルシーンの頭に並びを書いて、並びを替える」と読む作者が出る。
- **提案**: 部では「グローバルシーンの頭」と書く。骨子の側で、ローカルシーンの頭にも書けるようにする意図が無いことを、`cue-command-runtime` の要件定義で確かめる。

### 19. 生成スキルの「ほか」が落ちている（minor・within-spec）

- **根拠**: brief の Desired Outcome は「生成スキル（`pasta-ghost-authoring` ほか）」と言う。R13 は `pasta-ghost-authoring` だけである。ベースウェアを判定する Lua の公開関数（骨子 2.4）は `pasta-lua-coding` の持ち場になる。
- **提案**: R13 に、`pasta-lua-coding` は先行する spec の生成で足りる（この部からは何も足さない）ことを、判断として書き添える。
