# 執筆規約（Claudia 令嬢ボイスガイド＋権威と生成）

本書 `book/AUTHORING.md` は、pasta 利用者マニュアルの**執筆者向け内部規約**である。各内容章は本規約に準拠して執筆する。本ファイルは `SUMMARY.md` に掲載せず、公開サイトには含まれない（mdBook ビルド対象外）。

本マニュアルは利用者向け情報の**唯一の権威**であり、スキルの規範ファイルはマニュアルから生成される（第 4 節）。

> 対応要件: pasta-user-manual Requirement 7（執筆方針＝ボイス・トーン）、manual-ssot-authority Requirement 9.4（権威と生成）。
> 関連設計: pasta-user-manual design.md の Voice & Tone Guide／manual-ssot-authority design.md の GenSkillRefs・LinkCheck。

## 1. Claudia 令嬢ボイスの定義

本書の案内役は「**Claudia 令嬢**」。次の人物像で一貫させる。

- **一人称は「わたくし」**。お嬢様口調（「〜ですわ」「〜ますの」「おほほ」）を基調とする。
- **悪役令嬢風だが面倒見が良いツンデレ**。素直になりきれない励まし方をする（例:「フンッ、別にあなたのためじゃありませんわよ」）。
- **内に松岡修造的な熱血**を秘める。要所で読者の背中を押す（例:「さあ、熱く参りましょう！」）。
- **知識チートで的確**。説明は常に正確で、迷っている読者を最短距離で導く。

### 鉄則

味付け（キャラ口調）は読者を引き込むための装飾であり、**技術的正確さを最優先する**。口調によって説明が読みにくくなる、あるいは誤読の余地が生まれるなら、迷わず普通の文体を選ぶこと。

各章は次のリズムを基本形とする。

> **軽い導入（キャラ口調）→ 淡々とした本体（普通文体）→ ひとことの締め（キャラ口調）**

## 2. 文体の使い分け表（Do / Don't）

| パート | 文体 | Do | Don't |
| ------ | ---- | --- | ----- |
| 章の導入・読者への語りかけ | Claudia 令嬢のキャラ口調 | 章の狙いを一言で示し、学習意欲を引き出す | だらだらと長い前口上で本題を遅らせる |
| 章の繋ぎ・コラム・励まし | キャラ口調（生成対象章では導入・締めに限る） | 短く挟んでリズムを作る | キャラ語りに技術的説明を埋め込む |
| 章の締め | キャラ口調（ひとこと） | 次章への橋渡しや励ましで締める | 締めに新しい仕様を持ち込む |
| 仕様・構文・手順・API の**説明本体** | 普通の文体（淡々・正確・読みやすさ優先） | 主語と対象を明確にし、箇条書き・表で整理する | 「〜ですわ」等の口調で説明本体を書く |
| **コードブロック内**（`.pasta` / Lua / シェル） | 文体なし（コードのみ） | 動作するコードと、必要なら普通文のコメント | コメントや文字列にキャラ口調を入れる |
| **表のセル** | 文体なし（簡潔な記述） | 用語・値・説明を簡潔に | セル内をキャラ口調で飾る |
| **構文定義（EBNF 等）・コマンド例** | 文体なし（定義・コマンドのみ） | 正確な定義／実行可能なコマンド | 定義文やコマンド注釈にキャラ口調を混ぜる |

**キャラ口調を絶対に持ち込まない場所**（Requirement 7.4）:
コードブロック内、表のセル、構文定義（EBNF 等）、コマンド例、サンプル `.pasta` / Lua コード。これらは「正確さの母体」であり、装飾は禁止する。

## 3. 基準ボイスサンプル

後続の全内容章が**コピペ的に倣える**具体例を以下に示す。導入・本体・締めの 3 パートを 1 セットとし、grammar 章冒頭を模した例を提示する。新しい章を書くときは、この型をそのまま下敷きにすること。

### サンプル A: 文法章（grammar）の冒頭

```markdown
# シーンを定義する

わたくし Claudia が、ゴーストの心臓部――「シーン」の書き方を手ほどきいたしますわ。
むずかしく考える必要はございません。要は「いつ、誰が、何を話すか」を並べるだけですの。
さあ、肩の力を抜いて参りましょう。

---

シーンは会話のひとまとまりを表す単位である。行頭に `＊`（全角アスタリスク）
または `*`（半角アスタリスク）を置き、続けてシーン名を書くことで定義する。
シーン本体は、インデントしたアクション行で記述する。

```pasta
＊挨拶
    ぱすた：こんにちは！
    ラザニア：ごきげんよう！
```

同じ名前のシーンを複数定義した場合、実行時にそのうち 1 つがランダムに選択される。
これにより、毎回同じ反応にならない自然な会話を作れる。

| 要素 | マーカー | 役割 |
| ---- | -------- | ---- |
| グローバルシーン | `＊` / `*` | シーン定義 |
| アクション行 | （なし） | キャラクターの発言 |

---

ね、案外かんたんでしたでしょう？ フンッ、別にあなたが優秀だなんて言っていませんわよ。
次は、このシーンを呼び出す方法を覚えていきましょう。熱く参りますわよ！
```

このサンプルで確認すべき要点:

- **導入**（最初の段落）はキャラ口調。章で扱う対象を一言で示し、読者を引き込む。
- `---` で導入と本体を視覚的に区切る。
- **本体**（説明・コードブロック・表）は普通文体。コードブロックの中身（`＊挨拶` 等）にも、表のセルにもキャラ口調を入れない。
- **締め**（最後の段落）はキャラ口調のひとこと。励ましつつ次章へ橋渡しする。

### サンプル B: 手順章（getting-started）の冒頭

```markdown
# はじめてのゴーストを作る

ようこそ、ゴースト作りの世界へ。わたくしが最後まで付き添いますから、
ご安心なさいまし。最初の一歩は、誰だって手が震えるものですわ。
……フンッ、わたくしは震えませんでしたけれど。

---

このチュートリアルでは、ゼロから動作する最小限のゴーストを作成する。
作業を始める前に、次の準備が整っていることを確認すること。

- Windows 環境（本マニュアルは Windows を対象とする）
- ベースウェア SSP のインストール
- テキストエディタ（UTF-8 で保存できるもの）

`.pasta` 辞書ファイルは必ず **UTF-8** で保存する。旧来の Shift_JIS で
保存した辞書は文字化けの原因になるため、移行時は文字コードに注意すること。

---

準備はよろしくて？ では、最初のシーンを書いていきましょう。
怖がらず、一行ずつ確実に。わたくしがついておりますわ。
```

要点はサンプル A と同じ。前提環境や注意（UTF-8 等）は本体（普通文体）で正確に書き、励ましは導入・締め（キャラ口調）に寄せる。

## 4. 権威と生成

### 基本原則

1. **マニュアルが唯一の権威**である。利用者向け情報（文法・公開 Lua API・`pasta.toml`・起動シーケンス）は `book/src/` の各章を正とし、steering の要約やスキルなど他の文書と食い違う場合はマニュアルを優先する。
2. **スキルの規範ファイルは生成物**である。スキル `pasta-ghost-authoring`・`pasta-lua-coding` の `references/` のうち、1 行目が `<!-- GENERATED FROM PASTA MANUAL - DO NOT EDIT -->` のファイルはマニュアルの対応章から生成される。編集元はマニュアルの章であり、生成ファイルを手で編集しない。`SKILL.md` と生成ヘッダを持たない手書きファイルは従来どおり直接編集する。
3. **生成対象章の一覧は生成器の対応表が正**である。`book/tools/gen-skill-refs.mjs` の `GENERATION_MAP`（章 → スキル）を参照し、本規約には一覧を複製しない。出力名は章のファイル名と同じで、`index.md` だけ親ディレクトリ名を付ける（例: `grammar/index.md` → `grammar-index.md`、`lua/modules/index.md` → `modules-index.md`）。
4. **生成対象章を変更したら再生成してコミット**する。章と生成物を同じコミットに含める。

### 再生成と検証のコマンド

```sh
node book/tools/gen-skill-refs.mjs          # 再生成（内容が同じファイルは書き換えない）
node book/tools/gen-skill-refs.mjs --check  # 照合（不一致・孤立ファイルがあれば一覧を出して exit 1）
node book/tools/link-check.mjs              # リンク検証（マニュアルのリンク切れ＋スキルの自己完結）
```

生成に失敗した場合（構造違反・本文の口調・解決できないリンク）は、章パスと理由が標準エラーに出て exit 1 となり、何も書き出されない。章を直して再実行する。

### 生成対象章の執筆規約

生成対象章は通常の章の規約に加え、次を守る。章構造・本文の口調・解決できないリンクは生成器（`gen-skill-refs.mjs`）、リポジトリ内パスとスキル内アンカーはリンク検証（`link-check.mjs`）、`pasta.toml` の表形式は `cargo test`（`config_defaults_test`）が検査する。作例の構文と参照形式・HTML タグのリンクは機械検査されないため、書き手が確認する。

- **章構造**: 先頭行は H1（`# `）。コードフェンス外で行全体が `---` の行を区切りとし、最初の `---` より前が導入、最後の `---` より後が締め、その間が本文となる。生成物に入るのは H1 と本文だけで、導入と締めは捨てられる。本文の途中にある `---` はそのまま残る。区切りが 2 本未満、または先頭行が H1 でない章は生成に失敗する（`bad-structure`）。
- **本文に口調・コラムを置かない**: 本文の散文部（コードフェンス・表の行・インラインコードを除く。見出しと引用ブロックは含む）に口調マーカー（`gen-skill-refs.mjs` の `VOICE_MARKERS`）が現れると、行番号と語を示して生成に失敗する（`voice-in-body`）。コラム・励ましは導入か締めへ置く。作例の台詞に口調を含めたい場合はコードフェンス内に置く。
- **口調マーカーと衝突する語**: マーカーは部分一致のため、普通文体の語と衝突しうる。確認済みの「書かなくてよい」（`くてよ`）・「ですので」（`ですの`）・「ますので」（`ますの`）は、マーカー側を否定先読み（例: `ですの(?!で)`）にして判定から除外済みであり、言い換えは不要である。新たな衝突語が見つかった場合も本文を言い換えず、`VOICE_MARKERS` の該当語を同じ方法で直す（判定関数 `findVoice` は `verify-content.mjs` と共用）。
- **リンクの書き換え**: 書き換え対象はフェンス外・インラインコード外のインラインリンク `[text](target)` だけである。
  - 絶対 URL（`https://` 等）と `#anchor` のみのリンクはそのまま残る。
  - 章外への相対 `.md` リンク（アンカー付き可）は、リンク先が同じスキルの生成対象章なら兄弟ファイル名（例は `lua/modules/` の章から: `../shiori-events.md` → `shiori-events.md`）、それ以外（生成対象外の章・別スキルの章）なら公開 URL（例: `../patterns.md` → `https://ekicyou.github.io/pasta/lua/patterns.html`）に書き換わる。アンカーはそのまま渡る。
  - 同じスキル内へのアンカーは `link-check.mjs` が GitHub 方式の見出し slug で照合する。slug は見出しの生テキストから作るため、見出しに強調（`_x_` 等）や全角空白を入れない。
- **使わないリンク**: 相対パスの画像、`.md` 以外への相対リンク、`book/src/` の外へ出る相対リンクは生成に失敗する（`unresolvable-link`）。参照形式リンク（`[text][ref]`）と HTML タグのリンクは書き換えられないため使わない。
- **リポジトリ内パスを書かない**: 生成物はファイル全文（コードフェンス・HTML コメント内を含む）が `link-check.mjs` の禁止トークン（`FORBIDDEN_SKILL_TOKENS`。`book/src`・`crates/` 等）で検査される（`skill-forbidden-ref`）。部分一致のため絶対 URL も対象となり、crates.io の URL（`crates/` を含む）は書けない。クレートへのリンクは docs.rs 等を使い、Lua モジュールはファイルパスではなくモジュール名（例: `lua_test.mocks`）で書く。
- **作例**: 情報文字列 `pasta` のコードブロックは実パーサで通る形で書く。アクション行や引用なしの単語値の行末に `#` 注記を付けると台詞・値の一部になるため付けない。図示用の断片は情報文字列 `text` にする。
- **`pasta.toml` リファレンス章の表形式**: `reference/pasta-toml.md` は、検査対象の 4 キー（`talk_interval_min`・`talk_interval_max`・`hour_margin`・`spot_newlines`）について、キー名と `` `既定値` ``（例: `` `180` ``）を同じ表行に書く。`crates/pasta_lua/tests/loader/config_defaults_test.rs` の `config_reference_doc_matches_ssot` が章の各行を走査し、キー名と既定値を含む行があるかを照合する。値を別の行に分けると失敗する。同じキーの行が複数ある場合はどれか 1 行で合格してしまうため、既定値を変えるときはすべての行を更新する。

### 外部リファレンスのリンク方針

- 素の Lua 言語仕様は**取り込まず、リンク参照のみ**とする。リンク先は対象方言（**LuaJIT 2.1 / Lua 5.1 系**）に対応するもの:
  - 日本語 Lua リファレンス（Lua 5.1 / 5.2 相当、例: milkpot 版）
  - LuaJIT 公式ドキュメント（luajit.org、英語）
- 版の離れた **Lua 5.5 系資料は言語リファレンスとして案内しない**（ランタイム方言と不一致のため。Requirement 8.3）。

## 5. 執筆チェックリスト

新しい章を書き終えたら、以下を確認すること。

- [ ] 導入・締めが Claudia 令嬢のキャラ口調になっている（Requirement 7.1）。
- [ ] 仕様・構文・手順・API の説明本体が普通の文体で書かれている（Requirement 7.2）。
- [ ] コードブロック・表・構文定義・コマンド例の内部にキャラ口調が入っていない（Requirement 7.4）。
- [ ] キャラ口調によって技術的内容が不正確・読みにくくなっていない（Requirement 7.3）。
- [ ] 生成対象章（`GENERATION_MAP` に載る章）は第 4 節「生成対象章の執筆規約」を満たしている。
- [ ] 生成対象章を変更したら `node book/tools/gen-skill-refs.mjs` で再生成し、生成物を章と同じコミットに含めた（`--check` と `node book/tools/link-check.mjs` が exit 0）。
- [ ] 外部 Lua リファレンスは LuaJIT 2.1 / Lua 5.1 系に対応したものを案内している（lua55 系は不可。Requirement 8.2 / 8.3）。
