# 執筆規約（Claudia 令嬢ボイスガイド＋権威と生成）

本書 `book/AUTHORING.md` は、pasta 利用者マニュアルの**執筆者向け内部規約**である。各内容章は本規約に準拠して執筆する。本ファイルは `SUMMARY.md` に掲載せず、公開サイトには含まれない（mdBook ビルド対象外）。

本マニュアルは利用者向け情報の**唯一の権威**であり、スキルの規範ファイルはマニュアルから生成される（第 4 節）。

> 対応要件: pasta-user-manual Requirement 7（執筆方針＝ボイス・トーン）、manual-ssot-authority Requirement 9.4（権威と生成）、pasta-runtime-internals-doc Requirement 1.7・3.3・3.5・3.6・4.1（内部設計パートの執筆規約）、manual-claudia-theme Requirement 4.5・4.6（台詞部品）、getting-started-story-guide Requirement 8（入門ガイドの執筆規約）。
> 関連設計: pasta-user-manual design.md の Voice & Tone Guide／manual-ssot-authority design.md の GenSkillRefs・LinkCheck／manual-claudia-theme design.md の AuthoringGuide。

## 1. Claudia 令嬢ボイスの定義

本書の案内役は「**Claudia 令嬢**」。次の人物像で一貫させる。

- **一人称は「わたくし」**。お嬢様口調（「〜ですわ」「〜ますの」「おほほ」）を基調とする。
- **悪役令嬢風だが面倒見が良いツンデレ**。素直になりきれない励まし方をする（例:「フンッ、別にあなたのためじゃありませんわよ」）。
- **内に松岡修造的な熱血**を秘める。要所で読者の背中を押す（例:「さあ、熱く参りましょう！」）。
- **知識チートで的確**。説明は常に正確で、迷っている読者を最短距離で導く。

### アンソニー（執事）の人物像と口調

章の導入と締めは、Claudia と執事の「**アンソニー**」の二人の掛け合いで書く（記法は第 7 節）。アンソニーは次の人物像で一貫させる。口調は参考サイト（ponapalt/claudia）のアンソニーの台詞を手本にする。

- **Claudia に仕える執事**。お嬢様の一歩後ろに控え、前に出すぎない。
- **執事の丁寧語**で話す（「〜でございます」「左様でございますか。」「お嬢様、それは〜でございます。」）。
- **役どころは相づち・補足・手綱引き**。Claudia の話を受けて要点を一言で言い直す、読者が抱きそうな疑問を代わりに尋ねる、熱くなりすぎたお嬢様をたしなめる。
- **冷静が芯**。感情を表に出しすぎない。身も蓋もない事実を淡々と言う・質問で返す・一言で落とす、が持ち味である。からかっても、相手を本気で傷つける言い方はしない。
- **令嬢口調に寄らない**。Claudia の口調マーカー（`gen-skill-refs.mjs` の `VOICE_MARKERS`。「〜ですわ」「おほほ」「わたくし」など）をアンソニーの台詞に入れない。一人称が要るときは「私」と書く。逆に、Claudia が淡々とした丁寧語だけで話すこともしない。

### 鉄則

味付け（キャラ口調）は読者を引き込むための装飾であり、**技術的正確さを最優先する**。口調によって説明が読みにくくなる、あるいは誤読の余地が生まれるなら、迷わず普通の文体を選ぶこと。

各章は次のリズムを基本形とする。

> **軽い導入（二人の掛け合い）→ 淡々とした本体（普通文体）→ ひとことの締め（二人の掛け合い）**

ただし、入門ガイド（`book/src/getting-started/`）だけは本体も台詞部品で語る（第 8 節）。

## 2. 文体の使い分け表（Do / Don't）

| パート | 文体 | Do | Don't |
| ------ | ---- | --- | ----- |
| 章の導入・読者への語りかけ | 台詞部品による二人の掛け合い（Claudia とアンソニー） | 章の狙いを一言で示し、学習意欲を引き出す | だらだらと長い前口上で本題を遅らせる |
| 章の繋ぎ・コラム・励まし | キャラ口調（生成対象章・内部設計章では導入・締めに限る） | 短く挟んでリズムを作る | キャラ語りに技術的説明を埋め込む |
| 章の締め | 台詞部品による二人の掛け合い（短く） | 次章への橋渡しや励ましで締める | 締めに新しい仕様を持ち込む |
| 仕様・構文・手順・API の**説明本体** | 普通の文体（淡々・正確・読みやすさ優先） | 主語と対象を明確にし、箇条書き・表で整理する | 「〜ですわ」等の口調で説明本体を書く |
| **コードブロック内**（`.pasta` / Lua / シェル） | 文体なし（コードのみ） | 動作するコードと、必要なら普通文のコメント | コメントや文字列にキャラ口調を入れる |
| **表のセル** | 文体なし（簡潔な記述） | 用語・値・説明を簡潔に | セル内をキャラ口調で飾る |
| **構文定義（EBNF 等）・コマンド例** | 文体なし（定義・コマンドのみ） | 正確な定義／実行可能なコマンド | 定義文やコマンド注釈にキャラ口調を混ぜる |

入門ガイド（`book/src/getting-started/`）の説明本体は、この表の「説明本体」の行ではなく第 8 節に従う。

**キャラ口調を絶対に持ち込まない場所**（Requirement 7.4）:
コードブロック内、表のセル、構文定義（EBNF 等）、コマンド例、サンプル `.pasta` / Lua コード。これらは「正確さの母体」であり、装飾は禁止する。台詞部品もこれらの中には置けず、これらの代わりにも使えない（第 7 節「書けない内容」）。

## 3. 基準ボイスサンプル

後続の全内容章が**コピペ的に倣える**具体例を以下に示す。導入・本体・締めの 3 パートを 1 セットとし、grammar 章冒頭を模した例を提示する。新しい章を書くときは、この型をそのまま下敷きにすること。導入・締めは台詞部品（第 7 節）による二人の掛け合いで書く。サンプルはコードフェンスの中にあるため、検査ツールの対象にはならない。

### サンプル A: 文法章（grammar）の冒頭

````markdown
# シーンを定義する

> 【にっこり】ゴーストの心臓部――「シーン」の書き方を、わたくし Claudia が手ほどきいたしますわ。

> 【アンソニー】お嬢様、シーンとは要するに何でございましょう。

> 【したり顔】「いつ、誰が、何を話すか」を並べたものですの。むずかしく考える必要はございませんわ。

---

シーンは会話のひとまとまりを表す単位である。行頭に `＊`（全角アスタリスク）
または `*`（半角アスタリスク）を置き、続けてシーン名を書くことで定義する。
シーン本体は、インデントしたアクション行で記述する。

```pasta
＊挨拶
    ぱすた：こんにちは！
    ラザニア：ごきげんよう！
```

同じ名前のシーンを複数定義した場合、実行時にそのうち 1 つがランダムに選択される。
これにより、毎回同じ反応にならない自然な会話を作れる。

| 要素 | マーカー | 役割 |
| ---- | -------- | ---- |
| グローバルシーン | `＊` / `*` | シーン定義 |
| アクション行 | （なし） | キャラクターの発言 |

---

> 【にっこり】ね、案外かんたんでしたでしょう？ 次は、このシーンを呼び出す方法を覚えていきますわよ。熱く参りましょう！

> 【アンソニー】お嬢様、読者の方より先に熱くなっておいでです。
````

このサンプルで確認すべき要点:

- **導入**は 3 つの吹き出しの「振り→返し→落ち」。Claudia が章の話題を振り、アンソニーが読者の疑問を代わりに尋ね、Claudia が受けて本体へつなぐ。
- `---` で導入と本体を視覚的に区切る。台詞と `---` の間には空行を入れる。
- **本体**（説明・コードブロック・表）は普通文体。コードブロックの中身（`＊挨拶` 等）にも、表のセルにもキャラ口調を入れない。台詞部品も置かない。
- **締め**は 2 つの吹き出し。Claudia が励ましつつ次章へ橋渡しし、アンソニーが一言で手綱を引いて軽く落とす。
- 掛け合いを読み飛ばしても、本体だけで章の内容が通じる。台詞にしか無い技術情報は書かない。

### サンプル B: 手順章の冒頭

入門ガイド（`book/src/getting-started/`）の章は、この型ではなく第 8 節の型で書く。

````markdown
# はじめてのゴーストを作る

> 【お辞儀】ゴースト作りの世界へようこそ。わたくしが最後まで付き添いますから、ご安心なさいまし。

> 【アンソニー】最初の一歩は、どなたでも手が震えるものでございます。

> 【照れ】……フンッ、わたくしは震えませんでしたけれど。

---

このチュートリアルでは、ゼロから動作する最小限のゴーストを作成する。
作業を始める前に、次の準備が整っていることを確認すること。

- Windows 環境（本マニュアルは Windows を対象とする）
- ベースウェア SSP のインストール
- テキストエディタ（UTF-8 で保存できるもの）

`.pasta` 辞書ファイルは必ず **UTF-8** で保存する。旧来の Shift_JIS で
保存した辞書は文字化けの原因になるため、移行時は文字コードに注意すること。

---

> 【にっこり】準備はよろしくて？ 怖がらず、一行ずつ確実に。わたくしがついておりますわ。

> 【アンソニー：刮目】おや、お嬢様が今日はずいぶん素直でいらっしゃる。
````

要点はサンプル A と同じ。前提環境や注意（UTF-8 等）は本体（普通文体）で正確に書き、励ましは導入・締め（掛け合い）に寄せる。サンプル A との違いは掛け合いの型である。導入ではアンソニーの相づちが Claudia の強がりを引き出し、「……」で始まる照れで落とす。締めでは、素直に励ます Claudia にアンソニーが刮目で驚いて落とす（刮目はこの 1 回だけ）。章ごとに型を変えて、読者を飽きさせない。

## 4. 権威と生成

### 基本原則

1. **マニュアルが唯一の権威**である。利用者向け情報（文法・公開 Lua API・`pasta.toml`・起動シーケンス）は `book/src/` の各章を正とし、steering の要約やスキルなど他の文書と食い違う場合はマニュアルを優先する。
2. **スキルの規範ファイルは生成物**である。スキル `pasta-ghost-authoring`・`pasta-lua-coding` の `references/` のうち、1 行目が `<!-- GENERATED FROM PASTA MANUAL - DO NOT EDIT -->` のファイルはマニュアルの対応章から生成される。編集元はマニュアルの章であり、生成ファイルを手で編集しない。`SKILL.md` と生成ヘッダを持たない手書きファイルは従来どおり直接編集する。
3. **生成対象章の一覧は生成器の対応表が正**である。`book/tools/gen-skill-refs.mjs` の `GENERATION_MAP`（章 → スキル）を参照し、本規約には一覧を複製しない。出力名は章のファイル名と同じで、`index.md` だけ親ディレクトリ名を付ける（例: `grammar/index.md` → `grammar-index.md`、`lua/modules/index.md` → `modules-index.md`）。
4. **生成対象章を変更したら再生成してコミット**する。章と生成物を同じコミットに含める。

### 再生成と検証のコマンド

```sh
node book/tools/gen-skill-refs.mjs          # 再生成（内容が同じファイルは書き換えない）
node book/tools/gen-skill-refs.mjs --check  # 照合（不一致・孤立ファイルがあれば一覧を出して exit 1）
node book/tools/link-check.mjs              # リンク検証（マニュアルのリンク切れ＋スキルの自己完結）
```

生成に失敗した場合（構造違反・本文の台詞・本文の口調・解決できないリンク）は、章パスと理由が標準エラーに出て exit 1 となり、何も書き出されない。章を直して再実行する。

### 生成対象章の執筆規約

生成対象章は通常の章の規約に加え、次を守る。章構造・本文の台詞・本文の口調・解決できないリンクは生成器（`gen-skill-refs.mjs`）、リポジトリ内パスとスキル内アンカーはリンク検証（`link-check.mjs`）、`pasta.toml` の表形式は `cargo test`（`config_defaults_test`）が検査する。作例の構文と参照形式・HTML タグのリンクは機械検査されないため、書き手が確認する。

- **章構造**: 先頭行は H1（`# `）。コードフェンス外で行全体が `---` の行を区切りとし、最初の `---` より前が導入、最後の `---` より後が締め、その間が本文となる。生成物に入るのは H1 と本文だけで、導入と締めは捨てられる。本文の途中にある `---` はそのまま残る。区切りが 2 本未満、または先頭行が H1 でない章は生成に失敗する（`bad-structure`）。
- **本文に台詞部品を置かない**: 台詞部品（第 7 節）は導入と締めにだけ置ける。本文に台詞の開始行（行頭の `> 【`）や、字下げ・リスト・入れ子の引用の中の台詞があると、行番号を示して生成に失敗する（`talk-in-body`）。口調より先に検査される。
- **本文に口調・コラムを置かない**: 本文の散文部（コードフェンス・表の行・インラインコードを除く。見出しと引用ブロックは含む）に口調マーカー（`gen-skill-refs.mjs` の `VOICE_MARKERS`）が現れると、行番号と語を示して生成に失敗する（`voice-in-body`）。コラム・励ましは導入か締めへ置く。作例の台詞に口調を含めたい場合はコードフェンス内に置く。
- **口調マーカーと衝突する語**: マーカーは部分一致のため、普通文体の語と衝突しうる。確認済みの「書かなくてよい」（`くてよ`）・「ですので」（`ですの`）・「ますので」（`ますの`）は、マーカー側を否定先読み（例: `ですの(?!で)`）にして判定から除外済みであり、言い換えは不要である。新たな衝突語が見つかった場合も本文を言い換えず、`VOICE_MARKERS` の該当語を同じ方法で直す（判定関数 `findVoice` は `verify-content.mjs` と共用）。
- **リンクの書き換え**: 書き換え対象はフェンス外・インラインコード外のインラインリンク `[text](target)` だけである。
  - 絶対 URL（`https://` 等）と `#anchor` のみのリンクはそのまま残る。
  - 章外への相対 `.md` リンク（アンカー付き可）は、リンク先が同じスキルの生成対象章なら兄弟ファイル名（例は `lua/modules/` の章から: `../shiori-events.md` → `shiori-events.md`）、それ以外（生成対象外の章・別スキルの章）なら公開 URL（例: `../patterns.md` → `https://ekicyou.github.io/pasta/lua/patterns.html`）に書き換わる。アンカーはそのまま渡る。
  - 同じスキル内へのアンカーは `link-check.mjs` が GitHub 方式の見出し slug で照合する。slug は見出しの生テキストから作るため、見出しに強調（`_x_` 等）や全角空白を入れない。
- **使わないリンク**: 相対パスの画像、`.md` 以外への相対リンク、`book/src/` の外へ出る相対リンクは生成に失敗する（`unresolvable-link`）。参照形式リンク（`[text][ref]`）と HTML タグのリンクは書き換えられないため使わない。
- **リポジトリ内パスを書かない**: 生成物はファイル全文（コードフェンス・HTML コメント内を含む）が `link-check.mjs` の禁止トークン（`FORBIDDEN_SKILL_TOKENS`。`book/src`・`crates/` 等）で検査される（`skill-forbidden-ref`）。部分一致のため絶対 URL も対象となり、crates.io の URL（`crates/` を含む）は書けない。クレートへのリンクは docs.rs 等を使い、Lua モジュールはファイルパスではなくモジュール名（例: `lua_test.mocks`）で書く。
- **作例**: 情報文字列 `pasta` のコードブロックは実パーサで通る形で書く。アクション行や引用なしの単語値の行末に `#` 注記を付けると台詞・値の一部になるため付けない。図示用の断片は情報文字列 `text` にする。
- **`pasta.toml` リファレンス章の表形式**: `reference/pasta-toml.md` は、検査対象の 4 キー（`talk_interval_min`・`talk_interval_max`・`hour_margin`・`spot_newlines`）について、キー名と `` `既定値` ``（例: `` `180` ``）を同じ表行に書く。`crates/pasta_lua/tests/loader/config_defaults_test.rs` の `config_reference_doc_matches_ssot` が、キー名（`` `talk_interval_min` `` の形）を含む表行のすべてに既定値があるか、テンプレート内の `キー = 値  # 既定 …` 行の値が既定値と一致するかを照合する。値を別の行に分けたり、一部の行だけ古いまま残したりすると失敗する。

### 外部リファレンスのリンク方針

- 素の Lua 言語仕様は**取り込まず、リンク参照のみ**とする。リンク先は対象方言（**LuaJIT 2.1 / Lua 5.1 系**）に対応するもの:
  - 日本語 Lua リファレンス（Lua 5.1 / 5.2 相当、例: milkpot 版）
  - LuaJIT 公式ドキュメント（luajit.org、英語）
- 版の離れた **Lua 5.5 系資料は言語リファレンスとして案内しない**（ランタイム方言と不一致のため。Requirement 8.3）。

## 5. 執筆チェックリスト

新しい章を書き終えたら、以下を確認すること。

- [ ] 導入・締めが台詞部品の記法による Claudia とアンソニーの二人の掛け合いで書かれ、Claudia の台詞が令嬢のキャラ口調になっている（Requirement 7.1、manual-claudia-theme Requirement 4.6）。
- [ ] 各台詞の表情が、その台詞の感情に合っている（第 7 節「話し手と表情」の目安。検査ツールは名前の存在だけを見るため、人が確かめる）。
- [ ] 全章で同じ表情の組み合わせに偏っていない（`node book/tools/talk/talk.mjs --stats` の集計で確かめる）。

## 6. 内部設計パートの執筆規約

目次末尾の「内部設計（コントリビュータ向け）」パート（`book/src/internals/`）の章は、第 1〜5 節に加えて本節を守る。

### 読者と位置づけ

- 読者は pasta 本体のコードを読み・直すコントリビュータ（実装を担う AI エージェントを含む）である。ゴースト作者はこのパートを読まなくても利用者向け情報に到達できなければならない。
- このパートの権威は現行実装である。記述は執筆時点のコードと照合し、完了済み spec の design.md や旧文書とコードが食い違う場合はコードに合わせる。存在しないファイル・モジュール・関数・型を現存するものとして書かない。
- 利用者から観測できる挙動は利用者向け章が正である（概要章 `internals/index.md` の「利用者向け章との関係」）。
- 利用者向け章から内部設計章への逆リンクは張らない。

### 共通の章構造（全章）

- 先頭行は H1。二人の掛け合いの導入 → `---` → 普通文体の本体 → `---` → 二人の掛け合いの締め、の形にする（第 3 節の型と同じ）。
- 生成対象でない章でも、本体には台詞部品と口調マーカーを置かない（第 4 節「本文に台詞部品を置かない」「本文に口調・コラムを置かない」と同じ規則。`node book/tools/verify-content.mjs` が検査する）。
- 図は Mermaid を使わず、情報文字列 `text` のコードフェンスか表で書く（mdBook に Mermaid プラグインを入れない）。

### 題材章の H2 構成

概要章 `internals/index.md` と `internals/internal-modules.md` を除く題材章は、本体に次の H2 をこの順ですべて持つ。H2 の文言は変えない。必要なら各 H2 の下に H3 以下を置いてよい。

| 順 | H2 | 書く内容 |
| -- | -- | -------- |
| 1 | `## 目的と責務` | 題材が何を担い、どこまでがこの章の責務か |
| 2 | `## 構成要素` | 主要な型・モジュール・ファイルの役割（図は `text` フェンスか表） |
| 3 | `## 処理とデータの流れ` | 入力から出力までの処理の順序とデータの形 |
| 4 | `## 境界の受け渡し` | クレート間・Rust/Lua 間で誰が何を所有し何を渡すか。境界をまたがない題材では「この題材は単一クレート内で完結する」と 1 文書く |
| 5 | `## 不変条件と制約` | 常に成り立つ条件と、実装上の制約 |
| 6 | `## ソースの所在` | 題材のソースを、リポジトリルート相対パスのインラインコードの箇条書きで列挙する |
| 7 | `## 経緯` | 設計を確立した完了 spec を `https://github.com/ekicyou/pasta/tree/main/.kiro/specs/completed/<name>` のリンクで列挙する。本文は spec を読まなくても理解できる形で書く |

概要章 `internals/index.md` は、本体に次の H2 をこの順で持つ。

1. `## この章の読者` — 対象読者がコントリビュータであり、ゴースト作成には読む必要がないこと。
2. `## 全体像` — クレート構成とデータの流れ（パース → トランスパイル → ローダ → VM 実行 → SHIORI 応答）を 1 枚の図と短い説明で示し、各章へ案内する。
3. `## 利用者向け章との関係` — 利用者から観測できる挙動は利用者向け章が正であることと、リンク規則の要約。
4. `## 対象外` — `pasta_lsp`・`pasta_check`・`pasta_sample_ghost` はランタイム外のツールであり対象外であること。
5. `## 章と対象ソース範囲` — 章とソース範囲の対応表（後述「対応表の同時更新」）。

### ソースパスの表記規則

- リポジトリ内パスはリポジトリルートからの相対パスをインラインコードで書く（例: `crates/pasta_lua/src/loader/`）。ディレクトリは末尾を `/` にする。
- 行番号（`foo.rs:12`）・`#L` アンカー・ワイルドカード・クレート相対の短縮形（`src/...`・`pasta_scripts/...` 単独）は書かない。
- 接頭辞 `crates/`・`book/`・`.github/`・`.cargo/`・`.kiro/`・`.claude/` で始まるインラインコード（コードフェンスの外）は、`link-check.mjs` の `internals-path` 検査で実在を確認され、リポジトリ外へ出るもの・実在しないものは失敗する。上記の行番号付き・ワイルドカード入りの表記も実在しないため失敗する。
- 説明のための架空のパスは、インラインコードではなく情報文字列 `text` のコードフェンスに置く（フェンス内は検査対象外）。
- ゴーストディレクトリ内のパス（`scripts/`・`profile/pasta/cache/` 等）は上記の接頭辞を持たないため検査対象外であり、そのままインラインコードで書いてよい。
- リポジトリルート直下のファイル（`Cargo.toml` 等）は `https://github.com/ekicyou/pasta/blob/main/<ファイル名>` のリンクで書く（既存のリンク検証が実在を確認する）。

### 章の責務分担（1 事実 1 章）

1 つの事実は 1 つの章だけに書き、他の章はリンクで参照する。

| 章 | 書くこと | 書かずにリンクすること |
| -- | -------- | ---------------------- |
| 題材章 | 仕組み・処理の流れ・Rust 側の実装・境界の受け渡し・不変条件。Lua モジュールはモジュール間の関係と処理の流れまで | 個々のフィールド・関数・データ構造（`internals/internal-modules.md` の該当見出しへ） |
| `internals/internal-modules.md` | Lua ランタイム内部モジュールのモジュール単位のリファレンス（フィールド・関数・データ構造・内部パターン） | 仕組み全体の説明（題材章へ） |
| `lua/script-api.md` | ゴースト作者が `scripts/` から呼ぶ API の利用者向けリファレンス | 内部の仕組み（触れない。内部設計章への逆リンクも張らない） |
| 既存の利用者向け章 | 文法・公開 Lua API・`pasta.toml`・起動シーケンスとモジュール解決の利用者向け挙動・デバッグ操作（これらの権威） | — |

- 内部設計章は、利用者向け章が権威を持つ事実を再記述せず、該当する利用者向け章へリンクする。
- 起動シーケンスは `reference/startup.md` が利用者向け挙動の権威である。内部設計章はそれへリンクし、その挙動を実現する仕組みだけを書く。

### 生成元章 `internals/internal-modules.md` の追加規則

`internals/internal-modules.md` はスキル `pasta-lua-coding` の `references/internal-modules.md` の生成元である。第 4 節「生成対象章の執筆規約」に加えて、次を守る。

- リポジトリ内パスを、本文・コードフェンス・HTML コメントのどこにも書かない。`crates/` を含む URL（GitHub の URL を含む）も書かない。Lua モジュールはモジュール名（`pasta.store` 等）で示す。
- ソースの所在は、「この章が扱うモジュールのソースの所在は [ランタイム実行モデル](execution-model.md#ソースの所在) を参照する」の形で、題材章の「ソースの所在」へリンクして示す（生成時に公開マニュアルの絶対 URL へ書き換わる）。
- 章を変更したら第 4 節のとおり再生成し、生成物を同じコミットに含める。

### 将来構想を書かない

未実装の構想・将来の最適化候補・今後の予定は、現行の内部設計として書かない。書き残す価値がある場合は、ロードマップ（`.kiro/steering/roadmap.md`）へ 1 項目 1 行のキー情報で申し送る。

### 実装の不備は書かずにロードマップへ送る

執筆中に現行実装の不備（バグ候補など、実行されるコードの修正を要するもの）を見つけた場合は、実装を変更しない。章には現行の挙動だけを書き、不備はロードマップ（`.kiro/steering/roadmap.md`）のバグ候補の小節へ 1 項目 1 行（名称 — 要旨 — 根拠の所在）で記録する。spec の作業中であれば、根拠をその spec の成果物（吸収台帳など）にも残す。

### ソースコメントの食い違いの修正手順

執筆中にソース内のコメント・doc コメントが現行実装と食い違っていると判明した場合は、コメントだけを現行実装に合わせて直してよい。

1. 対象は `crates/{pasta_dsl,pasta_core,pasta_lua,pasta_shiori}/` の `src/`・`pasta_scripts/`・`build.rs`・`build_zip.rs`・`Cargo.toml` のコメントである。第三者のコードである `scriptlibs/` は対象外とする。
2. 差分はコメント行だけにする。実行される行・属性・文字列リテラルは変えない。
3. 環境変数 `NoDefaultCurrentDirectoryInExePath` を外したうえで、`cargo fmt --check` で整形差分が出ないこと、`cargo build` と `cargo test --all` が従来どおり成功することを確認する（挙動不変の確認）。
4. 直したコメントの位置と要旨を記録する（spec の作業中であれば、その spec の成果物に記録する）。

### 対応表の同時更新

- 概要章 `internals/index.md` の「章と対象ソース範囲」の対応表と、各題材章の「ソースの所在」は、同じ作業（同じコミット）で更新し、食い違わせない。ソースの追加・移動・リネームで章の対象範囲が変わったときも同様である。
- 対応表のセルはインラインコードのリポジトリルート相対パスで書く（`internals-path` 検査の対象になる）。`/` で終わるセルはディレクトリ配下のすべてのファイルに、それ以外は記載のファイルだけに一致する。範囲の重なりは許容し、一致したすべての章が照合の対象になる。
- 対応表は spec 完了時に、変更されたファイルと照合して内部設計章の追従を確認するために使う。リポジトリルート直下のファイル（`Cargo.toml` 等）は、依存更新のたびに照合対象にならないよう対応表に載せず、該当章の「ソースの所在」に blob URL のリンクで書く。

## 7. 台詞部品（Claudia とアンソニー）

章の導入と締めは、台詞部品（顔アイコン付きの吹き出し）による Claudia とアンソニーの掛け合いで書く。台詞部品は Markdown の引用ブロックの書き方で書き、ビルド時に `book/tools/talk/talk-html.mjs` が吹き出しの HTML に変換する。話し手と表情の唯一の定義は、登録簿 `book/tools/talk/talk.mjs` の `SPEAKERS` である。

### 記法

```markdown
> 【高笑い】さあ、熱く参りましょう！

> 【アンソニー】執事のアンソニーでございます。

> 【アンソニー：刮目】おや。

> 【クローディア：照れ】……別に。
```

- 行頭（字下げなし）の引用ブロックの 1 行目を、`【タグ】` で始める。1 つの引用ブロックが 1 つの吹き出しになる。
- タグの書き方は次の 3 つだけである。
  - `【表情】` — 既定の話し手 Claudia の、その表情。
  - `【話し手】` — その話し手の「素」。
  - `【話し手：表情】` — 区切りは全角コロン `：` だけ。半角コロンは使えない。
- 話し手名はカタカナの `クローディア`・`アンソニー` だけである。別名（`Claudia`・`お嬢様`・`執事` など）は使えない。話し手を省くと Claudia、表情を省くと「素」になる。タグの中に空白を入れない。
- 本文はタグの後ろから書き始め、空にしない。続きの行も `>` で始める。空の `>` の行で段落を分けられる。
- 本文の中では、強調・インラインコード・リンクを章の本文と同じ書き方で書ける。
- 台詞と台詞、台詞と段落、台詞と区切り `---` の間には、必ず空行を入れる。台詞のすぐ後ろに空行なしで `---` や段落を書くと、引用ブロックに吸い込まれて失敗する（`missing-blank-line`）。
- タグの行の末尾に強制改行（行末の空白 2 つ・バックスラッシュ）を書かない。本文が改行から始まってしまう。
- 続けて書いた台詞は別々の吹き出しとして順に並ぶ。Claudia の吹き出しは左、アンソニーの吹き出しは右に寄る。

### 話し手と表情

話し手は次の 2 人である。

| 話し手 | 名札 | 配置 | 役どころ |
| ------ | ---- | ---- | -------- |
| クローディア | Claudia | 左 | 発信役。章の話題を振り、表情豊かに反応する（第 1 節の Claudia 令嬢） |
| アンソニー | Anthony | 右 | 反応役。相づち・補足・手綱引きを、ほぼ一定の表情で返す（第 1 節のアンソニー） |

Claudia の表情は次の 14 種である。使いどころと例文は目安であり、語句から表情を機械的に決める対応表ではない。台詞の感情に合わせて選ぶ。

| 表情 | 画像 | 使いどころ（目安） | 例文 |
| ---- | ---- | ------------------ | ---- |
| 素 | `f0` | 平常の語り。話題の提示や、本文への橋渡し | 「この章では、シーンの呼び出し方を扱いますわ。」 |
| 照れ | `f1` | 素直になった直後や褒められたときの照れ隠し。ツンデレの「デレ」 | 「……べ、別にあなたのためではありませんわ。」 |
| 驚き | `f2` | 意外な事実や、読者の上達に驚く | 「まあ！ もうそこまで書けましたの？」 |
| 不安 | `f3` | つまずきやすい所への心配。注意の前振り | 「ここは、少し心配ですわね……。」 |
| 落胆 | `f4` | 失敗や残念な知らせを軽く嘆く | 「あら、また保存し忘れましたの……。」 |
| 高笑い | `f5` | 自信満々の宣言、熱血の後押し、落ち | 「おほほほ！ わたくしにかかれば造作もありませんわ！」 |
| 目閉じ | `f6` | 落ち着いて語る、しみじみとした余韻 | 「基本には、何度でも立ち返る価値がありますのよ。」 |
| 不機嫌 | `f7` | ツンとした態度、むっとする | 「フンッ、そんな書き方は認めませんわよ。」 |
| 冷笑 | `f8` | 余裕の笑み、皮肉、相手のボケを見下ろす | 「あら、その程度で音を上げますの？」 |
| 照れ怒り | `f9` | 図星を突かれてむきになる。強い落ち | 「な、なにを言っていますの！ 違いますわよ！」 |
| にっこり | `f25` | 励まし・歓迎・まとめ | 「よくできましたわ。その調子ですの。」 |
| したり顔 | `f26` | 得意げな解説の前振り、「言ったとおりでしょう」 | 「ふふん、ここが腕の見せどころですわ。」 |
| 考え中 | `f27` | 問いかけ、どう説明するか考える、迷い | 「さて、どこからお話ししましょうかしら……。」 |
| お辞儀 | `f28` | 挨拶・歓迎・お礼・別れ | 「ようこそいらっしゃいまし。」 |

アンソニーの表情は次の 2 種である。

| 表情 | 画像 | 使いどころ（目安） | 例文 |
| ---- | ---- | ------------------ | ---- |
| 素 | `f10` | 既定（半目）。相づち・補足・手綱引き・読者の疑問の代弁。アンソニーの台詞はほぼすべてこれ | 「左様でございますか。」 |
| 刮目 | `f11` | 本当に意外なことへの驚き（お嬢様が素直になった、とんでもないことを言った）。1 章に 1 回まで | 「おや、お嬢様が今日はずいぶん素直でいらっしゃる。」 |

表情を選ぶときの目安:

- 表情は台詞の「言い始めの感情」に合わせる。途中で感情が変わるなら、吹き出しを 2 つに分けて表情を変える（例: 驚き → 照れ、考え中 → 照れ、驚き → にっこり）。
- 語尾や書き出しと逆の表情は、ほぼ失敗である。驚きの顔で淡々と説明する、にっこりで注意事項を言う、などは避ける。「……」で始まる台詞は、不安・照れ・考え中・目閉じで受け、にっこり・高笑いでは受けない。
- 同じ話し手が同じ表情を続けるのは 2 回までにする。3 回目は「素」に戻すか、感情を 1 段ずらす（にっこり → したり顔、不安 → 落胆）。
- 強い表情（驚き・高笑い・照れ怒り）は落ちに取っておき、導入の 1 つ目の吹き出しでは使わない。
- アンソニーは「素」が既定である。表情が変わること自体が出来事になるので、「刮目」は 1 章に 1 回まで、Claudia が本当に意外なことを言ったときだけにする。

話し手や表情を増やすときは、登録簿の `SPEAKERS` と顔画像（`book/src/img/claudia/`）を足し、本節の表にも 1 セル 1 名で載せる（`verify-content.mjs` の T-authoring が、登録簿の全名前が本節の表のセルにあるかを照合する）。

### 掛け合いの書き方

- 基本の型は「**振り → 返し → 落ち**」の 3 手である。Claudia が振り、アンソニーが返し、Claudia が反応する。4 つ目にアンソニーが一言で落としてもよい。
- 長さの目安は、導入が 2〜3 吹き出し、締めが 2 吹き出しである。導入では Claudia が章の話題を振り、アンソニーが要点を一言で言い直すか、読者の疑問を代わりに尋ねる。締めでは Claudia がまとめ、アンソニーが次章への一言か軽い落ちを添える。これより長いと読み飛ばされる。
- 導入と締めのそれぞれに、両方の話し手の台詞を 1 つ以上置く（`missing-speaker`）。導入と締めには台詞だけを置き、地の文の段落を混ぜない（`prose-in-region`）。
- 話し手は交互を基本にする。アンソニーの返しは 1 文を基本とし、長い説明をさせない。
- 間は「……」と、吹き出しを分けることで出す。
- アンソニーに「読者の疑問を代わりに言う役」をさせると、導入が本文へ自然につながる。
- 掛け合いに技術情報を載せない。台詞が指す技術的な事実は本文にあるものだけにし、掛け合いを読み飛ばしても本文だけで章の内容が通じるようにする。
- 章ごとに型を変えて飽きを散らす（Claudia のボケにアンソニーが返す型、アンソニーが先にとぼける逆転の型、二人とも乗る型など）。目安であり、検査はしない。
- Claudia の台詞には第 1 節の口調マーカーを入れる（章の口調の検査 `D-voice`・`G-voice` は台詞の口調で満たされる）。アンソニーは執事の丁寧語で話し、令嬢口調に寄らない。からかいの範囲を超えない。重い話題で不意を打たない。
- 章の最初の台詞は、ありふれた句（「ごきげんよう」など）で始めない。最初の台詞の本文で最初に現れる 4 文字以上の日本語の並びが、検索の検査（`verify-search.mjs`）の語になる。ありふれた句だと説明本体の文字にもヒットして、検査が弱まる。その章に固有の言葉が先に来るように書く。
- 既存の章を書き換えるときは、もとの Claudia の台詞の趣旨（その章で学ぶこと・読み終えてできること）を Claudia の台詞に残す。

### 置ける場所

| 章の種類 | 導入・締め | 説明本体（最初と最後の `---` の間） |
| -------- | ---------- | ----------------------------------- |
| 生成対象章（`GENERATION_MAP` に載る章） | 置ける（掛け合いで書く） | 置けない（`talk-in-body`） |
| 内部設計章（`book/src/internals/`） | 置ける（掛け合いで書く） | 置けない（`talk-in-body`） |
| それ以外の章（入門・チュートリアル・デバッグなど） | 置ける（掛け合いで書く） | 置ける |

- 表紙（`introduction.md`）では、扉（`<section class="claudia-hero">`）の中にも置ける。
- どの章でも、台詞は行頭の引用ブロックとして置く。字下げした台詞、リストの中・引用の中（入れ子）の台詞は置けない（`nested-talk`）。注記（`> [!NOTE]`）の中にも置けない。

### 書けない内容

- 台詞の中に、コードブロック（フェンス）・表・入れ子の引用を書かない（`unsupported-content`）。
- 台詞部品を、コードブロック・表・構文定義（EBNF 等）・コマンド例の中に置かない。これらの代わりに台詞で仕様やコードを示すこともしない（第 2 節）。
- `【` で始まる引用ブロックは台詞部品専用である。普通の引用ブロックを `【` で始めない。台詞として解析され、タグが話し手名・表情名でなければ失敗する。

### 検査と表情の集計

台詞部品の不正は、公開前に次の検査が止める。どれも警告で続行せず、失敗（exit 1）にする。

| 検査 | 実行するもの | 見る内容 |
| ---- | ------------ | -------- |
| `T-syntax` | `verify-content.mjs` | 全章の記法（下の不正の種類） |
| `T-intro`・`T-outro` | `verify-content.mjs` | 導入・締めが台詞だけで、両方の話し手がいる |
| `T-assets` | `verify-content.mjs` | 顔画像が登録簿の 16 枚と `LICENSE.txt` だけで、各 20KB 以下 |
| `T-authoring` | `verify-content.mjs` | 本節の表のセルに、登録簿の全話し手名と全表情名がある |
| `talk-in-body` | `gen-skill-refs.mjs`・`verify-content.mjs`（`I-structure`） | 生成対象章・内部設計章の本体に台詞がない |
| 変換 | `talk/talk-html.mjs` | 1 件でも不正があれば何も書き込まずに止まる |
| 出力・検索 | `verify-static.mjs`・`verify-search.mjs` | 出力に台詞部品と顔画像があり、章の最初の台詞の語で章が検索できる |

記法の不正の種類（失敗メッセージには章のパス・行番号・種類・詳細が出る）:

| 種類 | 原因 |
| ---- | ---- |
| `malformed-tag` | `】` が無い、空のタグ、タグの中に `【` や `】` がある、半角コロン・空白入り、区切りが 2 つ以上、話し手か表情が空（`【：照れ】` など） |
| `unknown-speaker` | 登録簿に無い話し手名 |
| `unknown-expression` | 登録簿に無い表情名（その話し手に無い表情を含む） |
| `empty-body` | 本文が空 |
| `missing-blank-line` | 台詞と台詞・段落の間に空行が無い（遅延継続を含む）。台詞のすぐ後ろに空行なしで `---` が来る場合も含む（`---` や見出しのすぐ後ろの台詞は許されるが、規約としては空行を入れる） |
| `nested-talk` | 字下げ・リストの中・引用の中の台詞 |
| `unsupported-content` | 台詞の中のコードブロック・表・入れ子の引用 |
| `prose-in-region` | 導入・締めに台詞以外の内容がある |
| `missing-speaker` | 導入・締めに両方の話し手が揃っていない |

検査ツールが見るのは名前の存在と配置だけで、表情が台詞の感情に合っているか、全章で表情の組み合わせが偏っていないかは人がレビューする（第 5 節）。偏りは次のコマンドの集計で確かめる。全章の表情の出現数と、章ごとの導入・締めの表情の組み合わせを表で出す（合否は出さず、常に exit 0）。

```sh

```

## 8. 入門ガイドの執筆規約

入門ガイドは、初心者の「こんな表現をしたい」を 1 章に 1 つずつ叶えていく物語である。全編を Claudia が語り、詳しい文法はリファレンス章へ送り出す。本節は、入門ガイドだけに許す書き方と、入門ガイドだけが守る型を定める。

### 対象

- 本節は入門ガイド（`book/src/getting-started/`）の章だけに適用する。入口の章（`index.md`）、準備の章（`prerequisites.md`・`setup.md`）、段の章（`01-boot.md`〜`13-nar.md`）の 16 章である。
- 入門ガイドの章は、第 1〜5 節と第 7 節に加えて本節を守る。
- 本節が上書きするのは、説明本体の文体だけである（第 1 節のリズム、第 2 節の表の「説明本体」の行、第 3 節の型にあたる部分）。それ以外の規則はそのまま守る。
- 入門ガイドの章は、生成対象章でも内部設計章でもない。それらの章の規則（第 4 節・第 6 節。本文に台詞と口調を置かない）は、本節では変えない。

### 語りの形

- 説明本体の語りは、台詞部品（第 7 節の記法）だけで書く。説明の地の文の段落を置かない。
- 台詞以外に置けるのは、次の 5 つだけである。
  - 操作を指す普通文体の指示の一文（例: 「`ghost/master/dic/02-talk.pasta` を作り、次の内容を UTF-8 で保存する。」）
  - 箇条書き（番号付きを含む）
  - 表
  - コードブロック
  - 見出し
- 指示の一文は 1 行で書き、句点を 1 つにする。二文以上になるときは箇条書きにする（`verify-content.mjs` の `C-prose` が確かめる）。
- 引用ブロックは台詞部品だけに使う。用語の説明や出典の引用は、箇条書きか表に置く。
- 台詞が語る技術的な事実（構文・手順・値・ファイル名）は、同じ章の台詞以外の部分にも必ず置く。台詞にしか無い事実を作らない。台詞をすべて読み飛ばしても、「何を足すか」「どう書くか」「どう確かめるか」が追えるようにする（機械検査は無いため、レビューで確かめる）。
- アンソニーは本体にも登場させてよい。役どころは、読者の疑問を代わりに尋ねる役と、手綱を引く役である。事実の説明をアンソニーの台詞にだけ置かない。
- 導入と締めは第 7 節のまま書く（両方の話し手を置く・台詞だけを置く・技術情報を載せない）。

### 変えない規則

- コードブロック内・構文定義（EBNF 等）・コマンド例・サンプルコード（`.pasta` / Lua）・表のセルに、キャラ口調を持ち込まない（第 2 節のとおり）。台詞部品もこれらの中に置かない。口調が宿るのは台詞部品だけである。
- 技術的正確さを最優先する（第 1 節の鉄則）。語りで誤読の余地が生まれるなら、台詞以外の部分（箇条書き・表・コードブロック）で言い切る。
- 台詞部品の記法、話し手と表情の選び方、検査（`T-syntax`・`T-intro`・`T-outro`）は第 7 節のまま守る。

### 章の型

全章に共通の形:

- 先頭行は H1。導入（二人の台詞）→ `---` → 本体 → `---` → 締め（二人の台詞）の形にする。
- 本体に区切り `---` を置かない。区切りは、導入の後と締めの前の 2 本だけである。
- 最初の台詞は、その章に固有の 4 文字以上の日本語で始める（第 7 節「掛け合いの書き方」の、検索の語の規則）。
- リンクは、`link-check.mjs` に通る相対リンク（他のパートへは `../grammar/…` の形）と、外部の絶対 URL だけを使う。
- 例に使うゴーストの名前（フォルダ名と `name`）は、全章で `my-ghost` に統一する。読者には、自分の決めた名前に置き換えるよう指示する。

入口の章（`index.md`）は、本体に次の H2 をこの順で持つ。

| 順 | H2 | 置くもの |
| -- | -- | -------- |
| 1 | `## このガイドで作るもの` | 自分の名前を付けたゴーストを 1 体作り、13 段で育てること |
| 2 | `## このガイドの進め方` | 1 章 1 段・章の終わりで起動して試す・詳しい文法はリファレンスへ、の 3 点（箇条書き） |
| 3 | `## 章の一覧` | 準備の 2 章と 13 段の章の表（段・章へのリンク・叶うこと・足すファイル） |
| 4 | `## 作りこんだ実例` | emo2（<https://ekicyou.github.io/ghost_dev/emo2/>）を pasta.dll のショーケースゴーストとして紹介する |
| 5 | `## このガイドの先にあるもの` | 文法リファレンスと Lua 章への案内 |

準備の章は、本体に次の H2 をこの順で持つ。

| 章 | 題（H1） | 本体の H2（この順） |
| -- | -------- | ------------------- |
| `prerequisites.md` | 前提環境と準備 | 動作環境 → 必要なもの → 文字コードは必ず UTF-8 |
| `setup.md` | ゴーストの最小一式を置く | ゴーストのフォルダ構成 → 名前を決める → install.txt を書く → descript.txt を書く → pasta.toml を書く → hello-pasta から写す → SSP に入れて起動する → うまく起動しないときは |

- `setup.md` の見出し「ゴーストのフォルダ構成」は文言を変えない（クレートの README がこの見出しを指す。「章を足す・名前を変えるとき」を参照）。
- `prerequisites.md` から `UTF-8`・`Shift_JIS`・`Windows`・`SSP` の語を落とさない（`verify-content.mjs` の `C-utf8`・`C-sjis`・`C-env` が、入門の全章からこれらの語を探す）。
- 準備の終わりの状態は「辞書が無いので、立ち絵は出るがしゃべらない」である。1 段目の辞書を 1 ファイル足すだけで起動する状態まで、読者を連れていく。

段の章（`01-boot.md`〜`13-nar.md`）は、本体に次の 5 つの H2 をこの順ですべて持つ。H2 の文言と順序は変えない（`verify-content.mjs` の `C-sections` が確かめる）。必要なら各 H2 の下に H3 以下を置いてよい。

| 順 | H2 | 置くもの |
| -- | -- | -------- |
| 1 | `## 叶えたいこと` | 段階表の `願い` から起こす台詞。箇条書きで「この章で足すファイル」「叶うこと」 |
| 2 | `## 新しく覚える表現` | 段階表の `新しく覚える表現` の範囲の説明（台詞）。構文は辞書の抜き出し（`pasta`）と箇条書き・表で示す。初めて扱うイベントの出典の表もここに置く |
| 3 | `## 辞書ファイルを足す` | 指示の一文（「`ghost/master/dic/NN-name.pasta` を作り、次の内容を UTF-8 で保存する。」）と、辞書の全体の `pasta` ブロック 1 つ。前の段のファイルは変えないことを箇条書きで示す。辞書を持たない 13 段目は、この段で足す辞書ファイルが無いことを示す |
| 4 | `## 起動して確かめる` | 番号付きの手順と、「成功の目印」の箇条書き。段階表の「確かめるための道具」がその段に道具を指定しているときは、道具の手順をここに書く |
| 5 | `## もっと詳しく` | リファレンス章へのリンクの箇条書き。リンク先は、段階表の同じ行の `使う文法要素` と同じにする（`../../book/src/grammar/…` を `../grammar/…` に読み替える） |

- 段階表は `crates/pasta_sample_ghost/STAGES.md` である。段の章は段階表の 1 段を 1 章で教える。
- 題（H1 と目次）は「N 段目：」に段階表の `願い` を続けた形にする（例: 「7 段目：挨拶したい」）。辞書の先頭のコメント行と同じ文言になる。
- 確かめる手順の共通の操作は「SSP を終了して、もう一度起動する」に統一する（開発者用機能を有効にする前の段でも使えるため）。

段の章の雛形（1 段目）を次に示す。新しい段の章は、この形をそのまま下敷きにする。

````markdown
# 1 段目：しゃべらせたい

> 【にっこり】産声をあげる瞬間ですわ。準備で組み上げたあの子に、最初のひとことを授けましょう。

> 【アンソニー】お嬢様、辞書はまだ 1 枚もございませんが。

> 【したり顔】ですから、これから 1 枚目を書きますのよ。たった 2 行で、あの子はしゃべりますわ。

---

## 叶えたいこと

> 【クローディア】この章で叶えるのは「起動したら、ひとことしゃべる」ですわ。辞書を 1 枚足すだけですのよ。

- この章で足すファイル: `ghost/master/dic/01-boot.pasta`
- 叶うこと: ゴーストを起動すると、女の子がひとことしゃべる

## 新しく覚える表現

> 【考え中】ゴーストを起動すると、ベースウェアは「起動しましたわよ」と pasta に知らせてきますの。この知らせを **イベント** と呼び、起動の知らせの名前は `OnBoot` ですわ。

| イベント | いつ来るか（UKADOC より） |
| -------- | ------------------------- |
| [`OnBoot`](https://ssp.shillest.net/ukadoc/manual/list_shiori_event.html#OnBoot) | 「起動した際に発生。」 |

> 【したり顔】行の頭に `＊` を置いて名前を書くと、そこから「シーン」が始まりますの。名前を `OnBoot` にしておけば、起動のたびに pasta がこのシーンを呼びますわ。

```pasta
＊OnBoot
　女の子：やっほー、今日もよろしくね。
```

- `＊OnBoot` — シーンの始まり。`＊` の後ろがシーンの名前である
- `　女の子：やっほー、…` — アクション行。行の頭を字下げし、`アクター名：台詞` の形で書く
- `女の子` — `pasta.toml` の `[actor."女の子"]` で決めたアクターの名前である

## 辞書ファイルを足す

`ghost/master/dic/01-boot.pasta` を作り、次の内容を UTF-8 で保存する。

```pasta
＃ 1 段目：しゃべらせたい
＃ ゴーストが起動すると、pasta は ＊OnBoot という名前のシーンを呼ぶ。
＃ シーンの中に「アクター名：台詞」の行を書くと、そのアクターがしゃべる。

＊OnBoot
　女の子：やっほー、今日もよろしくね。
```

- `＃` で始まる行はコメントで、処理されない

## 起動して確かめる

1. SSP を終了し、もう一度起動する。
2. 自分のゴーストが出ていなければ、メニューから切り替える。

- 成功の目印: 女の子の吹き出しに「やっほー、今日もよろしくね。」と出る
````

### 章を足す・名前を変えるとき

段の章は、辞書と同じ名前にする（辞書 `dic/NN-name.pasta` に対して章 `getting-started/NN-name.md`）。作例の照合は、この名前の一致で段と章を対応づける。辞書を持たない段の章（`13-nar.md`）も、同じ `NN-name.md` の形にする。

章を足す・消す・名前を変えるときは、次を同じ変更で直す。

| 直す場所 | 直す内容 |
| -------- | -------- |
| `book/src/SUMMARY.md` | 入門パートの並び（`index.md` → `prerequisites.md` → `setup.md` → 段の章をファイル名の昇順）。目次の題は各章の H1 と同じにする（`verify-content.mjs` の `C-order` が並びを確かめる） |
| `book/src/getting-started/index.md` | 「章の一覧」の表 |
| `book/tools/verify-scripts-test.mjs` | 章の数の決め打ち（`T-syntax`・`T-intro`・`T-outro` の件数と、`C-sections`・`C-prose` の件数） |
| `book/tools/talk/talk-test.mjs` | 章の数の決め打ち（J-9） |
| `book/tools/gen-skill-refs-test.mjs` | 章の数の決め打ち（K-10） |
| `crates/pasta_lua/README.md`・`crates/pasta_shiori/README.md` | `getting-started/setup.html#ゴーストのフォルダ構成` を指すリンク。`setup.md` の名前かこの見出しを変えるときに直す（README のリンク検証は、ページと見出しの実在を見る） |
| `book/book.toml` の `[output.html.redirect]` | 章のファイルを消す・名前を変えるときは、古い URL からの転送を足す。転送先は相対で書く |
