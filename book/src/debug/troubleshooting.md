# うまく動かないとき（トラブルシューティング）

> 【落胆】手順どおりに選んだはずなのに、シーンが鳴らない――開発でいちばん心が折れる瞬間ですわね。

> 【アンソニー】まずは、ゴーストの側か、ベースウェアの側か、そこを分けるのでございますね。

> 【にっこり】そこさえ分ければ、原因はたいてい一本道ですの。落ち着いて、わたくしと一緒に順に確かめてまいりましょう。

---

このページでは、[開発支援アクション](./dev-actions.md) の 3 つのコマンドがうまく動かないときの確かめ方を扱う。拡張が出す知らせの全文と詳しい内容は、出力のパネル「Pasta 開発」に残っている。まずパネルを開き、止まった所の行を見る。デバッグの有効化は [デバッグ概要](./index.md)、拡張の導入と MCP の窓口は [VSCode 接続と拡張導入](./vscode-setup.md) を参照する。

ただし、**ゴーストがそもそも起動しない・まったく喋らない**場合は、本ページではなく [起動シーケンスとモジュール解決](../reference/startup.md) を先に参照する。起動シーケンスのどこかでロードに失敗している可能性が高く、その場合は 500 応答の `X-ERROR-REASON` ヘッダとログファイルの `fatal=true` の行に原因が出ている。

起動はしていて、イベントの処理中に Lua のエラーでシーンや要求が止まった場合は、既定ではバルーンに `【スクリプトのエラー：…】`・`【時間切れ：…】` の表記が出る（[止まるエラーの表記](../reference/runtime-failures.md#止まるエラーの表記)）。表記を出さない設定（`balloon_warning = false`）では表記は出ず、500 応答の `X-Error-Reason` の行とログの警告で理由を見る。

## デバッグが有効になったか確かめる

シーンの再生と保存変数の表示は、デバッグを有効にしたゴーストでだけ働く。有効になったかは、ゴーストの `pasta.log` で確かめる。デバッグが有効な状態で SHIORI を読み込むと、開発用のイベントを許したことを示す info の行が 1 行出る。

読み込み直した後にこの行が無ければ、設定がまだ効いていない。次を確かめる。

- `pasta.toml` に `[debug]` の `enabled = true` を書いたか（[pasta.toml による有効化](./index.md#pastatoml-による有効化)）。
- 書いた後に SHIORI を読み込み直したか（「SHIORI をリロード」か、ゴーストの再起動）。
- 環境変数 `PASTA_DEBUG` で有効にする場合、その値がベースウェアのプロセスに渡っているか。別のシェルで設定しただけでは、SSP・areka から起動したゴーストには伝わらないことがある。設定した後はベースウェアを起動し直す。確実なのは `pasta.toml` での有効化である。
- `PASTA_DEBUG` に無効の値（`0`・`false` など）が入っていないか。環境変数は `pasta.toml` より優先される（[優先順位](./index.md#優先順位)）。

## 送る相手が見つからない

次の知らせが出たときは、拡張が、そのゴーストが動いている SSP・areka を見つけられていない。

```text
このゴーストが動いている SSP・areka が見つかりません: <表示名>（<ルート>）。確かめること: ベースウェアでこのゴーストを起動しているか・SSP の MCP の窓口が有効か
```

- **ベースウェアでそのゴーストを起動しているか。** 拡張は、編集中のファイルから見つけたゴーストのルート（知らせの括弧の中のパス）で相手に聞く。同じ名前のゴーストでも、別のフォルダに置いた写しが動いているだけでは見つからない。知らせのパスのゴーストを起動する。
- **ベースウェアの MCP の窓口が有効か。** 窓口はベースウェアが開く。ベースウェアの設定で MCP の窓口が有効になっているかを確かめる。窓口の番号と待ち受けの決まりは [SSP と areka の MCP の窓口](./vscode-setup.md#ssp-と-areka-の-mcp-の窓口) を参照する。
- **開いているファイルが、そのゴーストのフォルダの中にあるか。** 「ゴーストのフォルダの中のファイルではありません」と出たときは、`ghost/master` の外のファイルを開いている。拡張は、開いているファイルのフォルダから上へ 3 フォルダまでの間で `descript.txt` を持つ `ghost/master` を探す（[ゴーストの見つけ方](./dev-actions.md#ゴーストの見つけ方)）。

## 読み込みの終わりを確かめられない

「読み込みの終わりを確かめられませんでした」と出たときは、拡張が待つ間に、ゴーストの `pasta.log` に読み込みの終わりの行（`SHIORI load entry completed`）が出なかった。「▶ シーンを実行」は、このときシーンを再生しない。

- **ゴーストの読み込みが長くかかっていないか。** 拡張はおよそ 20 秒待つ。辞書が大きく読み込みが長いときは、もう一度選ぶ。
- **`pasta.toml` の `[logging]` の `level`・`filter` や環境変数 `PASTA_LOG` で、info の行を外していないか。** 読み込みの終わりの行は info の行である。`level` を `warn` 以上にしたり、`filter` で pasta.dll の info の行を外したりしていると、この行が `pasta.log` に書かれず、毎回この知らせになる。`level` を既定の `info` に戻すか、`filter` から外れないようにする。`PASTA_LOG` が設定されていると `level`・`filter` より優先されるので、その値も確かめる（[[logging]](../reference/pasta-toml.md#loggingログ出力)）。
- **`[logging]` の `file_path` が拡張の読む場所と合っているか。** 拡張は `file_path` に従って `pasta.log` を読む。パネルに「pasta.toml の [logging] file_path …ため、既定の profile/pasta/logs/pasta.log を読みます」と添えられたときは、拡張が `file_path` の値を読めず、既定の場所を読んでいる。`file_path` は `[logging]` の表の中に、`file_path = "profile/…"` の 1 行の文字列で書く。`profile/` の下を指す相対パスだけが使える。

## 台本が返らない（204）

次の案内が出たときは、ゴーストが台本を返さなかった（204）。

```text
ゴーストは台本を返しませんでした（204）。pasta.toml に [debug] enabled = true を書いて、SHIORI をリロードしてください。
```

- **デバッグが有効か。** [デバッグが有効になったか確かめる](#デバッグが有効になったか確かめる) の手順で確かめる。
- **イベントが外からのもの（SecurityLevel が external）として届いていないか。** ベースウェアが SecurityLevel を external にしてイベントを渡すと、ゴーストはデバッグが有効でも断って 204 を返す。
- **`pasta.toml` の `[logging]` に `balloon_warning = false` を書いていないか。** この設定では、シーンが見つからないときや引数の誤りのときも、失敗の表記を載せずに 204 を返す（[OnPastaSceneAt](../lua/shiori-events.md#onpastasceneat位置でシーンを再生)）。

どの場合も、パネルに `OnPastaSceneAt:` を含む警告の行が添えられていれば、それが理由である。

「保存変数を表示」で同じ案内（`pasta.toml に [debug] enabled = true を書いてリロードしてください`）が出たときは、ゴーストが `variables.toml` を新しく書き出さなかった。まず、デバッグが有効かを [デバッグが有効になったか確かめる](#デバッグが有効になったか確かめる) の手順で確かめる。`OnPastaDumpVariables:` の行が添えられていれば、それが理由である。

## 応答が無い

ベースウェアの答えが `No response from server` のときは、拡張は失敗とせず、ベースウェアの再生の記録から台本を引いて出す。その記録にも台本が見つからないと「台本を確かめられませんでした」と出る。

- ゴーストが重い処理で答えを返すのが遅れていないか。もう一度選んで、同じになるかを見る。
- ゴーストのバルーンに `【時間切れ：…】` などの表記が出ていないか（[止まるエラーの表記](../reference/runtime-failures.md#止まるエラーの表記)）。
- ベースウェアの再生の記録に、そのゴーストの台本が残っているか。

## `pasta.log` を読めない

パネルに「pasta.log を読めなかったため、ベースウェアの誤りの記録だけで要約しました（<パス>）」と出たときは、拡張がそのパスの `pasta.log` を読めなかった。要約はベースウェアの誤りの記録だけで作られ、`pasta.log` の誤りと警告は数えられていない。

- 括弧の中のパスに `pasta.log` があるか。ゴーストを一度も読み込んでいないと、まだ無い。
- `[logging]` の `file_path` を変えているなら、その場所と合っているか（[読み込みの終わりを確かめられない](#読み込みの終わりを確かめられない)）。
- `pasta.log` を別のプログラムが開いたままにしていないか。

`pasta.log` を読めないときは読み込みの終わりの行も見えないので、「読み込みの終わりを確かめられませんでした」も一緒に出る。

## 古い `launch.json` が残っている

前の版の拡張で作った `.vscode/launch.json` に `"type": "pasta"` の構成が残っていると、F5 などで「実行とデバッグ」を始めたときに、VSCode が「デバッグの種類 `pasta` が分からない」という旨の誤りを出す。今の拡張はこの構成を使わない。

ゴーストのフォルダ（か、VSCode で開いているフォルダ）の `.vscode/launch.json` を開き、`"type": "pasta"` の構成を探して消す。ほかの構成が無ければ、`launch.json` ごと消してよい（[前の版から移るとき](./vscode-setup.md#前の版から移るとき)）。

## 知らせと確かめる所の一覧

| 知らせ | 確かめる所 |
| ------ | ---------- |
| ゴーストを特定できません（…） | ディスク上の `.pasta`（「▶ シーンを実行」）か `.pasta`・`.lua`・`pasta.toml` を開いているか |
| ゴーストのフォルダの中のファイルではありません | [送る相手が見つからない](#送る相手が見つからない) |
| このゴーストが動いている SSP・areka が見つかりません | [送る相手が見つからない](#送る相手が見つからない) |
| このゴーストへのコマンドが進んでいます | 前のコマンドが終わるのを待つ |
| 保存できなかったファイルがあるので止めました | パネルに出たパスのファイルを保存できるか |
| 読み込みの終わりを確かめられませんでした | [読み込みの終わりを確かめられない](#読み込みの終わりを確かめられない) |
| 読み込みの誤りが N 件あります・シーンを再生しませんでした | パネルの要約の行。辞書の誤りを直す |
| pasta.toml に [debug] enabled = true を書いてリロードしてください | [台本が返らない（204）](#台本が返らない204) |
| 台本を確かめられませんでした | [応答が無い](#応答が無い) |
| SHIORI の読み込み直しを頼めませんでした・シーンの再生を頼めませんでした | パネルに出たベースウェアの誤りの文言 |
