# 設計ディスカッション — Kiro Spec Design Discussion

設計（design.md）および設計分析レポートの完了後に実行する精査・ディスカッションワークフロー。
修正点・疑問点・不安点をイシューとして収集・分類し、自明な修正を済ませたうえで、仕様の目的と設計の骨子、議案一覧（全議題に推奨案付き）を一括提示する。開発者が一括承認すれば全議題を推奨案で確定し、議論したい議題を指定されればその議題だけを1つずつ議論する。

## 前提条件

- `.kiro/specs/{feature}/design.md` が生成済み
- `.kiro/specs/{feature}/requirements.md` が生成済み（要件との整合確認用）
- ステアリングコンテキスト（`.kiro/steering/`）がロード可能

## ワークフロー

### Phase 1: コンテキストロード

1. `.kiro/specs/{feature}/spec.json` を読み、language と現在のフェーズを確認
2. `.kiro/specs/{feature}/brief.md` を全文読み込み（存在する場合。spec の動機・背景の一次情報）
3. `.kiro/specs/{feature}/design.md` を全文読み込み
4. `.kiro/specs/{feature}/requirements.md` を全文読み込み（要件との整合確認用）
5. `.kiro/specs/{feature}/gap-analysis.md` を全文読み込み（存在する場合、設計判断の解決確認用）
6. `.kiro/specs/{feature}/research.md` を全文読み込み（存在する場合、調査結果の反映確認用）
7. `.kiro/steering/` 配下をすべて読み込み（product.md, tech.md, structure.md + カスタム）

### Phase 2: イシューの収集・分類と事前処理（開発者への出力前に内部で済ませる）

#### 2a. イシュー収集

design.md を中心に、関連ドキュメントとの整合性も含めて精査し、以下の観点でイシューを網羅的に収集する：

**収集観点**:
- **矛盾・不整合**: 設計内の矛盾、要件との不整合、gap-analysis の設計判断との齟齬
- **曖昧性**: what/why/how が不明確な設計、複数の解釈が可能な記述
- **要件カバレッジ**: requirements.md の要件・受入基準が設計で未対応
- **インターフェース不備**: コンポーネント間の契約・型・引数が不明確
- **過剰**: 要件スコープ外の設計、YAGNI 違反
- **テスト困難**: 設計上テストが困難な構造
- **リスク**: 未解決のリスク、gap-analysis で指摘されたリスクの設計側カバレッジ不足
- **設計判断未解決**: gap-analysis の設計判断項目が design.md で未解決のまま残っている

#### 2b. イシュー分類

収集したイシューを以下の2カテゴリに分類する：

| カテゴリ | 判定基準 | アクション |
|---------|---------|-----------|
| **A: 自明な修正** | 誤字・明らかな不整合・記述漏れなど、開発者確認不要 | 即座に修正してコミット |
| **B: 開発者確認** | what/why/how が曖昧、ドメイン知識依存、トレードオフ判断が必要 | 議案として推奨案付きで一括提示 |

#### 2c. 自明な修正の実行（カテゴリ A）

1. design.md を更新
2. requirements.md に影響がある場合はそちらも更新
3. 変更をコミット（コミットメッセージ: `docs({feature}): fix obvious issues in design`）
4. 修正内容（修正前→修正後）は Phase 3 の課題一覧で報告する

### Phase 3: 仕様の目的と議案一覧の一括提示（開発者への最初の出力）

開発者は spec 名やコンポーネント名を見ても、パッと目的が分からないことが多い。そこで最初に仕様の目的と、設計がそれをどう実現するかを具体例付きで説明し、続けて議論すべき議案をすべて推奨案付きで並べる。根拠は brief.md → requirements.md の導入部 → design.md の Overview の順に取る。

**守るべき原則**:
- 仕様書の文言をそのままコピペせず、平易な言葉で言い換える。専門用語・内部識別子（関数名、クレート名、spec 名）は初めて出てきたときに一言説明を添える
- 説明には必ず具体例かコードを付ける（シナリオ、入出力例、使用イメージのコード、インターフェースのシグネチャ、データ構造の例など）
- コード例はインターフェース・使用イメージ・データ構造の説明に使う。実装本体の詳細には踏み込まず、アーキテクチャとインターフェースに集中する
- どの議題にも必ず推奨案と根拠を示す。「どちらでもよい」で終わらせない

**出力テンプレート**:

````markdown
## 仕様の目的

**一言で**: {この spec は何をするものか、設計がそれをどう実現するか。ゴースト作者や利用者から見た言葉で 1〜3 文}

**具体例**:
```{lang}
{使用イメージのコード、主要インターフェースのシグネチャ、データ構造の例など}
```

## 課題一覧

### A. 自明な修正（修正済み）
- {修正前} → {修正後}

### 議案一覧

#### 議題 1: {タイトル}
- **何を決めるか**: {決めること}
- **現在の設計**: {該当する設計セクション・コンポーネントの要約（引用付き）}
- **具体例**: {シナリオ・使用イメージ・シグネチャ・データ構造}
- **推奨案**: {案} — {根拠}
- **他の選択肢とトレードオフ**: {案}: {選んだ結果どうなるか}

#### 議題 2: {タイトル}
…

**ご判断ください**
- 「承認」と答えれば、全議題を推奨案で確定します
- 「議題2と4を議論したい」のように答えれば、指定外の議題は推奨案で確定し、指定された議題だけを1つずつ議論します
````

**提示前のチェックリスト**:
- [ ] 仕様書の文言をそのまま貼らず、言い換えているか
- [ ] 専門用語に初出で一言説明を添えているか
- [ ] 仕様の目的と各議題に、具体例かコードが付いているか
- [ ] 全議題に推奨案と根拠が付いているか

開発者確認が必要な議題（カテゴリ B）が0件のときは、仕様の目的と課題一覧を報告してから Phase 5 に進む。

### Phase 4: 開発者の回答に応じた確定

#### 4a. 一括承認された場合

1. 全議題を推奨案で確定し、design.md に反映する（必要に応じて requirements.md も更新し、`research.md` に決定の根拠を追記する）
2. 1回のコミットにまとめる（コミットメッセージ: `docs({feature}): 全設計議題を推奨案で確定`）
3. 一部の議題だけ結論を直接指定された場合（例:「議題3は他の選択肢で、残りは承認」）は、その議題は指定どおりに、それ以外は推奨案で確定する

#### 4b. 特定の議題について議論を指定された場合

1. 指定されなかった議題を推奨案で確定して design.md に反映し、コミットする（コミットメッセージ: `docs({feature}): 設計議題{X,Y} を推奨案で確定`）。確定した内容を報告する
2. 指定された議題のみ、1議題ずつ議論する。各議題は次の形で提示する：

```markdown
## 議題 M（残り K 件）: {タイトル}
- **背景**: この議題が spec の目的・設計の骨子のどこに関わり、なぜ決める必要があるか
- **現在の設計**: どの設計セクション・コンポーネントに関わるか（引用付き）
- **問題点**: 何が曖昧・不明確か
- **具体例**: {シナリオ・使用イメージ・シグネチャ・データ構造}
- **選択肢**: 考えられる設計方針や代替案（2-3個。それぞれ選んだ結果どうなるかを一言で）
- **推奨案**: {案} — {根拠}
```

3. 開発者の回答を受けて：
   1. design.md を更新：議論で明らかになった点の記載、不要になった要件の集約・削除も実施（必要に応じて requirements.md も更新）
   2. 変更をコミット（コミットメッセージ: `docs({feature}): resolve design discussion #{n} - {topic}`）
   3. **修正内容の要約**を報告し、残り議題の**サマリーレポート**を提示してから次の議題へ

**サマリーレポート形式**（各議題完了後に表示）:
```
## 進捗サマリー
- 完了: {n}/{total} 議題
- 直前の解決: {topic} → {decision}
- 残り: {remaining_topics}
- 次の議題: {next_topic_preview}
```

### Phase 5: 完了報告

すべての議題が確定したら：

1. 最終サマリーを表示：
   - カテゴリA（自明修正）: {n}件 修正済み
   - カテゴリB（議案）: {n}件 確定（推奨案で確定: X 件 / 個別議論で確定: Y 件）
2. 次のステップを案内：
   - 「設計の精査が完了しました。次のコマンドでタスク分解に進めます: `/kiro-spec-tasks {feature} [-y]`」

## エラーハンドリング

- **design.md 未生成**: 「先に `/kiro-design {feature}` を実行してください」と案内して停止
- **requirements.md 未生成**: 警告を出しつつ design.md のみで続行
- **イシューなし**: Phase 3 の仕様の目的を提示したうえで「精査の結果、修正すべき点は見つかりませんでした。タスク分解に進めます」と即座に案内

## コミット規約

- prefix: `docs({feature})`
- 自明修正は1コミットにまとめる
- 一括承認: `docs({feature}): 全設計議題を推奨案で確定`（1コミット）
- 指定外議題の確定: `docs({feature}): 設計議題{X,Y} を推奨案で確定`（1コミット）
- 個別議題クローズは議題ごとに個別コミット

## 注意事項

- 最初に仕様の目的を、具体例付きで説明する
- 議案は最初にまとめて提示し、全議題に推奨案を付ける
- 一括承認なら全議題を推奨案で確定する。議論の指定があれば、指定外は推奨案で確定し、指定議題だけを1つずつ議論する
- コード例はインターフェース・使用イメージ・データ構造の説明に使う。実装本体の詳細には踏み込まず、アーキテクチャとインターフェースに集中する
- チャットで会話形式に進め、`AskUserQuestion` は使わない
