# 要件ディスカッション — Kiro Spec Requirements Discussion

要件定義（requirements.md）およびギャップ分析（gap-analysis.md）の完了後に実行する精査・ディスカッションワークフロー。
修正点・疑問点・不安点をイシューとして収集・分類し、自明な修正と設計判断の整理を済ませたうえで、仕様の目的と議案一覧（全議題に推奨案付き）を一括提示する。開発者が一括承認すれば全議題を推奨案で確定し、議論したい議題を指定されればその議題だけを1つずつ議論する。

## 前提条件

- `.kiro/specs/{feature}/requirements.md` が生成済み
- `.kiro/specs/{feature}/gap-analysis.md` が生成済み（推奨、なくても実行可能）
- ステアリングコンテキスト（`.kiro/steering/`）がロード可能

## ワークフロー

### Phase 1: コンテキストロード

1. `.kiro/specs/{feature}/spec.json` を読み、language と現在のフェーズを確認
2. `.kiro/specs/{feature}/brief.md` を全文読み込み（存在する場合。spec の動機・背景の一次情報）
3. `.kiro/specs/{feature}/requirements.md` を全文読み込み
4. `.kiro/specs/{feature}/gap-analysis.md` を全文読み込み（存在する場合）
5. `.kiro/steering/` 配下をすべて読み込み（product.md, tech.md, structure.md + カスタム）
6. `.kiro/settings/rules/ears-format.md` を読み込み（EARS形式検証用）

### Phase 2: イシューの収集・分類と事前処理（開発者への出力前に内部で済ませる）

#### 2a. イシュー収集

requirements.md と gap-analysis.md を精査し、以下の観点でイシューを網羅的に収集する：

**収集観点**:
- **矛盾・不整合**: 要件間の矛盾、ギャップ分析との不整合
- **曖昧性**: what/why が不明確な要件、複数の解釈が可能な記述
- **EARS形式違反**: 受入基準のEARS形式不備
- **欠落**: gap-analysis で指摘されているが requirements に未反映の項目
- **過剰**: 要件スコープ外の記述、実装詳細の混入
- **設計判断**: gap-analysis の設計判断項目（design decisions）の要件側への影響
- **テスト困難**: 検証が困難または不可能な受入基準
- **リスク**: gap-analysis で指摘されたリスクの要件側カバレッジ

#### 2b. イシュー分類

収集したイシューを以下の3カテゴリに分類する：

| カテゴリ | 判定基準 | アクション |
|---------|---------|-----------|
| **A: 自明な修正** | 誤字・EARS形式修正・明らかな不整合など、開発者確認不要 | 即座に修正してコミット |
| **B: 設計判断** | how に関わる判断、アーキテクチャ選択、トレードオフ | 設計フェーズへ先送り（gap-analysis.md の設計判断セクションと統合） |
| **C: 開発者確認** | what/why が曖昧、ドメイン知識依存、優先度判断が必要 | 議案として推奨案付きで一括提示 |

#### 2c. 自明な修正の実行（カテゴリ A）

1. requirements.md を更新
2. gap-analysis.md に影響がある場合はそちらも更新
3. 変更をコミット（コミットメッセージ: `docs({feature}): fix obvious issues in requirements`）
4. 修正内容（修正前→修正後）は Phase 3 の課題一覧で報告する

#### 2d. 設計判断の整理（カテゴリ B）

1. gap-analysis.md の設計判断セクションに未記載の項目があれば追記（新規ファイルは作らない）
2. 変更がある場合はコミット
3. カテゴリ B は議論の対象外。Phase 3 の課題一覧に「設計フェーズ（`/kiro-design`）で解決します」と添えて載せる

### Phase 3: 仕様の目的と議案一覧の一括提示（開発者への最初の出力）

開発者は spec 名や要件 ID を見ても、パッと目的が分からないことが多い。そこで最初に仕様の目的を具体例付きで説明し、続けて議論すべき議案をすべて推奨案付きで並べる。根拠は brief.md → requirements.md の導入部 → gap-analysis.md の順に取る。

**守るべき原則**:
- 仕様書の文言をそのままコピペせず、平易な言葉で言い換える。専門用語・内部識別子（関数名、クレート名、spec 名）は初めて出てきたときに一言説明を添える
- 説明には必ず具体例かコードを付ける（シナリオ、入出力例、使用イメージのコードなど。可能なら「今はこう書くとこうなる → これからはこうなる」）
- どの議題にも必ず推奨案と根拠を示す。「どちらでもよい」で終わらせない

**出力テンプレート**:

````markdown
## 仕様の目的

**一言で**: {この spec は何をするものか。ゴースト作者や利用者から見た言葉で 1〜2 文}

**具体例**:
```{lang}
{今の書き方・挙動と、これからの書き方・挙動を示すコード例や入出力例}
```

## 課題一覧

### A. 自明な修正（修正済み）
- {修正前} → {修正後}

### B. 設計フェーズに回す事項
- {設計判断の要約}（設計フェーズ `/kiro-design` で解決します）

### 議案一覧

#### 議題 1: {タイトル}
- **何を決めるか**: {決めること。対象の要件 ID を添える}
- **具体例**: {シナリオ・入出力例・コード}
- **推奨案**: {案} — {根拠}
- **他の選択肢とトレードオフ**: {案}: {選んだ結果どうなるか}

#### 議題 2: {タイトル}
…

**ご判断ください**
- 「承認」と答えれば、全議題を推奨案で確定します
- 「議題2と4を議論したい」のように答えれば、指定外の議題は推奨案で確定し、指定された議題だけを1つずつ議論します
````

**提示前のチェックリスト**:
- [ ] 仕様書の文言をそのまま貼らず、言い換えているか
- [ ] 専門用語に初出で一言説明を添えているか
- [ ] 仕様の目的と各議題に、具体例かコードが付いているか
- [ ] 全議題に推奨案と根拠が付いているか

開発者確認が必要な議題（カテゴリ C）が0件のときは、仕様の目的と課題一覧を報告してから Phase 5 に進む。

### Phase 4: 開発者の回答に応じた確定

#### 4a. 一括承認された場合

1. 全議題を推奨案で確定し、requirements.md に反映する（議論で明らかになった点の記載、不要になった要件の集約・削除も実施。必要に応じて gap-analysis.md も更新）
2. 1回のコミットにまとめる（コミットメッセージ: `docs({feature}): 全議題を推奨案で確定`）
3. 一部の議題だけ結論を直接指定された場合（例:「議題3は他の選択肢で、残りは承認」）は、その議題は指定どおりに、それ以外は推奨案で確定する

#### 4b. 特定の議題について議論を指定された場合

1. 指定されなかった議題を推奨案で確定して requirements.md に反映し、コミットする（コミットメッセージ: `docs({feature}): 議題{X,Y} を推奨案で確定`）。確定した内容を報告する
2. 指定された議題のみ、1議題ずつ議論する。各議題は次の形で提示する：

```markdown
## 議題 M（残り K 件）: {タイトル}
- **背景**: この議題が spec の目的のどこに関わり、なぜ決める必要があるか
- **対象**: どの要件・受入基準に関わるか（ID付き引用）
- **問題点**: 何が曖昧・不明確か
- **具体例**: {シナリオ・入出力例・コード}
- **選択肢**: 考えられる解釈や方向性（2-3個。それぞれ選んだ結果どうなるかを一言で）
- **推奨案**: {案} — {根拠}
```

3. 開発者の回答を受けて：
   1. requirements.md を更新：議論で明らかになった点の記載、不要になった要件の集約・削除も実施（必要に応じて gap-analysis.md も更新）
   2. 変更をコミット（コミットメッセージ: `docs({feature}): resolve discussion #{n} - {topic}`）
   3. **修正内容の要約**を報告し、残り議題の**サマリーレポート**を提示してから次の議題へ

**サマリーレポート形式**（各議題完了後に表示）:
```
## 進捗サマリー
- 完了: {n}/{total} 議題
- 直前の解決: {topic} → {decision}
- 残り: {remaining_topics}
- 次の議題: {next_topic_preview}
```

### Phase 5: 完了報告

すべての議題が確定したら：

1. 最終サマリーを表示：
   - カテゴリA（自明修正）: {n}件 修正済み
   - カテゴリB（設計判断）: {n}件 設計フェーズへの申し送り
   - カテゴリC（議案）: {n}件 確定（推奨案で確定: X 件 / 個別議論で確定: Y 件）
2. 次のステップを案内：
   - 「要件の精査が完了しました。次のコマンドで設計フェーズに進めます: `/kiro-design {feature}`」
3. 設計フェーズの推奨モデルを根拠1行付きで示す。既定は **Opus**。Fable は次の (i)(ii) を両方満たすときだけ推奨する（例: 「設計の推奨モデル: **Opus** — 設計判断 3 件はどれも推奨案が立っており、後戻りできない決定を含まないため」／「設計の推奨モデル: **Fable** — 新しい待機構文の意味論が、SHIORI 応答のタイミングと Lua コルーチンの再開順の 2 点に絡んで未決のため」）：
   - **(i) 後戻りしにくい土台の決定がある**: 新しい DSL の構文・意味論、永続化データの形式、公開 Lua API の約束など、既存のゴーストや後続の spec がその上に建つもの
   - **(ii) その決定がまだ深い**: 互いに絡む未決の論点が 3 つ以上あって推奨案が立っていない、または伺か／SSP／SHIORI の正典があいまいで文書で決着しない、または Rust・Lua・SHIORI をまたぐタイミングや並行性の意味論を決める
   - **それだけでは Fable にしない**: 複数クレートにまたがる、Lua/Rust 境界をまたぐ、規模が大きい、議題が多い、移行手順の明らかな破壊的変更、選択肢が 2 案まで絞られ推奨が付いている
   - Fable と書くときは該当する決定と (ii) のどれに当たるかを根拠に名指しする。名指しできない・境界のケースは Opus にする

## エラーハンドリング

- **requirements.md 未生成**: 「先に `/kiro-spec-requirements {feature}` を実行してください」と案内して停止
- **gap-analysis.md 未生成**: 警告を出しつつ requirements.md のみで続行（「ギャップ分析なしで精査します。`/kiro-validate-gap {feature}` の実行を推奨します」）
- **イシューなし**: Phase 3 の仕様の目的を提示したうえで「精査の結果、修正すべき点は見つかりませんでした。設計フェーズに進めます」と即座に案内（Phase 5 の手順 3 と同じく推奨モデルも示す）

## コミット規約

- prefix: `docs({feature})`
- 自明修正は1コミットにまとめる
- 設計判断の追記は1コミットにまとめる
- 一括承認: `docs({feature}): 全議題を推奨案で確定`（1コミット）
- 指定外議題の確定: `docs({feature}): 議題{X,Y} を推奨案で確定`（1コミット）
- 個別議題クローズは議題ごとに個別コミット

## 注意事項

- 最初に仕様の目的を、具体例付きで説明する
- 議案は最初にまとめて提示し、全議題に推奨案を付ける
- 一括承認なら全議題を推奨案で確定する。議論の指定があれば、指定外は推奨案で確定し、指定議題だけを1つずつ議論する
- チャットで会話形式に進め、`AskUserQuestion` は使わない
